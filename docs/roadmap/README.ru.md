# Дорожная карта NeverD

Документ описывает основные направления за пределами нативного конвейера PE / ELF / Mach-O. Принципы: **1:1-поднятие**, **strict fail-loud**, общий **четырёхступенчатый IR**.

---

## 1. Завершение нативных форматов

Довести цели, которые loader’ы уже частично узнают.

| Пункт | Заметки |
|-------|---------|
| PE AArch64 | Windows ARM64: unwind/`.pdata`, трамплины, rewrite roundtrip |
| PE ARM32 (Thumb-2) | Windows on ARM — только Thumb |
| Mach-O i386 | Обычные reloc clang; сначала thin objects |

### Принципы

- Не помечать поддержку до форматных тестов
- Не ломать ELF / PE x86 / Mach-O arm64+x64
- Режим инструкций на уровне образа

---

## 2. Декомпиляция байткода EVM

Расширить NeverD на **байткод EVM**: 1:1-поднятие в тот же IR с выводом C, Solidity и LLVM IR.

### Цели

- Loader EVM · 1:1 lifter opcodes (strict) · стек/память · JUMP/JUMPI → CFG · storage/calldata · C23/Solidity/LLVM · единый CLI/C API

**Статус:** Decode и lifting legacy opcodes от Frontier до Fusaka завершены и
покрыты регрессионными тестами. Реконструкция исходника продолжается
консервативно: selectors, events, типы, стандарты, имена и динамическое
управление сообщаются только при достаточных свидетельствах, не как исходный
код, полный ABI или полная совместимость с ERC. Канонические selectors функций,
ABI variants отдельных стандартов и успешные return shapes разделены: общий ERC
selector не может придумать стандарт или заимствовать несовместимый return type.
Amsterdam — явная opt-in цель
Review/development; `latest` остаётся Fusaka. EOFv1/EIP-7692 не запланирован, а
EIP-3540 имеет статус Stagnant, поэтому они не выдаются за mainnet. Подробнее:
[декомпиляция EVM](../evm.ru.md).

### Зачем EVM

- Верность для аудита · один движок для натива и контрактов · без тихого пропуска

---

## 3. Декомпиляция Solana eBPF (SBF)

Программы **Solana eBPF / SBF** с той же strict-семантикой.

### Цели

- Loader SBF · 1:1 eBPF/SBF lifter · Account/CPI · тот же конвейер · единый API

**Статус:** Поддержка текущих контрактов Anza `sbpf` v0-v4 завершена. Реализованы устаревшие ELF с секциями/релокациями и строгие ELF только с program headers, полная версионированная база инструкций, строгая верификация, поэтапные Low/Med/High IR, наблюдения syscall/CPI/account, проверенный LLVM, переносимый C11, безопасный стабильный Rust, интеграция CLI/C API и независимый ограниченный семантический oracle для сырого байткода. v4 отслеживается по upstream; возможность развёртывания или выполнения в конкретном кластере по-прежнему зависит от активации функций этого кластера. См. [Декомпиляция Solana SBF](../sbf.ru.md).

### Зачем Solana eBPF

- Важная цель аудита · BPF-ISA подходит MedIR · один C SDK

## 4. Аудит и охота на ошибки безопасности памяти

Анализировать поднятый двоичный файл на дефекты жизни кучи (утечка, двойное освобождение, использование после освобождения) и переполнения опасных копий, структурированным JSON, с ограниченной моделью солвера для доказанного переполнения. Анализ идёт на формат-нейтральном IR и общем представлении идентичности, поэтому **PE, ELF и Mach-O равноправны**, и повторно использует собственное символьное исполнение и битвекторный солвер — без внешнего солвера и контейнера.

| Пункт | Заметки |
|-------|---------|
| Дорожка `audit` | Машина состояний кучи над IR + сводки побега: утечка, двойное освобождение, использование после освобождения |
| Дорожка `hunt` | Каталог стоков + предфильтр аргументов + ёмкость назначения + свидетель солвера |
| Свидетельство достижимости | Состояние управления от известных входов, независимая фиксированная точка атакующего и точный свидетель корня/цепочки вызовов |
| Контракт идентичности | Разрешение стоков по формату (IAT PE, PLT ELF, dyld bind Mach-O) и источники имён PDB / DWARF / MAP |

**Статус:** Phase 1 реализована для PE, ELF и Mach-O. P0 включает анализ в закрытом мире жизненного цикла кучи и опасных копирований, а также добавочное свидетельство схемы v1 с воспроизведением `process-input-v1` для точных литеральных значений окружения и первого потребления стандартного ввода; прочие виды ввода остаются невоспроизводимыми с указанием причины. P1 охватывает переполнения стека/глобальных объектов, неинициализированные локальные чтения и строки формата. Неизвестные или лишь частично применимые эффекты вызовов остаются UNKNOWN. Покрытие вердиктов и идентичности закреплено [`unittests/safety`](../../unittests/safety) и сквозным [`SafetyIntegrationTests.cpp`](../../unittests/safety/SafetyIntegrationTests.cpp), который на каждом хосте запускает обязательную матрицу PE/ELF/Mach-O × x86-64/AArch64. См. [Аудит и охота на ошибки безопасности памяти](../memory-safety.ru.md).

Текущий межпроцедурный срез добавляет в схему v1 `reachability.status` и
`reachability.attacker_control`, не меняя независимый `verdict`. Он сообщает
корни `application`, `image` или `export`, точные внутренние цепочки вызовов и
закрытые отказом состояния UNKNOWN. Бюджеты `max_call_depth` и
`max_summary_iterations` доступны через C API, обе команды CLI и оба метода
Python. Поэтому `control_reachable` и
`attacker_reachable` — счётчики достижимости, а не альтернативные счётчики
вердиктов.

Поверхности анализа и планы P2 используют версионированные границы с явным статусом:

| План | Объём | Статус |
|------|-------|--------|
| `lowir-concolic-v1` | Гибридное/concolic-исследование LowIR и генерация seed | Экспериментальный; проверенные воспроизведением seed регистров на PE/ELF/Mach-O × x86-64/AArch64 |
| `binary-sanitizer-v1` | Runtime-проверки, вставляемые в переписанный нативный бинарный файл | Экспериментальный на Darwin: counted-write-защита по принципу «все точки или отказ» и аутентифицированная публикация create-exclusive либо same-source no-change |
| `process-replay-v1` | Более широкое воспроизведение процесса для argv, файлов, сети и повторных чтений сверх `process-input-v1` | Только граница Phase 0: проверка плана/координатора и fail-closed запрос нативной доступности; ни один хост не предоставляет нативных операций replay |

Concolic-адаптер — отдельная поверхность анализа, а не расширение контракта
приёмки отчётов безопасности Phase 1. Экспериментальный sanitizer доступен через
`neverd_session_sanitize`, `neverd patch --sanitize=strict` и Python
`Session.sanitize`; хосты не-Darwin отказывают до lifting или изменения
namespace. Полный receipt аутентифицирует только удерживаемый во время
транзакции объект каталога назначения. Каталог можно переименовать после
открытия, поэтому receipt не доказывает, что исходный pathname продолжал
указывать на этот объект во время транзакции или после возврата, и не является
устойчивой привязкой пути. `NativeProcessReplayAdapter` остаётся границей
query/factory Phase 0 с принципом «все возможности или ни одной»: сейчас все
хосты возвращают false для всех возможностей и не предоставляют таблицу
операций.

## Сроки

Нативные форматы, legacy EVM decode/lifting до Fusaka, Solana SBF и безопасность
памяти Phase 1, включая текущий срез достижимости от известных входов, покрыты
регрессионными тестами. Консервативная реконструкция исходника EVM продолжается.
Даты не обещаем.

| Функция | Статус |
|---------|--------|
| Завершение нативных форматов (PE ARM*, Mach-O i386) | Завершено |
| Legacy EVM decode/lifting | Завершено до Fusaka; регрессионное покрытие |
| Реконструкция исходника EVM | Продолжается — по свидетельствам и консервативно |
| Декомпиляция Solana eBPF (SBF) | Завершено — v0-v4, C, Rust и LLVM; регрессионное покрытие |
| Аудит и охота на ошибки безопасности памяти | Phase 1 и срез достижимости от известных входов завершены; `lowir-concolic-v1` и Darwin-`binary-sanitizer-v1` экспериментальны; нативный `process-replay-v1` остаётся недоступным за fail-closed адаптером Phase 0 |
| Укрепление движка и продукта | Постоянно |
