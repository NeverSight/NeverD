# GUI plugins

The workbench now runs these providers through [NPH](plugin-host.md). Its
Qt-independent process, task and protocol libraries are also consumed by the
`neverd-plugin-host` CLI. `Session` owns the GUI query/publication adapter;
closing or destroying the task pane leaves tasks and accepted publications
alive. The pane reads their state again when recreated.

The separate [Tools layer](tools-layer.md) can expose the same process actions
to model-independent callers. Its optional tools catalog and command extensions
are currently consumed by the headless Tools entry point. This GUI pane does
not yet discover those catalogs; ordinary v1 plugins retain their behavior.

GUI process plugins add external commands to the workbench without linking
their code into NeverD. A provider can be written in any language that implements
the protocol below. The standalone Python helper requires Python 3.8+, uses
only the standard library, and does not depend on NeverD's embedded Python build.

This is separate from [native/Python engine plugins](plugins.md) and the worker's
[read-only contribution manifests](../tools/neverd-worker/PROTOCOL.md#declarative-contribution-manifests).
Their existing contracts are unchanged. No engine C++ objects or Qt widgets
cross the provider boundary.

For producer integrations that need to display newly generated machine code in
the original image, use the [analysis-section C ABI and worker commands](analysis-sections.md).
The native workbench has an add-section action. Process-plugin `Task.query()`
remains read-only; applying generated bytes requires a host-side write action.

## Native workbench views

A native GUI plugin can build and draw its own Qt Widgets and mount them inside
the workbench. Import its `plugin.json` in **Plugins → Plugin manager… → Import
plugin…**, then select it and choose **Enable**. The manager identifies these
packages as **Native GUI**. Import records the manifest path. Enabling loads the
module, so enable only modules you trust.

The [GUI SDK header](../pluginsdk/gui/GuiPluginUi.h) declares
`neverd::gui::pluginui::Module` and the `neverd.gui-ui.v1` contract. Build a Qt
`MODULE` library against the same Qt, C++ toolchain, architecture and build
configuration as the workbench. Use `Q_PLUGIN_METADATA` with
`NEVERD_GUI_PLUGIN_UI_IID` and `Q_INTERFACES` for the SDK's `Module`. The
[selection inspector](../tools/neverd-gui/tests/NativeSelectionUi.cpp) shows
how to implement a view with just Qt Widgets and this header.

```json
{
  "schema": "neverd.plugin-package.v2",
  "id": "example.selection",
  "name": "Selection inspector",
  "version": "1.0.0",
  "components": [{
    "id": "inspector",
    "kind": "gui-native",
    "interface": "neverd.gui-ui.v1",
    "entry": {"library": "selection-inspector.dll"}
  }]
}
```

Use the module's actual filename for the target platform. This package form
accepts one GUI component. The CLI can inspect the declaration. Running its
component requires the workbench.

- Create project instance state under the `lifetime` object passed to
  `Module::activate`. Call `Context::mountView` on the GUI thread with a unique
  view ID, a corner, an optional anchor ID from this component, and a factory
  that creates a child of the provided parent. The host places and destroys
  the root widget. Use `sizeHint()` for the preferred size and Qt's
  `show()`, `hide()` and `close()` to manage visibility and release.
- A plugin can set the `ViewPositionProperty` dynamic property on an
  unanchored view to a `QPoint` in workbench coordinates. The host fits the
  view within the workbench and places its anchored views beside it. Clear
  the property to return the view to its original corner.
- `captureContext` returns the active workbench selection and project identity.
  `watchContext` scopes its observer to the activation and the receiving
  `QObject`. Use `attachSession` for a private read-only MCP connection and
  `navigate` for an explicit address jump. Both recheck the binding when called.
- A component can query `MenuContext` from `Context` with `dynamic_cast`.
  During activation, `mountMenuAction` adds a native Qt action under
  **Plugins → package name**. The factory gives the action the supplied parent.
  The host keeps the action for that component activation.
- A component that styles or paints its views can query `ThemeContext` the
  same way. `themeColor` returns a workbench color role by its chrome color
  name (`Menu`, `Border`, `SecondaryText`, `ButtonPrimary`, ...) in the current
  light, dark or high contrast theme. Standard Qt controls need nothing: the
  workbench style already draws them. Read the roles again on
  `QEvent::ApplicationPaletteChange`, which a theme change sends.
- Closing a project or disabling the plugin retires its NPH component and
  destroys its views. A project switch creates new view instances. Restart
  the workbench before replacing a loaded module binary.

The desktop distribution supplies the
[NeverD Agent floating chat plugin](../tools/neverd-agent/README.md#chat-in-neverd-gui).
On Windows and Linux, find its module and `plugin.json` in
`bin/plugins/neverd-agent-ui/`. The workbench resolves `plugins/` from the
executable's directory. On macOS, find the package in
`Contents/PlugIns/neverd-agent-ui/` inside the workbench bundle.
The workbench registers its manifest from the current installation and enables
it on first use. The plugin manager shows it as bundled and keeps changes to
its enabled setting across launches and upgrades. For users who imported an
earlier version, the current package supplies the module and the existing
enabled preference still applies.

## Run the independent example

Prepare a complete copy outside the repository:

```powershell
python pluginsdk/gui/examples/workbench-explorer/prepare.py E:/plugins/workbench-explorer
```

The script copies the provider and helper, writes `plugin.json` and
`plugin-developer.json` with the exact Python executable used to prepare them,
and prints the default manifest path. The source manifest also works directly
with Python 3.8+ on PATH; its provider locates the SDK helper. No CMake
change, SDK installation, `PYTHONPATH`, target execution, or ND engine library is
needed for the provider itself.

The default report manifest declares `imports`, `resolve` and optional icon
fields. Use the matching rebuilt GUI. Earlier example hosts may refuse the
updated manifest with `Invalid process plugin manifest` or
`Unsupported or repeated plugin query`; changing the Python helper does not
update that host executable. Current
hosts distinguish unsupported operations, duplicate entries and non-string
entries and name the refused query in their diagnostic.

In the GUI choose **Plugins → Plugin manager…** (also available under
**Options** and in the command palette), then **Import plugin…** and select the
manifest. The **Plugins → Import plugin…** shortcut also works.
Use **Plugins → Workbench Explorer** to run its commands.

The manager lists installed plugins, versions, saved enabled settings
and activation state. Select a row to see its stable ID, manifest path, NPH
component generation and diagnostics. Filter by name, ID or path. **Disable**
removes the current registrations and cancels active/queued work while keeping
the installation; the saved disabled state survives restart. **Enable** binds
a new component generation. **Stopping** remains visible until NPH finishes
the old owner, so the manager cannot enable a replacement during cleanup.
Missing or invalid manifests stay in the list with their saved enabled intent
and diagnostic. After repairing the manifest, use **Retry activation** or import
its corrected path. **Uninstall** forgets the installation and retires its
runtime; plugin files, generated artifacts and project edits remain governed
by their existing file/history rules. **Open folder** visits the manifest's
directory. Reading the list never starts a provider process.

Installation intent and component activation are owned by NPH `PluginCatalog`.
The Session's `PluginServices` only adapts persistence, with existing paths under
`guiPlugins/installed` and independent preferences under `guiPlugins/enabled`.
The manager projects shared discovery, activation and cleanup diagnostics.
Older installations default to enabled. Closing a manager
or task pane does not reset that state or create a second runtime. The manager
covers process-plugin manifests and native GUI modules. Native engine plugins
use their own loader.

GUI commands invoke the same `Actions` / `ProcessActions` entry used by the CLI
and Tools consumer. `PluginJobs` adapts query replies and shared process events
to Qt history and result views. It owns no provider process, protocol parser,
deadline timer or task admission state machine. Existing v1 providers and their
views, artifact, SourceIR and image-addition results retain their wire format.

The same host also offers [versioned services and owner-scoped events](plugin-host.md#services-and-events).
Optional manifest declarations let a process discover exact capability versions,
call read services and subscribe to project/task changes. GUI revision changes
update the shared service context. Notifications do not change a task's captured
analysis revision; a subsequent stale query receives a refusal. The independent
[Host Observer](../pluginsdk/common/examples/host-observer/README.md) displays the
service table and a received event, and exports the same report as the CLI.

**Plugin tasks and results** reopens
the dock. It starts hidden, including when a saved desktop previously showed
an empty task pane. Running a plugin command opens it automatically; importing
or restoring plugin registrations alone does not. Opening another project
also closes the transient task pane. Its global controls open import, the
plugin manager and menu settings. Task history
is grouped by plugin name and stable plugin ID, so plugins with identical display
names remain distinguishable. Expand a plugin to select a task; its command name
and short task ID distinguish repeated invocations. Group expansion and task
selection survive progress refreshes.

The result area names the selected command, owning plugin and task. Its controls
apply only to that task: cancellation appears while unfinished, export appears
for successful artifacts, and code import appears only when the result
supplies an image-addition candidate. Selecting a plugin group clears the task
controls. **Show log** reveals only the selected task's retained log; switching
tasks switches the log as well. Controls wrap when the dock is narrow. Splitter
handles resize the history, results and log.
Import is registration only; actions run when invoked. Registration
is remembered for subsequent workbench launches. Startup reloads each manifest
without starting a provider process; tasks run only when an action is invoked.
`--process-plugin` loads a manifest at startup; `--plugin` is a compatibility
spelling normalized before Qt parses its own reserved `--plugin` argument.
Both accept an already restored manifest from the same path. A missing or
invalid remembered manifest produces a diagnostic without preventing startup;
import its corrected path to register it again.
To replace an active manifest from another path, use the manager's **Uninstall**
button, then import the updated manifest. Uninstalling cancels active and queued
jobs and removes its actions
from the menu, disassembly/CFG/code/function-list context menus and command
palette, and forgets its registration for subsequent launches. Function-list
actions use the selected row; code-view actions use that code view's function.

| Example command / interaction | What it demonstrates |
|---|---|
| Analyze current function | Function summary, call sites, imported API names, references and linear instructions; export JSON and Markdown |
| Browse largest functions | Rank up to 512 catalogue entries by size without analyzing bodies; activate a row to navigate |
| Inspect selected instructions | Address-dependent availability, disassembly/code context menu, byte and instruction queries |
| Function report with CFG | Function report plus a bounded CFG preview; double-click/Enter navigates nodes, `+`/`-` zooms and dragging pans |
| Show captured context (developer manifest) | Works with or without a file; project, epoch, current address/function and selected text |
| Run background demonstration (developer manifest) | Integer/string/choice/boolean dialog fields, remembered values, unknown/known progress, logs, normal completion and optional report artifact |
| Cancel task | Queued cancellation or actual provider termination; the main analysis worker remains usable |
| Exercise failure handling (developer manifest) | Reported error, process failure, malformed result and timeout |
| Export artifact | Explicit destination, SHA256 recheck and no overwrite of an existing file |
| Dock / theme / palette | Docking, floating, close/reopen, standard keyboard focus, palette search and current workbench colors/fonts |

The default manifest contains the four analysis commands. To exercise task
mechanics, unload it and import `plugin-developer.json` instead (same plugin ID).
Its background command performs demonstration work. The example has no TVM
dependency or sample-specific addresses and does not execute or rewrite the binary.

Function reports inspect at most 512 linear instructions within ND's declared
extent, or an explicitly marked 64-instruction window if size is unavailable.
They query references at up to 32 instruction sites, use the first 512 import
slots for naming, and keep unresolved operands visible. An IAT slot is reported
as a slot, not an inferred runtime callee address. Counts describe the linear
listing, not reachable execution paths. Optional query failures appear in
coverage notes; required disassembly and stale-session/protocol errors still
fail. CFG previews cap at 128 blocks/512 edges, while JSON keeps the CFG returned
by ND. See the example walkthrough for exact bounds and output fields.

## Manifest v1

See the complete [example manifest](../pluginsdk/gui/examples/workbench-explorer/plugin.json).
The root schema is `neverd.gui-plugin.v1`, with these fields:

| Field | Contract |
|---|---|
| `id`, `name`, `version` | Unique lowercase ID, display name, provider version string |
| `program` | Absolute executable, a file relative to the manifest, or an executable name resolved on PATH during import |
| `arguments` | Explicit string array; never a shell command. The working directory is the manifest directory |
| `queries` | Declared subset of `metadata/functions/disasm/decompile/cfg/xrefs/strings/bytes/imports/resolve/analysis_sections` |
| `icon` | Optional plugin-group icon: `builtin:extensions` or a local file relative to the manifest |
| `actions` | 1–32 entries with `id,title,context`, optional `context_menu,icon,parameters,timeout_ms` |

An action's `context` is `none`, `project`, `address`, or `function`. Availability
is owned by the plugin bridge and checked again before admission. Actions are
available in the Plugins menu and command palette; `context_menu:true` adds
them to disassembly/code context menus. IDs become
`plugin.<plugin-id>:<action-id>`. Duplicate plugin IDs require explicit unload.

### Context menu placement and icons

Context commands default to **Plugins → plugin name → command**. Each installed
plugin gets its own submenu, keyed by plugin ID. If display names coincide,
the menus append their IDs so the groups remain distinguishable. Plugin groups
are ordered by display name, then ID. A plugin with
no grouped context commands does not create an empty submenu.

Open **Plugins → Context menu settings…**, or **Menu settings…** in the task pane.
For each command, choose **Plugins submenu** or **Direct context menu**. Both
forms can coexist: keep frequent commands at the outer level and group the
rest. The top menu and command palette remain available in either case. All
entry points share the same action, contextual availability and task admission.
Changing presentation does not start work or register an extra command.

The same dialog lets users replace each command's icon. The manifest supplies
defaults through optional `icon` fields on the plugin and individual actions:

```json
{
  "icon": "builtin:extensions",
  "actions": [{
    "id": "report",
    "title": "Analyze current function",
    "context": "function",
    "context_menu": true,
    "icon": "icons/function-report.svg"
  }]
}
```

This excerpt belongs inside a complete manifest. `builtin:name` selects a
workbench icon from `tools/neverd-gui/resources/icons/` without the `.svg`
suffix. Local PNG, ICO and SVG files can be absolute paths or relative to the
manifest. SVGs use the workbench's DPI-aware renderer and do not require a Qt
SVG icon-engine plugin. Files are limited to 1 MiB; raster images to 1024×1024.
An unavailable manifest command icon produces a diagnostic while its command remains
usable. Invalid user selections keep the settings dialog open without saving
partial changes. Clear a field to remove the icon.

Preferences are stored by stable plugin/action IDs under
`guiPlugins/<plugin-id>/menus/<action-id>/` in QSettings and survive unload and
reimport. Cancel saves nothing; **Restore Defaults** prepares grouped placement
and the manifest's icons, applied only after OK. Unloading removes commands
from future context menus and the command palette. Previously saved preferences
remain for a later reimport. Installation itself is still per window.

Parameter fields have `id,title,type,default`. Supported types are `string`
(up to 4096 characters), `boolean`, bounded `integer` (`minimum/maximum`, default
0–1000000), and `choice` (a nonempty array of up to 32 distinct strings).
The host builds the dialog, validates both manifest defaults and invocation
values through NPH's shared resolver. Checking **Remember these values for this
action** saves the accepted values by plugin/action/field using QSettings;
otherwise they apply only to this invocation.
Closing the dialog with Cancel starts no job. A project switch while it is
open refuses the invocation. The action's exact registration is also captured:
unloading/replacing it while the dialog is open rejects the old invocation.
Existing user preferences are not deleted on unload.

Limits: 64 KiB manifest, 16 installed plugins, 32 arguments/action definitions,
16 parameter fields, 8 unfinished jobs and 64 in-memory history rows. Completed
history can be evicted; its on-disk receipt and artifacts are retained.

## Captured context and queries

`start.context` includes `loaded`, `epoch`, `project_id`, `revision`,
`input_path`, `project_path`, `architecture`, `format`, and, when available,
`address`, `function_address`, `selection_text` (up to 65536 characters).
Addresses are hexadecimal strings, including kernel addresses above 2^53;
epoch/revision/project IDs are opaque strings. A parameter dialog keeps the
selection captured at invocation, rather than substituting its own focus.

Context is a snapshot per invocation, not a live cursor subscription.
`input_path` can be a database's unpacked file; it is not a portable storage
location or a certified immutable file snapshot. Providers that read the file
directly must establish the input identity they need. This API does not cache
analysis correctness or certify machine-code rewriting.

A provider sends a declared read-only query with a unique request ID. The bridge
routes it through the existing QueryService with the captured exact revision;
payloads and replies follow the [worker protocol](../tools/neverd-worker/PROTOCOL.md).
The reply keeps its status/error/payload envelope. Unknown or undeclared
operations fail; the bridge does not expose annotation, rename, patch or open
commands. At most 16 queries can be outstanding. Queries still share the main
worker's execution queue; running a long engine query can delay other engine
reads even though the external provider itself runs independently.

Changing session epoch/project makes unfinished old jobs stale and stops their
provider. Completed results remain inspectable, but their address links cannot
navigate a different session. Late query replies to retired jobs are ignored.

## Process protocol v1

Messages use a four-byte unsigned big-endian length followed by UTF-8 JSON.
The maximum frame is 1 MiB. stdout is protocol-only; use `log` or stderr for
diagnostics. Every message includes `protocol:1`.

1. Provider sends `{type:"hello",protocol:1}` within five seconds. It must not
   start work or descendants before receiving `start`.
2. Host sends `start` with `task_id,action,context,parameters,output_dir`.
3. Provider may send `progress`, `log`, or `query`; each carries `task_id`.
4. Provider sends exactly one `result` or `error`, then exits. A result is
   published only after successful process exit, complete framing, current
   session ownership and artifact checks.

| Message | Fields besides `protocol,type,task_id` |
|---|---|
| `progress` | `progress:{label,done?,total?}`; counts are nonnegative integers, `done≤total`; omit total when unknown |
| `log` | `text`, up to 8192 characters |
| `query` | `id,operation,payload` |
| Host `query_reply` | `id,reply`, where reply is the worker response envelope |
| `result` | `result:{views:[],artifacts?:[],image_addition?:object}` |
| `error` | `message` |

The host limits a job to 10000 messages, 16 MiB of protocol output and 64 KiB
of combined logs/stderr. Drain work yields between bounded chunks to keep the
UI responsive. Default action timeout is 60000 ms; a manifest can select
100–3600000 ms. Progress reports completed work; never fabricate a percentage
from an unbounded analysis iteration count.

## Task lifecycle and cancellation

Jobs run serially: `queued → starting → running → succeeded/failed`.
Additional terminal states are `cancelled`, `timed_out`, and `stale`.
A running stop first reports `cancelling`; it becomes terminal after actual
process exit. A queued cancellation starts no process. Failed jobs publish
diagnostics, not result views/artifacts.

V1 cancellation terminates the provider; there is no cooperative cancel
message. Windows providers and descendants belong to a kill-on-close Job Object;
on Unix the provider starts a separate session/process group. The host cleans up
that group on stop and normal provider exit. Providers should keep descendants
in the assigned job/group. Closing a result dock does not cancel work; explicit
Cancel, unload, project switch or window destruction does.

## Result views and artifacts

- `text`: `{kind:"text",title,text}`. Plain text, up to 262144 characters.
- `table`: `{kind:"table",title,columns:[string],rows:[{cells:[string],address?}]}`.
  Up to 16 columns/512 rows; every row has exactly the declared number of cells.
  Sortable, read-only; Enter/double-click follows the optional address.
- `graph`: `{kind:"graph",title,nodes:[{id,text,address?}],edges:[{from,to}]}`.
  Up to 128 nodes/512 edges, unique node IDs and existing endpoints. This is a
  compact relationship view, not the main worker's scalable CFG layout API.
- At most 16 views. Unknown view kinds or malformed rows/edges reject the result.
- `artifacts`: up to 16 `{title,path,sha256}` records. Paths are relative to the
  assigned job directory; parent escapes and out-of-directory symlinks are
  refused. Files are at most 64 MiB each and their bytes are checked before
  publication and export. Export copies to a new file, then verifies its digest.

### Importing generated code into the analysis image

A completed provider can offer one optional `image_addition`, referencing a
normal SHA256-checked artifact by its zero-based index. The provider still has
only read queries. The user imports it with **Import code into image** in the
task pane; producing a result does not itself edit the project.

```json
{
  "views": [],
  "artifacts": [{"title": "Generated x64", "path": "code.bin", "sha256": "<64 lowercase hex digits>"}],
  "image_addition": {
    "artifact": 0,
    "sample_sha256": "<SHA256 of the original input>",
    "description": {
      "schema": "neverd.analysis-section.v1",
      "name": ".generated",
      "address": "0x150000000",
      "permissions": "rx",
      "functions": [{"name": "generated", "offset": "0x0", "size": 6,
                     "source_address": "0x140001000"}]
    }
  }
}
```

The host checks successful completion, current epoch/project and exact revision,
input SHA256, contained artifact path and exact bytes. It sends the verified
bytes inline, not a provider-selected filesystem path. The import cap is 3 MiB
so hexadecimal and metadata fit the worker's 8 MiB frame. The SDK then validates
the section and every function atomically through the existing
[analysis-section API](analysis-sections.md). Other additions are preserved.
The command keeps the captured revision even while queued behind another edit;
it cannot silently apply to the newer project revision. Changed/stale results
remain exportable, but require a new task before import. Read-only projects
cannot import. Arbitrary `path`/`data_hex` fields in the provider's description
are refused.

On success the first new function opens in the normal disassembly/CFG/F5 views.
Save persists its code and provenance in the project folder; **File → Pack database** includes them in `.nddb`. These are
analysis sections, not PE/ELF rewriting, entry-point patches or equivalence
certificates. The provider owns code placement and any relocation requirements;
the host does not guess relocations or invent function ABIs.

The TVM-independent developer example's **Create analysis function** action
produces a real six-byte x64 function returning a chosen integer. Select a free
VA in its parameter dialog, import it and verify the result with F5. The separate
[TVM provider](../tools/neverd-devirt/gui-plugin/README.md) adapts an existing
recovery executable using the same contract. Prepare it independently; it is not
an ND build target. `neverd-gui --plugin /path/plugin.json binary` loads a
manifest at startup; `--plugin` is repeatable and startup reports invalid
manifests immediately.

Job directories are under the application's local data directory in
`plugin-jobs/<task-id>/`. `receipt.json` records context, parameters, terminal
state, diagnostic, bounded provider stderr, elapsed time and accepted result.
Pre-handshake import/startup failures retain their actual stderr in the task
diagnostic and receipt instead of only an exit code. The current window keeps
64 history rows; reopening old receipts, database embedding and portable result
packages are not implemented. Providers must not use `receipt.json` as an
artifact name. Result text is not evaluated as HTML, scripts or QML.

This version supplies host-owned views. It does not load arbitrary Qt widget
classes, stream cursor events, attach generated code as engine functions, or
write a binary. Those require separate public contracts.

## Development and verification

Provider helper and runnable source:
[GUI SDK](../pluginsdk/gui/README.md),
[Workbench Explorer](../pluginsdk/gui/examples/workbench-explorer/README.md).

```sh
python -m unittest discover -s pluginsdk/gui/tests -v
python scripts/build.py build-gui --target neverd-gui-plugin-tests --parallel 4
ctest --test-dir build-gui -R '^NeverDGuiPlugins$' --output-on-failure
```

The Qt suite uses the real MainWindow and fixture worker. It covers external
directories/Unicode paths, views, forms, settings, address navigation, task
termination, descendants, stale projects, malformed protocol, unauthorized
queries, artifact identities and post-result failures. The
`taskActionsStayWithTheirPluginAndSelectedResult` case also runs two providers
with the same display name, repeated tasks, result-specific controls, isolated
logs, group collapse across refreshes, and narrow layouts in both themes. Set
`NEVERD_PLUGIN_GROUP_SCREENSHOT_DIR` to save actual Qt captures from that case;
run it again with `QT_SCALE_FACTOR=1.5` to check fractional DPI.
Real desktop keyboard,
screen reader, platform packaging and other OS behavior still require their
own qualification; offscreen tests do not establish them.
