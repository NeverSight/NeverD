# Участие в разработке NeverD

NeverD — проект анализа бинарных файлов, в котором семантика ставится на
первое место. Полезное изменение имеет чёткие границы, явно завершает работу
при неподдерживаемом поведении и содержит минимальный тест, доказывающий
изменённый контракт.

При включении существующего кода сохраняйте уведомления об авторских правах,
лицензии и происхождении, в том числе для кода, скопированного или переработанного
с помощью инструментов ИИ/LLM. Следуйте [руководству по указанию авторства](ATTRIBUTION.md),
указывайте исходный источник и ревизию повторно используемых материалов и проверяйте
их лицензию перед отправкой. Сохраняйте уведомления третьих сторон под их исходными лицензиями.

Перед изменениями прочитайте [руководство по архитектуре](architecture.md).
Для выбора набора тестов используйте [руководство по тестированию](testing.md),
а запланированную продуктовую работу сверяйте с
[дорожной картой](roadmap.md).

<!-- i18n-section: prerequisites -->
## Требования

- Git с поддержкой рекурсивных субмодулей
- CMake 3.20 или новее
- Ninja
- Компилятор C++20
- CPython 3.10+ с файлами разработки для встраивания, если включены плагины Python
- Clang и LLD (`ld.lld` и `lld-link`) для полного набора межцелевых fixture

Рекурсивные субмодули предоставляют форки LLVM и Capstone для NeverD, Unicorn
и данные сигнатур. При проверке изменения не заменяйте их произвольными
системными версиями.

<!-- i18n-section: clone -->
## Клонирование и инициализация

Разработка интегрируется в `dev`, который также является веткой репозитория по
умолчанию. Клонируйте её со всеми субмодулями:

```bash
git clone --branch dev --recurse-submodules \
  https://github.com/NeverSight/NeverD.git
cd NeverD
```

В существующем клоне синхронизируйте субмодули перед первой сборкой и после
любого коммита, меняющего записанные версии субмодулей:

```bash
git submodule sync --recursive
git submodule update --init --recursive
```

<!-- i18n-section: build -->
## Выбор профиля сборки

| Профиль | Назначение | Важное поведение |
|---------|------------|------------------|
| Release | Обычная разработка, все тесты, бенчмарки декодирования/подъёма | Оптимизирован; репрезентативная производительность |
| RelWithDebInfo | Профилирование или отладка оптимизированных горячих путей | Оптимизирован с отладочными символами |
| Debug | Assertions, пошаговая отладка исходников, локальная проверка корректности | Не оптимизирован; бенчмарки декодирования намеренно намного медленнее |

Используйте Release, если задаче не требуется именно поведение Debug:

```bash
cmake -S . -B build-release -G Ninja \
  -DCMAKE_BUILD_TYPE=Release \
  -DBUILD_TESTING=ON
python scripts/build.py build-release --parallel
```

По умолчанию сборка компилирует `third_party/llvm-project` как встроенную
зависимость. Первая сборка обычно занимает 30–60 минут, последующие выполняются
инкрементально. `CMakePresets.json` также определяет пресеты конфигурации/сборки
`release`, `relwithdebinfo` и `debug`, но выше использованы явные каталоги,
чтобы включённые тесты были видны.

Для отладки на уровне исходного кода используйте отдельный каталог, а не
перенастраивайте дерево Release:

```bash
cmake -S . -B build-debug -G Ninja \
  -DCMAKE_BUILD_TYPE=Debug \
  -DBUILD_TESTING=ON
python scripts/build.py build-debug --parallel
```

Никогда не публикуйте показатели декодирования или подъёма из Debug-сборки.
Для бенчмарков используйте Release, а если профилировщику нужны символы —
RelWithDebInfo.

### Аллокатор процесса

Linux, macOS и Windows MSVC/clang-cl по умолчанию включают `NEVERD_ENABLE_MIMALLOC`.
Инструменты, рабочий процесс анализа и тесты, созданные общим помощником CMake, используют
ветку по умолчанию форка mimalloc NeverSight, следуя модели хоста NeverC. Unix встраивает
аллокатор один раз в каждый исполняемый файл. Windows использует DLL mimalloc и
`mimalloc-redirect*.dll` той же архитектуры для перенаправления динамического CRT, включая
libneverd и нативные плагины. Обе DLL размещаются рядом с программами и устанавливаются
в `bin`; распространяйте их вместе. Windows требует `/MD` или `/MDd`; со статическим CRT
отключайте mimalloc. Сам SDK не навязывает аллокатор встраивающему приложению. На Windows
ARM64 нужна нативная ARM64-сборка: DLL x64 не перенаправляет CRT ARM64EC эмуляции x64.
MinGW сохраняет системный аллокатор. См. [требования Windows в исходном проекте](https://github.com/NeverSight/mimalloc/blob/main3/bin/readme.md).

Используйте `-DNEVERD_ENABLE_MIMALLOC=OFF` для системного эталона или внешнего аллокатора.
Старый `NEVERD_WORKER_MIMALLOC=OFF` отключает только worker. CMake подавляет mimalloc с
санитайзерами address, thread, memory, leak, включая комбинированные и зависящие от
конфигурации флаги компилятора/линкера. Один UBSan совместим. Если санитайзер задан только
флагами отдельной цели, явно установите OFF. Windows допускает сравнение без пересборки
через `MIMALLOC_DISABLE_REDIRECT=1`; `MIMALLOC_VERBOSE=1` показывает активацию.

Поддерживаемая точка входа `python scripts/build.py BUILD_DIR` перед каждой сборкой
обновляет все пять форков NeverSight из удалённых веток по умолчанию. Это подмодули в
`third_party`, как Capstone и Unicorn. Скрипт определяет реальные имена веток, обновляет
пять подмодулей и экспортирует закоммиченные исходники в
`BUILD_DIR/third_party/<library>/<commit>/src`. Незакоммиченные или разошедшиеся локальные
изменения останавливают сборку без перезаписи; сетевые ошибки тоже её останавливают.
Каталог блокируется на время обновления, переконфигурации и компиляции; снимок сохраняется
до следующего вызова. Инкрементальные сборки также получают новые коммиты.

`neverd-dependency-inputs.json` фиксирует входы конфигурации, коммит и SHA-256 экспорта,
поставляется с установленными продуктами, но не сертифицирует бинарный файл.
`neverd-build-receipt.json` фиксирует успех/ошибку только запрошенных целей и конфигурации.
CI сохраняет оба файла. Установка отвергает неудачные сборки, изменённые входы и несобранные
конфигурации; продуктовая CI собирает все устанавливаемые цели перед проверкой установки.
Основная ветка меняется между запусками: сравните коммиты до объединённой квалификации
платформ. Прямой `cmake --build` проверяет актуальность и отвергает устаревший снимок;
обновляйте через Python. Автоматическая регенерация сохраняет тот же снимок.
`FETCHCONTENT_SOURCE_DIR_NEVERD_*` доступен для изолированных локальных фикстур, но запрещён
основной точкой входа. Мультиконфигурационные генераторы требуют `--config`. Компилируйте
через точку входа, затем отдельно запускайте тесты и `cmake --install`; прямая цель `install` отвергается до компиляции.

См. [проверку аллокатора](../testing.md#allocator-validation) для дымовых тестов и сравнения производительности.

<!-- i18n-section: acceleration -->
### Библиотеки ускорения

Обычные сборки включают побайтовый поиск Highway, проверку UTF-8 simdutf, транспортный
парсер simdjson и планирование oneTBB, сохраняя аллокатор процесса. JSON сохраняет DOM и
сериализацию nlohmann. Корректные кадры только с целыми копируются из SIMD tape;
дробные числа и отрицательный ноль сохраняют исходное преобразование. Входы вне области
simdjson проходят исходный допуск; некорректный внешний текст сохраняет побайтовые escape-
последовательности. Библиотеки и mimalloc поступают из форков NeverSight в
`third_party/forks.json`, исправления совместимости — в их ветках по умолчанию. Сборка
копирует актуальные лицензии и фиксирует точные коммиты, не закрепляя пять зависимостей на старых выпусках.

`NEVERD_ENABLE_HIGHWAY`, `NEVERD_ENABLE_SIMDUTF`, `NEVERD_ENABLE_SIMDJSON` и
`NEVERD_ENABLE_TBB` имеют значение `ON`; для сравнения каждую можно переключить в `OFF`.
oneTBB сохраняет workers между пакетами, проверяет стеки 8 MiB и не собирает/загружает
`tbbmalloc` или его proxy. Вызывающие с большим стеком используют доступный запас, остальные
получают нативный координатор. Хосты с fork после первого использования или динамической
выгрузкой SDK обязаны использовать нативные потоки (`NEVERD_ENABLE_TBB=OFF`): сохраняемый
планировщик не поддерживает эти жизненные циклы. oneTBB статически компонуется с общим
ядром, а его символы остаются внутренними для этого ядра. Вызовы компонентов из CLI и
запросы к worker GUI используют тот же планировщик; DLL или разделяемая библиотека TBB
не распространяется. Цели, компонующиеся с `neverd_shared`, автоматически выбирают общий
планировщик. Клиенты, которые используют SDK через другую цель и также компонуют архивы
компонентов, должны применять `neverd_use_shared_task_scheduler` к своей конечной цели.
Автономные инструменты компонентов сохраняют собственную среду выполнения.
Эта ограниченная интеграция предотвращает появление нескольких планировщиков NeverD
в одном процессе; upstream по-прежнему считает [статические сборки oneTBB](https://uxlfoundation.github.io/oneTBB/main/intro/static_linking.html)
неподдерживаемыми и не рекомендует их для общего использования.

См. [проверку ускорения](../testing.md#acceleration-libraries) для нативных тестов, сравнений и ограничений совместимости.

<!-- i18n-section: prebuilt-llvm -->
### Предварительно собранный LLVM на macOS

Участники с Apple Silicon могут не собирать форк LLVM локально:

```bash
cmake -S . -B build-release -G Ninja \
  -DCMAKE_BUILD_TYPE=Release \
  -DBUILD_TESTING=ON \
  -DNEVERD_LLVM_PREBUILT=ON
python scripts/build.py build-release --parallel
```

CMake загружает настроенный в репозитории пакет релиза, проверяет его SHA-256 и
повторно использует распакованный пользовательский кеш в следующих сборках.
Канал готовых сборок поддерживает только macOS arm64. Intel Mac и универсальные
сборки должны использовать локальную сборку LLVM по умолчанию. Расширенные
переопределения, включая `NEVERD_LLVM_PREBUILT_TAG`, URL зеркала, каталог кеша
и явную контрольную сумму, описаны в `cmake/NeverDLLVMPrebuilt.cmake`.

Исправления LLVM должны находиться в [форке LLVM NeverSight](https://github.com/NeverSight/llvm-project).
Сначала закоммитьте и объедините их в форке, затем обновите ревизию подмодуля LLVM в NeverD.
Интегрированная сборка напрямую компилирует эти исходники; не добавляйте в NeverD файлы патчей LLVM или изменённые копии исходников в каталоге сборки.
Для подтверждения того же поведения готовые пакеты нужно пересобрать из исправленного форка.

## Работа с ветками и pull request

Начните с актуального `dev` и создайте тематическую ветку с узкой задачей:

```bash
git switch dev
git pull --ff-only origin dev
git switch -c docs/contributor-guide
```

Открывайте pull request в `dev`, а не в предполагаемую релизную ветку. Делайте
коммиты удобными для проверки: одна связная цель, без сгенерированных артефактов
сборки и постороннего форматирования; не меняйте версии субмодулей, если это не
часть предложения.

<!-- i18n-section: code-style -->
## Стиль кода

C/C++ следуют [LLVM Coding Standards](https://llvm.org/docs/CodingStandards.html).
[`.clang-format`](../../.clang-format) задаёт форматирование, [`.editorconfig`](../../.editorconfig)
— кодировку, окончания строк и пробелы. Версию C++ определяет `CMakeLists.txt`, а не внешняя
стилевая инструкция. Форматируйте изменённые файлы:

```bash
clang-format -i path/to/changed.cpp path/to/changed.h
git diff --check
```

CI использует версию из [`scripts/check_clang_format.py`](../../scripts/check_clang_format.py);
для воспроизведения нужна та же. Форматтер не проверяет принадлежность заголовков или
литералы политик. Не переформатируйте весь репозиторий ради локального исправления.
Следуйте соседним именам и декомпозиции, держите платформенное поведение на границах
loader/lifter/backend и не раскрывайте внутренние C++-типы через чистый C SDK.

### Структура файлов и заголовков

- Новые C++-файлы начинаются с LLVM-баннера имени/назначения, `NeverD Decompiler` и
  Doxygen `\file`, как `lib/debug/PDBLoader.cpp`. Сохраняйте авторские и лицензионные уведомления.
- Самодостаточные заголовки имеют `.h` и явные зависимости; реализация первой включает
  свой интерфейс. Далее `.clang-format` упорядочивает частные соседние, публичные `neverd/`,
  LLVM/Capstone в кавычках и заголовки в угловых скобках. Не полагайтесь на случайный порядок или транзитивные включения.
- Новые заголовки используют защиту `NEVERD_..._H` по пути: `NEVERD_SDK_LIMITS_H` для
  `neverd/sdk/Limits.h`. Включайте достаточно каталогов частных/инструментальных компонентов
  для уникальности; у `#endif` комментируйте имя. Применяйте при явной унификации старого
  заголовка, не меняя посторонние файлы.
- Общие интерфейсы — в `include/neverd/<component>/`, частные заголовки рядом с исходниками
  в `lib/` или `tools/`. Расположение не гарантирует стабильный публичный C SDK API.
  Зависимости ацикличны; ядро/читатели независимы от сессий и транспортных адаптеров.
  Алгоритмы принадлежат компоненту, без повторения семантики CLI/SDK/worker. См. [архитектуру](architecture.md).
- Используйте пространство имён владельца и ясные имена: новые типы/поля `UpperCamelCase`,
  функции `lowerCamelCase`, константы политик `kUpperCamelCase`. Сохраняйте существующие
  интерфейсы, написание контрактов C/Python и соглашения STL. Не добавляйте общие
  директивы `using namespace` в заголовки.
- Намеренно многократно включаемые таблицы сохраняют `.def`/`.inc` и описывают макроконтракт.
  Это не самостоятельные `.h`-интерфейсы; защита не должна блокировать повторное развёртывание.
  Генерируемые заголовки меняйте через генератор.

Пример самодостаточного заголовка политики:

```cpp
//===- Limits.h - SDK resource limits and defaults ------------*- C++ -*-===//
//
// NeverD Decompiler
//
//===----------------------------------------------------------------------===//
///
/// \file
/// SDK request bounds, retained-state limits and default work budgets.
///
//===----------------------------------------------------------------------===//

#ifndef NEVERD_SDK_LIMITS_H
#define NEVERD_SDK_LIMITS_H

#include <cstdint>

namespace neverd::sdk {

/// Traversal ceiling for a function without a recorded instruction extent.
inline constexpr uint64_t kMaxUnsizedInstructions = 65536;

} // namespace neverd::sdk

#endif // NEVERD_SDK_LIMITS_H
```

### Принадлежность лимитов, значений по умолчанию и конфигурации

В каталогах инструментов, непосредственно включённых в путь поиска заголовков, используйте `ResourceLimits.h`. В файловой системе без учёта регистра локальный `Limits.h` может скрыть системный `<limits.h>`.

Каждая политика имеет единственный авторитетный источник в заголовке лимитов/конфигурации
своей подсистемы даже с одним вызывающим: вход/выход, рекурсия/графы, бюджеты работы/итераций,
эвристические пороги, кеш, страницы/пакеты, повторы и тайм-ауты. Это относится к `constexpr`,
макросам, сравнениям с литералами, `min`/`clamp`, инициализаторам и параметрам по умолчанию.

Сначала выберите существующего владельца:

| Владелец | Определение |
| --- | --- |
| Общее ядро/конвейер | [`include/neverd/Limits.h`](../../include/neverd/Limits.h) |
| SDK | [`include/neverd/sdk/Limits.h`](../../include/neverd/sdk/Limits.h) |
| Web | [`include/neverd/web/Limits.h`](../../include/neverd/web/Limits.h) или существующее специальное определение |
| Другой компонент | Существующий заголовок/таблица, иначе специализированный `Limits.h` в своём слое |
| Только CLI, worker или GUI | Локальный `ResourceLimits.h`/`Config.h`; ядро не зависит от заголовков инструментов |
| Настройки вызывающего | Модель владельца `Config.h`, `*Options.h` или `*Configuration.h` |

Заголовки лёгкие, сгруппированные по назначению. Переиспользуйте `*Limits.def`/таблицы
конфигурации с самодостаточным C++-представлением. Не дублируйте определения в `Limits.h`,
`Constants.h`, `Config.h`; общие политики ядра не размещайте в SDK/инструментах, несвязанные
политики модулей не собирайте все в корневом `Limits.h`.

Скалярные C++-политики — типизированные `inline constexpr` в существующем пространстве
(`neverd::limits`, `neverd::sdk`). Названия отражают назначение/единицу: `kMaxSourceBytes`,
`kDefaultPageRows`, `kRetryDelayMilliseconds`. Опишите ноль/сентинелы и необычные границы.
Разделяйте начальное значение и жёсткий максимум, если смысл разный. Модель опций может
владеть значением поля; потребители используют модель/фабрику/ту же константу. Связанные
значения выводите из общего определения без повторения литералов.

Адаптеры, проверка сохранённых данных, CLI/GUI/worker и Python/MCP используют тот же источник,
включая максимумы схем и числовые диагностики. Межъязыковые контракты выводите из таблицы
или генерируемых привязок; иначе добавьте контроль расхождений. Сохраняйте чистую C-совместимость.
Более строгий лимит предпросмотра/страницы имеет отдельное имя/владельца; равные числа не доказывают общую политику.

Бинарные структуры, ABI/протоколы/инструкции, целочисленные диапазоны и расходы конкретного
алгоритма доказательства остаются в семантических моделях. Начальные состояния, индексы,
подсказки выделения и независимые тестовые входы не становятся политикой автоматически.
Не заменяйте независимую ожидаемую границу тестируемой константой реализации.

Проверяйте объявления и литералы: многострочные условия, циклы, макросы, значения по умолчанию,
таймеры, привязки. Установите смысл/владельца каждой затронутой политики; поиска `Max*`
недостаточно. Централизация сохраняет типы, значения, направление сравнений, сентинелы и
исчерпание/ошибки. Изменения политики отделяйте и запускайте [затронутые проверки](testing.md).

## Запуск тестов

Запустите все зарегистрированные тесты через агрегирующую цель:

```bash
python scripts/build.py build-release --parallel
cmake --build build-release --target check-neverd
```

Во время разработки используйте минимальную подходящую цель или метку CTest:

```bash
# Main Unicorn differential suite
cmake --build build-release --target check-neverd-semantic

# Lifter/loader/format binary only
python scripts/build.py build-release --target NeverDLiftTests --parallel 4
ctest --test-dir build-release --build-config Release \
  -L '^NeverDLiftTests$' --output-on-failure --parallel 4
```

[Руководство по тестированию](testing.md) описывает все вспомогательные
цели, наборы трансформаций только с метками, регулярные выражения для одного
теста, компиляцию fixture и циклы Unicorn. Если цель пропущена из-за отсутствия
кросс-компилятора или линкера, сообщите об этом ограничении; не называйте
неисполненный путь пройденным.

### SDK плагинов Python

При изменениях SDK сначала запускайте чистые Python-тесты и проверки расхождений, затем нативные адаптеры:

```bash
PYTHONPATH=pluginsdk/python python3 -m unittest discover \
  -s pluginsdk/python/tests -v
python3 -m mypy --config-file pluginsdk/python/pyproject.toml \
  pluginsdk/python/neverd_plugin
PYTHONPATH=pluginsdk/python python3 scripts/check_python_plugin_sdk.py
python scripts/build.py build-release --target \
  NeverDPluginRuntimeTests NeverDPythonRuntimeTests NeverDPythonPluginTests
ctest --test-dir build-release -R 'NeverD(Python|Plugin)' --output-on-failure
```

Публичные объявления C, сигнатуры ABI Python, версии пакета/CMake и политика доставки —
единый проверяемый контракт; обновляйте вместе. См. [руководство плагинов Python](python-plugins.md).

## Контрольный список pull request

Перед запросом проверки:

- Выполните rebase или merge последнего `dev` согласно процессу, который
  предпочитают сопровождающие, и осознанно разрешите изменения субмодулей.
- Соберите затронутые цели в Release или объясните необходимость другого
  профиля.
- Запустите точные регрессионные тесты и самый широкий практически доступный
  релевантный набор; укажите точные команды и все skips в описании PR.
- Сохраните строгий подъём: неподдерживаемая инструкция не должна незаметно
  превращаться в предполагаемую операцию или `NOP`.
- Для изменений поведения добавляйте семантическое покрытие, а не только
  текстовые снимки IR.
- Не включайте в diff постороннюю чистку, сгенерированные файлы и локальные
  артефакты сборки.
- Проверьте [правила заголовков и принадлежности политик](#стиль-кода), числовые условия/
  значения по умолчанию и расхождения привязок; одного форматирования недостаточно.
- Обновляйте публичную документацию и документацию для участников, когда
  меняются поведение, поддержка, флаги, команды или ответственность тестов.

Для чувствительных отчётов о безопасности, которые не следует начинать с
публичного pull request, следуйте [SECURITY.md](../../SECURITY.md).
