# Эмуляция драйверов Windows

Необязательный эмулятор драйверов NeverD выполняет точку входа PE поддерживаемого драйвера WDM x64 и может исполнить явный сценарий запросов до выгрузки. CLI с `auto` выбирает KVM на совместимом хосте Linux и WHP на Windows. Прежние значения C++ по умолчанию и API V1 сохраняют Unicorn. Все транспорты используют ограниченную модель Windows NeverD, которая обрабатывает вызовы гостевых API и изолирует драйвер от ядра хоста.

## Исполняющие бэкенды

`driver-strict` поддерживает KVM на совместимых хостах Linux x64 и WHP на Windows x64; `auto` выбирает этот нативный транспорт, а другая ISA использует Unicorn. Явный Unicorn и прежний API V1 сохраняют переносимый программный профиль. Нативное выполнение проверяет канонические адреса и эффекты до входа; недоступное оборудование вызывает ошибку без подмены. Неподдерживаемые инструкции и поведение OS завершаются явной ошибкой. Нативная CI для Windows x64 с отключённым Unicorn проходит все 359 обязательные проверки: 131 проверок CPU, 224 результата драйверов из 26 встроенных образов, 46 образов WDK и 40 сценарных вариантов по предпочтительным и перемещённым адресам, а также четыре проверки границ SEH ([`9d4c130c`](https://github.com/NeverSight/NeverD/actions/runs/36981864458)). Нативные свидетельства ARM64 ещё отсутствуют; совместимость произвольных драйверов или Android/Darwin не установлена.

Приведённая выше нативная проверка охватывает объявленные точки входа драйверов и опубликованные сценарии. Для описанных ниже подробных проверок отдельных функций и C API/CLI/Python свидетельства по-прежнему ограничены Linux, если выполнение в Windows не указано явно; успешное прохождение нативного корпуса не подтверждает все варианты тестов в Windows.

`DriverImage.def` объявляет ограничения размера и выравнивания и диагностические сообщения строгой проверки PE; ширина указателей берётся из `DriverProfile.def`. Проверка и релокация принадлежат `DriverImage.cpp`; допустимые образы и тексты ошибок не меняются.

На ARM64-хосте `checked-x64-v1` использует Unicorn для x64-гостя. Каждая инструкция и операция с памятью проверяется до пошагового исполнения; сохраняются проверки объектов Windows, наблюдатели записей, RAM-алиасы и контексты только CPU. Скалярная арифметика памяти, естественно выровненная locked-арифметика, SETcc и `BT/BTS/BTR/BTC` допускаются с проверками чтения/записи; флаги обрабатывает нативное исполнение. Ограниченный SIMD включает legacy-перемещения/логику SSE/SSE2, `MOVLHPS`/`MOVHLPS` и маскированные скалярные преобразования/вычитания. Все 16 XMM и MXCSR сохраняются при входе и восстановлении. Немаскированные SIMD-ошибки требуют нативных KVM/WHP с `precise_simd_exceptions`. Полноширинная запись XMM создаёт два упорядоченных наблюдения записи по 8 байт до изменения любого слова. Невыровненные aligned-vector-формы остаются неподдерживаемыми. Обычный операнд RAM может пересекать отдельно выделенные или алиасные страницы; до записи проверяется весь диапазон и сообщается первый недоступный байт. MOVS сохраняет завершённые элементы и регистры перезапуска сбойного элемента без частичной фиксации этого элемента.

Supervisor-x64 допускает одну выровненную скалярную MMIO-транзакцию 1/2/4 байта; страницы устройств не входят в native RAM. MOVS/REP MOVS выполняет один элемент на границе возобновления. Источник-устройство должен предоставить чистое подготовленное чтение, чтобы наблюдатель назначения мог остановить выполнение до commit. Windows register banks поддерживают подготовку; другие устройства отклоняют строковое чтение до эффектов. Device RMW, широкое MMIO и портовый I/O не поддерживаются. Байты запросов, состояние устройства и события записи сравниваются отдельно от дополнительного Unicorn REP-hook завершения при нулевом счётчике. KVM передаёт XMM/MXCSR и биты наличия FP/SSE через стандартный XSAVE. Контракт супервизора не предоставляет среду пользовательских процессов; timeout/отмена проверяются между допущенными инструкциями без общей асинхронной преэмпции или смены backend после старта. Встроенный корпус и доступные WDK-сценарии сравниваются с Unicorn на обычных/CFG и перемещённых образах; паритет корпуса не гарантирует совместимость произвольных драйверов.

Проверенный x64 также допускает маскированные legacy-формы `SS`, `SD`, `PS`, `PD` инструкций `ADD`, `SUB`, `MUL`, `DIV`, `SQRT`, `MIN`, `MAX`. `X64SSEInstructions.def` централизует ширины, выравнивание и допуск. `MaskedSSEArithmeticMatchesIndependentHostExecution` сравнивает регистры/RAM с независимым эталоном CPU хоста: четыре режима округления, FTZ, знаковые нули, субнормальные числа и NaN. `SSEMemoryObserverStopsBeforeResultAndStatusChanges` проверяет остановку до эффектов.

Параметры сборки: `NEVERD_EMULATION_BACKEND_KVM`, `NEVERD_EMULATION_BACKEND_WHP`. KVM требует доступа к `/dev/kvm`. WHP динамически загружает системную DLL. Новый C API `neverd_emulate_driver_backend_json` сохраняет ABI v1. Отчёт содержит бэкенд, контракт и причину выбора.

```bash
build-release/bin/neverd emulate-driver path/to/driver.sys \
  --backend auto --execution-contract checked-x64-v1
```

## Сборка и запуск

Функция включается явно и не зависит от `BUILD_TESTING`:

```bash
cmake -S . -B build-release -G Ninja \
  -DCMAKE_BUILD_TYPE=Release \
  -DNEVERD_ENABLE_DRIVER_EMULATION=ON
cmake --build build-release --target neverd --parallel 4
build-release/bin/neverd emulate-driver path/to/driver.sys \
  --instruction-limit 100000 > driver-report.json
```

Отчёт всегда выводится в stdout в формате JSON; диагностика запросов и настройки направляется в stderr. Ограничения по умолчанию: 100000 гостевых инструкций, 64 MiB гостевой памяти, 10000 записанных событий и 5000 миллисекунд. Лимит инструкций должен быть положительным. При исчерпании бюджета выполнение останавливается с сохранением частичных наблюдений; API выделения памяти сохраняют свои контракты возврата при нехватке ресурсов, включая описанный ниже NULL для отображений MMIO.

| Код завершения | Значение |
|----------------|----------|
| `0` | Инициализация и все запрошенные завершённые операции выполнены успешно |
| `1` | Неверные входные данные/параметры, ошибка настройки или функция отключена при сборке |
| `2` | Инициализация или завершённый запрос вернули `NTSTATUS` ошибки |
| `3` | Выполнение остановилось до завершения сценария, например из-за неподдерживаемого API, ошибки доступа или лимита бюджета |

Возвращённый статус ошибки также является завершённым наблюдением данной операции. Успешный возврат описывает только этот запуск в модели; он не доказывает работоспособность драйвера в Windows.

## Совместимость драйверов

Совместимость определяется выполняемым путём кода и его зависимостями, а не расширением `.sys`. Текущие подтверждения приёмки охватывают самостоятельно написанные freestanding fixture и пути buffered, in-direct и out-direct примера Microsoft SIOCTL WDM, включая сборку с отладочным журналом, а также прямые операции чтения и записи публичного примера Zero Павла Йосифовича. Это не подтверждает совместимость с произвольными сторонними драйверами.

| Класс драйвера или требование | Текущий объём поддержки | Недостающее окружение |
|-------------------------------|-------------------------|-----------------------|
| Программный x64 WDM-драйвер, использующий перечисленные API | Ограниченная инициализация x64 WDM, последовательные buffered/direct запросы, рабочие элементы, таймеры, DPC, события и ожидания, отчёты и ограничения | Для каждого дополнительного выполняемого API нужна определённая модель |
| `METHOD_BUFFERED` IOCTL | Последовательный buffered/direct I/O с завершением рабочим элементом или DPC | Только перечисленные ниже API; без произвольной параллельной подачи публичных сценариев и общей отмены запросов WDM |
| `METHOD_IN_DIRECT`, `METHOD_OUT_DIRECT` | MDL запросов, системные отображения и общие PFN модели только для чтения | Интерфейсы DMA за пределами описанного ниже подмножества |
| MDL, выделенные драйвером | Отдельные или связанные с IRP дескрипторы, частичные MDL, общие пользовательские/системные отображения и освобождение при завершении | Квоты, ручные MDL, произвольные адресные пространства процессов |
| READ/WRITE | Последовательный buffered/direct/neither I/O с завершением рабочим элементом или DPC | Только перечисленные API; без произвольной параллельной подачи публичных сценариев, общей отмены WDM и неявной позиции файла |
| WDM `METHOD_NEITHER` | Раздельные пользовательские буферы, проверки доступа, MDL, синтетические ID заявителей, отзыв VA или выход после диспетчеризации и ограниченная отмена | Нет таблиц страниц или общего менеджера процессов; ограниченные MDL-представления по PID поддерживаются |
| Драйвер KMDF 1.33 без PnP | Привязка, объекты/контексты, именованные управляющие устройства, последовательные или параллельные очереди по умолчанию с конечным или неограниченным пределом и буферизованные/прямые/neither-запросы с исполняемыми обратными вызовами | Нет поведения PnP за пределами описанного подмножества, общего планирования очередей, расширений классов и UMDF |
| Драйвер шины/функции/фильтра PnP | Явные PDO без ресурсов или с банками регистров, гостевой AddDevice и восемь основных minor-функций жизненного цикла PnP | Другие операции PnP, общая политика питания, прочее оборудование/ресурсы и общий KMDF PnP |
| Драйверы хранения, сети, дисплея, файловой системы и минифильтры | Контракты подсистем не поддерживаются | Фреймворки портов/классов/минипортов, NDIS/WFP, графические службы или службы файловой системы |
| Рабочие элементы, таймеры, DPC, события и ожидания | Текущий IRQL равен `PASSIVE_LEVEL` для диспетчеризации и рабочих элементов, `DISPATCH_LEVEL` для DPC | Только перечисленные ниже API; без произвольной параллельной подачи публичных сценариев и общей отмены запросов WDM |
| Драйвер с обратными вызовами процессов/потоков, дескрипторами, операциями с реестром/файлами или поиском модулей ядра | Перечисленные операции реестра поддерживаются для явно настроенного дерева; остальные операции не поддерживаются | Общий диспетчер объектов, операции с файлами, состояние системы и источники обратных вызовов/событий |
| Драйвер оборудования, DMA, PCI, прерываний или виртуализации | Явные банки, MMIO, исключительные или разделяемые latched/уровневые прерывания и когерентный DMA common/SG/channel | Другие модели устройств, произвольная физическая RAM, PCI, порты, другие интерфейсы DMA и привилегированное состояние CPU |
| Драйвер Windows x86 или ARM64 | Отклоняется | Загрузка, ABI и модель выполнения для соответствующей архитектуры |
| x64 CFG | Проверенные таблицы целей и вызовы check/dispatch; неактивная инструментация сохраняет гостевые резервные функции | XFG, подавление экспортов, немоделируемая конфигурация загрузки и TLS отклоняются |

Неиспользуемый неподдерживаемый импорт может оставаться связанным. Достижение неподдерживаемой операции останавливает выполнение с диагностикой и накопленными наблюдениями. Один лишь успешный DriverEntry не доказывает поддержку последующей диспетчеризации, оборудования или путей фреймворка. Таблица API ниже определяет поддерживаемое подмножество.

## Контракт выполнения

Профиль моделирует жизненный цикл x64 WDM на CPU0 с детерминированным кооперативным планированием по умолчанию. Выполнение начинается в точке входа PE; при наличии сохраняется обёртка входа, созданная компилятором. Для успешной инициализации DriverEntry должен вернуть `STATUS_SUCCESS`. Ненулевой успешный статус или статус pending останавливает выполнение как неподдерживаемый контракт инициализации. Статус ошибки сохраняется как завершённый результат инициализации. Все объекты, строки, стеки, указатели на функции и выделенные области находятся в гостевой памяти. Модель предоставляет `DRIVER_OBJECT` и путь реестра для настроенного имени службы (по умолчанию `NeverDDriver`). Адаптер использует виртуальный режим TLB Unicorn, сохраняющий гостевые виртуальные адреса, включая канонические высокие адреса ядра, без создания таблиц страниц Windows. Начальное значение RFLAGS — `0x202`; профиль программного устройства использует фиксированную строку кэша размером 64 байта. Это явно заданные свойства данного сценария выполнения.
Встроенное чтение x64 CR8 наблюдает тот же `PASSIVE_LEVEL` / `DISPATCH_LEVEL`; запись CR8 и остальные операции с управляющими регистрами по-прежнему не поддерживаются.

Только абсолютное 8-байтовое чтение `GS:[0x188]` предоставляет заимствованную непрозрачную идентичность текущего логического потока. Формы компилятора, например `MOV` и `CMP`, выполняются исходной инструкцией backend с её собственными эффектами для регистров и флагов. Вложенные callbacks того же потока видят тот же объект, другие потоки различаются; моделируемые системные потоки используют существующий объект. Частное представление процессора предоставляет лишь это поле, не моделируя полный KPCR и не давая доступа к структуре или владения ссылкой. Другие смещения GS, все обращения FS, индексные или неполноразрядные чтения и записи не поддерживаются.

Неизвестные импорты связываются с отложенными ловушками. Неиспользуемый импорт не мешает выполнению; выполнение его thunk или чтение немоделируемого экспортируемого значения данных приводит к `unsupported_api`. Неподдерживаемые эффекты окружения CPU также вызывают явную остановку. NeverD не заменяет нереализованные вызовы успешными значениями. Некорректные образы или неподдерживаемые требования загрузки вызывают ошибку до начала выполнения.

Элементы `DelayedWorkQueue` исполняются на `PASSIVE_LEVEL`, гостевые DPC — на `DISPATCH_LEVEL` с четырьмя предусмотренными аргументами. CPU0 по умолчанию использует детерминированное кооперативное планирование на границах возврата вызовов и блокирующего ожидания. Относительные, абсолютные и периодические таймеры используют виртуальное время; если ни один кадр не готов, оно продвигается до ближайшего срока таймера, ожидания или отмены. События/таймеры уведомления и синхронизации сохраняют разные правила потребления сигнала. У каждого вызова свой гостевой стек; несколько заблокированных кадров сохраняют локальные переменные и полные контексты CPU при общей памяти. Win64 передаёт первые четыре аргумента в регистрах, остальные в стеке. Запросы по умолчанию последовательны: диспетчеризация, пометившая IRP ожидающим, должна вернуть `STATUS_PENDING`. Для передач WDM через разные файлы или один асинхронный файл явный `defer_callback_drain` позволяет подать следующий запрос до выполнения обратных вызовов. Без доступного источника ожидающий запрос или бесконечное ожидание останавливается с `model_error` из-за зависания. Бюджеты инструкций, памяти, наблюдений и реального времени общие.

Ограниченная модель не обеспечивает полную асинхронность Windows. Не поддерживаются alertable-ожидания и ожидания пользовательского режима, APC, общая отмена запросов WDM, параллельные публичные сценарии, UMDF, устройства PnP KMDF и общее планирование очередей, полный PnP/питание, произвольное оборудование, другие интерфейсы DMA и другие режимы прерываний. Инициализация выполняет явно поставленные в очередь вызовы без неявного создания запросов или выгрузки.

Рабочий элемент извлекается из очереди до начала обратного вызова, поэтому тот может освободить собственный элемент. Освобождение элемента в очереди, повторная постановка, устаревшие объекты и адреса вызова вне исполняемой гостевой памяти явно отклоняются. Ссылка на устройство удерживается до возврата. Выгрузка требует освободить все рабочие элементы и завершить очередь. Контексты CPU сохраняют общие регистры, SIMD, FPU и управляющее состояние; гостевая память остаётся общей, а восстановление контекста не позволяет возобновить CPU после сбоя.
Удаление откладывается, пока остаются файловые объекты или ссылки рабочих элементов в очереди/исполнении. При исчерпании арены объектов выделение рабочего элемента возвращает NULL.

Образы используют предпочтительный базовый адрес, если сценарий не задаёт допустимый адрес перемещения; это должны быть исполняемые файлы PE32+ x64 с подсистемой native. Импорты могут предоставляться `ntoskrnl.exe`, `ntkrnlmp.exe`, `HAL.dll` или `WDFLDR.SYS`. Загрузчик выполнения поддерживает проверенные базовые релокации x64 `DIR64` и ограниченную конфигурацию загрузки security cookie, который инициализируется детерминированным гостевым значением до запуска обёртки входа. Другие немоделируемые поля конфигурации загрузки, TLS, отложенные/связанные импорты, импорты по ordinal и managed-образы отклоняются. Образы также должны пройти строгую проверку диапазонов и выравнивания.

Активный Control Flow Guard (CFG) проверяет флаги PE, слоты указателей и отсортированные исполняемые цели. Обработчики check/dispatch допускают только объявленные входы образа или зарегистрированные API-thunk, сохраняют состояние вызова Win64 и отклоняют остальные цели. Инструментация без активного CFG сохраняет исходные гостевые резервные указатели. Активный XFG, подавление экспортов и другие немоделируемые политики отклоняются; исполняемая память сама по себе не делает адрес допустимой целью.

Стек WDM может содержать несколько устройств одного гостевого драйвера. `IoAttachDeviceToDeviceStack` присоединяет отдельное исходное устройство над текущей вершиной целевого стека и возвращает прежнюю вершину. Он задаёт `StackSize` и `AlignmentRequirement`, не меняя список `NextDevice` и не копируя флаги буферизации. `IoDetachDevice` принимает сохранённое нижнее устройство и требует `PASSIVE_LEVEL`; присоединение допускается до `DISPATCH_LEVEL`. Открытие именованного нижнего устройства направляет запрос текущей вершине, но `FILE_OBJECT.DeviceObject` и отчёт сохраняют именованную идентичность. READ/WRITE использует флаги выбранной вершины. Сохранённый маршрут удерживает все устройства до возврата диспетчеризации, в том числе после отсоединения/удаления; внутренние ссылки не увеличивают `ReferenceCount`, считающий открытые дескрипторы.

`IofCallDriver` и вспомогательный `IoCallDriver` вызывают точно указанное устройство сохранённого маршрута. Настоящие inline-функции `IoCopyCurrentIrpStackLocationToNext`, `IoSkipCurrentIrpStackLocation` и `IoSetCompletionRoutine` работают с исходным гостевым IRP; проверяются курсор, число позиций и управляющие флаги. Нижняя диспетчеризация возвращает свой фактический статус отдельно от `IoStatus` и результата процедуры завершения. Разворачивание продвигает курсор, выбирает callbacks по успеху/ошибке/отмене и передаёт pending вверх. Вызванная процедура завершения отвечает за эту передачу, включая передачу после прежнего возврата `STATUS_PENDING`. `STATUS_MORE_PROCESSING_REQUIRED` останавливает разворачивание, сохраняя IRP, MDL и буферы; последующее завершение возобновляет его. Вложенное завершение требует внешнего результата остановки; окончательное освобождение выполняется один раз. Продолжения с владельцем-подсистемой сохраняют вложенные кадры WDM/WDF и унаследованный IRQL. Каждая использованная нижняя позиция стека обнуляется перед верхним callback завершения.

`IoAllocateIrp` и `IoFreeIrp` поддерживают IRP во владении вызывающего до `DISPATCH_LEVEL` с `ChargeQuota=FALSE`. Первый `IoCallDriver` проверяет пакет и сохраняет точный нижний маршрут. Этот объём поддерживает ядерный `IRP_MJ_INTERNAL_DEVICE_CONTROL` с буферами `METHOD_NEITHER` драйвера, без пользовательского файла и копирования пользовательских буферов. Выполняются настоящие гостевые процедуры завершения и отмены. Освобождение внутри завершения требует `STATUS_MORE_PROCESSING_REQUIRED`: доступ к пакету прекращается сразу, метаданные сохраняются до возврата кадров. Неотправленный пакет можно освободить; утечки, повторное освобождение, чужие или ещё удерживаемые пакеты явно отклоняются. Произвольное переиспользование, другие форматы, `IoBuildDeviceIoControlRequest` не поддерживаются.

Наблюдения используют `kind: "internal_ioctl"`, `origin: "driver_allocated_irp"` и `file: null`, сохраняя `code`, `irp`, статусы, время отмены и точный `information_hex`. Нативные и JSON-сценарии отклоняют `internal_ioctl` до загрузки; строки создают только реальные гостевые выделение и отправка.

Вне описанного ниже протокола USB idle: Нижняя цель должна быть живым гостевым WDM-устройством; процедура завершения должна покрывать успех, ошибку и отмену. Настоящий `driver_wdm_owned_irp.c` использует `NEVERD_WDM_OWNED_IRP_FIXTURE` / `NEVERD_WDM_OWNED_IRP_CFG_FIXTURE`. [Сценарий IRP вызывающего](../examples/driver-owned-irp-scenario.json) проверяет отложенное завершение. Образы normal/active-CFG покрывают предпочтительные/перемещённые адреса; C API/CLI сохраняют отдельные ядерные строки. Отсутствующие артефакты явно пропускаются; свидетельства выполнения ограничены Linux.

Пример намеренно отменяет один дочерний запрос: ожидаются код выхода CLI 2 и `scenario_success: false`, при этом `stop_reason: "returned"`, выгрузка штатная и ошибок fixture нет. Завершённый вывод ядра можно сохранить в `output_hex`; буфер остаётся собственностью драйвера.

Общая политика питания, остальные minor-функции PnP и прочие модели оборудования/ресурсов не поддерживаются. Перенаправление на цель WDF вне прямого файлового маршрута FDO/PDO, присоединение к стеку с активными файлами или callbacks, отсоединение среднего слоя, смена основной функции и цели вне сохранённого маршрута явно отклоняются. Необязательный оригинальный `driver_wdm_stack.c` с настоящим WDK задаётся через `NEVERD_WDM_STACK_FIXTURE` и `NEVERD_WDM_STACK_CFG_FIXTURE`. Нативные тесты и C API/CLI включают перемещение базы; отсутствие артефактов явно отмечается пропуском. Свидетельства выполнения ограничены Linux.

Сценарий может явно задать до 64 `pnp_devices`. Каждый элемент требует `id`, `bus: "resource_free"` / `bus: "register_bank"`, `initial_device_power: "D0"` и `initial_system_power: "working"`; пропущенные факты не угадываются. ID — регистрозависимая ASCII-строка длиной 1–64 байта, начинающаяся с буквы/цифры и далее содержащая только буквы, цифры, `_`, `-`, `.`. Обычный запрос может использовать настроенный `device_id` вместо `device`, но не оба поля. Для `kind: "pnp"` обязательны `device_id`, `minor`, `bus_completion`. Поддерживаются `start`, `query_remove`, `cancel_remove`, `remove`, `query_stop`, `stop`, `cancel_stop` и `surprise_removal`. Обязательный `bus_completion.status` — 32-битное целое или шестнадцатеричная строка; необязательный `delay_100ns` — неотрицательное целое до INT64_MAX, отсчитываемое от фактического получения провайдером. Конечный статус не может быть `STATUS_PENDING`; stop/cancel-stop/surprise-removal/cancel-remove/remove требуют ровно `STATUS_SUCCESS` (0). Файловые поля, передача и отмена для PnP отклоняются даже при нулевых значениях. C++ API использует ту же предварительную проверку.

После успешного DriverEntry для каждого заданного PDO один раз исполняется `AddDevice`. Провайдер владеет отдельным `DRIVER_OBJECT`; гость не может удалять или подменять его объекты. PnP IRP имеют `KernelMode`, не связаны с файлом, получают ресурсы согласно заданной шине и начинаются с `STATUS_NOT_SUPPORTED`. Ответ шины используется только при фактической передаче в этот PDO; задержка использует общие виртуальные часы и существующие продолжения завершения. Окончательное верхнее завершение фиксирует или откатывает состояние независимо от статуса шины. Обычное удаление из Started требует успешного query, закрытых файлов, завершённых прежних запросов и гостевого отсоединения/удаления. Чистая ошибка AddDevice освобождает только провайдера; утечки новых гостевых устройств, даже отсоединённых, вызывают `model_error`. Перед unload все провайдеры должны отсутствовать. Другие операции PnP, общая политика питания, прочее оборудование/ресурсы и общий KMDF PnP не входят в этот набор. Успех PnP требует фактического завершения провайдера; ранняя верхняя ошибка START/QUERY_STOP/QUERY_REMOVE может оставить наблюдения шины null. Идентичность жизненного цикла устройства/файла сохраняется после отсоединения.

Исходные настройки сохраняются в `configuration.pnp_devices`. Наблюдаемые `pnp_devices` содержат `id`, `pdo`, nullable `add_device_status`, текущее `attached`, `pnp_state`, `provider_present`; после удаления `attached` равно false. Фаза AddDevice — `add_device:<ID>`; ошибки влияют на `scenario_success`, не заменяя `nt_status` DriverEntry. Каждый запрос получает nullable `device_id` и `pnp`; у PnP `file` равен null. Объект `pnp` содержит `minor`, `state_before`, `state_after`, nullable `bus_status`, `bus_received_at_100ns`, `bus_completed_at_100ns`. Настроенный статус становится наблюдением только при фактическом завершении на шине; время получения независимо. Типы прежних полей не меняются.

Необязательное поле `parent_id` явно задаёт родительского провайдера по настроенному ID. Родитель может стоять позже в массиве; отсутствие поля означает независимый корень. Нативная и JSON-проверки отклоняют неизвестных родителей, ссылки на себя, циклы и неверные ID до создания PDO. Граф не создаёт присоединения WDM или иерархию объектов WDF. Наблюдаемые `parent_id` и `parent_pdo` сохраняют исходную идентичность после удаления любого из провайдеров. START потомка требует присутствующего родителя в Started и физическом D0 без незавершённого перехода жизненного цикла или питания. Для STOP и SurpriseRemoval родителя потомки должны покинуть активные состояния PnP и завершить переходы и WAIT_WAKE. Перед REMOVE нужно удалить всех дочерних провайдеров. Неявного каскада нет.

Обычные CREATE/READ/WRITE/IOCTL/CLEANUP/CLOSE поступают в реальный гостевой dispatch, пока устройство существует вне Removing/Removed. Модель не создаёт отказ по состоянию Stopped, StopPending, RemovePending или питания: драйвер сам завершает программный I/O, отклоняет или удерживает запрос. Публичный исполнитель по умолчанию последователен; исключение — описанные ниже явно заданные ограниченные пакеты с `defer_callback_drain`. Вне этого контракта удерживаемая IRP без доступного сейчас источника завершения не может дождаться последующего start/cleanup сценария и останавливается с зависшим `model_error`. Закрытие файлов и завершение предыдущих запросов до Remove — ограничения профиля. Конечный `STATUS_RESOURCE_REQUIREMENTS_CHANGED` (0x119) для `query_stop` требует немоделируемого повторного запроса ресурсов и отклоняется как в preflight, так и при гостевом завершении; см. [контракт Microsoft QUERY_STOP](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/irp-mn-query-stop-device). Stop/restart и surprise-removal не реализуют переназначение ресурсов.

PnP без ресурсов использует оригинальный `driver_wdm_pnp.c` с настоящим WDK, необязательные `NEVERD_WDM_PNP_FIXTURE`/`NEVERD_WDM_PNP_CFG_FIXTURE` и нативные тесты/C API/CLI. Отсутствие артефактов явно пропускается; выполнение проверено только на Linux.

WDM remove-lock исполняет реальные экспорты `IoInitializeRemoveLockEx`, `IoAcquireRemoveLockEx`, `IoReleaseRemoveLockEx` и `IoReleaseRemoveLockAndWaitEx`; имена WDK без Ex являются макросами. Владелец — точный DEVICE_OBJECT, расширение которого содержит всю выровненную область, независимо от состояния PDO и вида Tag. Инициализация разрешена до присоединения. Поддерживаются retail 32/DBG 120 байт с совпадающим отдельным аргументом размера; вся зарегистрированная область непрозрачна. NULL и повторные Tags учитываются отдельно для каждого замка и не разыменовываются, поэтому release после завершения IRP допустим. Инициализация/AndWait требуют `PASSIVE_LEVEL`, acquire/release допускают `DISPATCH_LEVEL`.

AndWait закрывает приём, снимает одно совпавшее получение и приостанавливает настоящий гостевой кадр до освобождения остальных. Последующие acquire возвращают `STATUS_DELETE_PENDING` без новой обязанности release. Последний release фиксирует готовность до возврата callback; worker может освободить замок и ждать событие от продолжившего REMOVE. Нет синтетического callback, таймаута или успеха без производителя. Нужен связанный маршрут активного REMOVE с владельцем и фактический приём провайдером (`bus_received_at_100ns` допускает ноль), но не нижнее завершение. Очередь нижнего драйвера до приёма провайдером вне профиля; это не полная проверка OutsideRemoveDevice/Driver Verifier. Перед REMOVE всё ещё нужны закрытые файлы и завершённые прежние запросы, но callbacks, освобождающие замки, могут оставаться. Маршрут удерживается через ожидание, отсоединение/удаление и нижний pending до возврата оставшихся кадров.

Неизвестная/несовпадающая область, release без получения, повторный drain, переинициализация и удаление расширения с получениями или непотреблённым drain-ожиданием отклоняются до изменений. Чистый отказ AddDevice может удалить инициализированный неиспользованный замок. Замок не заменяет реальные ссылки устройства/worker; регистрация исчезает только при физическом освобождении расширения. Debug-метаданные не включают таймауты/high-water Verifier. Подлинный `driver_wdm_remove_lock.c` имеет варианты `NEVERD_WDM_REMOVE_LOCK_FIXTURE`/`NEVERD_WDM_REMOVE_LOCK_CFG_FIXTURE`/`NEVERD_WDM_REMOVE_LOCK_DBG_FIXTURE`/`NEVERD_WDM_REMOVE_LOCK_DBG_CFG_FIXTURE`. Отсутствие явно пропускается, native и C API/CLI доказаны только на Linux, без заявления о полном менеджере удаления или общем параллельном дренировании I/O.

Синтетическая шина `bus: "register_bank"` добавляет PDO явно заданные фиксированные ресурсы памяти. При наличии массив `resources` содержит `id`, `raw_start`, `translated_start`, `length` и `registers`; каждому регистру нужны `offset`, `width`, `access` (`read_only` или `read_write`) и начальное `value`. Общий контракт C++/JSON определён в `DriverResources.h` / `DriverResources.def`. ID ресурсов подчиняются ограниченным правилам ASCII-идентификаторов и уникальны внутри PDO. Допускаются 8 ресурсов на PDO / 32 суммарно, 256 регистров на ресурс / 4096 суммарно и 1–1048576 байт на ресурс. Поддерживаются только точные естественно выровненные обращения шириной 1/2/4 байта; значение должно помещаться в эту ширину. Оба физических диапазона должны исключать переполнение; исходные диапазоны не пересекаются внутри PDO, преобразованные — глобально. Пустой `registers` явно делает весь банк недоступным. Адреса и начальные значения являются декларациями, а не оборудованием хоста или неявно обнулённой памятью. `resource_free` по-прежнему не содержит ресурсов и передаёт нулевые указатели START.

START получает отдельные исходные и преобразованные выделения `CM_RESOURCE_LIST` только для чтения, с соответствующими упорядоченными дескрипторами Memory: один полный дескриптор, интерфейс Internal, шина 0, версия/ревизия 1, совместное использование DeviceExclusive и флаги диапазона READ_WRITE. RO отдельных регистров независимо от этих флагов. Успешное нижнее START делает назначение доступным до верхних callbacks; каждый START из NotStarted/Stopped создаёт новое поколение с тем же фиксированным назначением. Значения инициализируются из конфигурации PDO и переживают unmap, STOP и повторный запуск. При неудачном START и успешном STOP/REMOVE драйвер обязан снять отображения до терминального завершения IRP; скрытая очистка не выполняется. Внезапное удаление сразу запрещает новые отображения и обращения к регистрам, но позволяет снять существующие отображения. Фактическое успешное завершение SET устройства у провайдера меняет физическую доступность: D3 запрещает обращения, D0 разрешает их только при доступном назначении. В D3 можно создавать отображения без доступа к регистрам; D3hot сохраняет отображения и значения; явный цикл D3cold восстанавливает настроенные значения перед доступом D0.

`MmMapIoSpace` поддерживает NonCached, а `MmMapIoSpaceEx` — PAGE_NOCACHE вместе с PAGE_READONLY или PAGE_READWRITE. Обе функции принимают только объявленный преобразованный поддиапазон одного назначения, сохраняя смещение внутри страницы. Алиасы разделяют один банк, имеют независимые разрешения и требуют точных исходных базы и длины для `MmUnmapIoSpace`. Исчерпание отображений, окна или заданного бюджета памяти возвращает NULL; сбои backend остаются явными ошибками. Снятый виртуальный адрес не становится доступным через последующее отображение. Реальные скалярные и REP-инструкции проходят проверки MMIO CPU; пробелы, неверная ширина, невыровненность, запись RO, переход между отображениями и исполнение отклоняются до эффектов регистров. Обращения к памяти через моделируемые API также должны укладываться в одну выровненную транзакцию размером 1/2/4 байта; более крупные диапазоны отклоняются, а не разбиваются на обращения к регистрам. Произвольная физическая RAM, перераспределение ресурсов, порты, другие режимы прерываний, другие интерфейсы DMA и общее поведение оборудования не реализованы.

Исполняемый [сценарий банка регистров](../examples/driver-register-bank-scenario.json) использует оригинальный `driver_wdm_resources.c`, собранный настоящим WDK, через `NEVERD_WDM_RESOURCE_FIXTURE` / `NEVERD_WDM_RESOURCE_CFG_FIXTURE`. Он выполняет 14 запросов с отложенным START, файловым I/O, STOP, перезапуском и удалением и наблюдает сохраняемые значения через IOCTL драйвера. `configuration.pnp_devices[].resources` сохраняет исходные данные с шестнадцатеричными физическими адресами без потери точности; это не второй отчёт о состоянии банка. C API и Python используют прежний `scenario_json` и неизменённый `neverd_driver_options_v1`. Отсутствующие настоящие артефакты явно пропускаются; данные исполнения получены только на Linux.

Провайдер `register_bank` допускает `interrupts` отдельно или с `resources`; хотя бы один список должен быть непустым. `resource_free` отклоняет поле даже пустым. Каждая линия требует `id`, `raw_vector`, `raw_level`, `raw_affinity`, `translated_vector`, `translated_level`, `translated_affinity`, `mode` (`latched` или `level_sensitive`) и `share` (`device_exclusive` или `shared`). Источник уровня требует положительный `retrigger_after_100ns` до INT64_MAX; latched запрещает это поле. Пределы: 8 линий на PDO, всего 32, ограниченные ASCII-ID, уникальные внутри PDO, исходный уровень 0–65535 и переведённый DIRQL 3–12. Обе affinity равны 1 (CPU0/group0); векторы сохраняют 32 бита. Общий переведённый вектор требует одинаковых уровня, affinity, режима и периода, а также `share: "shared"` у всех участников. Дескрипторы памяти предшествуют упорядоченным дескрипторам прерываний с корректными флагами режима и разделения. Это явно заданные синтетические линии, а не контроллер PCI. `DriverInterrupts.h` / `DriverInterrupts.def` задают имена и ограничения.

READ/WRITE/IOCTL могут объявлять `interrupt_events` с `after_100ns`, `device_id` и `interrupt_id`. `action` по умолчанию равен `pulse` для latched; источники уровня требуют `assert` или `deassert` и запрещают `pulse`. Источники latched допускают только `pulse`. Другие запросы отклоняют поле даже пустым. Пределы: 64 события на запрос, 1024 объявленных на сеанс, неотрицательная задержка до INT64_MAX. Подача фиксирует живые подключения и поколение PDO; завершение IRP не отменяет события. По умолчанию доставка происходит на границах callbacks, а время движется при простое. С `scheduling` сроки продвигаются и при исполнении инструкций; произвольная вложенность прерываний не поддерживается. Публикация оборудования предшествует допуску, ISR по назначенному DIRQL идут перед DPC/workers. Потеря подключения, недоступное поколение или D3 дают `undelivered_reason` без неявной перепривязки.

Разделяемый latched-импульс вызывает все зафиксированные ISR по порядку регистрации, даже после TRUE. Линия уровня — логическое ИЛИ состояний по PDO/источнику/поколению; повторный `assert` идемпотентен. Все изменения одного момента применяются до опроса. Пока линия активна, следующий опрос назначается после завершения раунда ISR плюс `retrigger_after_100ns`. Для уровня TRUE прекращает поиск в этом раунде, но не подтверждает и не сбрасывает источник; его сбрасывает только `deassert`. Записи регистров не подразумевают подтверждения. Допускается до 4096 раундов доставки, максимум 32 обработчика в каждом, дополнительно к бюджетам callbacks и инструкций. Отключение и удаление устройства отклоняются при ещё активном источнике.

`IoConnectInterrupt` использует одиннадцать аргументов и точное переведённое назначение. `IoConnectInterruptEx` поддерживает FullySpecified (1), LineBased (2, одна линия явного PDO) и FullySpecifiedGroup (4, group0); отключение требует совпадения версии/контекста. Регистрация и отключение требуют PASSIVE_LEVEL. Допустим собственный lock либо инициализированный вызывающей стороной невыгружаемый `KSPIN_LOCK`. Несколько подключений могут разделять его с одинаковым `SynchronizeIrql`, не ниже каждого назначенного DIRQL. Ноль в LineBased выбирает назначенный уровень; приоритет планировщика не меняется. Сохраняются CPU0/group0 и отсутствие сохранения floating state. Настоящий ISR получает непрозрачный `KINTERRUPT` и ServiceContext, возвращает BOOLEAN в AL. ISR, `KeSynchronizeExecution` и ручные acquire/release используют один реальный нерекурсивный lock. Synchronize работает на IRQL синхронизации и восстанавливает IRQL/CR8; проверяются владелец и сохранённый IRQL. Executive spin-lock API не могут обращаться к подключённому lock. Произвольная вложенность прерываний не поддерживается. Неудачный START и успешный STOP/REMOVE требуют отключения до окончательного завершения; DPC в очереди не удаляются неявно.

`configuration.pnp_devices[].interrupts` хранит ресурсы, а `configuration.interrupt_events` — объявления. Наблюдения `interrupts` содержат `source_request_index`, `event_index`, `device_id`, `interrupt_id`, `action`, `epoch`, `due_at_100ns`, `occurred_at_100ns`, `delivered_at_100ns`, `returned_at_100ns`, `interrupt_object`, `return_value`, `claimed` и `undelivered_reason`. `handlers[]` записывает каждый реально вызванный ISR: объект, времена, BOOLEAN, `claimed` и `delivery_index`. Одна активация может породить несколько раундов; deassert или assert, отменённый в тот же момент, не создаёт вымышленный ISR. `occurred_at_100ns` означает применение изменения состояния. `claimed` объединяет реальные возвраты; невостребованное прерывание допустимо. `delivered_at_100ns` обозначает первую доставку; `returned_at_100ns` и `claimed` описывают последний раунд, а `handlers[]` хранит всю историю. Исполняемый [сценарий прерываний](../examples/driver-interrupt-scenario.json) использует оригинальный `driver_wdm_interrupts.c`, собранный настоящим WDK, и необязательные `NEVERD_WDM_INTERRUPT_FIXTURE` / `NEVERD_WDM_INTERRUPT_CFG_FIXTURE`: семь запросов включают отложенный START, pending IOCTL с завершением ISR→DPC, cleanup/close файла и удаление. Граница C/Python `scenario_json` и layout `neverd_driver_options_v1` не меняются. Отсутствующие настоящие артефакты явно пропускаются; свидетельства исполнения ограничены Linux.

`DriverDMA.h` / `DriverDMA.def` добавляют необязательный объект `dma` в PDO `register_bank` наряду с назначениями памяти/прерываний; один DMA не заменяет эти ресурсы. Все семь полей задаются явно: `address_bits` (32 или 64), `maximum_length` (1–1048576 байт), `map_registers` (1–256), `alignment` (степень двойки от 1 до 4096), `logical_base` (ненулевой, выровненный по странице), `logical_length` (кратно странице, 4096–1073741824 байт) и логическое `scatter_gather`. Окно не должно переполняться и должно укладываться в разрядность адреса. У каждого PDO независимый логический домен; одинаковые адреса разных устройств не образуют алиасы. Все переведённые MMIO-ресурсы обязаны обходить зарезервированную RAM модели `[0x1000000000, 0x1004000000)`, даже без настройки DMA. Это факты о когерентном синтетическом ведущем шины, а не физической памяти хоста или устройстве PCI.

`IoGetDmaAdapter` принимает исторические поля `DEVICE_DESCRIPTION` версии 0/1 для Internal bus master и публикует `DMA_ADAPTER` версии один с настоящей 104-байтовой таблицей `DMA_OPERATIONS`. Запросы версий 2/3 возвращают NULL, не читая современное окончание описания. Каждый косвенный метод привязан к конкретному живому адаптеру независимо от импортов ядра. Реализованы `AllocateCommonBuffer`, `FreeCommonBuffer`, `GetDmaAlignment`, `GetScatterGatherList`, `PutScatterGatherList`, `PutDmaAdapter`, `AllocateAdapterChannel`, `MapTransfer`, `FlushAdapterBuffers` и `FreeMapRegisters`. `FreeAdapterChannel` и `ReadDmaCounter` остаются именованными ловушками: подчинённого/системного DMA-контроллера в профиле нет. Выделение/освобождение common buffer и запрос выравнивания требуют PASSIVE_LEVEL; Get/PutScatterGatherList требуют DISPATCH_LEVEL, освобождение адаптера допускает IRQL до DISPATCH_LEVEL. x64 игнорирует `CacheEnabled`. Неподдерживаемые версии, несовместимые объявленные возможности и документированная нехватка ресурсов возвращают NULL; некорректный или немоделируемый выбор интерфейса и сбои backend остаются явными ошибками.

Системные псевдонимы MDL для областей образа, принадлежащих загрузчику, допускают доступ к известным байтам образа в описанных страницах размером 4 КиБ. Доступ к заполнению вне объявленной области образа завершается ошибкой, даже если базовая страница отображена. `ByteOffset` и `ByteCount` сохраняют логический диапазон буфера и не задают границы прав CPU внутри страницы. Байты образа за пределами этого диапазона остаются общими с исходным отображением; защита и отмена отображения применяются ко всему диапазону страниц. Для памяти объектов сохраняются ограничения модели на заполнение.

`KernelPhysicalMemory` назначает существующей RAM не более 16384 физических страниц модели по 4096 байт. Виртуальные адреса CPU, идентичность физических страниц и логические адреса устройства различаются. Массивы PFN построенных MDL открывают общие идентификаторы только для чтения; у непостроенных дескрипторов нет пригодных PFN. Небольшие соседние выделения могут иметь общий PFN, сохраняя отдельные диапазоны байтов и сроки жизни. Common buffer, пул и буферы запросов используют те же байты, которыми уже владеет `GuestMemory`, без второй копии DMA. Живое SG-отображение фиксирует точный диапазон данных и дескриптор. Завершение, освобождение пула/MDL и удаление заранее отклоняют живые зависимости. Снятие отображения прямого MDL отзывает только системное отображение CPU; DMA сохраняет доступ к заблокированной памяти. `DmaWritable` отдельно хранит контракт блокировки для записи и права CPU: запись устройства требует прямого READ/OUT_DIRECT или доступной для записи невыгружаемой памяти; WRITE/IN_DIRECT не получают это право лишь из-за записываемого отображения CPU.

`GetScatterGatherList` проверяет CurrentVa/Length по исходному диапазону MDL и создаёт логические фрагменты страниц поверх существующей памяти. При доступных регистрах отображения настоящий четырёхаргументный void `AdapterListControl` выполняется внутри вызова до возврата API; иначе сохраняются данные/дескриптор и резервируется callback в FIFO данного PDO до освобождения ресурсов. В этом профиле нет владельца StartIo, поэтому второй аргумент IRP равен NULL. Возврат callback не освобождает отображение. `PutScatterGatherList` допустим внутри callback; после Put драйвер может завершить запрос и освободить последний адаптер, при этом продолжение callback и удержание устройства сохраняются до возврата. Освобождение common buffer требует исходных адаптера, длины, логического и CPU-адресов. Логические адреса не переиспользуются в течение сеанса, включая перезапуск. Ожидание ресурсов без реального производителя явно останавливается, не выдумывая завершение или срок. Пока живое SG-отображение передало данные во владение устройства, доступ CPU требует сначала Put; ожидающий регистров callback ещё не передал такое владение байтами.

`AllocateAdapterChannel` требует DISPATCH_LEVEL и резервирует непрозрачный ненулевой токен регистров отображения. Common buffer, списки SG и резервы каналов используют общую квоту и FIFO каждого PDO. Успех означает принятие настоящего немедленного или отложенного `AdapterControl`; превышение доступного числа возвращает `STATUS_INSUFFICIENT_RESOURCES` без callback. На гостевом устройстве допускается один незавершённый callback выделения; вызов AllocateAdapterChannel из AdapterControl запрещён, в том числе через вложенный callback. Четыре аргумента содержат реальный снимок `DEVICE_OBJECT.CurrentIrp` при регистрации. Именно это восьмибайтовое поле доступно гостю для записи; принимаются ноль или живой IRP, маршрут которого включает устройство. Очередь удерживает пакет до входа в callback, после чего тот может его завершить. StartIo по-прежнему не моделируется; неиспользуемый IRP отдельного SG callback остаётся NULL.

`AdapterControl` возвращает 32-битный `IO_ALLOCATION_ACTION`; старшие биты RAX игнорируются, действие не заменяет `STATUS_SUCCESS` у AllocateAdapterChannel. `DeallocateObject` освобождает неиспользованные или полностью обработанные flush регистры при возврате. `DeallocateObjectKeepRegisters` сохраняет их до вызова `FreeMapRegisters` с точными адаптером, токеном и первоначальным числом. `KeepObject` требует немоделируемого системного контроллера и явно отклоняется. Только что переданное выделение нельзя освободить как сохранённое до возврата его callback; другое ранее сохранённое выделение можно освободить при соблюдении его собственного контракта. Идентичность callback, сохранённые регистры и отображённые байты имеют отдельные сроки жизни; все они проверяются перед удалением адаптера или устройства.

`MapTransfer` и `FlushAdapterBuffers` допускают IRQL до DISPATCH_LEVEL; выделение канала и освобождение регистров требуют DISPATCH_LEVEL. MapTransfer принимает индекс относительно MDL, читает и обновляет настоящую длину ULONG и возвращает логический адрес по значению. Ограниченный SG-профиль возвращает один фрагмент физической страницы за вызов; последующие непрерывные индексы того же MDL и направления расширяют одну операцию. Без SG весь запрошенный диапазон отображается одним вызовом, если помещается в резерв, без сокращения длины. Первый вызов резервирует непереиспользуемое логическое окно размером с резерв регистров; другие выделения могут чередоваться, не пересекая его. Все фрагменты используют одно расширяемое закрепление физической памяти. Транзакция устройства может охватывать всю отображённую операцию, но доступ CPU, освобождение MDL и завершение с удалением закреплённой памяти блокируются до общего flush. Flush должен совпадать по начальному индексу, MDL, направлению и полной фактически отображённой длине. Он освобождает байты, сохраняя регистры для следующей операции с тем же токеном. Частичный flush, смешение MDL и другие схемы MapTransfer находятся вне профиля; они не объявляются недопустимыми на любой Windows.

`KeFlushIoBuffers` проверяет живой заблокированный/невыгружаемый MDL. Моделируемая платформа когерентна: ни одно значение ReadOperation или DmaOperation не требует отдельной копии кэша; вызов не снимает владение DMA и не заменяет FlushAdapterBuffers. [Сценарий канала](../examples/driver-dma-channel-scenario.json) исполняет оригинальный `driver_wdm_dma_channel.c`: два MapTransfer, одна транзакция через границу страниц, отдельно объявленные IRQ/DPC, общий flush и точное освобождение регистров. Настоящие normal/CFG-образы задаются через `NEVERD_WDM_DMA_CHANNEL_FIXTURE` и `NEVERD_WDM_DMA_CHANNEL_CFG_FIXTURE`.

Только READ/WRITE/IOCTL принимают `dma_events`. Каждое событие требует `after_100ns`, `device_id`, `logical_address`, `direction` и `length`; для `write_memory` также нужен `data_hex` точной длины, а `read_memory` запрещает это поле. Направление задаётся с точки зрения устройства. Ограничения: 64 события на запрос, 1024 всего, 16 MiB суммарных данных и 1 MiB на транзакцию; задержка от нуля до INT64_MAX. Подача фиксирует текущую назначенную эпоху PDO и исходное виртуальное время, но не требует отображения, которое предстоящая диспетчеризация ещё должна создать. При доставке разрешаются весь живой логический диапазон и направление, требуется физическое D0 и проверяются все байты до любых эффектов. Завершение исходного IRP не отменяет событие. Отсутствующие/освобождённые отображения, устаревшие эпохи, внезапное удаление или D3 фиксируют ошибку и останавливают выполнение; события не перепривязываются и не создают вымышленные прерывания, протокол регистров или завершения IRP. На одной границе планирования сначала публикуется оборудование провайдера, затем байты DMA, затем отдельно объявленные импульсы прерываний. По умолчанию время кооперативное; `scheduling` включает сроки и вытеснение на основе инструкций.

Отчёты сохраняют `configuration.pnp_devices[].dma` и развёрнутый `configuration.dma_events`. Корневые строки `dma_transfers` содержат `source_request_index`, `event_index`, `device_id`, `epoch`, `logical_address`, `direction`, `length`, `due_at_100ns` и допускающие null поля `occurred_at_100ns`, `completed_at_100ns`, `mapping`, `adapter`, `failure_reason`; `data_hex` содержит реально переданные байты. Для `scenario_success` все объявленные транзакции должны завершиться без ошибок. [Сценарий DMA](../examples/driver-dma-scenario.json) использует оригинальный `driver_wdm_dma.c`, собранный настоящим WDK, и необязательные пути `NEVERD_WDM_DMA_FIXTURE` / `NEVERD_WDM_DMA_CFG_FIXTURE`: common buffer обрабатывается через настоящие указатели адаптера, завершение ISR→DPC объявлено отдельно. C/Python продолжают применять `scenario_json` без изменения `neverd_driver_options_v1`. Отсутствующие артефакты явно пропускаются; доказательства ограничены Linux. Подчинённые контроллеры, методы V2/V3, аппаратные механизмы дескрипторов, общий DMA KMDF и другие модели устройств не поддерживаются.

Запрос питания WDM синтетической шины использует `kind: "power"` и настроенный `device_id`. Обязательны `minor` (`query`/`set`), `power_type` (`device`/`system`), `power_state` (`D0`/`D2`/`D3` либо `working`/`sleeping3`), `power_action` (`none`/`sleep`), явный 32-битный `system_context` (целое или hex-строка) и `bus_completion`. System Query к Working не поддерживается; поля файла, передачи и отмены запрещены. Весь `system_context` сохраняется как непрозрачный факт, без вывода родительского запроса, гибернации или быстрого запуска. Маршрут требует `DO_POWER_PAGABLE` без `DO_POWER_INRUSH`; фактическая выгружаемая диспетчеризация питания выполняется на `PASSIVE_LEVEL`. `PoCallDriver` передаёт исходный управляемый IRP, а `PoStartNextPowerIrp` следует контракту Vista+ без дополнительного протокола сериализации. Общая политика питания, другие состояния/действия, выключение/гибернация, пусковой ток, неперемещаемые в файл подкачки маршруты, произвольное оборудование и общий KMDF PnP не входят в профиль.

Query/Set `PoRequestPowerIrp` допускает вызывающих до `DISPATCH_LEVEL`. При APC или DISPATCH он резервирует независимый IRP с транзакцией и возвращает `STATUS_PENDING`; реальное состояние устройства меняется только при завершении. IRQL и CR8 вызывающего сохраняются. Планировщик затем выполняет настоящий выгружаемый DispatchPower на `PASSIVE_LEVEL`: DPC callback пробуждения может запросить D0 напрямую без гостевого work item. PASSIVE сохраняет inline-диспетчеризацию и раннее завершение. Отказ при проверке не расходует FIFO, строки отчёта, память пакета или ёмкость планировщика. Callback завершения сохраняет IRQL фактического пути завершения. Для WAIT_WAKE по-прежнему нужен `PASSIVE_LEVEL`. См. [сценарий питания с повышенным IRQL](../examples/driver-wdm-elevated-power-scenario.json).

Нативный WDM-драйвер может вызвать `PoRequestPowerIrp(IRP_MN_WAIT_WAKE)` с системным состоянием `Working` или `Sleeping3`. Нужны `PASSIVE_LEVEL`, стабильный физический D0, отсутствие активной транзакции питания и реальное успешное подтверждение нижнего START; верхний START ещё может выполняться. Необязательный выход `PIRP` записывается до гостевой диспетчеризации; callback независимо необязателен. Ошибка предварительной проверки сохраняет выход, строки отчёта и бюджет памяти. Отправленный запрос возвращает `STATUS_PENDING` даже при синхронном отказе, с `origin: "PoRequestPowerIrp"`, `response_index: null`, не расходуя `requested_device_power`. Публичные сценарии допускают только Query/Set; маршрут framework отклоняет нативный WAIT_WAKE до выделения памяти.

Каждый поставщик удерживает один нативный либо framework WAIT_WAKE. Отсутствующие или полностью ложные `wake_capabilities` дают `STATUS_NOT_SUPPORTED`, неподдерживаемый системный предел — `STATUS_INVALID_DEVICE_STATE`, дубликат — `STATUS_DEVICE_BUSY`. Реальное нижнее завершение проходит IoCompletion, включая `STATUS_MORE_PROCESSING_REQUIRED`, до конечного void callback `REQUEST_POWER_COMPLETE` с пятью аргументами. Отдельный `IO_STATUS_BLOCK` живёт до возврата callback. Верхнее завершение не может выдумать успешное пробуждение. `IoCancelIrp` вызывает установленную процедуру по настоящему протоколу блокировки отмены и лишь тогда возвращает TRUE. Успешная доставка отдельно проверяет независимую возможность S0/Sx относительно реального Working/Sleeping3; предел Sleeping3 в IRP не предоставляет пробуждение S0.

Нативное событие `wake` захватывает уже удерживаемый IRP и точную успешную идентичность START. Отмена/перевыпуск и STOP/перезапуск не меняют цель. Событие записывает `wake_source_device_id` / `wake_source_pdo`, но не меняет D0/D2/D3 или Working/Sleeping3: нужны отдельные запросы. Исходный драйвер отменяет и завершает WAIT_WAKE и callback до несовместимого удаления. Только наблюдаемая отмена, реально завершённая поставщиком, считается ожидаемым управлением. Сырое распространение WDM-пробуждения детям пока не поддерживается.

Нативный WDM USB idle требует отдельного от `bus` поля `usb_idle`: `role` равен `independent_function`, `composite_parent` или `composite_function`. Непосредственный `parent_id` составной функции указывает составного родителя. `remote_wake` по умолчанию false; true требует также `wake_capabilities`, а реальное USB-пробуждение требует D2. Одного D3hot недостаточно. `usb_idle_permission` в `power_policy_events` адресуется независимой функции или составному родителю без `component`/`state`. Захватываются все удержанные IRP и успешные START; отсутствие участника отклоняет всю группу, а отмена/переподача или перезапуск не меняют цель.

Настоящий `IOCTL_INTERNAL_USB_SUBMIT_IDLE_NOTIFICATION` отправляется в стабильном S0/D0 на `PASSIVE_LEVEL`: ядровый `METHOD_NEITHER`, 16 байт callback info, без выхода, прямо явному поставщику или через гостевой FDO. Info заимствуется до завершения; context непрозрачен и может быть NULL. Разрешение запускает void callback с одним аргументом на PASSIVE. Он отправляет один настоящий SET D2 и ждёт завершения; наблюдаемый отказ выделения допускает отмену и возврат. Затем idle IRP остаётся удержанным. Отмена до входа удаляет callback из очереди, после входа ждёт возврата. Получение D0 успешно завершает idle до независимого подтверждения D0; D3 даёт `STATUS_POWER_STATE_INVALID`, S3/удаление отменяют. Освобождение в IoCompletion сохраняет правило `STATUS_MORE_PROCESSING_REQUIRED`.

`usb_idle` хранит `start_epoch`, получение, времена callback, `d2_irp`, результат D2, `completion_cause`, время выбора причины и конца; ненаблюдаемые факты остаются null. `usb_idle_members` сообщает захваченные PDO/IRP/START без выдуманного перехода питания. Только реальные результаты, соответствующие причине, считаются ожидаемым управлением; дубликат `STATUS_DEVICE_BUSY` остаётся ошибкой. [USB idle сценарий](../examples/driver-wdm-usb-idle-scenario.json) использует `NEVERD_WDM_USB_IDLE_FIXTURE` / `NEVERD_WDM_USB_IDLE_CFG_FIXTURE`. дескрипторы, URB, каналы и цели передачи не поддерживаются.

KMDF `IdleUsbSelectiveSuspend` поддерживает `DriverManagedIdleTimeout` с явным D2. `PowerDeviceMaximum` требует явного факта шины функции `usb_idle.device_wake: "D2"`; отсутствие означает неизвестность. `remote_wake` независим: ни одно поле не выводится из другого. Составной родитель отклоняет `device_wake`. Нулевой USB-таймаут означает 5000 ms; пользовательские переопределения запрещены, `PowerUpIdleDeviceOnSystemWake` должен быть `WdfUseDefault`.

Таймаут удерживает настоящий framework idle IRP в D0. Лишь `usb_idle_permission` запускает callback и настоящее подтверждение D2 для всех составных участников. Пробуждению нужны явная USB- и общая S0-возможность с отдельным `WAIT_WAKE`. Управляемый I/O и StopIdle сначала отменяют старый IRP: `framework_usb_idle` сообщает `cancel` / `STATUS_CANCELLED`, но доставка ждёт отдельного подтверждения D0 и D0Entry. Пробуждение без прежней отмены завершает idle при получении D0. file/response-index равны null; доказательства те же, что у WDM. [Сценарий KMDF USB](../examples/driver-kmdf-usb-idle-scenario.json) использует `NEVERD_KMDF_USB_IDLE_FIXTURE` / `NEVERD_KMDF_USB_IDLE_CFG_FIXTURE`.

USB также поддерживает `SystemManagedIdleTimeout` и `SystemManagedIdleTimeoutWithHint`, назначенные до завершения первого входа D0. Первый игнорирует таймаут драйвера, WithHint задаёт нижнюю границу PoFx без дополнительного таймера. Одно `idle` не разрешает снижение питания: `power_not_required` удерживает настоящий USB idle IRP и подтверждает PoFx в физическом D0. Отдельное `usb_idle_permission` разрешает callback и D2. Предшествующая активность отменяет idle без лишнего D0 IRP; после D2 управляемый I/O и StopIdle ждут D0/D0Entry, затем F0/ActiveCondition. Удалённое пробуждение само восстанавливает компонент. Ошибки arm/выделения восстанавливают активность после настоящей отмены/disarm; STOP/REMOVE и перезапуск обновляют владельцев. [Сценарий USB PoFx](../examples/driver-kmdf-usb-pofx-scenario.json) показывает оба разрешения и восстановления. Настоящая ошибка `EvtDeviceD0Entry` при `RemovePending` подтверждает Required лишь для завершения очистки ошибочного IRP и оборудования, без F0/ActiveCondition. Это не разрешает отказ SET_POWER присутствующего устройства и не добавляет самостоятельный surprise removal фреймворка.

`WdfDeviceConfigureRequestDispatching` направляет READ, WRITE и внешний IOCTL в действующую нестандартную очередь того же устройства при IRQL <= DISPATCH_LEVEL. Автоматической очереди нужен callback или `EvtIoDefault`; ручная сохраняет обычное извлечение. Повтор возвращает `STATUS_WDF_BUSY`. Неотображённые запросы сохраняют очередь по умолчанию, уже переданные — владельца; назначенную очередь нельзя удалить отдельно. `WdfDeviceEnqueueRequest` захватывает выбранную в этот момент очередь; поздние отображения не перемещают уже поставленные запросы. Отображение CREATE и внутреннего IOCTL явно не поддержано этим профилем. Реальные тесты проверяют прямой READ и `WdfRequestForwardToIoQueue` после готовности D0.

[Нативный сценарий WAIT_WAKE](../examples/driver-wdm-wait-wake-scenario.json) использует настоящий WDK fixture `driver_wdm_wait_wake.c` через `NEVERD_WDM_WAIT_WAKE_FIXTURE` / `NEVERD_WDM_WAIT_WAKE_CFG_FIXTURE`. Проверяются отправка во время START, аргументы, пробуждение без неявного D0, перевыпуск, отмена, MPR, отмена в DPC с D0 из worker, точный захват и независимые поставщики. Выполнение обычных/active-CFG образов по исходному/перемещённому адресу подтверждено только в Linux; отсутствующие файлы явно пропускаются.

D2 — отдельное состояние, а не замена D3. Пакеты native/JSON, `requested_device_power` и `initial_reported_device_power` допускают D0/D2/D3. `PoSetPowerState` меняет только историю уведомлений вызывающего объекта; D2/D3 требуют IRQL <= APC_LEVEL. `DeviceLifecycle::validateDevicePowerRequest` отклоняет прямой SET между разными состояниями малого энергопотребления, не меняя операцию и не расходуя ticket. Если цель S3 отличается от текущего Dx, сначала завершается настоящий дочерний D0, затем выдаётся выбранный Dx с отдельным явным ответом FIFO. Обработчики D0 получают точное предыдущее/целевое состояние D2.

Настройки S0 idle и Sx wake сохраняют явный `DxState` D2 либо D3 и обновляют цель при повторном назначении. Существующие `wake_capabilities` провайдера обещают пробуждение из D3hot и охватывают D2, не создавая вымышленный `DeviceWake` шины. D1 и `PowerDeviceMaximum` вне USB не поддерживаются. D2 блокирует MMIO, DMA и обычные прерывания. Провайдер register-bank сохраняет регистры, псевдонимы, назначения и общую RAM в D2; это контракт модели, а не любого оборудования. D2 не может входить в D3cold или менять поколение сброса. Значение idle `DxState` D2 не разрешает D3cold, даже если последующий системный переход выбирает D3. Повторный SET D3 для уже холодного провайдера завершает настоящий запрос, сохраняя существующее холодное поколение.

[Сценарий D2](../examples/driver-d2-power-scenario.json) использует `NEVERD_KMDF_CHILD_WAKE_FIXTURE` / `NEVERD_KMDF_CHILD_WAKE_CFG_FIXTURE`. Native и настоящие WDK-тесты проверяют пакеты D2/D0, порядок и число обработчиков, запрет прямых переходов Dx и настоящий D0 перед сном системы; C API/CLI сохраняют те же наблюдения. Образы normal/active-CFG охватывают предпочтительные/перемещённые адреса; отсутствующие артефакты явно пропускаются, выполнение проверено только на Linux. Точные значения аргументов состояния обработчиков отдельно проверяют тесты модели framework.

В `pnp_devices` можно задать `initial_reported_device_power: "D0"` или `"D2"` или `"D3"` независимо от обязательных начальных состояний D0/working. PDO и каждый впервые связанный гостевой DEVICE_OBJECT имеют отдельную историю уведомления; `PoSetPowerState` возвращает и обновляет предыдущее значение только данного устройства. Без явного начального значения вызов завершается ошибкой, а не предполагает D0. Необязательный `requested_device_power` содержит device-шаблоны с теми же шестью обязательными фактами, до 64 записей суммарно. Только реальный `PoRequestPowerIrp(Query/Set)`, совпавший по PDO/minor/цели с головой FIFO этого PDO, расходует запись. Отсутствие/несовпадение — ошибка; неиспользованные записи не создают запросов, context не определяет родителя. У ребёнка отдельные IRP и строка отчёта: `origin: "PoRequestPowerIrp"`, нулевой начальный `response_index`; у сценария `origin: "scenario"` и null-индекс. Синхронный ребёнок может вызвать пятиаргументный void-callback до возврата `STATUS_PENDING`; callback может ждать, а System S0 — завершиться раньше независимого D0. Снимок IO_STATUS_BLOCK действует до возврата callback.

Отчёт добавляет nullable `power`; для питания `file` равен null. Записываются факты пакета, `device_state_before`/`device_state_after`, `system_state_before`/`system_state_after`, nullable `requested_device_object` и фактические `bus_status`/`bus_received_at_100ns`/`bus_completed_at_100ns`. Итоговые PnP-устройства добавляют `device_power`/`system_power`, живые устройства — nullable `reported_device_power`. `scenario_success` сравнивает количество только сценарных строк, но требует успешного завершения всех фактических строк, включая детей; неиспользованные шаблоны не вызывают отказа. Подлинный `driver_wdm_power.c` использует `NEVERD_WDM_POWER_FIXTURE`/`NEVERD_WDM_POWER_CFG_FIXTURE` для обычного/active-CFG native и C API/CLI покрытия. Отсутствующие артефакты явно пропускаются; доказательства исполнения ограничены Linux.

[Полный сценарий питания](../examples/driver-power-scenario.json) запускается через `--scenario` с подлинным драйвером: start, системные query/сон/возврат, remove и три явных дочерних ответа.

KMDF 1.33 использует точную ABI 1.33.0: 458 слотов функций имеют стабильные гостевые идентификаторы, а перечисленные ниже API реализуют семантику исполнения. `WdfVersionBind` и `WdfVersionUnbind` управляют гостевой привязкой вокруг настоящей оболочки WDK `FxDriverEntry`. `WdfGetDriver` читает публичные глобальные данные драйвера. Драйверы без PnP, общие объекты, управляющие устройства, очереди и входящие запросы используют типизированные контексты, счётчики ссылок и исполняемые обратные вызовы очистки/уничтожения/выгрузки. За исключением API блокировок, автоматически сериализуемых callbacks, DDI прерываний и описанных ниже операций с запросами и объектами с явно указанной поддержкой IRQL, вызовы фреймворка требуют `PASSIVE_LEVEL`; добавление ссылок после завершения очистки остаётся вне этого профиля. Немоделируемые слоты, `WdfLdrQueryInterface`, расширения классов и UMDF явно останавливают исполнение.

API прерываний: `WdfInterruptCreate`, `WdfInterruptQueueDpcForIsr`, `WdfInterruptQueueWorkItemForIsr`, `WdfInterruptSynchronize`, `WdfInterruptAcquireLock`, `WdfInterruptReleaseLock`, `WdfInterruptEnable`, `WdfInterruptDisable`, `WdfInterruptWdmGetInterrupt`, `WdfInterruptGetInfo`, `WdfInterruptGetDevice`.

Прерывания framework используют назначенные линии/MSI, соединения и блокировки. ISR работает на DIRQL или `PASSIVE_LEVEL`; `WdfInterruptGetInfo` сообщает фактический IRQL. DPC/рабочие задания используют `DISPATCH_LEVEL`/`PASSIVE_LEVEL`. Дубликаты в очереди объединяются; приостановленные callbacks сохраняют владение до возврата. Обычные прерывания разрешаются после D0Entry, запрещаются и освобождают callbacks перед D0Exit. `ReportInactiveOnPowerDown` сохраняет inactive-соединение; `WdfInterruptReportInactive`/`WdfInterruptReportActive` используют то же состояние. Окончательное освобождение аппаратуры разрывает соединение. Пассивный `CanWakeDevice` требует назначенного ресурса `wake_capable: true` и взведённой политики. В Dx он остаётся активным и не помечается inactive; явный импульс запрашивает пробуждение, ISR ждёт физического D0 и успешного D0Entry.

API блокировок: `WdfSpinLockCreate`, `WdfSpinLockAcquire`, `WdfSpinLockRelease`, `WdfWaitLockCreate`, `WdfWaitLockAcquire`, `WdfWaitLockRelease`, `WdfObjectAcquireLock`, `WdfObjectReleaseLock`. Внешние `WDFSPINLOCK`/`WDFWAITLOCK` используют общую с прерываниями модель executive/dispatcher; удаление проверяет владельцев, ожидающих и ссылки родителя. Спин-блокировки повышают и восстанавливают IRQL. Блокировки ожидания принадлежат реальному потоку и отключают обычные APC ядра на время ожидания и владения; поддерживаются бесконечные, относительные, абсолютные и нулевые тайм-ауты. Нулевой требует IRQL ниже `DISPATCH_LEVEL`, остальные — `PASSIVE_LEVEL`. Спин-блокировка прерывания использует его API. Области устройства/очереди сериализуют callbacks ввода-вывода, файлов, отмены и отложенных прерываний с наследуемым уровнем исполнения. Пассивные блокировки могут ждать, dispatch-блокировки не блокируются. Автоматические callbacks допускают вложенность одного потока, явные блокировки объектов нерекурсивны. DPC и рабочие задания требуют совместимого уровня родителя.

API политики питания: `WdfDeviceInitSetPowerPolicyEventCallbacks`, `WdfDeviceAssignS0IdleSettings`, `WdfDeviceAssignSxWakeSettings`, `WdfDeviceStopIdleNoTrack`, `WdfDeviceResumeIdleNoTrack`, `WdfDeviceStopIdleActual`, `WdfDeviceResumeIdleActual`. Управляемый драйвером простой требует явного положительного тайм-аута в миллисекундах, `IdleCannotWake`/`IdleCanWake` и отсутствия пользовательского переопределения. S0/Sleeping3 выполняют arm, triggered и disarm callbacks с настоящим удерживаемым IRP `WAIT_WAKE`. StopIdle/ResumeIdle используют парные вложенные ссылки; TRUE ждёт D0 в реальном кадре при `PASSIVE_LEVEL`. FALSE, ResumeIdle и настройки допускают до `DISPATCH_LEVEL`, регистрация требует `PASSIVE_LEVEL`. Синхронный StopIdle в callback управляемой очереди или при выключении сообщает взаимоблокировку. Sx-wake всё ещё требует явного системного запроса Working. Общая политика PEP/платформы и автоматическое повторное перечисление неисправных устройств не поддерживаются.

Объявленные связи `parent_id` поддерживают пробуждение дочерних устройств KMDF в Sx. `ArmForWakeIfChildrenAreArmedForWake` и `IndicateChildWakeOnParentWake` — независимые логические настройки. `EvtDeviceArmWakeFromSxWithReason` получает отдельные причины для самого устройства и его потомков, включая `(FALSE, TRUE)`, если пробуждение нужно только потомкам. Учитываются только успешно взведённые в Sx потомки с настоящим удерживаемым `WAIT_WAKE`; родитель сохраняет их PDO и эпохи START. Пробуждение родителя проверяет весь пакет перед завершением IRP и распространяется рекурсивно только через устройства, включившие эту возможность. Отключённые, снятые со взвода, неуспешные или перезапущенные потомки не получают выдуманного пробуждения. Nullable-поля `wake_source_device_id` и `wake_source_pdo` успешного WAIT_WAKE сохраняют исходный источник. Каждому устройству по-прежнему нужны явные запросы Working и D0 через собственную FIFO ответов.

Потомков нужно взводить до перехода родителя в Sx/Dx. Если непосредственный родитель уже в Sx/Dx и включена хотя бы одна дочерняя настройка, новый взвод отклоняется до создания WAIT_WAKE. Отмена последнего сохранённого потомка также отменяет WAIT_WAKE родителя, взведённого только ради потомков, и выполняет disarm ровно один раз. Родитель с собственной причиной или уже успешным пробуждением сохраняет обычный порядок disarm в D0. Используется объявленная топология; перечисление PDO гостевой шиной и прямые дочерние WDM-callbacks пробуждения не поддерживаются.

Настоящий WDK-fixture `driver_kmdf_child_wake.c` использует необязательные `NEVERD_KMDF_CHILD_WAKE_FIXTURE` / `NEVERD_KMDF_CHILD_WAKE_CFG_FIXTURE`. [Сценарий потомков](../examples/driver-kmdf-child-wake-scenario.json) выполняется через CLI. Отсутствующие образы явно пропускаются; свидетельства normal/active-CFG по предпочтительным/перемещённым адресам получены только в Linux.

`WdfDeviceWdmAssignPowerFrameworkSettings` (KMDF 1.33, слот 425) поддерживает настраиваемые Fx-состояния одного компонента. После успешного назначения системной политики простоя настройки копируются один раз при `PASSIVE_LEVEL`, до завершения первого START. Гостевые callbacks активного/неактивного условия и состояния простоя выполняются в реальных кадрах; для пропущенных callbacks действует стандартная обработка фреймворка. `PoFxDeviceFlags` должен быть 0, а `DirectedPoFxEnabled` — `WdfFalse`; управление PEP не моделируется.

После регистрации вызывается `EvtDeviceWdmPostPoFxRegisterDevice`; управление начинается только после его успеха. Handle действителен до возврата из `EvtDeviceWdmPrePoFxUnregisterDevice`. STOP/REMOVE ожидает завершения callbacks, а перезапуск получает новый handle. Ошибка Post завершает START неуспехом и приостанавливает работающий самостоятельный ввод-вывод до освобождения оборудования. Handle допускает `PoFxCompleteIdleCondition`, `PoFxCompleteIdleState` и подсказки задержки, пребывания и пробуждения компонента. Ссылками активности, питанием и регистрацией владеет фреймворк; прямые вызовы PoFx Activate/Idle/Start/Unregister явно отклоняются. Это граница профиля, а не запрет WDK. Настоящий `driver_kmdf_pofx.c` использует `NEVERD_KMDF_POFX_FIXTURE`/`NEVERD_KMDF_POFX_CFG_FIXTURE`; отсутствующие образы явно пропускаются, свидетельства исполнения ограничены Linux. Этот образ запускает [сценарий настраиваемого KMDF PoFx](../examples/driver-kmdf-pofx-scenario.json).

Если подтверждение питания устройства PoFx ещё ожидается, профиль отклоняет STOP/REMOVE до освобождения оборудования: сначала должна завершиться реальная транзакция D-состояния. Подготовка к остановке отменяет только ещё не выданные решения и завершает существующие callbacks компонентов до D0Exit, не создавая фиктивного завершения питания. Это граница сериализации модели, а не общее правило WDK.

WDM PoFx v1 копирует компоненты/состояния простоя и управляет ссылками и реальными callbacks. Вход, подтверждение и возврат сохраняют раздельное владение; блокирующие вызовы продолжаются в вызывающем потоке. API: `PoFxRegisterDevice`, `PoFxUnregisterDevice`, `PoFxStartDevicePowerManagement`, `PoFxActivateComponent`, `PoFxIdleComponent`, `PoFxCompleteIdleCondition`, `PoFxCompleteIdleState`, `PoFxCompleteDevicePowerNotRequired`, `PoFxReportDevicePoweredOn`, `PoFxSetComponentLatency`, `PoFxSetComponentResidency`, `PoFxSetComponentWake`, `PoFxSetDeviceIdleTimeout`. `SystemManagedIdleTimeout`/`SystemManagedIdleTimeoutWithHint` по умолчанию используют единственный компонент F0 framework; STOP/REMOVE снимает регистрацию, перезапуск создаёт новую. Idle и подсказки тайм-аута не выдумывают решение ОС. В `power_policy_events` действие `component_idle_state` требует `component` и `state`; `power_not_required` запрещает оба поля. Нужны текущая регистрация и захваченная эпоха START; задержка, время пребывания и пробуждение ограничивают переходы. PoFx v2/v3, направленное управление питанием и произвольные запросы управления платформой не поддерживаются.

Оригинальный `driver_wdm_pofx.c` использует необязательные пути CMake `NEVERD_WDM_POFX_FIXTURE` / `NEVERD_WDM_POFX_CFG_FIXTURE` для обычного/CFG-образа; [сценарий PoFx](../examples/driver-pofx-scenario.json) выполняет F1 и затем F0. Отсутствующие образы явно пропускаются; свидетельства исполнения относятся только к Linux.

Необязательный объект PDO `d3cold: {supported, enabled_by_default, wake_s0, wake_sx}` требует четыре логических значения для отдельного питания. Холодное пробуждение требует соответствующих `wake_capabilities`. `ExcludeD3Cold` True сохраняет D3hot, False разрешает явно поддержанный холодный режим, Default следует провайдеру; без холодного пробуждения взведённое устройство остаётся D3hot. Только успешный D3hot→D3cold меняет поколение питания и восстанавливает настроенные регистры перед доступом D0. Эпоха назначения и MMIO-псевдонимы сохраняются; MMIO/DMA требуют физического D0. Незавершённые DMA-транзакции, отображения или владение каналом запрещают отключение; простаивающие адаптеры и общие RAM-буферы могут оставаться. Общие шины питания и возможности firmware не выводятся из предположений.

PDO явно задаёт логические `wake_capabilities: {s0, sx}`. READ/WRITE/IOCTL допускают `power_policy_events: [{device_id, after_100ns, action}]` с `idle`/`active`/`wake`. Отчёт сохраняет захваченную `device_epoch` без привязки к последующему перезапуску. D0/D2/D3 потребляют `requested_device_power` и сообщают `framework_power_policy`; независимый `framework_wait_wake` удерживает настоящий WAIT_WAKE, завершённая отмена которого допустима. [Полный сценарий](../examples/driver-kmdf-power-policy-scenario.json).

Необязательный `service_name` в корне сценария переопределяет базовую конфигурацию; отсутствие сохраняет имя вызывающей стороны. Допустимы 1–128 букв ASCII, цифр, `_` или `-`; CLI, C и Python используют одну проверку.

Следующие API запросов и объектов поддерживают IRQL до `DISPATCH_LEVEL` включительно: `WdfObjectDereferenceActual`, `WdfRequestComplete`, `WdfRequestCompleteWithInformation`, `WdfRequestRetrieveInputBuffer`, `WdfRequestRetrieveOutputBuffer`, `WdfRequestRetrieveInputMemory`, `WdfRequestRetrieveOutputMemory`, `WdfRequestRetrieveInputWdmMdl`, `WdfRequestRetrieveOutputWdmMdl`, `WdfRequestGetInformation`, `WdfRequestSetInformation`, `WdfRequestGetIoQueue`, `WdfRequestGetFileObject`, `WdfRequestWdmGetIrp`, `WdfRequestGetParameters`, `WdfRequestGetStatus`, `WdfRequestMarkCancelable`, `WdfRequestMarkCancelableEx`, `WdfRequestUnmarkCancelable`, `WdfRequestIsCanceled`, `WdfMemoryGetBuffer`.

`WdfObjectGetTypedContextWorker`, `WdfObjectContextGetObject`, `WdfObjectReferenceActual` также поддерживают моделируемые IRQL прерываний; доступ к контексту и получение ссылки не вызывают пассивных callbacks.

Завершение запроса или освобождение последней ссылки на объект выше `PASSIVE_LEVEL` планирует настоящую очистку, уничтожение и последующие вызовы фреймворка на `PASSIVE_LEVEL`. Остальные API сохраняют существующие ограничения IRQL.

Управляющие устройства требуют скопированного имени из печатных ASCII-символов и строго заданной SDDL `D:P(A;;GA;;;WD)`. Она разрешает доступ всем, не требуя выдуманного токена вызывающей стороны; другие дескрипторы безопасности, безымянные устройства и автоматические имена не поддерживаются. Инициализация владеет одним устройством WDM. Запросы могут выбирать его в существующем пространстве имён сеанса через псевдонимы символических ссылок `\DosDevices\Name` или `\??\Name`; в отчёте сохраняется каноническое имя устройства. Успешное создание потребляет объект инициализации и обнуляет его указатель; ошибка отменяет частично установленное владение устройством. `WdfControlFinishInitializing` разрешает доставку ввода-вывода. Удаление убирает устройство и его ссылки только тогда, когда это допускают моделируемые файлы, рабочие элементы и запросы; отмена или опустошение очереди запросов при удалении не поддерживаются.

Структура `WDF_IO_QUEUE_CONFIG` размером 96 байт поддерживает стандартные и нестандартные ручные, последовательные и параллельные очереди с конечным или неограниченным пределом с уровнем исполнения и областью синхронизации, заданными атрибутами объектов. Очереди управляющих устройств не участвуют в управлении питанием. Специализированные обратные вызовы READ/WRITE/IOCTL имеют приоритет над вызовом по умолчанию. Принятые в очередь запросы возвращают `STATUS_PENDING` даже при синхронном завершении; регистр возврата void-функции не завершает её запрос. Отложенное завершение использует существующий планировщик. Без обработчика запрос завершается с `STATUS_INVALID_DEVICE_REQUEST`; READ/WRITE нулевой длины завершается без доставки, если она не включена. Стандартный файловый пакет успешно завершает CREATE/CLEANUP/CLOSE с Information=0. Нестандартные ручные очереди принимают запросы через `WdfRequestForwardToIoQueue`; `WdfIoQueueRetrieveNextRequest` возвращает их в порядке FIFO. Если запрос отменён до извлечения, платформа удаляет его из очереди и завершает с `STATUS_CANCELLED`. Нестандартные автоматические очереди доставляют перенаправленные запросы собственным обработчикам, а стандартная ручная очередь удерживает входящие запросы до извлечения. `WdfIoQueueRetrieveNextRequest` работает для ручных и последовательных очередей; параллельные возвращают `STATUS_INVALID_DEVICE_STATE`. Если подходящего обработчика нет, автоматическая очередь завершает запрос с `STATUS_INVALID_DEVICE_REQUEST`, когда освобождается слот доставки. Более широкий набор операций PnP и питания остаётся вне этого профиля. `WdfRequestRequeue` возвращает извлечённый запрос в начало той же ручной очереди. `NumberOfPresentedRequests` ограничивает число одновременно переданных запросов; остальные ждут завершения или отмены переданного запроса. Последовательная очередь по умолчанию принимает новые запросы, пока один запрос предоставлен драйверу; остальные ждут свободного слота в порядке FIFO и могут быть отменены до передачи. `WdfIoQueueStop` останавливает передачу запросов драйверу, продолжая принимать их. `WdfIoQueueStart` передаёт ожидающие запросы, а `WdfIoQueueGetState` сообщает числа ожидающих и уже переданных запросов. Получение из остановленной очереди возвращает `STATUS_WDF_PAUSED`; callback завершения остановки получает указанный контекст после завершения или выхода из очереди всех уже переданных драйверу запросов; ожидающие запросы его не задерживают. Повторная регистрация до его вызова отклоняется.

`WdfIoQueueReadyNotify` регистрирует один callback `EvtIoQueueState` для ручной очереди. При переходе числа ожидающих запросов от нуля к положительному значению он получает `(WDFQUEUE, WDFCONTEXT)` на `PASSIVE_LEVEL`, даже если драйвер ещё владеет ранее извлечёнными запросами. Уже непустая очередь может уведомить сразу после регистрации; остановленная ждёт `WdfIoQueueStart`. Повторная регистрация или отмена регистрации до остановки возвращает `STATUS_INVALID_DEVICE_REQUEST`. После `WdfIoQueueStop` значение NULL отменяет регистрацию.

`WdfIoQueueFindRequest` просматривает ручную очередь, не передавая владение запросом, и при успехе добавляет одну ссылку. Драйвер снимает её через `WdfObjectDereference`. `WdfIoQueueRetrieveFoundRequest` передаёт владение запросом, который ещё находится в очереди; удалённый при отмене запрос возвращает `STATUS_NOT_FOUND`. Необязательные параметры имеют ту же структуру, что и у `WdfRequestGetParameters`. Живой файловый объект фреймворка служит фильтром для `WdfIoQueueFindRequest`. `WdfIoQueueRetrieveRequestByFileObject` извлекает следующий подходящий запрос из ручной или последовательной очереди и не меняет выходное значение при отсутствии совпадений.

Настроенный `EvtIoCanceledOnQueue` получает `(WDFQUEUE, WDFREQUEST)` только для запроса, ранее переданного драйверу, а затем перенаправленного или повторно поставленного в очередь, либо явно поставленного туда callback в контексте вызывающего процесса. Запрос, ни разу не переданный драйверу, платформа завершает с `STATUS_CANCELLED` без этого callback. Уведомление возвращает запрос драйверу: он обязан завершить его в callback или позже и не может снова поставить в очередь. Очистка очереди и уведомление о состоянии ждут возврата callback и завершения запроса.

`WdfIoQueueDrain` отклоняет новые запросы с `STATUS_INVALID_DEVICE_STATE` и доставляет уже стоящие в очереди. Обратный вызов выполняется, когда в очереди и у драйвера больше нет запросов. Перенаправление возвращает `STATUS_WDF_BUSY`; `WdfIoQueueStart` возобновляет приём.

`WdfIoQueuePurge` также отменяет недоставленные запросы с `STATUS_CANCELLED` и запрашивает отмену уже доставленных запросов, помеченных как отменяемые, на исходном IRP. Очистка выполняется до освобождения IRP. Обратный вызов состояния ждёт окончания запросов в очереди, у драйвера и активных обратных вызовов отмены. Неотменяемые запросы завершает драйвер.

`WdfIoQueueStopSynchronously`, `WdfIoQueueDrainSynchronously` и `WdfIoQueuePurgeSynchronously` приостанавливают гостевой вызов на `PASSIVE_LEVEL` до завершения соответствующих запросов. Stop продолжает приём, останавливает доставку и ждёт уже доставленные запросы. Drain отклоняет новые запросы, доставляет ожидающие и ждёт обе группы. Purge отменяет ожидающие и помеченные как отменяемые запросы и ждёт возврата callbacks отмены. Если источника завершения нет, ожидание сообщает об ошибке остановившейся модели.

`WdfIoQueueStopAndPurge` и `WdfIoQueueStopAndPurgeSynchronously` отменяют уже ожидающие запросы и помеченные как отменяемые запросы во владении драйвера, затем продолжают принимать новые запросы без доставки до `WdfIoQueueStart`. Асинхронный callback состояния и синхронное ожидание завершаются после старых запросов и их callbacks отмены; новые остаются в очереди и не задерживают уведомление. Обе формы Stop также возобновляют приём после Drain или Purge.

Параметры запроса используют 40-байтную структуру `WDF_REQUEST_PARAMETERS`. Функции доступа к вводу/выводу возвращают логические длины, сохраняя алиасы буферов и существующие MDL-отображения прямого ввода-вывода; вход прямого IOCTL остаётся буферизованным. Неверное направление и недостаточный буфер возвращают документированные статусы. Завершение очищает запрос при ещё действующих буферах, завершает IRP и освобождает закреплённые страницы запроса; затем уничтожает дочерние объекты и запрос, когда это допускают ссылки. Новые вызовы функций доступа к буферам и параметрам отклоняются с начала завершения; ранее полученные указатели буферов остаются доступны во время очистки. Внешняя ссылка сохраняет контекст, но не доступ к завершённому IRP.

Отмена моделируется для запросов описанных выше очередей управляющих устройств. Если отмена уже произошла, `WdfRequestMarkCancelableEx` возвращает `STATUS_CANCELLED` без обратного вызова. Успешный `WdfRequestUnmarkCancelable` снимает обработчик; последующая отмена лишь записывает состояние отмены. `WdfRequestIsCanceled` читает это состояние у живого запроса без отметки об отменяемости. После успешной отметки об отменяемости завершение требует успешного снятия отметки либо начала доставки обратного вызова отмены: постановки в очередь недостаточно. После начала доставки обработчик может согласовать завершение с рабочим элементом, в том числе во время собственного ожидания. Отдельная внутренняя ссылка удерживает запрос до возврата обработчика отмены. При завершении IRP всё равно становится недействительным первым, а заключительное продолжение уничтожения запроса тоже может ожидать. Приоритет имеют DPC, затем обработчики отмены в порядке FIFO, затем обычные рабочие элементы; обработчики отмены также предшествуют возобновлению готовых пассивных ожиданий.

Прежний void-метод `WdfRequestMarkCancelable` поддерживает уровни до `DISPATCH_LEVEL`. Для уже отменённого запроса `EvtRequestCancel` синхронен лишь при совместимости текущего IRQL с уровнем очереди и отсутствии у потока той же callback-блокировки. Иначе он ставит worker или DPC и возвращается; последующая отмена также планируется. Только фактический вход гостевого callback после получения блокировки означает delivered; постановка в очередь не разрешает преждевременное завершение запроса. Без автоматической синхронизации (`WdfSynchronizationScopeNone`) Microsoft рекомендует Ex. [Microsoft](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdfrequest/nf-wdfrequest-wdfrequestmarkcancelable).

`WdfRequestGetInformation` и `WdfRequestSetInformation` используют исходное 64-битное поле `IRP.IoStatus.Information`, включая прямую запись гостя. Set лишь присваивает значение; длина передачи проверяется при завершении. `WdfRequestCompleteWithInformation` записывает то же поле до очистки; изменения через заранее сохранённый IRP во время очистки определяют итоговый Information, хотя GetInformation в этой фазе уже возвращает ноль. `WdfRequestGetIoQueue` возвращает исходную очередь. При стандартной файловой конфигурации `WdfRequestGetFileObject` возвращает NULL, не выдавая WDM FILE_OBJECT за файловый объект WDF. `WdfRequestWdmGetIrp` возвращает тот же IRP; гостевые `IoCompleteRequest`/`IofCompleteRequest` не могут обойти завершение WDF. Пока дескриптор запроса действителен во время или после завершения, GetInformation/GetIoQueue возвращают ноль; получение MDL сначала записывает NULL в допустимый выход, затем возвращает `STATUS_INTERNAL_ERROR`. SetInformation/GetFileObject/WdmGetIrp в этой фазе отклоняются. Ограничения существующих функций буферов и параметров не меняются.

`WdfRequestRetrieveInputWdmMdl` и `WdfRequestRetrieveOutputWdmMdl` по требованию описывают имеющийся SystemBuffer для буферизованных входа WRITE, выхода READ и входа/выхода IOCTL. Направление должно быть допустимым и ненулевой длины до использования единственного кэшированного MDL запроса; первое успешное получение фиксирует ByteCount даже при иной логической длине другого направления. `MmGetSystemAddressForMdlSafe` возвращает исходный VA; дополнительные отображения, их снятие и освобождение драйвером запрещены. Прямые выходы READ/IOCTL и вход WRITE возвращают исходный `IRP.MdlAddress`, не создавая отображения самим получением; вход прямого IOCTL использует кэш SystemBuffer. MDL, IRP и буферы прекращают существование при завершении. Внутренние ссылки отмены и внешние ссылки сохраняют только контекст WDF. Получение MDL через WDF для `METHOD_NEITHER` и PFN непостроенных MDL остаются неподдерживаемыми; WDFMEMORY запроса использует отдельное отображение закреплённых страниц.

Для буферизованных, прямых и neither-запросов KMDF `WdfDeviceInitSetIoInCallerContextCallback` выполняется до очереди в процессе инициатора при `PASSIVE_LEVEL`. Обработчик должен завершить запрос либо один раз вызвать `WdfDeviceEnqueueRequest`. Этот вызов фиксирует очередь, назначенную типу запроса через `WdfDeviceConfigureRequestDispatching`, или очередь по умолчанию при отсутствии назначения. Последующие изменения назначения не перемещают принятый запрос. Для IOCTL `METHOD_NEITHER` и neither READ/WRITE `WdfRequestRetrieveUnsafeUserInputBuffer` и `WdfRequestRetrieveUnsafeUserOutputBuffer` возвращают исходные пользовательские адреса только в этом обработчике. `WdfRequestProbeAndLockUserBufferForRead` и `WdfRequestProbeAndLockUserBufferForWrite` проверяют права страниц и закрепляют их за запросом; `WdfMemoryGetBuffer` даёт системный алиас для обработчика очереди вне контекста инициатора. Завершение освобождает страницы и алиасы. Поддерживаются встроенные указатели на явно объявленные `user_buffers`; произвольные отображения остаются вне модели.

Запросы neither могут объявлять `user_buffers` (`id`, `size`, необязательные `input`/`access`) и `user_pointers`. Ссылки `source`/`target` задают `buffer` (`input`, `output`, `memory`) и `offset`; только `memory` использует локальный для запроса `id`. Восьмибайтовые поля указателей не должны пересекаться; цель может находиться внутри буфера или на его конце. Сценарий допускает 64 дополнительных буфера и 256 указателей, до 64 KiB на буфер в общем бюджете 512 KiB. Общие цели используют одни и те же байты и существующие правила прав, закрепления, отзыва и завершения процесса. `configuration.user_memory` сохраняет объявления. `user_buffers[].backing_hex` — диагностический снимок RAM при остановке, в том числе после отзыва адресов или ошибки; он не заменяет `output_hex` и не разрешает доступ. `id`: 1–64 ASCII, `[A-Za-z0-9][A-Za-z0-9_.-]*`.

`WdfRequestRetrieveInputMemory` и `WdfRequestRetrieveOutputMemory` предоставляют принадлежащие запросу представления WDFMEMORY существующих буферизованных или прямых буферов ввода-вывода. Повторное получение того же направления сохраняет дескриптор; `WdfMemoryGetBuffer` возвращает исходный буфер и логическую длину. Нулевая длина или неверное направление дают ошибочный статус WDF; neither-ввод-вывод по-прежнему требует проверки и закрепления страниц в контексте инициатора. Заимствованные представления не добавляют блокировку MDL и становятся недействительными после завершения запроса.

Ограниченный профиль KMDF PnP поддерживает прямую пару FDO/PDO. `EvtDriverDeviceAdd` получает инициализатор фреймворка; `WdfDeviceCreate` создаёт FDO, а `WdfFdoInitWdmGetPhysicalDevice` и `WdfDeviceWdmGetPhysicalDevice` сохраняют идентичность PDO. После сбоя AddDevice или завершения Remove фреймворк выполняет callbacks очистки/уничтожения и удаляет устройство. Очереди PnP поддерживают `WdfUseDefault` и `WdfTrue` для управления питанием; `WdfFalse` отключает автоматическое управление. `WdfDeviceInitSetPnpPowerEventCallbacks` поддерживает `EvtDevicePrepareHardware`, `EvtDeviceD0Entry`, `EvtDeviceD0Exit`, `EvtDeviceReleaseHardware`, `EvtDeviceQueryStop`, `EvtDeviceQueryRemove` и `EvtDeviceSurpriseRemoval`. `EvtDeviceQueryStop` и `EvtDeviceQueryRemove` выполняются до шины и могут ждать или отказать. Отказ завершает IRP их статусом без наблюдения шины или перехода питания; `STATUS_PENDING` и `STATUS_NOT_SUPPORTED` недопустимы. `EvtDeviceSurpriseRemoval` — уведомление void перед пересылкой на шину; регистр возврата игнорируется. PrepareHardware получает два разных списка ресурсов до D0Entry; для устройств без ресурсов они пусты; Для пустых списков `WdfCmResourceListGetCount` возвращает ноль, а `WdfCmResourceListGetDescriptor` — NULL. Ошибка PrepareHardware или D0Entry становится статусом START, но ReleaseHardware всё равно вызывается. При остановке или удалении из D0 сначала вызывается D0Exit, затем ReleaseHardware до завершения IRP. Настроенные устройства `register_bank` предоставляют дескрипторы `CM_PARTIAL_RESOURCE_DESCRIPTOR` только для чтения до ReleaseHardware; драйвер может отобразить переведённую память через `MmMapIoSpace` и обязан снять отображение до завершения STOP или Remove. Другие типы ресурсов и общая политика питания не поддерживаются. `WdfIoQueuePnpHeld` обозначает приостановку выдачи до D0 и после выхода из D0; перед выходом из D0 для каждого запроса, которым владеет драйвер в управляемой питанием очереди, вызывается `EvtIoStop`; драйвер может завершить запрос, вызвать `WdfRequestStopAcknowledge` или дождаться уже запланированного завершения. Если `EvtIoStop` не зарегистрирован, фреймворк также ждёт завершения всех выданных запросов. TRUE возвращает его в очередь для повторной выдачи после запуска, FALSE сохраняет владение драйвера и вызывает `EvtIoResume` после возврата в D0. Уже поставленные в очередь запросы ждут запуска. Когда источника завершения больше нет, ожидание заканчивается остановкой `model_error`. WDK-фикстура `driver_kmdf_pnp.c` использует `NEVERD_KMDF_PNP_FIXTURE` / `NEVERD_KMDF_PNP_CFG_FIXTURE`.

Для PnP FDO вызов `WdfDeviceInitSetDeviceType` записывает указанный 32-битный тип в WDM `DEVICE_OBJECT`; без вызова по умолчанию остаётся `FILE_DEVICE_UNKNOWN`. Повышение приоритета ввода-вывода в зависимости от типа устройства не моделируется.

`WdfDeviceInitSetExclusive` устанавливает `DO_EXCLUSIVE` для WDM-устройства, созданного из инициализатора. Именованное управляющее устройство отклоняет второе независимое открытие до закрытия первого файла. Для PnP FDO этот флаг сам по себе не делает эксклюзивным именованный PDO или весь стек; эксклюзивность PDO, задаваемая INF, находится вне этого профиля.

`WdfDeviceInitSetFileObjectConfig` регистрирует `EvtDeviceFileCreate`, `EvtFileCleanup` и `EvtFileClose` до создания устройства и копирует необязательные атрибуты контекста. Профиль поддерживает `WdfFileObjectNotRequired`, `WdfFileObjectWdfCanUseFsContext`, `WdfFileObjectWdfCanUseFsContext2` и `WdfFileObjectWdfCannotUseFsContexts`. Выбранное поле контекста WDM хранит дескриптор WDF до неудачного CREATE или CLOSE и должно быть изначально пустым. При `WdfFileObjectCanBeOptional` вызов `WdfRequestGetFileObject` возвращает NULL для запроса ввода-вывода без соответствующего файлового объекта WDM. CREATE, CLEANUP и CLOSE по-прежнему требуют объект WDM; `WdfFdoInitSetFilter` включает пересылку по умолчанию для фильтра; `WdfTrue` включает её явно, а `WdfFalse` отключает. Для пересылки файлового запроса нужны прямой маршрут FDO/PDO и явный `bus_completion`. Положительный `delay_100ns` допускается для автоматической пересылки CREATE/CLEANUP/CLOSE и для синхронной, асинхронной с процедурой завершения или `SEND_AND_FORGET` отправки CREATE. Обработчики CLEANUP и CLOSE выполняются до передачи нижнему устройству. Обработчик CREATE с `WdfFileObjectNotRequired` может получить локальную цель устройства через `WdfDeviceGetIoTarget` и переслать исходный запрос вызовом `WdfRequestSend` только с `WDF_REQUEST_SEND_OPTION_SEND_AND_FORGET`. Сохранённое PDO потребляет явно заданный ответ шины и отвечает за окончательное завершение, даже если нижний ответ задержан. Обработчик CREATE с файловым объектом фреймворка может использовать `WDF_REQUEST_SEND_OPTION_SYNCHRONOUS`, получить результат нижнего устройства через `WdfRequestGetStatus` и завершить исходный запрос с этим статусом. При асинхронной отправке по умолчанию запрос сначала форматируется вызовом `WdfRequestFormatRequestUsingCurrentType`, затем регистрируется `WdfRequestSetCompletionRoutine`. Обработчик получает `WDF_REQUEST_COMPLETION_PARAMS`, может прочитать результат нижнего устройства через `WdfRequestGetCompletionParams` или `WdfRequestGetStatus` и завершает исходный запрос со статусом, выбранным независимо от нижнего устройства. При отправке с процедурой завершения отложенный ответ PDO оставляет запрос ожидающим до срока виртуального времени, после чего процедура ставится в очередь с окончательным статусом нижнего устройства. `WDF_REQUEST_SEND_OPTION_TIMEOUT` принимает отрицательный относительный интервал или положительный абсолютный срок виртуальных часов в единицах 100 нс для синхронного CREATE или асинхронного CREATE с completion callback. Более ранний timeout даёт `STATUS_IO_TIMEOUT`; немедленное нижнее завершение или равный срок имеют приоритет. Прошедший абсолютный срок не имеет оставшегося интервала. Ноль отключает timeout; другие опции не поддерживаются. Дескриптор WDF и WDM `FILE_OBJECT` имеют разные идентификаторы; действующий объект доступен через `WdfRequestGetFileObject`, `WdfFileObjectGetDevice` и `WdfFileObjectWdmGetFileObject`. При неудачном CREATE объект WDF удаляется без вызовов очистки и закрытия файла; после успешного открытия CLEANUP и CLOSE предшествуют очистке и уничтожению контекста.

Отложенный синхронный `WdfRequestSend` сохраняет и приостанавливает настоящий кадр вызова гостя, затем возобновляет его с логическим результатом отправки после завершения. Итоговый NTSTATUS доступен через `WdfRequestGetStatus`. `WDF_REQUEST_SEND_OPTION_TIMEOUT` принимает отрицательный относительный интервал или положительный абсолютный срок виртуальных часов в единицах 100 нс для синхронного CREATE или асинхронного CREATE с completion callback. Более ранний timeout даёт `STATUS_IO_TIMEOUT`; немедленное нижнее завершение или равный срок имеют приоритет. Прошедший абсолютный срок не имеет оставшегося интервала. Ноль отключает timeout; другие опции не поддерживаются. Автоматическая пересылка вызывает файловые обработчики до нижней передачи и сохраняет IRP и файл WDM на время обработчиков очистки и уничтожения, необходимых при завершении. Внешние ссылки WDF сохраняют контекст, но не продлевают срок жизни файла WDM завершённого запроса.

WDM-запросы CREATE/CLEANUP/CLOSE, пересланные настроенному PDO, также принимают явно отложенный `bus_completion`. После нижнего срока вызывается настоящая гостевая процедура завершения с сохранением правил распространения ожидания и владения окончательным статусом.

Необязательная проверка с настоящим WDK отдельно компилирует `driver_kmdf_lifecycle.c` и `driver_kmdf_control.c` с подлинной библиотекой входа KMDF. `NEVERD_KMDF_FIXTURE` / `NEVERD_KMDF_CFG_FIXTURE` выбирают образы жизненного цикла; `NEVERD_KMDF_CONTROL_FIXTURE` / `NEVERD_KMDF_CONTROL_CFG_FIXTURE` выбирают обычный образ управляющего устройства и вариант с активным CFG. Отсутствующие внешние артефакты явно пропускаются. Нативная и C API/CLI-проверка описана в [тестировании](testing.md). Текущие доказательства исполнения ограничены Linux.

`MmProbeAndLockPages` принимает в `KernelMode` непрерывный диапазон образа драйвера, принадлежащий загрузчику, при IRQL <= APC_LEVEL. Страницы должны быть доступны для чтения и укладываться в физическую квоту. Их память уже частная и резидентная: `IoWriteAccess` и `IoModifyAccess` разрешают запись через псевдоним MDL даже при защите исходного отображения от записи; `IoReadAccess` сохраняет только чтение. Исходная защита не меняется. Разрывы и посторонние отображения исключены; владение распознаёт и образы ниже границы пользовательских адресов. Требуются разблокировка и освобождение дескриптора. Временные MDL страниц образа, принадлежащих загрузчику, перестают добавлять зависимость восстановления после удаления всех отображений, снятия всех блокировок и освобождения всех дескрипторов. Контракт допускает кэшируемые отображения режима ядра без запрошенного адреса. Живые MDL, другие виды владения или отображения и чтение гостем физических идентификаторов PFN остаются зависимостями; учитываются также чтения моделируемыми службами копирования, перемещения и сравнения.

`KernelDispatcher` трактует `Count`, `Limit` и `Adjustment` семафора как знаковые 32-битные `LONG`, `Level` мьютекса как 32-битный `ULONG`, а `Wait` как 8-битный `BOOLEAN`, игнорируя неопределённые биты регистров согласно [Windows x64 ABI](https://learn.microsoft.com/en-us/cpp/build/x64-calling-convention?view=msvc-170). Недопустимые значения в заданной разрядности и переполнение семафора отклоняются до изменения состояния объекта.

Пределы IRQL заданы в `KernelAPIIRQL.def`; зависимые от аргументов правила проверяет соответствующая модель. DPC не может вызывать API реестра, выделять, освобождать или читать/писать страничный пул. Unicode-преобразования `DbgPrint` требуют `PASSIVE_LEVEL`, поддерживаемые ANSI-вывод и операции с нестраничной памятью доступны на `DISPATCH_LEVEL`. Стеки ограничены: вышедший за границы указатель не может попасть в стек другого заблокированного рабочего потока. Активные таймеры в расширении устройства запрещают преждевременное освобождение устройства.

Истечение таймера удовлетворяет зарегистрированные ожидания до того, как DPC сбросит или переустановит таймер. DPC из очереди выполняются раньше возобновления пробуждённых кадров `PASSIVE_LEVEL`. Если память запроса ещё содержит DPC в очереди, завершение IRP отвергает её освобождение до завершения и аннулирования буфера.

Форматирование `DbgPrint` поддерживает целые `d/i/u/o/x/X`, указатель `p`, текст `s/c`, `%%`, Unicode с заданной длиной `wZ/lZ`, широкие строки `ls/ws`, флаги, ширину/точность, включая `*`, и модификаторы длины целых Windows. Считывается не более 32 переменных аргументов и 1024 байтов формата. Ширина и точность ограничены 512. Числа с плавающей точкой, `%n`, неизвестные сочетания и преобразования текста вне ASCII явно останавливают выполнение; модель не угадывает кодовую страницу Windows и не вызывает хостовый printf для гостевых данных.

Время жизни исходных записи и буфера RegistryPath заканчивается при возврате DriverEntry. Если строка нужна позже, драйвер должен скопировать её во время инициализации.

Арена объектов/пула занимает 1 MiB. Неинициализированные байты пула имеют детерминированное содержимое `0xCD`, освобождённые — `0xDD`. Это один конкретный сценарий выполнения. Доступы CPU и моделируемые буферные API отклоняют обращения к освобождённым выделениям пула, удалённым устройствам, невыделенным байтам арены, непрозрачным полям объектов и запись в поля объектов только для чтения. Эти проверки охватывают время жизни объектов данной модели; это не общий анализ безопасности памяти драйвера. Незаписанные слоты таблицы диспетчеризации показываются нулём со значением «не зарегистрирован». Запрос сценария к незарегистрированной основной функции завершается моделируемым обработчиком по умолчанию с `STATUS_INVALID_DEVICE_REQUEST`; ошибка остаётся видимой и в статусе диспетчеризации, и в статусе ввода-вывода. Модель не выдумывает гостевой адрес функции для этого обработчика, а чтение гостем незаписанного слота по-прежнему не поддерживается. Явная регистрация null-указателя обратного вызова является ошибкой.

## Сценарии запросов

Передайте JSON-файл через `--scenario`, чтобы выбрать запросы и необязательную выгрузку:

```bash
build-release/bin/neverd emulate-driver path/to/driver.sys \
  --scenario scenario.json > driver-report.json
```

Пример `scenario.json` для драйвера, создающего `\Device\NeverDIO` и принимающего буферизованный IOCTL `0x222000`:

```json
{
  "requests": [
    {"kind": "create", "device": "\\Device\\NeverDIO"},
    {"kind": "ioctl", "code": "0x222000", "input": "00112233", "output_size": 4},
    {"kind": "cleanup"},
    {"kind": "close"}
  ],
  "unload": true
}
```

Имя устройства и код IOCTL должны соответствовать драйверу. При create отсутствие `device` выбирает единственное живое устройство; неоднозначный выбор завершается ошибкой. Последующие запросы используют устройство своего файла, если явно не указано совпадающее имя. Необязательный `file` — беззнаковый 32-битный идентификатор сценария, по умолчанию ноль. У каждого идентификатора собственные FILE_OBJECT и FsContext, а порядок операций — create, передачи, cleanup, close. Запросы независимых файлов могут чередоваться. Эксклюзивные устройства отклоняют второе открытие. Эти идентификаторы представляют файловые объекты, а не дублированные дескрипторы. Поддерживаются buffered и оба метода direct IOCTL. Диспетчеризация должна завершить IRP синхронно либо соблюдать описанный выше контракт обратных вызовов для ожидающего запроса. Недопустимая длина вывода и доступ к завершённому IRP явно завершаются ошибкой. Запрошенная выгрузка не должна оставлять живые устройства, символические ссылки, выделения пула или файловые объекты.

Необязательное корневое поле `"load_address": "0x190000000"` запрашивает изменение базового адреса; отсутствие поля или `"0x0"` означает предпочтительный адрес. Образ должен удовлетворять требованиям релокации. Исходная команда инициализации и C API не подразумевают никакого сценария.

В корне допустимы только `load_address`, `requests`, `unload`, `kernel_exports`, `registry` и `pnp_devices`. Обычные файловые запросы принимают `kind`, необязательные `device` или `device_id` (взаимоисключающие) и `file`. Для IOCTL обязателен `code`, допустимы `input`, `output_size` и `direct_input`. Запрос `read` принимает `output_size` и `byte_offset`; `write` — `input` и `byte_offset`. Смещения по умолчанию равны нулю, принимают целые числа или шестнадцатеричные строки и должны помещаться в неотрицательное знаковое 64-битное значение. Запросы жизненного цикла отклоняют поля передачи данных. Неизвестные или повторяющиеся поля отклоняются. `code` принимает беззнаковое 32-битное целое JSON или шестнадцатеричную строку с `0x`. `input` — шестнадцатеричная строка байтов чётной длины без префикса и пробелов; отсутствие означает пустой ввод. `output_size` — беззнаковое целое JSON, по умолчанию ноль. Дроби и записи с плавающей точкой отклоняются.

Только READ/WRITE/IOCTL принимают необязательное поле `cancel_after_100ns`, целое число JSON от 0 до `INT64_MAX` (9223372036854775807). Задержка отсчитывается от подачи запроса в виртуальных единицах по 100 нс, а не в реальном времени. Для KMDF ноль применяет отмену после маршрутизации фреймворком и до гостевого обработчика ввода-вывода; если маршрутизация уже завершила запрос, завершение имеет приоритет. Для WDM ноль действует после возврата диспетчера. При положительной задержке время продвигается к сроку таймера, ожидания или отмены только при отсутствии готовых обработчиков и кадров. Ожидающий WDM IRP вызывает зарегистрированную процедуру отмены на `DISPATCH_LEVEL` при удерживаемой блокировке отмены; перед завершением она должна освободить блокировку через `Irp->CancelIrql`. Общая отмена очередей и PnP остаётся неподдерживаемой. Каждый отчёт о запросе содержит `cancel_requested_at_100ns`: фактическое абсолютное виртуальное время отмены либо null, если её не было, в том числе когда завершение произошло раньше. Запрос отмены сам по себе не завершает IRP и не определяет его итоговый статус.
`IoSetCancelRoutine`, `IoAcquireCancelSpinLock`, `IoReleaseCancelSpinLock` и `IoCancelIrp` используют одно состояние IRP и одну блокировку отмены; `IoCancelIrp` синхронно вызывает зарегистрированную процедуру и сообщает, была ли она вызвана.

Необязательное логическое поле `user_unmap_after_dispatch` закрывает доступ к исходным пользовательским адресам непустой WDM neither-передачи после возврата диспетчера и до запланированной работы или отмены. Зафиксированные MDL страницы и их системные псевдонимы доступны до разблокировки; прямые пользовательские указатели и новые блокировки не работают. При отзыве выходного адреса `output_hex` пуст. Адреса пользовательских выделений, изначально объявленных сценарием, не используются повторно; их отзыв в произвольные моменты также не моделируется.

`requestor_process_id` задаёт синтетический ID процесса-заявителя (по умолчанию 4096, от 5 до `UINT32_MAX`). `IoGetRequestorProcessId` возвращает его для активного IRP, а `PsGetCurrentProcessId` — при прямой диспетчеризации либо 4 в моделируемом системном рабочем потоке. Смена процесса закрывает доступ к исходным пользовательским VA другого процесса, сохраняя системные псевдонимы заблокированных MDL. `requestor_exit_after_dispatch` после возврата из диспетчера отзывает все исходные пользовательские VA этого процесса и отклоняет его новый ввод-вывод; явные CLEANUP/CLOSE допустимы, без автоматического вывода отмены или закрытия дескрипторов.

Системный рабочий поток может получить непрозрачный объект процесса активного IRP через `IoGetRequestorProcess`, временно подключиться к его исходным пользовательским VA через `KeStackAttachProcess` с доступным для записи ядровым `KAPC_STATE`, а затем вызвать `KeUnstackDetachProcess` с тем же состоянием. `IoGetCurrentProcess` и `PsGetProcessId` отражают подключённый процесс; `PsGetCurrentProcessId` остаётся равным 4 — ID создателя потока. Завершённый процесс, завершённый IRP, несоответствие состояния, ожидание или завершение IRP во время подключения явно отклоняются.

Для direct IOCTL поле `input` инициализирует первый системный буфер, а `direct_input` — отдельный второй буфер, описанный MDL, с дополнением нулями до `output_size`. `METHOD_IN_DIRECT` требует доступа на чтение, но не означает системное отображение только для чтения. Оба метода используют доступные для чтения и записи буферы сценария. `MdlMappingNoWrite` снимает право записи отображения, а `MdlMappingNoExecute` — право исполнения. Снятие отображения отзывает системный VA; повторное отображение сохраняет те же зафиксированные данные. Завершение прекращает время жизни MDL и отображения. Публичные поля MDL, используемые макросами WDM, моделируются; поля process и PFN непостроенных MDL, вручную созданные MDL, пользовательские отображения вне описанной ниже модели MDL с владельцем-процессом и прямой доступ через исходный UserBuffer отклоняются. У direct-буфера нулевой длины MDL равен null.

`IoAllocateMdl` выделяет метаданные для непустого буфера без переполнения, не проверяя и не фиксируя его. Моделируемый дескриптор вместе с массивом PFN должен помещаться в 16-битное поле размера; смещение внутри страницы учитывается в ёмкости PFN. Размер памяти дескриптора независим от размера описываемого буфера. `Irp` может быть NULL или действующим моделируемым IRP. Первичный дескриптор заменяет голову цепочки драйвера; отсоединённые дескрипторы остаются у драйвера. `SecondaryBuffer` добавляет в конец, а для пустой цепочки становится головой. Исходный direct-I/O MDL запроса должен оставаться достижимым; драйвер не может заменить или освободить его. `ChargeQuota` должен быть FALSE; при исчерпании арены возвращается NULL. `MmBuildMdlForNonPagedPool` требует весь диапазон в одном живом выделении невыгружаемого пула. Безопасная функция и макросы WDM используют исходный адрес и права даже с новыми флагами запрета записи/исполнения. Дополнительные системные отображения и снятие отображения отклоняются. `IoFreeMdl` освобождает только указанный дескриптор драйвера, не отсоединяет его и не следует по `Next`. Пользовательский MDL перед ручным освобождением нужно разблокировать. Буфер пула живёт независимо; допустимы оба порядка освобождения без последующего доступа к освобождённой памяти.

Драйвер может менять `MDL.Next` и `IRP.MdlAddress`, вставляя или отсоединяя моделируемые дескрипторы. Окончательное завершение IRP сначала проверяет всю текущую цепочку, затем разблокирует присоединённые пользовательские MDL, отзывает их псевдонимы и освобождает все присоединённые дескрипторы. Отсоединённые дескрипторы и память пула остаются у драйвера. Циклы, неизвестные или освобождённые связи, общие дескрипторы нескольких живых IRP и частные WDF-дескрипторы в WDM-цепочках явно отклоняются. Действующие зависимости DMA и диспетчера предотвращают преждевременное освобождение. Остальные моделируемые поля MDL и построенные PFN доступны только для чтения; поля процесса, непостроенные PFN, ручные MDL не поддерживаются. Перед выгрузкой нужно освободить все оставшиеся дескрипторы драйвера.

`IoBuildPartialMdl` описывает непустой поддиапазон построенного исходного MDL; нулевая длина выбирает остаток. Целевой MDL должен вмещать нужное число PFN. Частичные дескрипторы разделяют физические страницы без дополнительной блокировки. Они наследуют действующее системное отображение источника либо создают независимое через `MmGetSystemAddressForMdlSafe`. Освобождение частичного MDL или подготовка к повторному использованию снимает только принадлежащее ему отображение. Настоящая inline-функция WDK `MmPrepareMdlForReuse` может затем предшествовать новому вызову `IoBuildPartialMdl`. Исходный дескриптор невыгружаемой памяти можно освободить независимо; корневая блокировка пользовательских страниц или заимствованный системный псевдоним сохраняются, пока существует зависимый частичный MDL. Завершение проверяет всю цепочку до освобождения зависимостей независимо от порядка дескрипторов. Активный DMA запрещает перестроение и преждевременное освобождение.

`MmMapLockedPagesSpecifyCache` принимает `UserMode` в контексте живого инициатора, включая присоединённый worker, при IRQL до `APC_LEVEL`. Каждый вызов создаёт отдельное представление процесса тех же страниц, не меняя `MappedSystemVa`. Представления всегда NX; `MdlMappingNoWrite` запрещает запись. Пул должен быть невыгружаемым и занимать полные отдельные страницы. Повторная фиксация через `MmProbeAndLockPages` сохраняет физическую идентичность. Запрошенный адрес сохраняет смещение MDL внутри страницы и лежит в ограниченной арене; исчерпание вызывает перехватываемое `STATUS_INSUFFICIENT_RESOURCES`. `MmNonCached`, `MmCached` и `MmWriteCombined` наследуют уже заданный страницам атрибут кэша; обычная RAM остаётся cached. Зарезервированные значения и противоречивые регистрации физических страниц отклоняются явно.

`MmUnmapLockedPages` требует точную пару пользовательского адреса/MDL и PID создателя. Представление действительно удаляется, адрес и бюджет отображения освобождаются для запрошенного или автоматического повторного использования. Снятие исходного VA сценария сохраняет независимые представления MDL. Физические фиксации и системные псевдонимы остаются связанными с исходными страницами, даже если VA переиспользован для других данных или прав. Живые представления препятствуют освобождению дескриптора, корневой фиксации, пула и памяти запроса.

Ключ представления — `(PID, VA)`: разные процессы могут одновременно владеть одним числовым адресом с разными страницами и правами. Смена процесса атомарно заменяет весь активный набор после полной предварительной проверки; возврат восстанавливает прежние страницы и права. Unmap или выход одного PID не удаляет представление другого PID. Живой непрозрачный объект dispatcher в снимаемом представлении запрещает переключение до удаления объекта. Эта ограниченная модель не реализует произвольное выделение виртуальной памяти, таблицы страниц или общий менеджер процессов.

Для любого метода IOCTL при ненулевом `output_size` значение `Information` не должно превышать `output_size`, даже если входной буфер больше. Если выходного буфера нет, `Information` может содержать определённый драйвером 64-битный результат; это значение не используется как число копируемых байтов. Отчёт сохраняет числовое значение и добавляет точную шестнадцатеричную строку `information_hex` для клиентов JSON, которые не могут представить все 64-битные целые.

Для READ/WRITE флаги `DO_BUFFERED_IO` и `DO_DIRECT_IO` выбирают буферизованный или прямой метод. Если оба отсутствуют, исходный пользовательский адрес находится только в `IRP.UserBuffer`: WRITE использует вход, READ — выход; SystemBuffer и MDL автоматически не создаются. Драйвер должен проверить и использовать адрес в контексте вызывающего потока либо закрепить страницы до отложенной работы. `user_input_access` относится к neither WRITE, `user_output_access` — к neither READ. Явные права для буферизованного/прямого READ/WRITE или оба флага одновременно останавливают выполнение. Information проверяется относительно длины передачи; запись возвращает количество, чтение — байты.

`kernel_exports` сопоставляет именам процедур явные логические значения доступности, например `"kernel_exports": {"OptionalRoutine": false}`. Моделируемые экспорты и статические импорты получают стабильные адреса, общие с `MmGetSystemRoutineAddress`. Явно отсутствующий экспорт разрешается в NULL и не может удовлетворить статический импорт. Экспорт, объявленный присутствующим, но не имеющий модели API, разрешается в отложенную ловушку. Неизвестное динамическое имя останавливает выполнение с диагностикой неопределённой доступности; отсутствие никогда не выводится из отсутствия реализации. Имена ограничены по длине и состоят из печатных ASCII-символов; разрешение учитывает регистр. Реестр — свойство конкретного сценария, а не утверждение о соответствии каждому выпуску Windows.
`IoMarkIrpPending`, `IoGetCurrentIrpStackLocation` и `MmGetSystemAddressForMdlSafe` — моделируемые вспомогательные функции заголовков WDM; это не объявляет их экспортируемыми по умолчанию, поэтому их доступность как экспортов требует статического импорта или явного объявления в `kernel_exports`.

Текст сценария ограничен 2 MiB; допускается не более 64 запросов, не более 65536 байтов на каждый входной или выходной буфер и не более 512 KiB запрошенных байтов суммарно, включая содержимое `direct_input`. Бюджеты инструкций, наблюдений, гостевой памяти и времени действуют на весь сценарий. Арена 1 MiB также содержит объекты и метаданные, поэтому образ может исчерпать память модели до использования максимального объёма буферов сценария.

## Сценарии реестра

Необязательный массив `registry` задаёт конкретное дерево реестра внутри сеанса.
У каждой записи ключа есть обязательный `path` и необязательный массив `values`;
каждое значение содержит `name`, беззнаковое целое `type` и шестнадцатеричные
`data`. Пустое имя выбирает значение по умолчанию. Например, значение DWORD
задаётся как `{"name":"Mode","type":4,"data":"01000000"}`. Байты сохраняются
точно: модель не исправляет завершающие нули строк и не раскрывает переменные
окружения.

Пути должны быть абсолютными ASCII-путями внутри `\\Registry\\Machine` или
`\\Registry\\User`. Родительские ключи создаются неявно. Имена ключей и значений
сравниваются без учёта регистра по правилам ASCII; имена вне ASCII и дубликаты
отклоняются. Если `registry` отсутствует, доступность реестра не определена и
вызовы реестра останавливают выполнение. `"registry": []` явно задаёт пустое
пространство имён. Ключи, значения, данные реестра хоста и настройки службы не
выводятся из самого драйвера.

`ZwOpenKey` и `ZwCreateKey` возвращают независимые непрозрачные дескрипторы;
права каждого дескриптора проверяются при запросе, записи, создании дочерних
ключей и удалении. Настроенное дерево предоставляет поддерживаемые биты
`KEY_ALL_ACCESS`, включая обычные маски `KEY_READ` и `KEY_WRITE`. Это явно
доступное тестовое дерево без ACL Windows и проверки привилегий. Общие права,
`MAXIMUM_ALLOWED`, альтернативные представления реестра, пользовательские
дескрипторы безопасности, классы и символические ссылки не поддерживаются.
Относительное создание требует дескриптора непосредственного родителя с
`KEY_CREATE_SUB_KEY`. Входные ключи энергонезависимы; новые ключи могут быть
временными (volatile), но создание энергонезависимого дочернего ключа внутри
временного отклоняется. Перезагрузка и сохранение на диск не моделируются.

`ZwQueryValueKey` реализует классы Basic, Full, Partial и их определённые
варианты Align64: точные размеры, выровненные данные, частичные результаты и
различающиеся статусы `STATUS_BUFFER_TOO_SMALL` и `STATUS_BUFFER_OVERFLOW`.
`ZwSetValueKey` и `ZwDeleteValueKey` изменяют только дерево этого сеанса.
`ZwDeleteKey` отклоняет удаление ключа с существующими дочерними ключами;
дескрипторы удалённого ключа возвращают `STATUS_KEY_DELETED` до закрытия.
`ZwClose` освобождает дескриптор независимо от ключа; запрошенная выгрузка
завершается ошибкой, пока остаются открытые дескрипторы реестра.

Ограничения: 256 ключей с учётом родителей, 1024 значения, 65536 байтов на
значение, 512 KiB данных значений суммарно, 1024 байта ASCII на путь ключа,
256 байтов на имя значения и 256 одновременно открытых дескрипторов. Создание
и изменения соблюдают те же ограничения, что и предварительная проверка
сценария. Поле отчёта `configuration.registry` сохраняет исходные входные
данные, а `registry` перечисляет итоговые пути и значения существующих ключей,
включая изменения до остановки. Неопределённое состояние реестра представлено
как null. Признак volatile и идентификаторы дескрипторов не входят в этот снимок.

## Проверка примера Microsoft

Запускаемый по желанию [скрипт проверки](../../scripts/validate_windows_driver_sample.py) загружает исходники Microsoft SIOCTL ревизии, закреплённой в [манифесте проверки](../../unittests/emulation/fixtures/sioctl-validation.json), проверяет хеши SHA-256 и компилирует неизменённый исходный код с заголовками MinGW-w64 DDK. В выбранном выходном каталоге сохраняются исходная лицензия/происхождение, команды сборки, сценарий и отчёты. Нужны доступ к сети, Clang, `lld-link`, `nm` и заголовки DDK из MinGW-w64:

```bash
python3 scripts/validate_windows_driver_sample.py \
  --neverd build-release/bin/neverd \
  --output build-release/driver-validation/sioctl
```

Для нестандартного каталога заголовков MinGW-w64 используйте `--headers`. Скрипт создаёт библиотеку импорта MS COFF из зависимостей скомпилированного объектного файла. Проверка запускает отдельные сценарии buffered, in-direct и out-direct через DriverEntry, create, IOCTL, cleanup, close и unload. Добавьте `--debug` и выберите отдельный выходной каталог, чтобы скомпилировать с `DBG=1` и проверить гостевые сообщения журнала. Исходный пример не регистрирует обработчик cleanup, поэтому моделируемый обработчик по умолчанию завершает cleanup с `STATUS_INVALID_DEVICE_REQUEST` (`0xC0000010`). Драйвер всё же закрывается и выгружается, а успешный IOCTL возвращает ожидаемые байты. Для этого полного сценария ожидаемый код выхода CLI — **2**, а `scenario_success` равен false. Сам скрипт завершается успешно только при совпадении всех этих результатов, включая видимый сбой cleanup; он не переписывает пример, чтобы скрыть этот результат.

Дополнительный [скрипт проверки Zero](../../scripts/validate_zero_driver_sample.py)
собирает неизменённый публичный пример Zero WDM Павла Йосифовича по ревизии и

Запустите `python3 scripts/validate_zero_driver_sample.py` с теми же требованиями

умолчанию сохраняются в `build-release/driver-validation/zero`. Девять запросов
проверяют прямое чтение через границы страниц, число записанных байтов,
атомарную статистику гостя и buffered IOCTL для чтения статистики. Ошибка
чтения нулевой длины и отсутствие обработчика CLEANUP в примере остаются

выходных байтов.

## Отчёты и SDK

JSON-отчёт различает `stop_reason`, допускающие null поля `nt_status` и `nt_success`, PC остановки и число инструкций. Он сохраняет вызовы API и наблюдаемое состояние до остановки, включая объекты устройств и адреса обратных вызовов драйвера. Гостевые адреса представлены шестнадцатеричными строками, чтобы потребители JSON не теряли 64-битную точность. Объект `configuration` записывает ограничения запуска, имя службы, переопределения `kernel_exports` и входное дерево `registry`. Профиль — `wdm-x64-scheduled-v101`. Поле `nt_status` остаётся результатом DriverEntry, а `scenario_success` описывает инициализацию и завершённые запросы вместе. `phase`, `requests` и `unload_completed` показывают, какие части запрошенного жизненного цикла были выполнены. Каждый вызов API и каждая запись CPU также содержат фазу (`driver_entry`, `add_device:<ID>`, `request:N`, `callback:N` или `unload`). Для каждого запроса приводятся статусы диспетчеризации и ввода-вывода, завершение, длина информации и возвращённые байты `output_hex`. `preferred_image_base` описывает исходный базовый адрес PE. `security_cookie` — гостевой адрес инициализированного cookie либо `"0x0"`, если он не требовался. Поля запроса: `kind`, `device`, `device_id`, `pnp`, `file`, `requestor_process_id`, `byte_offset`, `code`, `irp`, `completed`, `cancel_requested_at_100ns`, `dispatch_status`, `io_status`, `information`, `information_hex` и `output_hex`. Числовое поле `information` остаётся точным десятичным целым JSON; `information_hex` сохраняет те же биты и для клиентов, читающих числа JSON с точностью только до 53 бит.

Наблюдения рабочих элементов имеют фазу `callback:N`. Для ожидающего запроса `dispatch_status` сохраняет `STATUS_PENDING`; окончательный статус отдельно записывается в `io_status` и определяет вклад в `scenario_success`.

`ExRaiseStatus` передаёт младшие 32 бита NTSTATUS гостевому обработчику исключения; `ExRaiseAccessViolation` и `ExRaiseDatatypeMisalignment` вызывают `STATUS_ACCESS_VIOLATION` и `STATUS_DATATYPE_MISALIGNMENT`. Профиль следует отдельным страницам DDI Microsoft: ExRaiseStatus допускает `APC_LEVEL`, а две процедуры без аргументов требуют `PASSIVE_LEVEL`. Некоторые аннотации SAL WDK допускают для этих двух процедур APC_LEVEL; профиль сохраняет более строгое документированное ограничение. Вызов с исключением оставляет `result: null` и записывает код в `detail`; успешный возврат API не подставляется.

Доставка использует x64 V1 unwind и `__C_specific_handler`. Константная область `EXCEPTION_EXECUTE_HANDLER` напрямую выбирает обработчик. Выполняются настоящие гостевые фильтры: ноль продолжает поиск, положительное значение выбирает handler, отрицательное запрашивает продолжение. После выбора `__finally` покидаемых областей выполняются в порядке unwind до handler; очистка не выполняется во время поиска или возобновления. Обычные пути `__finally` исполняет гостевой код. Обычные кадры восстанавливают невольатильные общие регистры в пределах исходного стека. `GetExceptionCode()` сохраняет код исключения; handler может снова вызвать исключение во внешнюю поддерживаемую область.

Диапазоны C SEH остаются полуоткрытыми. Допустимая точка перехода `__C_specific_handler` может находиться внутри защищённого диапазона: [LLVM 20.1.8](https://github.com/llvm/llvm-project/blob/llvmorg-20.1.8/llvm/lib/CodeGen/AsmPrinter/WinException.cpp#L600-L608) записывает `EndLabel + 1` как конечную границу. Модель Windows сохраняет исходные границы и отдельно проверяет исполнимость цели, принадлежность функции и совпадение адреса продолжения, включая перенос образа. `KernelSEHContinuationCases.def` сохраняет расположение исходной фикстуры; `ScopeEndLabelMayOverlapTheHandlerLandingPad` проверяет постоянные обработчики и фильтры. Дополнительные тесты проверяют исключение конечной границы и отклонение неверных целей без изменения состояния диспетчеризации. Эти чистые проверки выполняются в `NeverDNativeDriverTests` при отключённом Unicorn.

При раскрутке к цели также используется исходная конечная граница: область `finally` не покидается, если её диапазон ещё содержит цель обработчика. `FinallyRespectsRawScopeEndAtHandlerTarget` проверяет обе стороны границы и на Windows x64 напрямую сравнивает их с `ntdll.dll!__C_specific_handler`. NeverD не исправляет диапазоны, созданные компилятором. Сборки исходной фикстуры Clang 20/21 возвращают гостевую ошибку в режимах `T` и `J`, поскольку смещённая граница включает выбранную цель; Clang 23 выполняет обе очистки. [Изменение LLVM #144745](https://github.com/llvm/llvm-project/pull/144745) удаляет прежнее смещение `+1`. Такие результаты компилятора учитываются отдельно от сбоев бэкенда.

Фильтры получают стабильные `EXCEPTION_POINTERS`, запись исключения и `CONTEXT_INTEGER | CONTEXT_CONTROL` в отдельном ограниченном стеке вне shadow space Win64. Полное исходное состояние CPU, включая SIMD/floating point и flags, сохраняется. Отрицательный фильтр может возобновить пользовательский CPU fault чтения/записи после проверки изменений GPR, RIP/RSP и арифметических флагов/флага направления. Неизменяемые поля проверяются при любом результате фильтра. Возобновление исключения, вызванного моделируемым API, не поддерживается. Идентичность потока/процесса, PreviousMode и права наследуются от родителя без повышения полномочий независимого worker; присоединённый worker сохраняет системный процесс-создатель и KernelMode.

Нативные x64 KVM/WHP передают реальные ошибки `#XM` в C SEH драйвера через `X64SIMDException`. Аппаратный `CONTEXT` сохраняет XMM0–15 и MXCSR. Фильтры, finally при раскрутке исключения и выбранные обработчики работают с MXCSR `0x1f80` и сброшенным DF. Отрицательный фильтр может изменить XMM и верхнее поле `CONTEXT.MxCsr`, ограниченное маской гостевого CPU, затем повторить исходную инструкцию; `FltSave.MxCsr` не управляет восстановлением ядра. Исключения моделируемых API сохраняют целочисленные/управляющие поля; изменения x87/AVX по-прежнему отклоняются.

Поддерживаются вложенные исключения и collided unwind, цепочки V1, частичные прологи, канонические эпилоги и полное восстановление XMM6–XMM15. Записи сохраняют связи; уже начатый finally не повторяется. C++ и неполные метаданные по-прежнему отклоняются. Необработанное API- или пользовательское исключение даёт `model_error`; другие CPU memory faults, interrupts и invalid instructions остаются терминальными. При каждом возврате фильтра `EXCEPTION_POINTERS`, `EXCEPTION_RECORD` и неподдерживаемые поля `CONTEXT` должны оставаться неизменными.

`__GSHandlerCheck_SEH` проверяет текущий cookie образа до поиска обработчика и при раскрутке, включая кадры без finally. Поддерживаются фиксированные и динамически выровненные слоты, проверяемые знаковые смещения и кодирование исходным указателем кадра. Флаги C-обработчика не отключают проверки самого cookie. Прологи и эпилоги не читают ещё не созданный cookie. Несовпадение останавливает выполнение до соответствующего фильтра, очистки или обработчика. Отдельный `__GSHandlerCheck` также проверяет cookie при поиске и раскрутке, не создавая областей C. Требуется точная идентичность символа или импорта; анонимный код не угадывается по инструкциям. Обёртки GS/C++ и обработчики исключений C++ пока не поддерживаются. Исходные кадры в `driver_seh_gs.h` также вызывают связанный проверяющий код WDK.

Оригинальный образец `driver_wdm_seh.c` использует настоящие заголовки WDK и `/GS-`. Для обычного образа и образа с активным CFG задаются `NEVERD_WDM_SEH_FIXTURE` и `NEVERD_WDM_SEH_CFG_FIXTURE`. Пример [driver-seh-scenario.json](../examples/driver-seh-scenario.json) перемещает базу образа, перехватывает исключение API в DriverEntry и выгружает драйвер. Отдельный путь WDM METHOD_NEITHER поддерживает проверки пользовательской памяти, закреплённые MDL и перехватываемые сбои памяти.

Объект `fault`, допускающий null, сохраняет первую ошибку бэкенда. Его `kind`, `pc` и допускающие null поля `address`, `size`, `access` и `interrupt` различают неотображённую или защищённую память, недопустимые диапазоны, недопустимые инструкции и исключения CPU. Адреса представлены шестнадцатеричными строками, размеры и векторы прерываний — целыми числами. Чтение для наблюдения не может заменить исходную ошибку. Бэкенд с ошибкой не может продолжить выполнение, и эта запись не подразумевает обработку гостевых SEH.

`instructions` считает допущенные попытки выполнения гостевых инструкций. Инструкция, отклонённая политикой выполнения, не учитывается; допущенная инструкция, вызвавшая ошибку CPU, учитывается. Синтетическая диспетчеризация API и маркер возврата не увеличивают этот счётчик.

Необязательное логическое поле сценария `trace_memory_writes` по умолчанию равно true. При false массив `writes` пуст, а бюджет событий учитывает только вызовы API. Проверки памяти, наблюдатели завершённых записей и ограничения инструкций и времени остаются активными. Выбор отражается в `configuration.trace_memory_writes`; в C++ используется `DriverOptions::TraceMemoryWrites`.

Каждая запись `writes` имеет `semantics: "attempted_guest_write"`: она описывает попытку записи CPU вне стека, включая попытку, которая позднее может вызвать ошибку или остановку по бюджету. Это не гарантия завершённой записи; записи моделей API сюда не входят. Снимки устройств и объекта драйвера описывают состояние, наблюдаемое при остановке выполнения.

Подключите `neverd/sdk/NeverDCAPIEmulation.h` (либо общий заголовок C API), создайте сеанс и вызовите `neverd_emulate_driver_json(session, path, options)`. Явно заданный непустой путь сразу запускает строгую предварительную проверку выполнения без начальной загрузки через общий API анализа. CLI использует этот путь. Передача `NULL` в качестве options выбирает значения по умолчанию. Явные параметры `neverd_driver_options_v1` требуют точного `struct_size` и положительных бюджетов инструкций, памяти, событий и времени. Освободите результат через `neverd_free_string`.

Передача `NULL` вместо пути требует загруженного сеанса и заново разбирает его файл независимо от анализа IR и загрузки с ограничением по функциям. Оба пути сохраняют образ сеанса. В течение вызова входной файл должен оставаться доступным и неизменным. Ошибки запроса/настройки возвращают `NULL` и устанавливают `neverd_last_error`; остановки выполнения возвращают JSON. API доступен и в сборках с отключённой функцией и сообщает, как её включить.

`neverd_emulate_driver_scenario_json(session, path, scenario_json, options)` использует те же параметры v1 и правила владения, добавляя строгий ввод сценария. Требуется не-NULL строка JSON с завершающим NUL. Исходный ABI `neverd_emulate_driver_json` остаётся неизменным и выполняет только инициализацию. C++-парсер `driverOptionsFromScenarioJSON` предоставляет ту же проверку сценария вызывающим `emulateDriver`.

Внутренняя точка входа C++ — `neverd::emulation::emulateDriver` в `include/neverd/emulation/DriverSession.h`. Разбор формата относится к существующему загрузчику; поведение объектов/API Windows — к `lib/emulation/os/windows`; состояние CPU и выполнение — к адаптеру Unicorn. Адаптер и модель используют один интерфейс гостевой памяти. Поведение Windows API не должно находиться в форке Unicorn.

В WDM `METHOD_NEITHER` поля `Type3InputBuffer` и `IRP.UserBuffer` указывают на разные пользовательские выделения. `ProbeForRead` проверяет диапазон и выравнивание без обращения к страницам; `ProbeForWrite` обращается к каждой странице. `ExGetPreviousMode` возвращает режим запроса. `MmProbeAndLockPages` закрепляет одно пользовательское выделение, `MmGetSystemAddressForMdlSafe` даёт общий алиас, а `MmUnlockPages` удаляет алиас и освобождает страницы. Произвольные процессы не моделируются.

Для непустого буфера WDM `METHOD_NEITHER` IOCTL поля `user_input_access` и `user_output_access` независимо принимают `read_write` (по умолчанию), `read_only` или `no_access`. Для буферизованных/прямых методов и пустых буферов поля отклоняются; `no_access` сохраняет указатель, но запрещает доступ к страницам.
В отчёте `configuration.user_page_access` указаны только явно заданные права с `source_request_index`, начинающимся с нуля; для пропущенного направления действует `read_write`.

## Ограниченное параллельное выполнение запросов WDM

Запрос WDM READ/WRITE/IOCTL или запрос неограниченной параллельной очереди KMDF может задать `defer_callback_drain: true`. Следующий запрос отправляется до выполнения обратных вызовов только если диспетчер вернул `STATUS_PENDING`, а IRP действительно остался ожидающим. После следующего запроса без этого поля выполняются обратные вызовы и завершается вся группа; для последнего помеченного запроса это происходит в конце сценария. Перекрывающиеся запросы могут использовать разные файловые объекты либо один объект, явно открытый в асинхронном режиме. Перекрытие на синхронном файле, произвольное вытеснение и внешнее поступление запросов не поддерживаются.

## Асинхронный файловый объект

Только запрос CREATE может задать логическое поле `asynchronous_file: true`; отсутствие или false сохраняет синхронный режим. Асинхронное открытие снимает `FO_SYNCHRONOUS_IO` у гостевого `FILE_OBJECT` и не устанавливает `IRP_SYNCHRONOUS_API` для последующих файловых IRP. READ/WRITE/IOCTL на одном асинхронном файле перекрываются только при явной отсрочке обратных вызовов. CLEANUP/CLOSE ждут завершения и финализации всех предыдущих передач. Неявная позиция файла не поддерживается: `byte_offset` задаётся для каждого запроса и по умолчанию равен нулю. Другие типы запросов отвергают поле даже со значением false.

## Дополнительная семантика

`MmAllocatePagesForMdl`, `MmAllocatePagesForMdlEx` и `MmFreePagesFromMdl` управляют независимыми страницами с физическими границами, частичным выделением и непрерывными блоками. Страницы и дескриптор освобождаются отдельно. `MmProtectMdlSystemAddress` меняет права PAGE частного системного отображения, сохраняя PFN, кэш и права пользовательских представлений. `MmProbeAndLockPages` поддерживает пулы KernelMode: выгружаемый пул блокируется не выше APC_LEVEL, после чего доступен при DISPATCH_LEVEL; освобождение до разблокировки запрещено.

Явные `messages` задают MSI-адрес, данные, вектор, уровень, affinity и полярность. `message_id` локален для дескриптора; третий аргумент ISR нумеруется по всему PDO. `CONNECT_MESSAGE_BASED` (3) возвращает реальную таблицу. `CONNECT_MESSAGE_BASED_PASSIVE` (5) и пассивные линии допускают ожидания PASSIVE_LEVEL, сериализуют одно прерывание и сохраняют независимые кадры. Прибытие и доставка фиксируются отдельно, без выдуманного протокола PCI.

`WdfDeviceInitSetPowerPolicyOwnership` задаёт владельца политики. Init/Suspend/Restart/Flush/Cleanup и callbacks D0 исполняются; D3/D0 сохраняет ресурсы. Политика по умолчанию связывает Sleeping3/Working с D3/D0 через явные `requested_device_power`. Дочерний IRP имеет `origin: "framework_power_policy"` и `response_index`. S3 ждёт его завершения; S0 может завершиться после отправки D0. Автоматическое повторное перечисление не моделируются.

Системный Query ждёт соответствующего Query устройства и передаёт его результат без изменения состояния питания.

## Нативные синхронные исключения x64

Checked x64 выполняет `DIV`/`IDIV` с реальными результатами процессора и `#DE`. KVM использует закрытые supervisor IDT/IST, WHP — явную маску исключений; исходный контекст и доступные коды отделены от ошибок транспорта. ОС получает восстанавливаемое событие перед установкой продолжения. Windows-драйверы преобразуют деление на ноль и переполнение частного в `STATUS_INTEGER_DIVIDE_BY_ZERO`, выполняя настоящие SEH-фильтры, `__finally` и повтор инструкции. `NeverDX64ExceptionTests` собирается без Unicorn; `DriverWDMCPUException` проверяет исходные WDK-примеры. Недоступные ARM64-хосты явно пропускаются.

## Полное состояние x87

`NeverDEmulationArch` владеет контрактами ISA, таблицами страниц и форматом FP, общим для нативных транспортов и Unicorn. Контексты x64 сохраняют управление, статус, TOP, физические теги, код операции, указатели инструкций/данных и восемь 80-битных регистров. `FP0`–`FP7` используют `RegisterValue`; скалярный доступ отвергает усечение. `FPTag` — физическая маска непустых регистров. `NeverDX64FPTests` проверяет все TOP, точные операции по FXSAVE/FXRSTOR хоста и восстановление. Это не разрешает инструкции x87 в checked и не доказывает всю семантику округления. Недоступные нативные хосты явно пропускаются.

Выбранный профиль можно запросить через `executionCapabilities(Contract, ISA, Backend)`. `NativeLegacyX64` описывает нативное выполнение драйверов x64. `NeverDNativeDriverTests` проверяет существующий набор драйверов и работает также в сборке без Unicorn.

Checked ARM64 использует единую границу полного состояния. `Registers.def` задаёт 39 скалярных полей и 32 вектора по 128 бит; `captureAArch64State` сначала читает всё, применяет ширины и нормализацию NZCV, затем публикует один раз. Unicorn, KVM и WHP передают один набор, включая TPIDR_EL0, TPIDRRO_EL0, TPIDR_EL1, FPCR и FPSR. Нативные адаптеры включают FP/SIMD через CPACR_EL1. Ошибка чтения или отмена входа сохраняет всё состояние вызывающей стороны.

Запуск ARM64 KVM/WHP выполняет частную программу `AArch64MachineProbe.def`: NOP, сложение FP32 с округлением к положительной бесконечности и сложение SIMD в двух каналах. Каждый шаг сравнивает все 39 скалярных полей и 32 вектора, включая TLS, NZCV, обнуление верхних битов результата и сохранённое/накопленное состояние FPCR/FPSR. Проверка использует только память монитора supervisor и один общий срок. Успех подтверждает эту ограниченную программу инициализации; независимая проверка нативных ARM64-нагрузок всё ещё нужна. Программа также включает подпись и аутентификацию адресов возврата A/B при отключённых ключах и все четыре формы BTI на незащищённых страницах.

Проверка также дважды выполняет `MRS CTR_EL0`, затем `DC CVAU`, `DSB ISH`, `IC IVAU` и `ISB`, проверяя стабильность геометрии кэша и полное состояние. Checked EL0/EL1 допускает исходные инструкции, все именованные базовые варианты DSB и только ISB SY. CTR считывается из выбранного виртуального CPU и может различаться между транспортами. Цели должны указывать на обычную RAM, доступную для чтения с текущими правами; допустимы невыровненные адреса и алиасы, остальные цели отклоняются как неподдерживаемые. Обслуживание кэша не создаёт событий чтения/записи данных. Проекция сохраняет когерентность исполнения, не моделируя частные кэши или параллельный аппаратный SMP. `NeverDAArch64CacheTests` проверяет состояние, концы страниц только для чтения, отказы, остановки, контексты, бюджеты и обновление гостевого кода через RW/RX-алиасы на двух страницах. Недоступные KVM/WHP явно пропускаются.

Нативная инициализация x64 KVM/WHP исполняет `X64MachineProbe.def` в закрытых supervisor-страницах. Единый срок охватывает NOP, FP32-сложение с округлением к положительной бесконечности, двухполосное SIMD-сложение, загрузки FS/GS и чтения CS/SS/CR8; каждый шаг сравнивает полное скалярное состояние, XMM, физические x87 и управляющие поля. Проверки x64 и ARM64 требуют исключительного права исполнения физической памяти. `MemoryProjection` владеет идентичностью кеша (ISA, адресное пространство, поколение отображений, привилегия и вариант монитора) и историей подтверждённых корней для каждой ISA. Перед перезаписью кеш инвалидируется: неудачная замена не использует частично записанные таблицы, а вызывающая сторона не передаёт устаревшие корни. Проверки подтверждают только эту ограниченную инициализацию; независимая проверка нативных нагрузок ARM64 ещё не завершена.

Общий декодер XSAVE различает начальное состояние SSE в стандартном и компактном форматах. При сброшенном XSTATE_BV[1] оба формата инициализируют XMM; стандартный по-прежнему читает и проверяет MXCSR, а компактный инициализирует MXCSR. `X64XsaveCases.def` содержит независимые схемы пакетов и оригинальные программы XRSTOR для хоста. `X64XsaveTests.cpp` проверяет атомарный отказ и сравнивает оба формата с реальным выполнением, сохраняя FP/SSE вызывающей стороны. При неподходящей архитектуре или отсутствии нужной функции инструкций проверка на хосте явно пропускается.

`X64FPState.def` задаёт компактные транспортные схемы AVX, AVX-512, CET_U/CET_S и AMX с выравниванием компонентов на 64 байта. Присутствующие данные расширений должны соответствовать нулевому начальному состоянию; отсутствующие компоненты и заполнение не определяют состояние. Биты схемы задают смещения; неизвестная схема, неначальные данные или неверная длина отвергаются до публикации. `CompactedOffsetsFollowLayoutRatherThanPresentBits`, `WideLayoutIgnoresAbsentComponentsAndAlignmentPadding`, `InitialCETComponentsDoNotHideFPState` и `InitialWideComponentsDoNotHideFPState` проверяют пакеты WHP на 872 и 10752 байта. Такой транспорт не разрешает выполнение инструкций расширений.

`WhpXsaveRegisters.def` дополняет полные пакеты XSAVE именованными регистрами управления x87/SSE. Последний код операции и указатели инструкции/данных явно записываются и считываются с хоста. Нулевые поля пакета можно дополнить; конфликт ненулевых метаданных или общих управляющих полей вызывает ошибку до публикации. `NamedMetadataRestoresOmittedPacketFields` проверяет пропущенные поля, сохраняя все данные FP.

Нативные `FOP/FIP/FDP` следуют правилам сохранения x87 хоста. AMD может обнулять их без ожидающего немаскированного исключения; снимки сохраняют наблюдаемые значения. `X64MachineProbe.def` и точные тесты NOP/контекста задают согласованное ожидающее исключение, чтобы сравнивать все действительные поля без маскирования различий. Эталон FXRSTOR64/FXSAVE64 в процессе хоста проверяет оба состояния; бэкенды никогда не подменяют результаты хоста входными метаданными.

Общий кодек `encodeX64XsaveState` / `decodeX64XsaveState` владеет стандартными и уплотнёнными FP/SSE-пакетами, физическим вращением TOP, начальным состоянием отсутствующих компонентов и атомарной проверкой. WHP использует полные XSAVE API, предпочитая `WHvGetVirtualProcessorState` / `WHvSetVirtualProcessorState`, а прежние XSAVE API оставляет для совместимости. Отдельные старые регистры x87 не заменяют полные пакеты. Расширенные компоненты не в начальном состоянии, неверные заголовки, управляющие значения и усечённые результаты явно отклоняются. Ошибки отображений WHP сохраняют HRESULT, GPA и размер для диагностики.

`CheckedX64Instructions.def` допускает беззнаковое `MUL` шириной 8/16/32/64 бита и `CBW/CWDE/CDQE/CWD/CDQ/CQO` через существующий транспорт CPU. `NeverDX64IntegerTests` использует независимые кодировки и ожидаемые значения из `X64IntegerCases.def` на обоих уровнях привилегий: сохранение незатронутых частей регистров, расширение нулями при 32-битной записи, обе половины произведения, определённые CF/OF и неизменность флагов при знаковом расширении. Умножение в обычной RAM сохраняет проверку прав всего диапазона и наблюдателей чтения; ошибка или остановка наблюдателем сохраняет неявные выходные регистры и PC. Операнды устройств не поддерживаются. Эти случаи также выполняются в checked Unicorn; недоступные нативные транспорты явно пропускаются.

`X64BitInstructions.def` допускает `BT/BTS/BTR/BTC` для регистров и обычной RAM разрядностью 16/32/64 бита. Регистровый индекс трактуется как знаковое значение ширины операнда и выбирает целое слово; непосредственный индекс остаётся в базовом слове. Усечение до ширины адреса выполняется перед прибавлением базы FS/GS. Процессор формирует CF и записываемые значения; `RAMTransaction` не публикует результат до принятия наблюдателями. Права проверяются для всего диапазона, включая отдельно выделенные страницы и псевдонимы. Остановка, ошибка callback или отказ в доступе сохраняют исходные CPU и RAM. LOCK ограничен естественно выровненными изменениями памяти; MMIO и параллельный аппаратный SMP не поддерживаются. `X64BitStringTests.cpp` сравнивает независимые кодировки с реальным исполнением на x64 и проверяет отрицательные индексы, усечение ширины, границы страниц, отмену и недопустимые формы LOCK. См. [справочник Intel](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html).

`X64StringInstructions.def` задаёт `MOVS/STOS/LODS` для обычной RAM шириной 8/16/32/64 бита; `CLD/STD` меняет только флаг направления. Каждый элемент REP проверяет весь операнд до вызовов наблюдателей и фиксируется на границе возобновления. Последующий сбой сохраняет завершённые элементы; остановка или исключение наблюдателя не меняет текущий элемент. FS/GS прибавляется только к источнику после усечения адреса. Загрузка AL/AX сохраняет старшие биты, EAX обнуляет их. При нулевом счётчике REP и 32-битной адресации старшие биты счётчика, а для MOVS/STOS также используемых адресов, должны быть нулевыми: иначе реальные процессоры дают разные результаты. REPNE для MOVS/STOS/LODS и обращения STOS/LODS к устройствам пока не поддерживаются. `X64StringTransferTests.cpp` сравнивает ширины, направление, перекрытия и нулевые счётчики с независимыми инструкциями хоста, проверяя также права, псевдонимы, циклическую адресацию, сбои и возобновление. Оригинальный драйвер ресурсов WDK выполняет все четыре ширины STOS/LODS через `driver_resource_strings.def`.

`X64StringInstructions.def` также задаёт `CMPS/SCAS` для обычной RAM шириной 8/16/32/64 бита с `REPE/REPNE`. Каждый элемент проверяет все чтения до наблюдателей, обновляет шесть арифметических флагов и останавливается при первом условии завершения. Ошибка данных восстанавливает флаги начала непрерывного REP, сохраняя изменения указателей и счётчика завершённых элементов; публичное возобновление начинается с опубликованного состояния CPU. Остановка и исключения наблюдателей не меняют текущий элемент, досрочное завершение не читает следующий. FS/GS действует только на источник CMPS; SCAS сохраняет аккумулятор и неиспользуемый регистр источника. Устройства и неоднозначные старшие биты при нулевом 32-битном счётчике исключены. `X64StringComparisonTests.cpp` сравнивает независимые инструкции хоста, флаги, направление, псевдонимы, циклическую адресацию, права и восстановление; сигнальный тест Linux x64 фиксирует регистры реального сбоя. Оригинальный драйвер WDK выполняет оба условных повтора во всех четырёх ширинах через `driver_resource_strings.def`. См. [справочник Intel](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html).

Существующие CPU WHP используют один нативный раздел; его окончательное закрытие и повторное создание защищены общей блокировкой реестра. `WhpResourceCache.h` повторно использует кооперативный VP 0; перед сменой логического CPU этот VP и его отображения удаляются. Параллельные CPU сохраняют отдельные VP и диапазоны GPA. Передача регистров, XSAVE и отмена адресуются своему VP. x64 сохраняет стандартный набор XSAVE хоста и проверяет фактическую конфигурацию через `WHvGetPartitionProperty`. По умолчанию планирование остаётся кооперативным.

`CheckedAArch64Instructions.def` и `AArch64InstructionEffects` допускают в EL0/EL1 ограниченную базовую арифметику FP32/FP64, сравнения, пересылки и SIMD фиксированной ширины. FPCR сохраняет четыре режима округления, FZ и DN; FPSR сохраняет накопленные флаги и QC. Неподдерживаемые биты отклоняются до изменений. Арифметика FP16, SVE/SME, немаскированные исключения, дополнительные расширения и неперечисленные формы явно завершаются ошибкой. Загрузка драйверов Windows ARM64 и другие среды ОС не добавлены.

`AArch64InstructionEffects` владеет скалярными и FP/SIMD диапазонами одиночных/парных операций RAM до 128 бит на операнд. Общее адресное пространство проверяет каждую страницу до входа; `RAMTransaction` публикует только полные заявленные физические записи. Наблюдатель 128-битной записи получает два упорядоченных 64-битных слова до эффектов. Остановки и ошибки сохраняют RAM, векторы и обновление адреса. Совпадение номера Xn/Vn допустимо; оборачивающиеся парные диапазоны отклоняются. `NeverDAArch64MemoryTests` использует независимые `AArch64CrossPageCases.def` и `AArch64VectorMemoryCases.def`.

KVM x64/ARM64 использует `KvmRunControl` для подготовки, входа в `KVM_RUN` и захвата состояния на одном выделенном потоке vCPU. Подготовка выполняется один раз даже при `EINTR`; отмена и ошибка чтения запрещают публикацию. `KvmAArch64Machine.cpp` выполняет обслуживание трансляции и полные скалярные/векторные передачи с одним сроком шага. Вызывающий поток публикует после подтверждения и владеет декодированием ISA, транзакциями RAM, политикой ОС и наблюдателями. Нативные свидетельства ARM64 ещё отсутствуют.

KVM сравнивает общие регистры и полное состояние FP/SSE с последним подтверждённым чтением после отладки по `X64HostRegisters.def` и `X64FPState.def`, повторно задавая изменённые входные данные. Записи хоста и восстановление контекста также сравниваются; исключения, отмена и ошибки запрещают повторное использование. Пошаговый режим и чтение реального общего/FP-состояния сохраняются для каждой инструкции.

Аппаратное исполнение само по себе не гарантирует меньшую общую задержку. Текущее нативное исполнение выполняет допуск, наблюдение, передачу состояния и выход VM для каждой инструкции. Сравнивайте те же исходные образы и сценарии с одинаковыми бюджетами инструкций и событий, указывая совпадение результатов вместе со временем; при измерении задержки CLI учитывайте запуск и загрузку.

Неактивные слоты указателей CFG остаются допустимыми при нулевом `GuardFlags`. Загрузчик проверяет их память, исполняемые резервные обработчики и полное покрытие `DIR64` при смене базы, сохраняя исходные гостевые указатели. Активный CFG по-прежнему требует бита включения в образе и флагов инструментирования/таблицы функций. `DriverGuardCases.def` и `NeverDDriverGuardMetadataTests` проверяют это с Unicorn, KVM и WHP, в том числе в сборках без Unicorn.

Проверенный Unicorn использует `MachineRunControl`: один временной допуск охватывает обслуживание ARM64, выполнение гостя и полный захват состояния. `UC_HOOK_CODE` проверяет заимствованный токен остановки и срок на входе в инструкцию. Синхронный вызов движка освобождает ссылку hook перед возвратом, но машинный шаг сохраняет управление до публикации. Unicorn и WHP сначала сохраняют полное состояние CPU приватно и проверяют тот же контроль перед публикацией успешного шага. WHP создаёт допуск один раз до подготовки. Подтверждённое исключение CPU x64 имеет приоритет над остановкой во время захвата. Проверенная транзакция RAM отбрасывает спекулятивные записи при отмене захвата; неограниченный программный контракт не меняется. `MachineInterruptedError` отличает подтверждённую отмену от ошибки хоста или захвата. Общая проверенная CPU возвращает `Stopped` или `Deadline`, сохраняет CPU/RAM и допускает повтор; реальные ошибки остаются `BackendFailure` даже при одновременной остановке.

`RunDeadline::invoke` отклоняет остановленный или просроченный вход WHP до вызова хоста, сохраняет фактический результат хоста при отмене и подтверждает завершение обработчиков прерывания до освобождения заимствованного токена остановки. KVM и WHP проверяют полностью считанное закрытое состояние в вызывающем потоке, владеющем правом исполнения, до классификации одновременной остановки или истечения срока. Реальные ошибки хоста или чтения состояния и подтверждённые исключения CPU x64 сохраняют приоритет. Обычный успешный результат остаётся закрытым до окончания проверки отмены; подтверждённое прерывание отбрасывает спекулятивные эффекты CPU/RAM и разрешает повтор. Подготовка, нативное исполнение и чтение состояния используют единый допуск на шаг. Управление отменой кооперативное и не гарантирует жёсткую границу реального времени.

Явное вытеснение CPU0, виртуальное время и ограничения описаны в [планировании драйверов](driver-scheduling.md).

## Экспорты HAL и счётчик производительности

`HAL.dll` является отдельным поставщиком импортов с регистронезависимым именем модуля. Статические импорты и `MmGetSystemRoutineAddress` используют точные регистрозависимые идентификаторы экспортов ядра и HAL; конфликтующие действующие идентификаторы отклоняются. `kernel_exports` переопределяет известные процедуры HAL в пространстве HAL; остальные явные объявления остаются экспортами ядра. Неизвестные импорты HAL сохраняют отложенные ловушки и не получают семантику API ядра только из-за совпадения имени.

`KeQueryPerformanceCounter` возвращает общее время планировщика в единицах 100 нс с фиксированной частотой 10 000 000 в секунду. Необязательный выходной указатель проверяется на запись всех восьми байтов и время жизни объекта. Разрешён любой допустимый x64 IRQL. Кооперативный режим продвигает время только на существующих границах планирования; режим по инструкциям сохраняет настроенный отсчёт. Чтение не создаёт вторые часы и само не продвигает время. Это детерминированный профиль, а не измерение оборудования хоста. Независимо скомпилированный тест проверяет статическую/динамическую идентичность, частоту и монотонность по предпочтительным и перемещённым адресам на нативных CPU-бэкендах.

`RDTSC` и `RDTSCP` читают те же часы планировщика с частотой 10 МГц, что и `KeQueryPerformanceCounter`. `RDTSCP` возвращает ноль в ECX для единственного моделируемого процессора. Верхние половины EAX/EDX и ECX для RDTSCP обнуляются; остальные регистры и флаги сохраняются. В кооперативном режиме чтение не продвигает время. При явном планировании инструкций время читается после учёта самой инструкции независимо от кванта. Переполнение останавливает выполнение до записи результатов; бюджеты инструкций и остановки наблюдателя действуют. Профиль не измеряет частоту TSC и не раскрывает идентификатор процессора хоста. Доступ к MSR, RDPMC и другие немоделируемые запросы CPU остаются неподдерживаемыми.

Необязательное поле `cpuid` объявляет до 64 результатов запросов CPU. Каждая запись требует беззнаковых 32-битных целых `leaf`, `eax`, `ebx`, `ecx`, `edx`. Необязательный `subleaf` ограничивает входной ECX; без него подходят все подлистья этого leaf. Повторы и пересечения отвергаются до исполнения. CPUID использует младшие 32 бита EAX/ECX, расширяет четыре результата нулями и сохраняет флаги и остальные регистры. Необъявленный запрос останавливается с диагностикой leaf/subleaf до публикации результата. `configuration.cpuid` сохраняет объявления. Эти явные входные данные среды не запрашивают хост и не гарантируют поддержку инструкций. Их использование сохраняет зависимость UNPACK драйвера и диагностику явных снимков.

Чтение часов через `KeQueryPerformanceCounter`, `RDTSC` или `RDTSCP` сохраняет явную зависимость восстановления драйвера. Для захваченных значений счётчика и частоты нет контракта привязки к новой среде ядра. Восстановление по умолчанию возвращает `unsupported_state`; `snapshot_only` сохраняет диагностику.

`KernelModuleImages` строит читаемые заголовки PE и таблицы экспорта из `KernelExportRegistry`; статические импорты, динамический поиск и перечисление модулей используют одни адреса. Код поставщиков остаётся непрозрачным, а список описывает модель, а не ядро хоста. Оба выхода проверяются до записи, включая срок жизни пула и перекрытия. Nt требует известный previous-mode ядра; Zw использует контракт ядра. Полный запрос сохраняет явную зависимость восстановления даже после освобождения буфера; указатели на образы поставщиков также учитываются как заимствованное состояние. `KernelExportTests.cpp` проверяет PE, права, поля ABI, отказ в записи и зависимости; оригинальный скомпилированный тест обходит экспорт на процессорных бэкендах.
