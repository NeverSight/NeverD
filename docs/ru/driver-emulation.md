# Эмуляция драйверов Windows

Необязательный эмулятор драйверов NeverD выполняет точку входа PE поддерживаемого драйвера x64 WDM и, при необходимости, явно заданный сценарий последовательных запросов перед выгрузкой драйвера. Для выполнения инструкций используется Unicorn, а для окружения Windows — собственная ограниченная модель NeverD. Драйвер не загружается в ядро хоста, а вызовы гостевых API не передаются службам ОС хоста.

## Сборка и запуск

Функция включается явно и не зависит от `BUILD_TESTING`:

```bash
cmake -S . -B build-release -G Ninja \
  -DCMAKE_BUILD_TYPE=Release \
  -DNEVERD_ENABLE_DRIVER_EMULATION=ON
cmake --build build-release --target neverd --parallel 4
build-release/bin/neverd emulate-driver path/to/driver.sys \
  --instruction-limit 100000 > driver-report.json
```

Отчёт всегда выводится в stdout в формате JSON; диагностика запросов и настройки направляется в stderr. Ограничения по умолчанию: 100000 гостевых инструкций, 64 MiB гостевой памяти, 10000 записанных событий и 5000 миллисекунд. Лимит инструкций должен быть положительным. При исчерпании бюджета выполнение останавливается с сохранением частичных наблюдений; API выделения памяти сохраняют свои контракты возврата при нехватке ресурсов, включая описанный ниже NULL для отображений MMIO.

| Код завершения | Значение |
|----------------|----------|
| `0` | Инициализация и все запрошенные завершённые операции выполнены успешно |
| `1` | Неверные входные данные/параметры, ошибка настройки или функция отключена при сборке |
| `2` | Инициализация или завершённый запрос вернули `NTSTATUS` ошибки |
| `3` | Выполнение остановилось до завершения сценария, например из-за неподдерживаемого API, ошибки доступа или лимита бюджета |

Возвращённый статус ошибки также является завершённым наблюдением данной операции. Успешный возврат описывает только этот запуск в модели; он не доказывает работоспособность драйвера в Windows.

## Совместимость драйверов

Совместимость определяется выполняемым путём кода и его зависимостями, а не расширением `.sys`. Текущие подтверждения приёмки охватывают самостоятельно написанные freestanding fixture и пути buffered, in-direct и out-direct примера Microsoft SIOCTL WDM, включая сборку с отладочным журналом, а также прямые операции чтения и записи публичного примера Zero Павла Йосифовича. Это не подтверждает совместимость с произвольными сторонними драйверами.

| Класс драйвера или требование | Текущий объём поддержки | Недостающее окружение |
|-------------------------------|-------------------------|-----------------------|
| Программный x64 WDM-драйвер, использующий перечисленные API | Ограниченная инициализация x64 WDM, последовательные buffered/direct запросы, рабочие элементы, таймеры, DPC, события и ожидания, отчёты и ограничения | Для каждого дополнительного выполняемого API нужна определённая модель |
| `METHOD_BUFFERED` IOCTL | Последовательный buffered/direct I/O с завершением рабочим элементом или DPC | Только перечисленные ниже API; без параллельной подачи публичных сценариев и общей отмены запросов WDM |
| `METHOD_IN_DIRECT`, `METHOD_OUT_DIRECT` | MDL запросов, системные отображения и общие PFN модели только для чтения | Пользовательские отображения и другие интерфейсы DMA |
| MDL, выделенные драйвером | Самостоятельные дескрипторы непагируемого пула или одного пользовательского выделения с общими физическими страницами | Без привязки к IRP, цепочек MDL и произвольных процессов |
| READ/WRITE | Последовательный buffered/direct/neither I/O с завершением рабочим элементом или DPC | Только перечисленные API; без параллельных IRP, общей отмены WDM и неявной позиции файла |
| WDM `METHOD_NEITHER` | Раздельные пользовательские буферы, проверки доступа, MDL, синтетические ID заявителей, отзыв VA или выход после диспетчеризации и ограниченная отмена | Без общего присоединения процессов и произвольных отображений или повторных отображений |
| Драйвер KMDF 1.33 без PnP | Привязка, объекты/контексты, именованные управляющие устройства, последовательные очереди по умолчанию и буферизованные/прямые запросы с исполняемыми обратными вызовами | Нет устройств PnP, общего планирования очередей, расширений классов и UMDF |
| Драйвер шины/функции/фильтра PnP | Явные PDO без ресурсов или с банками регистров, гостевой AddDevice и восемь основных minor-функций жизненного цикла PnP | Другие операции PnP, общая политика питания, прочее оборудование/ресурсы и KMDF PnP |
| Драйверы хранения, сети, дисплея, файловой системы и минифильтры | Контракты подсистем не поддерживаются | Фреймворки портов/классов/минипортов, NDIS/WFP, графические службы или службы файловой системы |
| Рабочие элементы, таймеры, DPC, события и ожидания | Текущий IRQL равен `PASSIVE_LEVEL` для диспетчеризации и рабочих элементов, `DISPATCH_LEVEL` для DPC | Только перечисленные ниже API; без параллельной подачи публичных сценариев и общей отмены запросов WDM |
| Драйвер с обратными вызовами процессов/потоков, дескрипторами, операциями с реестром/файлами или поиском модулей ядра | Перечисленные операции реестра поддерживаются для явно настроенного дерева; остальные операции не поддерживаются | Общий диспетчер объектов, операции с файлами, состояние системы и источники обратных вызовов/событий |
| Драйвер оборудования, DMA, PCI, прерываний или виртуализации | Явные банки, MMIO, исключительные latched-прерывания и когерентный DMA common/SG/channel | Другие модели устройств, произвольная физическая RAM, PCI, порты, разделяемые/уровневые/MSI-прерывания, другие интерфейсы DMA и привилегированное состояние CPU |
| Драйвер Windows x86 или ARM64 | Отклоняется | Загрузка, ABI и модель выполнения для соответствующей архитектуры |
| x64 CFG | Проверенные таблицы целей и вызовы check/dispatch; неактивная инструментация сохраняет гостевые резервные функции | XFG, подавление экспортов, немоделируемая конфигурация загрузки и TLS отклоняются |

Неиспользуемый неподдерживаемый импорт может оставаться связанным. Достижение неподдерживаемой операции останавливает выполнение с диагностикой и накопленными наблюдениями. Один лишь успешный DriverEntry не доказывает поддержку последующей диспетчеризации, оборудования или путей фреймворка. Таблица API ниже определяет поддерживаемое подмножество.

## Контракт выполнения

Профиль моделирует жизненный цикл x64 WDM на CPU0 с детерминированным кооперативным планированием. Выполнение начинается в точке входа PE; при наличии сохраняется обёртка входа, созданная компилятором. Для успешной инициализации DriverEntry должен вернуть `STATUS_SUCCESS`. Ненулевой успешный статус или статус pending останавливает выполнение как неподдерживаемый контракт инициализации. Статус ошибки сохраняется как завершённый результат инициализации. Все объекты, строки, стеки, указатели на функции и выделенные области находятся в гостевой памяти. Модель предоставляет `DRIVER_OBJECT` и путь реестра для настроенного имени службы (по умолчанию `NeverDDriver`). Адаптер использует виртуальный режим TLB Unicorn, сохраняющий гостевые виртуальные адреса, включая канонические высокие адреса ядра, без создания таблиц страниц Windows. Начальное значение RFLAGS — `0x202`; профиль программного устройства использует фиксированную строку кэша размером 64 байта. Это явно заданные свойства данного сценария выполнения.
Встроенное чтение x64 CR8 наблюдает тот же `PASSIVE_LEVEL` / `DISPATCH_LEVEL`; запись CR8 и остальные операции с управляющими регистрами по-прежнему не поддерживаются.

Неизвестные импорты связываются с отложенными ловушками. Неиспользуемый импорт не мешает выполнению; выполнение его thunk или чтение немоделируемого экспортируемого значения данных приводит к `unsupported_api`. Неподдерживаемые эффекты окружения CPU также вызывают явную остановку. NeverD не заменяет нереализованные вызовы успешными значениями. Некорректные образы или неподдерживаемые требования загрузки вызывают ошибку до начала выполнения.

Элементы `DelayedWorkQueue` исполняются на `PASSIVE_LEVEL`, гостевые DPC — на `DISPATCH_LEVEL` с четырьмя предусмотренными аргументами. CPU0 использует детерминированное кооперативное планирование на границах возврата вызовов и блокирующего ожидания. Относительные, абсолютные и периодические таймеры используют виртуальное время; если ни один кадр не готов, оно продвигается до ближайшего срока таймера, ожидания или отмены. События/таймеры уведомления и синхронизации сохраняют разные правила потребления сигнала. У каждого вызова свой гостевой стек; несколько заблокированных кадров сохраняют локальные переменные и полные контексты CPU при общей памяти. Win64 передаёт первые четыре аргумента в регистрах, остальные в стеке. Запросы последовательны: диспетчеризация, пометившая IRP ожидающим, должна вернуть `STATUS_PENDING` и завершить его до следующего запроса. Без доступного источника ожидающий запрос или бесконечное ожидание останавливается с `model_error` из-за зависания. Бюджеты инструкций, памяти, наблюдений и реального времени общие.

Ограниченная модель не обеспечивает полную асинхронность Windows. Не поддерживаются alertable-ожидания и ожидания пользовательского режима, APC, общая отмена запросов WDM, параллельные публичные сценарии, API KMDF для пользовательских буферов `METHOD_NEITHER`, UMDF, устройства PnP KMDF и общее планирование очередей, полный PnP/питание, произвольное оборудование, другие интерфейсы DMA и другие режимы прерываний. Инициализация выполняет явно поставленные в очередь вызовы без неявного создания запросов или выгрузки.

Рабочий элемент извлекается из очереди до начала обратного вызова, поэтому тот может освободить собственный элемент. Освобождение элемента в очереди, повторная постановка, устаревшие объекты и адреса вызова вне исполняемой гостевой памяти явно отклоняются. Ссылка на устройство удерживается до возврата. Выгрузка требует освободить все рабочие элементы и завершить очередь. Контексты CPU сохраняют общие регистры, SIMD, FPU и управляющее состояние; гостевая память остаётся общей, а восстановление контекста не позволяет возобновить CPU после сбоя.
Удаление откладывается, пока остаются файловые объекты или ссылки рабочих элементов в очереди/исполнении. При исчерпании арены объектов выделение рабочего элемента возвращает NULL.

Образы используют предпочтительный базовый адрес, если сценарий не задаёт допустимый адрес перемещения; это должны быть исполняемые файлы PE32+ x64 с подсистемой native. Импорты могут предоставляться `ntoskrnl.exe`, `ntkrnlmp.exe` или `WDFLDR.SYS`. Загрузчик выполнения поддерживает проверенные базовые релокации x64 `DIR64` и ограниченную конфигурацию загрузки security cookie, который инициализируется детерминированным гостевым значением до запуска обёртки входа. Другие немоделируемые поля конфигурации загрузки, TLS, отложенные/связанные импорты, импорты по ordinal и managed-образы отклоняются. Образы также должны пройти строгую проверку диапазонов и выравнивания.

Активный Control Flow Guard (CFG) проверяет флаги PE, слоты указателей и отсортированные исполняемые цели. Обработчики check/dispatch допускают только объявленные входы образа или зарегистрированные API-thunk, сохраняют состояние вызова Win64 и отклоняют остальные цели. Инструментация без активного CFG сохраняет исходные гостевые резервные указатели. Активный XFG, подавление экспортов и другие немоделируемые политики отклоняются; исполняемая память сама по себе не делает адрес допустимой целью.

Стек WDM может содержать несколько устройств одного гостевого драйвера. `IoAttachDeviceToDeviceStack` присоединяет отдельное исходное устройство над текущей вершиной целевого стека и возвращает прежнюю вершину. Он задаёт `StackSize` и `AlignmentRequirement`, не меняя список `NextDevice` и не копируя флаги буферизации. `IoDetachDevice` принимает сохранённое нижнее устройство и требует `PASSIVE_LEVEL`; присоединение допускается до `DISPATCH_LEVEL`. Открытие именованного нижнего устройства направляет запрос текущей вершине, но `FILE_OBJECT.DeviceObject` и отчёт сохраняют именованную идентичность. READ/WRITE использует флаги выбранной вершины. Сохранённый маршрут удерживает все устройства до возврата диспетчеризации, в том числе после отсоединения/удаления; внутренние ссылки не увеличивают `ReferenceCount`, считающий открытые дескрипторы.

`IofCallDriver` и вспомогательный `IoCallDriver` вызывают точно указанное устройство сохранённого маршрута. Настоящие inline-функции `IoCopyCurrentIrpStackLocationToNext`, `IoSkipCurrentIrpStackLocation` и `IoSetCompletionRoutine` работают с исходным гостевым IRP; проверяются курсор, число позиций и управляющие флаги. Нижняя диспетчеризация возвращает свой фактический статус отдельно от `IoStatus` и результата процедуры завершения. Разворачивание продвигает курсор, выбирает callbacks по успеху/ошибке/отмене и передаёт pending вверх. Вызванная процедура завершения отвечает за эту передачу, включая передачу после прежнего возврата `STATUS_PENDING`. `STATUS_MORE_PROCESSING_REQUIRED` останавливает разворачивание, сохраняя IRP, MDL и буферы; последующее завершение возобновляет его. Вложенное завершение требует внешнего результата остановки; окончательное освобождение выполняется один раз. Продолжения с владельцем-подсистемой сохраняют вложенные кадры WDM/WDF и унаследованный IRQL. Каждая использованная нижняя позиция стека обнуляется перед верхним callback завершения.

Общая политика питания, IRP, выделенные драйвером, остальные minor-функции PnP и прочие модели оборудования/ресурсов не поддерживаются. Присоединение/перенаправление WDF, присоединение к стеку с активными файлами или callbacks, отсоединение среднего слоя, смена основной функции и цели вне сохранённого маршрута явно отклоняются. Необязательный оригинальный `driver_wdm_stack.c` с настоящим WDK задаётся через `NEVERD_WDM_STACK_FIXTURE` и `NEVERD_WDM_STACK_CFG_FIXTURE`. Нативные тесты и C API/CLI включают перемещение базы; отсутствие артефактов явно отмечается пропуском. Свидетельства выполнения ограничены Linux.

Сценарий может явно задать до 64 `pnp_devices`. Каждый элемент требует `id`, `bus: "resource_free"` / `bus: "register_bank"`, `initial_device_power: "D0"` и `initial_system_power: "working"`; пропущенные факты не угадываются. ID — регистрозависимая ASCII-строка длиной 1–64 байта, начинающаяся с буквы/цифры и далее содержащая только буквы, цифры, `_`, `-`, `.`. Обычный запрос может использовать настроенный `device_id` вместо `device`, но не оба поля. Для `kind: "pnp"` обязательны `device_id`, `minor`, `bus_completion`. Поддерживаются `start`, `query_remove`, `cancel_remove`, `remove`, `query_stop`, `stop`, `cancel_stop` и `surprise_removal`. Обязательный `bus_completion.status` — 32-битное целое или шестнадцатеричная строка; необязательный `delay_100ns` — неотрицательное целое до INT64_MAX, отсчитываемое от фактического получения провайдером. Конечный статус не может быть `STATUS_PENDING`; stop/cancel-stop/surprise-removal/cancel-remove/remove требуют ровно `STATUS_SUCCESS` (0). Файловые поля, передача и отмена для PnP отклоняются даже при нулевых значениях. C++ API использует ту же предварительную проверку.

{
  "pnp_devices": [
    {"id": "sensor0", "bus": "resource_free", "initial_device_power": "D0", "initial_system_power": "working"}
  ],
  "requests": [
    {"kind": "pnp", "device_id": "sensor0", "minor": "start", "bus_completion": {"status": "0x0", "delay_100ns": 10}},
    {"kind": "pnp", "device_id": "sensor0", "minor": "query_stop", "bus_completion": {"status": "0x0"}},
    {"kind": "pnp", "device_id": "sensor0", "minor": "cancel_stop", "bus_completion": {"status": "0x0"}},
    {"kind": "pnp", "device_id": "sensor0", "minor": "query_stop", "bus_completion": {"status": "0x0"}},
    {"kind": "pnp", "device_id": "sensor0", "minor": "stop", "bus_completion": {"status": "0x0"}},
    {"kind": "pnp", "device_id": "sensor0", "minor": "start", "bus_completion": {"status": "0x0"}},
    {"kind": "pnp", "device_id": "sensor0", "minor": "query_remove", "bus_completion": {"status": "0x0"}},
    {"kind": "pnp", "device_id": "sensor0", "minor": "cancel_remove", "bus_completion": {"status": "0x0"}},
    {"kind": "pnp", "device_id": "sensor0", "minor": "surprise_removal", "bus_completion": {"status": "0x0"}},

После успешного DriverEntry для каждого заданного PDO один раз исполняется `AddDevice`. Провайдер владеет отдельным `DRIVER_OBJECT`; гость не может удалять или подменять его объекты. PnP IRP имеют `KernelMode`, не связаны с файлом, получают ресурсы согласно заданной шине и начинаются с `STATUS_NOT_SUPPORTED`. Ответ шины используется только при фактической передаче в этот PDO; задержка использует общие виртуальные часы и существующие продолжения завершения. Окончательное верхнее завершение фиксирует или откатывает состояние независимо от статуса шины. Обычное удаление из Started требует успешного query, закрытых файлов, завершённых прежних запросов и гостевого отсоединения/удаления. Чистая ошибка AddDevice освобождает только провайдера; утечки новых гостевых устройств, даже отсоединённых, вызывают `model_error`. Перед unload все провайдеры должны отсутствовать. Другие операции PnP, общая политика питания, прочее оборудование/ресурсы и KMDF PnP не входят в этот набор. Успех PnP требует фактического завершения провайдера; ранняя верхняя ошибка START/QUERY_STOP/QUERY_REMOVE может оставить наблюдения шины null. Идентичность жизненного цикла устройства/файла сохраняется после отсоединения.

Исходные настройки сохраняются в `configuration.pnp_devices`. Наблюдаемые `pnp_devices` содержат `id`, `pdo`, nullable `add_device_status`, текущее `attached`, `pnp_state`, `provider_present`; после удаления `attached` равно false. Фаза AddDevice — `add_device:<ID>`; ошибки влияют на `scenario_success`, не заменяя `nt_status` DriverEntry. Каждый запрос получает nullable `device_id` и `pnp`; у PnP `file` равен null. Объект `pnp` содержит `minor`, `state_before`, `state_after`, nullable `bus_status`, `bus_received_at_100ns`, `bus_completed_at_100ns`. Настроенный статус становится наблюдением только при фактическом завершении на шине; время получения независимо. Типы прежних полей не меняются.

Обычные CREATE/READ/WRITE/IOCTL/CLEANUP/CLOSE поступают в реальный гостевой dispatch, пока устройство существует вне Removing/Removed. Модель не создаёт отказ по состоянию Stopped, StopPending, RemovePending или питания: драйвер сам завершает программный I/O, отклоняет или удерживает запрос. Публичный исполнитель последователен. Удерживаемая IRP без доступного сейчас источника завершения не может дождаться последующего start/cleanup сценария и останавливается с зависшим `model_error`. Закрытие файлов и завершение предыдущих запросов до Remove — ограничения профиля. Конечный `STATUS_RESOURCE_REQUIREMENTS_CHANGED` (0x119) для `query_stop` требует немоделируемого повторного запроса ресурсов и отклоняется как в preflight, так и при гостевом завершении; см. [контракт Microsoft QUERY_STOP](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/irp-mn-query-stop-device). Stop/restart и surprise-removal не добавляют общее переназначение ресурсов, общую политику питания или KMDF PnP.

PnP без ресурсов использует оригинальный `driver_wdm_pnp.c` с настоящим WDK, необязательные `NEVERD_WDM_PNP_FIXTURE`/`NEVERD_WDM_PNP_CFG_FIXTURE` и нативные тесты/C API/CLI. Отсутствие артефактов явно пропускается; выполнение проверено только на Linux.

WDM remove-lock исполняет реальные экспорты `IoInitializeRemoveLockEx`, `IoAcquireRemoveLockEx`, `IoReleaseRemoveLockEx` и `IoReleaseRemoveLockAndWaitEx`; имена WDK без Ex являются макросами. Владелец — точный DEVICE_OBJECT, расширение которого содержит всю выровненную область, независимо от состояния PDO и вида Tag. Инициализация разрешена до присоединения. Поддерживаются retail 32/DBG 120 байт с совпадающим отдельным аргументом размера; вся зарегистрированная область непрозрачна. NULL и повторные Tags учитываются отдельно для каждого замка и не разыменовываются, поэтому release после завершения IRP допустим. Инициализация/AndWait требуют `PASSIVE_LEVEL`, acquire/release допускают `DISPATCH_LEVEL`.

AndWait закрывает приём, снимает одно совпавшее получение и приостанавливает настоящий гостевой кадр до освобождения остальных. Последующие acquire возвращают `STATUS_DELETE_PENDING` без новой обязанности release. Последний release фиксирует готовность до возврата callback; worker может освободить замок и ждать событие от продолжившего REMOVE. Нет синтетического callback, таймаута или успеха без производителя. Нужен связанный маршрут активного REMOVE с владельцем и фактический приём провайдером (`bus_received_at_100ns` допускает ноль), но не нижнее завершение. Очередь нижнего драйвера до приёма провайдером вне профиля; это не полная проверка OutsideRemoveDevice/Driver Verifier. Перед REMOVE всё ещё нужны закрытые файлы и завершённые прежние запросы, но callbacks, освобождающие замки, могут оставаться. Маршрут удерживается через ожидание, отсоединение/удаление и нижний pending до возврата оставшихся кадров.

Неизвестная/несовпадающая область, release без получения, повторный drain, переинициализация и удаление расширения с получениями или непотреблённым drain-ожиданием отклоняются до изменений. Чистый отказ AddDevice может удалить инициализированный неиспользованный замок. Замок не заменяет реальные ссылки устройства/worker; регистрация исчезает только при физическом освобождении расширения. Debug-метаданные не включают таймауты/high-water Verifier. Подлинный `driver_wdm_remove_lock.c` имеет варианты `NEVERD_WDM_REMOVE_LOCK_FIXTURE`/`NEVERD_WDM_REMOVE_LOCK_CFG_FIXTURE`/`NEVERD_WDM_REMOVE_LOCK_DBG_FIXTURE`/`NEVERD_WDM_REMOVE_LOCK_DBG_CFG_FIXTURE`. Отсутствие явно пропускается, native и C API/CLI доказаны только на Linux, без заявления о полном менеджере удаления или общем параллельном дренировании I/O.

Синтетическая шина `bus: "register_bank"` добавляет PDO явно заданные фиксированные ресурсы памяти. При наличии массив `resources` содержит `id`, `raw_start`, `translated_start`, `length` и `registers`; каждому регистру нужны `offset`, `width`, `access` (`read_only` или `read_write`) и начальное `value`. Общий контракт C++/JSON определён в `DriverResources.h` / `DriverResources.def`. ID ресурсов подчиняются ограниченным правилам ASCII-идентификаторов и уникальны внутри PDO. Допускаются 8 ресурсов на PDO / 32 суммарно, 256 регистров на ресурс / 4096 суммарно и 1–1048576 байт на ресурс. Поддерживаются только точные естественно выровненные обращения шириной 1/2/4 байта; значение должно помещаться в эту ширину. Оба физических диапазона должны исключать переполнение; исходные диапазоны не пересекаются внутри PDO, преобразованные — глобально. Пустой `registers` явно делает весь банк недоступным. Адреса и начальные значения являются декларациями, а не оборудованием хоста или неявно обнулённой памятью. `resource_free` по-прежнему не содержит ресурсов и передаёт нулевые указатели START.

START получает отдельные исходные и преобразованные выделения `CM_RESOURCE_LIST` только для чтения, с соответствующими упорядоченными дескрипторами Memory: один полный дескриптор, интерфейс Internal, шина 0, версия/ревизия 1, совместное использование DeviceExclusive и флаги диапазона READ_WRITE. RO отдельных регистров независимо от этих флагов. Успешное нижнее START делает назначение доступным до верхних callbacks; каждый START из NotStarted/Stopped создаёт новое поколение с тем же фиксированным назначением. Значения инициализируются один раз на PDO и переживают unmap, STOP и повторный запуск. При неудачном START и успешном STOP/REMOVE драйвер обязан снять отображения до терминального завершения IRP; скрытая очистка не выполняется. Внезапное удаление сразу запрещает новые отображения и обращения к регистрам, но позволяет снять существующие отображения. Фактическое успешное завершение SET устройства у провайдера меняет физическую доступность: D3 запрещает обращения, D0 разрешает их только при доступном назначении. В D3 можно создавать отображения без доступа к регистрам; смена питания не удаляет отображения и не сбрасывает значения.

`MmMapIoSpace` поддерживает NonCached, а `MmMapIoSpaceEx` — PAGE_NOCACHE вместе с PAGE_READONLY или PAGE_READWRITE. Обе функции принимают только объявленный преобразованный поддиапазон одного назначения, сохраняя смещение внутри страницы. Алиасы разделяют один банк, имеют независимые разрешения и требуют точных исходных базы и длины для `MmUnmapIoSpace`. Исчерпание отображений, окна или заданного бюджета памяти возвращает NULL; сбои backend остаются явными ошибками. Снятый виртуальный адрес не становится доступным через последующее отображение. Реальные скалярные и REP-инструкции проходят проверки MMIO CPU; пробелы, неверная ширина, невыровненность, запись RO, переход между отображениями и исполнение отклоняются до эффектов регистров. Обращения к памяти через моделируемые API также должны укладываться в одну выровненную транзакцию размером 1/2/4 байта; более крупные диапазоны отклоняются, а не разбиваются на обращения к регистрам. Произвольная физическая RAM, перераспределение ресурсов, порты, другие режимы прерываний, другие интерфейсы DMA и общее поведение оборудования не реализованы.

Исполняемый [сценарий банка регистров](../examples/driver-register-bank-scenario.json) использует оригинальный `driver_wdm_resources.c`, собранный настоящим WDK, через `NEVERD_WDM_RESOURCE_FIXTURE` / `NEVERD_WDM_RESOURCE_CFG_FIXTURE`. Он выполняет 14 запросов с отложенным START, файловым I/O, STOP, перезапуском и удалением и наблюдает сохраняемые значения через IOCTL драйвера. `configuration.pnp_devices[].resources` сохраняет исходные данные с шестнадцатеричными физическими адресами без потери точности; это не второй отчёт о состоянии банка. C API и Python используют прежний `scenario_json` и неизменённый `neverd_driver_options_v1`. Отсутствующие настоящие артефакты явно пропускаются; данные исполнения получены только на Linux.

Тот же провайдер `register_bank` может объявлять `interrupts` отдельно или вместе с `resources`; хотя бы один список должен быть непустым. `resource_free` отклоняет явно заданное поле `interrupts`, включая `[]`. Каждое прерывание требует `id`, `raw_vector`, `raw_level`, `raw_affinity`, `translated_vector`, `translated_level`, `translated_affinity`, `mode: "latched"` и `share: "device_exclusive"`. `DriverInterrupts.h` / `DriverInterrupts.def` определяют типы, написания и ограничения: 8 прерываний на PDO / 32 всего, ограниченные ASCII ID, уникальные внутри PDO, глобально исключительные преобразованные векторы, исходный уровень 0–65535 и преобразованный DIRQL 3–12. Векторы сохраняют все 32 бита без догадок о связи вектора и IRQL. Обе маски affinity должны равняться 1: CPU0 и группа0 — явные факты провайдера. Исходные и преобразованные значения независимы. Дескрипторы памяти сохраняют порядок, за ними идут упорядоченные дескрипторы прерываний в той же `CM_RESOURCE_LIST`; у прерываний тип 2, совместное использование DeviceExclusive и флаги LATCHED. Этот синтетический профиль срабатывания по фронту не моделирует разделяемые уровневые линии PCI.

Запросы READ/WRITE/IOCTL могут объявлять `interrupt_events`, каждый с явными `after_100ns`, `device_id` и `interrupt_id`; остальные виды отклоняют поле даже пустым. Допускается не более 64 событий на запрос / 1024 всего, задержка неотрицательная до INT64_MAX. Успешная подача запроса задаёт начало отсчёта и захватывает уже подключённое прерывание вместе с поколением ресурсов PDO. События — независимые внешние импульсы линии: завершение исходного IRP их не отменяет, записи регистров не подразумевают разрешение, состояние или подтверждение. Время движется только в простое; наступившие события исполняются на следующей поддерживаемой границе callback, поэтому `after_100ns: 0` не обещает вытеснение инструкций или доставку до первой гостевой инструкции. Вместимость производителей одного момента проверяется совместно; публикация аппаратного состояния предшествует допустимости, ISR — DPC/workers. Потерянное подключение, устаревшее/недоступное поколение или физическое D3 фиксируют `undelivered_reason` и останавливают выполнение с `model_error`; событие не перепривязывается и не задерживается молча.

`IoConnectInterrupt` использует все одиннадцать настоящих аргументов и точное преобразованное назначение. `IoConnectInterruptEx` поддерживает FullySpecified (1), LineBased (2, одна назначенная линия явного PDO) и FullySpecifiedGroup (4, группа 0); `IoDisconnectInterruptEx` требует соответствующую версию/контекст. Регистрация и отключение требуют PASSIVE_LEVEL. Поддерживаются только собственная блокировка прерывания, исключительный режим latched, CPU0/группа0 и отсутствие сохранения состояния floating point. IRQL синхронизации должен совпадать с назначенным DIRQL; ноль у LineBased выбирает этот уровень. `KINTERRUPT` непрозрачен, его адрес никогда не используется повторно. Настоящий ISR получает `(Interrupt, ServiceContext)` и возвращает BOOLEAN из AL; `FALSE` означает невостребованное прерывание, а не ошибку NTSTATUS. `KeSynchronizeExecution` исполняет настоящий callback одного аргумента под той же блокировкой на DIRQL и возвращает BOOLEAN, восстанавливая IRQL/CR8 вызывающего. `KeAcquireInterruptSpinLock` / `KeReleaseInterruptSpinLock` проверяют нерекурсивное владение, исходное исполнение и сохранённый IRQL; оставленный lock не может пережить возврат callback. Ожидания в прерываниях, предоставленные вызывающим общие блокировки, разделяемые/уровневые/MSI/пассивные прерывания и вытеснение на уровне инструкций не поддерживаются. Неудачный START и успешные STOP/REMOVE требуют отключения до терминального завершения; верхние callbacks могут сначала освободить ресурсы, а отключение никогда не удаляет поставленный в очередь DPC молча.

Отчёты разделяют объявления и наблюдения. `configuration.pnp_devices[].interrupts` сохраняет ресурсы, `configuration.interrupt_events` разворачивает входные события с индексами от нуля `source_request_index` (индекс настроенного запроса) и `event_index`. Корневые строки `interrupts` добавляют `device_id`, `interrupt_id`, `epoch`, абсолютное `due_at_100ns` и допускающие null поля `occurred_at_100ns`, `delivered_at_100ns`, `returned_at_100ns`, `interrupt_object`, `return_value`, `claimed`, `undelivered_reason`. `claimed` определяется только фактическим младшим байтом возврата; временные метки — наблюдения, а не вымышленные результаты callbacks. Для `scenario_success` каждое настроенное событие должно вернуться без ошибки недоставки; невостребованный ISR допустим. Эффекты DPC видны через реальные завершения запросов, вызовы API и сообщения. Исполняемый [сценарий прерываний](../examples/driver-interrupt-scenario.json) использует оригинальный `driver_wdm_interrupts.c`, собранный настоящим WDK, и необязательные `NEVERD_WDM_INTERRUPT_FIXTURE` / `NEVERD_WDM_INTERRUPT_CFG_FIXTURE`: семь запросов включают отложенный START, pending IOCTL с завершением ISR→DPC, cleanup/close файла и удаление. Граница C/Python `scenario_json` и layout `neverd_driver_options_v1` не меняются. Отсутствующие настоящие артефакты явно пропускаются; свидетельства исполнения ограничены Linux.

`DriverDMA.h` / `DriverDMA.def` добавляют необязательный объект `dma` в PDO `register_bank` наряду с назначениями памяти/прерываний; один DMA не заменяет эти ресурсы. Все семь полей задаются явно: `address_bits` (32 или 64), `maximum_length` (1–1048576 байт), `map_registers` (1–256), `alignment` (степень двойки от 1 до 4096), `logical_base` (ненулевой, выровненный по странице), `logical_length` (кратно странице, 4096–1073741824 байт) и логическое `scatter_gather`. Окно не должно переполняться и должно укладываться в разрядность адреса. У каждого PDO независимый логический домен; одинаковые адреса разных устройств не образуют алиасы. Все переведённые MMIO-ресурсы обязаны обходить зарезервированную RAM модели `[0x1000000000, 0x1000100000)`, даже без настройки DMA. Это факты о когерентном синтетическом ведущем шины, а не физической памяти хоста или устройстве PCI.

`IoGetDmaAdapter` принимает исторические поля `DEVICE_DESCRIPTION` версии 0/1 для Internal bus master и публикует `DMA_ADAPTER` версии один с настоящей 104-байтовой таблицей `DMA_OPERATIONS`. Запросы версий 2/3 возвращают NULL, не читая современное окончание описания. Каждый косвенный метод привязан к конкретному живому адаптеру независимо от импортов ядра. Реализованы `AllocateCommonBuffer`, `FreeCommonBuffer`, `GetDmaAlignment`, `GetScatterGatherList`, `PutScatterGatherList`, `PutDmaAdapter`, `AllocateAdapterChannel`, `MapTransfer`, `FlushAdapterBuffers` и `FreeMapRegisters`. `FreeAdapterChannel` и `ReadDmaCounter` остаются именованными ловушками: подчинённого/системного DMA-контроллера в профиле нет. Выделение/освобождение common buffer и запрос выравнивания требуют PASSIVE_LEVEL; Get/PutScatterGatherList требуют DISPATCH_LEVEL, освобождение адаптера допускает IRQL до DISPATCH_LEVEL. x64 игнорирует `CacheEnabled`. Неподдерживаемые версии, несовместимые объявленные возможности и документированная нехватка ресурсов возвращают NULL; некорректный или немоделируемый выбор интерфейса и сбои backend остаются явными ошибками.

`KernelPhysicalMemory` назначает существующей RAM не более 256 физических страниц модели по 4096 байт. Виртуальные адреса CPU, идентичность физических страниц и логические адреса устройства различаются. Массивы PFN построенных MDL открывают общие идентификаторы только для чтения; у непостроенных дескрипторов нет пригодных PFN. Небольшие соседние выделения могут иметь общий PFN, сохраняя отдельные диапазоны байтов и сроки жизни. Common buffer, пул и буферы запросов используют те же байты, которыми уже владеет `GuestMemory`, без второй копии DMA. Живое SG-отображение фиксирует точный диапазон данных и дескриптор. Завершение, освобождение пула/MDL и удаление заранее отклоняют живые зависимости. Снятие отображения прямого MDL отзывает только системное отображение CPU; DMA сохраняет доступ к заблокированной памяти. `DmaWritable` отдельно хранит контракт блокировки для записи и права CPU: запись устройства требует прямого READ/OUT_DIRECT или доступной для записи невыгружаемой памяти; WRITE/IN_DIRECT не получают это право лишь из-за записываемого отображения CPU.

`GetScatterGatherList` проверяет CurrentVa/Length по исходному диапазону MDL и создаёт логические фрагменты страниц поверх существующей памяти. При доступных регистрах отображения настоящий четырёхаргументный void `AdapterListControl` выполняется внутри вызова до возврата API; иначе сохраняются данные/дескриптор и резервируется callback в FIFO данного PDO до освобождения ресурсов. В этом профиле нет владельца StartIo, поэтому второй аргумент IRP равен NULL. Возврат callback не освобождает отображение. `PutScatterGatherList` допустим внутри callback; после Put драйвер может завершить запрос и освободить последний адаптер, при этом продолжение callback и удержание устройства сохраняются до возврата. Освобождение common buffer требует исходных адаптера, длины, логического и CPU-адресов. Логические адреса не переиспользуются в течение сеанса, включая перезапуск. Ожидание ресурсов без реального производителя явно останавливается, не выдумывая завершение или срок. Пока живое SG-отображение передало данные во владение устройства, доступ CPU требует сначала Put; ожидающий регистров callback ещё не передал такое владение байтами.

`AllocateAdapterChannel` требует DISPATCH_LEVEL и резервирует непрозрачный ненулевой токен регистров отображения. Common buffer, списки SG и резервы каналов используют общую квоту и FIFO каждого PDO. Успех означает принятие настоящего немедленного или отложенного `AdapterControl`; превышение доступного числа возвращает `STATUS_INSUFFICIENT_RESOURCES` без callback. На гостевом устройстве допускается один незавершённый callback выделения; вызов AllocateAdapterChannel из AdapterControl запрещён, в том числе через вложенный callback. Четыре аргумента содержат реальный снимок `DEVICE_OBJECT.CurrentIrp` при регистрации. Именно это восьмибайтовое поле доступно гостю для записи; принимаются ноль или живой IRP, маршрут которого включает устройство. Очередь удерживает пакет до входа в callback, после чего тот может его завершить. StartIo по-прежнему не моделируется; неиспользуемый IRP отдельного SG callback остаётся NULL.

`AdapterControl` возвращает 32-битный `IO_ALLOCATION_ACTION`; старшие биты RAX игнорируются, действие не заменяет `STATUS_SUCCESS` у AllocateAdapterChannel. `DeallocateObject` освобождает неиспользованные или полностью обработанные flush регистры при возврате. `DeallocateObjectKeepRegisters` сохраняет их до вызова `FreeMapRegisters` с точными адаптером, токеном и первоначальным числом. `KeepObject` требует немоделируемого системного контроллера и явно отклоняется. Только что переданное выделение нельзя освободить как сохранённое до возврата его callback; другое ранее сохранённое выделение можно освободить при соблюдении его собственного контракта. Идентичность callback, сохранённые регистры и отображённые байты имеют отдельные сроки жизни; все они проверяются перед удалением адаптера или устройства.

`MapTransfer` и `FlushAdapterBuffers` допускают IRQL до DISPATCH_LEVEL; выделение канала и освобождение регистров требуют DISPATCH_LEVEL. MapTransfer принимает индекс относительно MDL, читает и обновляет настоящую длину ULONG и возвращает логический адрес по значению. Ограниченный SG-профиль возвращает один фрагмент физической страницы за вызов; последующие непрерывные индексы того же MDL и направления расширяют одну операцию. Без SG весь запрошенный диапазон отображается одним вызовом, если помещается в резерв, без сокращения длины. Первый вызов резервирует непереиспользуемое логическое окно размером с резерв регистров; другие выделения могут чередоваться, не пересекая его. Все фрагменты используют одно расширяемое закрепление физической памяти. Транзакция устройства может охватывать всю отображённую операцию, но доступ CPU, освобождение MDL и завершение с удалением закреплённой памяти блокируются до общего flush. Flush должен совпадать по начальному индексу, MDL, направлению и полной фактически отображённой длине. Он освобождает байты, сохраняя регистры для следующей операции с тем же токеном. Частичный flush, смешение MDL и другие схемы MapTransfer находятся вне профиля; они не объявляются недопустимыми на любой Windows.

`KeFlushIoBuffers` проверяет живой заблокированный/невыгружаемый MDL. Моделируемая платформа когерентна: ни одно значение ReadOperation или DmaOperation не требует отдельной копии кэша; вызов не снимает владение DMA и не заменяет FlushAdapterBuffers. [Сценарий канала](../examples/driver-dma-channel-scenario.json) исполняет оригинальный `driver_wdm_dma_channel.c`: два MapTransfer, одна транзакция через границу страниц, отдельно объявленные IRQ/DPC, общий flush и точное освобождение регистров. Настоящие normal/CFG-образы задаются через `NEVERD_WDM_DMA_CHANNEL_FIXTURE` и `NEVERD_WDM_DMA_CHANNEL_CFG_FIXTURE`.

Только READ/WRITE/IOCTL принимают `dma_events`. Каждое событие требует `after_100ns`, `device_id`, `logical_address`, `direction` и `length`; для `write_memory` также нужен `data_hex` точной длины, а `read_memory` запрещает это поле. Направление задаётся с точки зрения устройства. Ограничения: 64 события на запрос, 1024 всего, 16 MiB суммарных данных и 1 MiB на транзакцию; задержка от нуля до INT64_MAX. Подача фиксирует текущую назначенную эпоху PDO и исходное виртуальное время, но не требует отображения, которое предстоящая диспетчеризация ещё должна создать. При доставке разрешаются весь живой логический диапазон и направление, требуется физическое D0 и проверяются все байты до любых эффектов. Завершение исходного IRP не отменяет событие. Отсутствующие/освобождённые отображения, устаревшие эпохи, внезапное удаление или D3 фиксируют ошибку и останавливают выполнение; события не перепривязываются и не создают вымышленные прерывания, протокол регистров или завершения IRP. На одной границе планирования сначала публикуется оборудование провайдера, затем байты DMA, затем отдельно объявленные импульсы прерываний. Время остаётся кооперативным, без вытеснения на уровне инструкций.

Отчёты сохраняют `configuration.pnp_devices[].dma` и развёрнутый `configuration.dma_events`. Корневые строки `dma_transfers` содержат `source_request_index`, `event_index`, `device_id`, `epoch`, `logical_address`, `direction`, `length`, `due_at_100ns` и допускающие null поля `occurred_at_100ns`, `completed_at_100ns`, `mapping`, `adapter`, `failure_reason`; `data_hex` содержит реально переданные байты. Для `scenario_success` все объявленные транзакции должны завершиться без ошибок. [Сценарий DMA](../examples/driver-dma-scenario.json) использует оригинальный `driver_wdm_dma.c`, собранный настоящим WDK, и необязательные пути `NEVERD_WDM_DMA_FIXTURE` / `NEVERD_WDM_DMA_CFG_FIXTURE`: common buffer обрабатывается через настоящие указатели адаптера, завершение ISR→DPC объявлено отдельно. C/Python продолжают применять `scenario_json` без изменения `neverd_driver_options_v1`. Отсутствующие артефакты явно пропускаются; доказательства ограничены Linux. Подчинённые контроллеры, методы V2/V3, аппаратные механизмы дескрипторов, общий DMA KMDF и другие модели устройств не поддерживаются.

Запрос питания WDM синтетической шины использует `kind: "power"` и настроенный `device_id`. Обязательны `minor` (`query`/`set`), `power_type` (`device`/`system`), `power_state` (`D0`/`D3` либо `working`/`sleeping3`), `power_action` (`none`/`sleep`), явный 32-битный `system_context` (целое или hex-строка) и `bus_completion`. System Query к Working не поддерживается; поля файла, передачи и отмены запрещены. Весь `system_context` сохраняется как непрозрачный факт, без вывода родительского запроса, гибернации или быстрого запуска. Маршрут требует `DO_POWER_PAGABLE` без `DO_POWER_INRUSH`; диспетчеризация питания и `PoRequestPowerIrp` выполняются на `PASSIVE_LEVEL`. `PoCallDriver` передаёт исходный управляемый IRP, а `PoStartNextPowerIrp` следует контракту Vista+ без дополнительного протокола сериализации. Общая политика питания, WAIT_WAKE, другие состояния/действия, выключение/гибернация, пусковой ток, неперемещаемые в файл подкачки маршруты, произвольное оборудование и KMDF PnP не входят в профиль.

В `pnp_devices` можно задать `initial_reported_device_power: "D0"` или `"D3"` независимо от обязательных начальных состояний D0/working. PDO и каждый впервые связанный гостевой DEVICE_OBJECT имеют отдельную историю уведомления; `PoSetPowerState` возвращает и обновляет предыдущее значение только данного устройства. Без явного начального значения вызов завершается ошибкой, а не предполагает D0. Необязательный `requested_device_power` содержит device-шаблоны с теми же шестью обязательными фактами, до 64 записей суммарно. Только реальный `PoRequestPowerIrp`, совпавший по PDO/minor/цели с головой FIFO этого PDO, расходует запись. Отсутствие/несовпадение — ошибка; неиспользованные записи не создают запросов, context не определяет родителя. У ребёнка отдельные IRP и строка отчёта: `origin: "PoRequestPowerIrp"`, нулевой начальный `response_index`; у сценария `origin: "scenario"` и null-индекс. Синхронный ребёнок может вызвать пятиаргументный void-callback до возврата `STATUS_PENDING`; callback может ждать, а System S0 — завершиться раньше независимого D0. Снимок IO_STATUS_BLOCK действует до возврата callback.

Отчёт добавляет nullable `power`; для питания `file` равен null. Записываются факты пакета, `device_state_before`/`device_state_after`, `system_state_before`/`system_state_after`, nullable `requested_device_object` и фактические `bus_status`/`bus_received_at_100ns`/`bus_completed_at_100ns`. Итоговые PnP-устройства добавляют `device_power`/`system_power`, живые устройства — nullable `reported_device_power`. `scenario_success` сравнивает количество только сценарных строк, но требует успешного завершения всех фактических строк, включая детей; неиспользованные шаблоны не вызывают отказа. Подлинный `driver_wdm_power.c` использует `NEVERD_WDM_POWER_FIXTURE`/`NEVERD_WDM_POWER_CFG_FIXTURE` для обычного/active-CFG native и C API/CLI покрытия. Отсутствующие артефакты явно пропускаются; доказательства исполнения ограничены Linux.

[Полный сценарий питания](../examples/driver-power-scenario.json) запускается через `--scenario` с подлинным драйвером: start, системные query/сон/возврат, remove и три явных дочерних ответа.

KMDF 1.33 использует точную ABI 1.33.0: 458 слотов функций имеют стабильные гостевые идентификаторы, а 40 перечисленных ниже API реализуют семантику исполнения. `WdfVersionBind` и `WdfVersionUnbind` управляют гостевой привязкой вокруг настоящей оболочки WDK `FxDriverEntry`. `WdfGetDriver` читает публичные глобальные данные драйвера. Драйверы без PnP, общие объекты, управляющие устройства, очереди и входящие запросы используют типизированные контексты, счётчики ссылок и исполняемые обратные вызовы очистки/уничтожения/выгрузки. Все моделируемые вызовы и обратные вызовы фреймворка пока требуют `PASSIVE_LEVEL`; добавление ссылок после завершения очистки остаётся вне этого профиля. Немоделируемые слоты, `WdfLdrQueryInterface`, расширения классов и UMDF явно останавливают исполнение.

Управляющие устройства требуют скопированного имени из печатных ASCII-символов и строго заданной SDDL `D:P(A;;GA;;;WD)`. Она разрешает доступ всем, не требуя выдуманного токена вызывающей стороны; другие дескрипторы безопасности, безымянные устройства и автоматические имена не поддерживаются. Инициализация владеет одним устройством WDM. Запросы могут выбирать его в существующем пространстве имён сеанса через псевдонимы символических ссылок `\DosDevices\Name` или `\??\Name`; в отчёте сохраняется каноническое имя устройства. Успешное создание потребляет объект инициализации и обнуляет его указатель; ошибка отменяет частично установленное владение устройством. `WdfControlFinishInitializing` разрешает доставку ввода-вывода. Удаление убирает устройство и его ссылки только тогда, когда это допускают моделируемые файлы, рабочие элементы и запросы; отмена или опустошение очереди запросов при удалении не поддерживаются.

Структура `WDF_IO_QUEUE_CONFIG` размером 96 байт поддерживает последовательную очередь по умолчанию с явно заданным пассивным исполнением и без синхронизации фреймворка. Очереди управляющих устройств не участвуют в управлении питанием. Специализированные обратные вызовы READ/WRITE/IOCTL имеют приоритет над вызовом по умолчанию. Принятые в очередь запросы возвращают `STATUS_PENDING` даже при синхронном завершении; регистр возврата void-функции не завершает её запрос. Отложенное завершение использует существующий планировщик. Без обработчика запрос завершается с `STATUS_INVALID_DEVICE_REQUEST`; READ/WRITE нулевой длины завершается без доставки, если она не включена. Стандартный файловый пакет успешно завершает CREATE/CLEANUP/CLOSE с Information=0. Параллельные/ручные очереди, файловые обратные вызовы, устройства PnP и полный PnP/питание не поддерживаются.

Параметры запроса используют 40-байтную структуру `WDF_REQUEST_PARAMETERS`. Функции доступа к вводу/выводу возвращают логические длины, сохраняя алиасы буферов и существующие MDL-отображения прямого ввода-вывода; вход прямого IOCTL остаётся буферизованным. Неверное направление и недостаточный буфер возвращают документированные статусы. Завершение выполняет очистку запроса и уничтожение дочерних объектов до аннулирования IRP и буферов, затем уничтожает запрос, когда это допускают ссылки. Новые вызовы функций доступа к буферам и параметрам отклоняются с начала завершения; ранее полученные указатели буферов остаются доступны во время очистки. Внешняя ссылка сохраняет контекст, но не доступ к завершённому IRP. Пользовательский KMDF `METHOD_NEITHER` по-прежнему требует нереализованной поддержки контекста вызывающей стороны, проверки доступа и блокировки.

Отмена моделируется для запросов описанных выше очередей управляющих устройств. Если отмена уже произошла, `WdfRequestMarkCancelableEx` возвращает `STATUS_CANCELLED` без обратного вызова. Успешный `WdfRequestUnmarkCancelable` снимает обработчик; последующая отмена лишь записывает состояние отмены. `WdfRequestIsCanceled` читает это состояние у живого запроса без отметки об отменяемости. После успешной отметки об отменяемости завершение требует успешного снятия отметки либо начала доставки обратного вызова отмены: постановки в очередь недостаточно. После начала доставки обработчик может согласовать завершение с рабочим элементом, в том числе во время собственного ожидания. Отдельная внутренняя ссылка удерживает запрос до возврата обработчика отмены. При завершении IRP всё равно становится недействительным первым, а заключительное продолжение уничтожения запроса тоже может ожидать. Приоритет имеют DPC, затем обработчики отмены в порядке FIFO, затем обычные рабочие элементы; обработчики отмены также предшествуют возобновлению готовых пассивных ожиданий.

Для уже отменённого запроса прежний void-метод `WdfRequestMarkCancelable` синхронно выполняет гостевой обработчик отмены до своего возврата. Дочернее продолжение может ожидать, завершить запрос через вложенную очистку и выполнить окончательное уничтожение до возобновления исходного API. Отмена после регистрации использует описанный выше планируемый путь. Это воспроизводит публичный код при `PASSIVE_LEVEL` и `WdfSynchronizationScopeNone`; [Microsoft](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdfrequest/nf-wdfrequest-wdfrequestmarkcancelable) требует от драйверов без автоматической синхронизации использовать Ex. Здесь реализована совместимость, а не рекомендация применять прежний API в такой конфигурации.

`WdfRequestGetInformation` и `WdfRequestSetInformation` используют исходное 64-битное поле `IRP.IoStatus.Information`, включая прямую запись гостя. Set лишь присваивает значение; длина передачи проверяется при завершении. `WdfRequestCompleteWithInformation` записывает то же поле до очистки; изменения через заранее сохранённый IRP во время очистки определяют итоговый Information, хотя GetInformation в этой фазе уже возвращает ноль. `WdfRequestGetIoQueue` возвращает исходную очередь. При стандартной файловой конфигурации `WdfRequestGetFileObject` возвращает NULL, не выдавая WDM FILE_OBJECT за файловый объект WDF. `WdfRequestWdmGetIrp` возвращает тот же IRP; гостевые `IoCompleteRequest`/`IofCompleteRequest` не могут обойти завершение WDF. Пока дескриптор запроса действителен во время или после завершения, GetInformation/GetIoQueue возвращают ноль; получение MDL сначала записывает NULL в допустимый выход, затем возвращает `STATUS_INTERNAL_ERROR`. SetInformation/GetFileObject/WdmGetIrp в этой фазе отклоняются. Ограничения существующих функций буферов и параметров не меняются.

`WdfRequestRetrieveInputWdmMdl` и `WdfRequestRetrieveOutputWdmMdl` по требованию описывают имеющийся SystemBuffer для буферизованных входа WRITE, выхода READ и входа/выхода IOCTL. Направление должно быть допустимым и ненулевой длины до использования единственного кэшированного MDL запроса; первое успешное получение фиксирует ByteCount даже при иной логической длине другого направления. `MmGetSystemAddressForMdlSafe` возвращает исходный VA; дополнительные отображения, их снятие и освобождение драйвером запрещены. Прямые выходы READ/IOCTL и вход WRITE возвращают исходный `IRP.MdlAddress`, не создавая отображения самим получением; вход прямого IOCTL использует кэш SystemBuffer. MDL, IRP и буферы прекращают существование при завершении. Внутренние ссылки отмены и внешние ссылки сохраняют только контекст WDF. WDF `METHOD_NEITHER` и PFN непостроенных MDL остаются неподдерживаемыми.

Для буферизованных и прямых запросов KMDF обработчик `WdfDeviceInitSetIoInCallerContextCallback` выполняется в процессе инициатора. Он должен завершить запрос или один раз вызвать `WdfDeviceEnqueueRequest` для последовательной очереди по умолчанию. Получение, проверка и закрепление пользовательских буферов `METHOD_NEITHER` пока не моделируются.

Стеки ограничены: вышедший за границы указатель не может попасть в стек другого заблокированного рабочего потока. Активные таймеры в расширении устройства запрещают преждевременное освобождение устройства.

Истечение таймера удовлетворяет зарегистрированные ожидания до того, как DPC сбросит или переустановит таймер. DPC из очереди выполняются раньше возобновления пробуждённых кадров `PASSIVE_LEVEL`. Если память запроса ещё содержит DPC в очереди, завершение IRP отвергает её освобождение до завершения и аннулирования буфера.

Форматирование `DbgPrint` поддерживает целые `d/i/u/o/x/X`, указатель `p`, текст `s/c`, `%%`, Unicode с заданной длиной `wZ/lZ`, широкие строки `ls/ws`, флаги, ширину/точность, включая `*`, и модификаторы длины целых Windows. Считывается не более 32 переменных аргументов и 1024 байтов формата. Ширина и точность ограничены 512. Числа с плавающей точкой, `%n`, неизвестные сочетания и преобразования текста вне ASCII явно останавливают выполнение; модель не угадывает кодовую страницу Windows и не вызывает хостовый printf для гостевых данных.

Время жизни исходных записи и буфера RegistryPath заканчивается при возврате DriverEntry. Если строка нужна позже, драйвер должен скопировать её во время инициализации.

Арена объектов/пула занимает 1 MiB. Неинициализированные байты пула имеют детерминированное содержимое `0xCD`, освобождённые — `0xDD`. Это один конкретный сценарий выполнения. Доступы CPU и моделируемые буферные API отклоняют обращения к освобождённым выделениям пула, удалённым устройствам, невыделенным байтам арены, непрозрачным полям объектов и запись в поля объектов только для чтения. Эти проверки охватывают время жизни объектов данной модели; это не общий анализ безопасности памяти драйвера. Незаписанные слоты таблицы диспетчеризации показываются нулём со значением «не зарегистрирован». Запрос сценария к незарегистрированной основной функции завершается моделируемым обработчиком по умолчанию с `STATUS_INVALID_DEVICE_REQUEST`; ошибка остаётся видимой и в статусе диспетчеризации, и в статусе ввода-вывода. Модель не выдумывает гостевой адрес функции для этого обработчика, а чтение гостем незаписанного слота по-прежнему не поддерживается. Явная регистрация null-указателя обратного вызова является ошибкой.

## Сценарии запросов

Передайте JSON-файл через `--scenario`, чтобы выбрать запросы и необязательную выгрузку:

```bash
build-release/bin/neverd emulate-driver path/to/driver.sys \
  --scenario scenario.json > driver-report.json
```

Пример `scenario.json` для драйвера, создающего `\Device\NeverDIO` и принимающего буферизованный IOCTL `0x222000`:

```json
{
  "requests": [
    {"kind": "create", "device": "\\Device\\NeverDIO"},
    {"kind": "ioctl", "code": "0x222000", "input": "00112233", "output_size": 4},
    {"kind": "cleanup"},
    {"kind": "close"}
  ],
  "unload": true
}
```

Имя устройства и код IOCTL должны соответствовать драйверу. При create отсутствие `device` выбирает единственное живое устройство; неоднозначный выбор завершается ошибкой. Последующие запросы используют устройство своего файла, если явно не указано совпадающее имя. Необязательный `file` — беззнаковый 32-битный идентификатор сценария, по умолчанию ноль. У каждого идентификатора собственные FILE_OBJECT и FsContext, а порядок операций — create, передачи, cleanup, close. Запросы независимых файлов могут чередоваться. Эксклюзивные устройства отклоняют второе открытие. Эти идентификаторы представляют файловые объекты, а не дублированные дескрипторы. Поддерживаются buffered и оба метода direct IOCTL. Диспетчеризация должна завершить IRP синхронно либо соблюдать описанный выше контракт обратных вызовов для ожидающего запроса. Недопустимая длина вывода и доступ к завершённому IRP явно завершаются ошибкой. Запрошенная выгрузка не должна оставлять живые устройства, символические ссылки, выделения пула или файловые объекты.

Необязательное корневое поле `"load_address": "0x190000000"` запрашивает изменение базового адреса; отсутствие поля или `"0x0"` означает предпочтительный адрес. Образ должен удовлетворять требованиям релокации. Исходная команда инициализации и C API не подразумевают никакого сценария.

В корне допустимы только `load_address`, `requests`, `unload`, `kernel_exports`, `registry` и `pnp_devices`. Обычные файловые запросы принимают `kind`, необязательные `device` или `device_id` (взаимоисключающие) и `file`. Для IOCTL обязателен `code`, допустимы `input`, `output_size` и `direct_input`. Запрос `read` принимает `output_size` и `byte_offset`; `write` — `input` и `byte_offset`. Смещения по умолчанию равны нулю, принимают целые числа или шестнадцатеричные строки и должны помещаться в неотрицательное знаковое 64-битное значение. Запросы жизненного цикла отклоняют поля передачи данных. Неизвестные или повторяющиеся поля отклоняются. `code` принимает беззнаковое 32-битное целое JSON или шестнадцатеричную строку с `0x`. `input` — шестнадцатеричная строка байтов чётной длины без префикса и пробелов; отсутствие означает пустой ввод. `output_size` — беззнаковое целое JSON, по умолчанию ноль. Дроби и записи с плавающей точкой отклоняются.

Только READ/WRITE/IOCTL принимают необязательное поле `cancel_after_100ns`, целое число JSON от 0 до `INT64_MAX` (9223372036854775807). Задержка отсчитывается от подачи запроса в виртуальных единицах по 100 нс, а не в реальном времени. Для KMDF ноль применяет отмену после маршрутизации фреймворком и до гостевого обработчика ввода-вывода; если маршрутизация уже завершила запрос, завершение имеет приоритет. Для WDM ноль действует после возврата диспетчера. При положительной задержке время продвигается к сроку таймера, ожидания или отмены только при отсутствии готовых обработчиков и кадров. Ожидающий WDM IRP вызывает зарегистрированную процедуру отмены на `DISPATCH_LEVEL` при удерживаемой блокировке отмены; перед завершением она должна освободить блокировку через `Irp->CancelIrql`. Общая отмена очередей и PnP остаётся неподдерживаемой. Каждый отчёт о запросе содержит `cancel_requested_at_100ns`: фактическое абсолютное виртуальное время отмены либо null, если её не было, в том числе когда завершение произошло раньше. Запрос отмены сам по себе не завершает IRP и не определяет его итоговый статус.
`IoSetCancelRoutine`, `IoAcquireCancelSpinLock`, `IoReleaseCancelSpinLock` и `IoCancelIrp` используют одно состояние IRP и одну блокировку отмены; `IoCancelIrp` синхронно вызывает зарегистрированную процедуру и сообщает, была ли она вызвана.

Необязательное логическое поле `user_unmap_after_dispatch` закрывает доступ к исходным пользовательским адресам непустой WDM neither-передачи после возврата диспетчера и до запланированной работы или отмены. Зафиксированные MDL страницы и их системные псевдонимы доступны до разблокировки; прямые пользовательские указатели и новые блокировки не работают. При отзыве выходного адреса `output_hex` пуст. Повторное использование и произвольные моменты снятия отображения не моделируются.

`requestor_process_id` задаёт синтетический ID процесса-заявителя (по умолчанию 4096, от 5 до `UINT32_MAX`). `IoGetRequestorProcessId` возвращает его для активного IRP, а `PsGetCurrentProcessId` — при прямой диспетчеризации либо 4 в моделируемом системном рабочем потоке. Смена процесса закрывает доступ к исходным пользовательским VA другого процесса, сохраняя системные псевдонимы заблокированных MDL. `requestor_exit_after_dispatch` после возврата из диспетчера отзывает все исходные пользовательские VA этого процесса и отклоняет его новый ввод-вывод; явные CLEANUP/CLOSE допустимы, без автоматического вывода отмены или закрытия дескрипторов.

Системный рабочий поток может получить непрозрачный объект процесса активного IRP через `IoGetRequestorProcess`, временно подключиться к его исходным пользовательским VA через `KeStackAttachProcess` с доступным для записи ядровым `KAPC_STATE`, а затем вызвать `KeUnstackDetachProcess` с тем же состоянием. `IoGetCurrentProcess` и `PsGetProcessId` отражают подключённый процесс; `PsGetCurrentProcessId` остаётся равным 4 — ID создателя потока. Завершённый процесс, завершённый IRP, несоответствие состояния, ожидание или завершение IRP во время подключения явно отклоняются.

Для direct IOCTL поле `input` инициализирует первый системный буфер, а `direct_input` — отдельный второй буфер, описанный MDL, с дополнением нулями до `output_size`. `METHOD_IN_DIRECT` требует доступа на чтение, но не означает системное отображение только для чтения. Оба метода используют доступные для чтения и записи буферы сценария. `MdlMappingNoWrite` снимает право записи отображения, а `MdlMappingNoExecute` — право исполнения. Снятие отображения отзывает системный VA; повторное отображение сохраняет те же зафиксированные данные. Завершение прекращает время жизни MDL и отображения. Публичные поля MDL, используемые макросами WDM, моделируются; поля process и PFN непостроенных MDL, вручную созданные MDL, пользовательские отображения и прямой доступ через исходный UserBuffer отклоняются. У direct-буфера нулевой длины MDL равен null.

`IoAllocateMdl` выделяет независимые метаданные для непустого буфера без переполнения адреса размером не более 1 MiB; буфер при этом не проверяется и не фиксируется. `Irp` должен быть NULL, а `SecondaryBuffer` и `ChargeQuota` — FALSE. При исчерпании арены возвращается NULL. `MmBuildMdlForNonPagedPool` требует, чтобы весь диапазон находился внутри одного живого блока невыгружаемого пула. Безопасная вспомогательная функция и обычные макросы WDM используют исходный адрес, сохраняя общую память и существующие права даже при новых флагах запрета записи/исполнения. Дополнительные системные отображения и снятие отображения отклоняются. `IoFreeMdl` завершает только время жизни дескриптора; буфер пула имеет независимое время жизни. Допустимы оба порядка освобождения, если освобождённая память больше не используется. Все моделируемые поля MDL доступны только для чтения; доступ к process и PFN непостроенных MDL, цепочки и ручное изменение полей не поддерживаются. При выгрузке должны быть освобождены все MDL драйвера.

Для любого метода IOCTL при ненулевом `output_size` значение `Information` не должно превышать `output_size`, даже если входной буфер больше. Если выходного буфера нет, `Information` может содержать определённый драйвером 64-битный результат; это значение не используется как число копируемых байтов. Отчёт сохраняет числовое значение и добавляет точную шестнадцатеричную строку `information_hex` для клиентов JSON, которые не могут представить все 64-битные целые.

Для READ/WRITE флаги `DO_BUFFERED_IO` и `DO_DIRECT_IO` выбирают буферизованный или прямой метод. Если оба отсутствуют, исходный пользовательский адрес находится только в `IRP.UserBuffer`: WRITE использует вход, READ — выход; SystemBuffer и MDL автоматически не создаются. Драйвер должен проверить и использовать адрес в контексте вызывающего потока либо закрепить страницы до отложенной работы. `user_input_access` относится к neither WRITE, `user_output_access` — к neither READ. Явные права для буферизованного/прямого READ/WRITE или оба флага одновременно останавливают выполнение. Information проверяется относительно длины передачи; запись возвращает количество, чтение — байты.

`kernel_exports` сопоставляет именам процедур явные логические значения доступности, например `"kernel_exports": {"OptionalRoutine": false}`. Моделируемые экспорты и статические импорты получают стабильные адреса, общие с `MmGetSystemRoutineAddress`. Явно отсутствующий экспорт разрешается в NULL и не может удовлетворить статический импорт. Экспорт, объявленный присутствующим, но не имеющий модели API, разрешается в отложенную ловушку. Неизвестное динамическое имя останавливает выполнение с диагностикой неопределённой доступности; отсутствие никогда не выводится из отсутствия реализации. Имена ограничены по длине и состоят из печатных ASCII-символов; разрешение учитывает регистр. Реестр — свойство конкретного сценария, а не утверждение о соответствии каждому выпуску Windows.
`IoMarkIrpPending`, `IoGetCurrentIrpStackLocation` и `MmGetSystemAddressForMdlSafe` — моделируемые вспомогательные функции заголовков WDM; это не объявляет их экспортируемыми по умолчанию, поэтому их доступность как экспортов требует статического импорта или явного объявления в `kernel_exports`.

Текст сценария ограничен 2 MiB; допускается не более 64 запросов, не более 65536 байтов на каждый входной или выходной буфер и не более 512 KiB запрошенных байтов суммарно, включая содержимое `direct_input`. Бюджеты инструкций, наблюдений, гостевой памяти и времени действуют на весь сценарий. Арена 1 MiB также содержит объекты и метаданные, поэтому образ может исчерпать память модели до использования максимального объёма буферов сценария.

## Сценарии реестра

Необязательный массив `registry` задаёт конкретное дерево реестра внутри сеанса.
У каждой записи ключа есть обязательный `path` и необязательный массив `values`;
каждое значение содержит `name`, беззнаковое целое `type` и шестнадцатеричные
`data`. Пустое имя выбирает значение по умолчанию. Например, значение DWORD
задаётся как `{"name":"Mode","type":4,"data":"01000000"}`. Байты сохраняются
точно: модель не исправляет завершающие нули строк и не раскрывает переменные
окружения.

Пути должны быть абсолютными ASCII-путями внутри `\\Registry\\Machine` или
`\\Registry\\User`. Родительские ключи создаются неявно. Имена ключей и значений
сравниваются без учёта регистра по правилам ASCII; имена вне ASCII и дубликаты
отклоняются. Если `registry` отсутствует, доступность реестра не определена и
вызовы реестра останавливают выполнение. `"registry": []` явно задаёт пустое
пространство имён. Ключи, значения, данные реестра хоста и настройки службы не
выводятся из самого драйвера.

`ZwOpenKey` и `ZwCreateKey` возвращают независимые непрозрачные дескрипторы;
права каждого дескриптора проверяются при запросе, записи, создании дочерних
ключей и удалении. Настроенное дерево предоставляет поддерживаемые биты
`KEY_ALL_ACCESS`, включая обычные маски `KEY_READ` и `KEY_WRITE`. Это явно
доступное тестовое дерево без ACL Windows и проверки привилегий. Общие права,
`MAXIMUM_ALLOWED`, альтернативные представления реестра, пользовательские
дескрипторы безопасности, классы и символические ссылки не поддерживаются.
Относительное создание требует дескриптора непосредственного родителя с
`KEY_CREATE_SUB_KEY`. Входные ключи энергонезависимы; новые ключи могут быть
временными (volatile), но создание энергонезависимого дочернего ключа внутри
временного отклоняется. Перезагрузка и сохранение на диск не моделируются.

`ZwQueryValueKey` реализует классы Basic, Full, Partial и их определённые
варианты Align64: точные размеры, выровненные данные, частичные результаты и
различающиеся статусы `STATUS_BUFFER_TOO_SMALL` и `STATUS_BUFFER_OVERFLOW`.
`ZwSetValueKey` и `ZwDeleteValueKey` изменяют только дерево этого сеанса.
`ZwDeleteKey` отклоняет удаление ключа с существующими дочерними ключами;
дескрипторы удалённого ключа возвращают `STATUS_KEY_DELETED` до закрытия.
`ZwClose` освобождает дескриптор независимо от ключа; запрошенная выгрузка
завершается ошибкой, пока остаются открытые дескрипторы реестра.

Ограничения: 256 ключей с учётом родителей, 1024 значения, 65536 байтов на
значение, 512 KiB данных значений суммарно, 1024 байта ASCII на путь ключа,
256 байтов на имя значения и 256 одновременно открытых дескрипторов. Создание
и изменения соблюдают те же ограничения, что и предварительная проверка
сценария. Поле отчёта `configuration.registry` сохраняет исходные входные
данные, а `registry` перечисляет итоговые пути и значения существующих ключей,
включая изменения до остановки. Неопределённое состояние реестра представлено
как null. Признак volatile и идентификаторы дескрипторов не входят в этот снимок.

## Проверка примера Microsoft

Запускаемый по желанию [скрипт проверки](../../scripts/validate_windows_driver_sample.py) загружает исходники Microsoft SIOCTL ревизии, закреплённой в [манифесте проверки](../../unittests/emulation/fixtures/sioctl-validation.json), проверяет хеши SHA-256 и компилирует неизменённый исходный код с заголовками MinGW-w64 DDK. В выбранном выходном каталоге сохраняются исходная лицензия/происхождение, команды сборки, сценарий и отчёты. Нужны доступ к сети, Clang, `lld-link`, `nm` и заголовки DDK из MinGW-w64:

```bash
python3 scripts/validate_windows_driver_sample.py \
  --neverd build-release/bin/neverd \
  --output build-release/driver-validation/sioctl
```

Для нестандартного каталога заголовков MinGW-w64 используйте `--headers`. Скрипт создаёт библиотеку импорта MS COFF из зависимостей скомпилированного объектного файла. Проверка запускает отдельные сценарии buffered, in-direct и out-direct через DriverEntry, create, IOCTL, cleanup, close и unload. Добавьте `--debug` и выберите отдельный выходной каталог, чтобы скомпилировать с `DBG=1` и проверить гостевые сообщения журнала. Исходный пример не регистрирует обработчик cleanup, поэтому моделируемый обработчик по умолчанию завершает cleanup с `STATUS_INVALID_DEVICE_REQUEST` (`0xC0000010`). Драйвер всё же закрывается и выгружается, а успешный IOCTL возвращает ожидаемые байты. Для этого полного сценария ожидаемый код выхода CLI — **2**, а `scenario_success` равен false. Сам скрипт завершается успешно только при совпадении всех этих результатов, включая видимый сбой cleanup; он не переписывает пример, чтобы скрыть этот результат.

## Отчёты и SDK

JSON-отчёт различает `stop_reason`, допускающие null поля `nt_status` и `nt_success`, PC остановки и число инструкций. Он сохраняет вызовы API и наблюдаемое состояние до остановки, включая объекты устройств и адреса обратных вызовов драйвера. Гостевые адреса представлены шестнадцатеричными строками, чтобы потребители JSON не теряли 64-битную точность. Объект `configuration` записывает ограничения запуска, имя службы, переопределения `kernel_exports` и входное дерево `registry`. Профиль — `wdm-x64-scheduled-v32`. Поле `nt_status` остаётся результатом DriverEntry, а `scenario_success` описывает инициализацию и завершённые запросы вместе. `phase`, `requests` и `unload_completed` показывают, какие части запрошенного жизненного цикла были выполнены. Каждый вызов API и каждая запись CPU также содержат фазу (`driver_entry`, `add_device:<ID>`, `request:N`, `callback:N` или `unload`). Для каждого запроса приводятся статусы диспетчеризации и ввода-вывода, завершение, длина информации и возвращённые байты `output_hex`. `preferred_image_base` описывает исходный базовый адрес PE. `security_cookie` — гостевой адрес инициализированного cookie либо `"0x0"`, если он не требовался. Поля запроса: `kind`, `device`, `device_id`, `pnp`, `file`, `requestor_process_id`, `byte_offset`, `code`, `irp`, `completed`, `cancel_requested_at_100ns`, `dispatch_status`, `io_status`, `information`, `information_hex` и `output_hex`. Числовое поле `information` остаётся точным десятичным целым JSON; `information_hex` сохраняет те же биты и для клиентов, читающих числа JSON с точностью только до 53 бит.

Наблюдения рабочих элементов имеют фазу `callback:N`. Для ожидающего запроса `dispatch_status` сохраняет `STATUS_PENDING`; окончательный статус отдельно записывается в `io_status` и определяет вклад в `scenario_success`.

`ExRaiseStatus` передаёт младшие 32 бита NTSTATUS гостевому обработчику исключения; `ExRaiseAccessViolation` и `ExRaiseDatatypeMisalignment` вызывают `STATUS_ACCESS_VIOLATION` и `STATUS_DATATYPE_MISALIGNMENT`. Профиль следует отдельным страницам DDI Microsoft: ExRaiseStatus допускает `APC_LEVEL`, а две процедуры без аргументов требуют `PASSIVE_LEVEL`. Некоторые аннотации SAL WDK допускают для этих двух процедур APC_LEVEL; профиль сохраняет более строгое документированное ограничение. Вызов с исключением оставляет `result: null` и записывает код в `detail`; успешный возврат API не подставляется.

Доставка исключений использует декодированные таблицы unwind x64 версии один из образа и постоянные области `EXCEPTION_EXECUTE_HANDLER` обработчика `__C_specific_handler`. Исполняется настоящее тело гостевого обработчика; поддерживается раскрутка обычных вспомогательных кадров, восстанавливаются сохранённые невольатильные регистры общего назначения и сохраняется граница стека текущего исполнения. `GetExceptionCode()` получает вызванный код. Обработчик может вызвать новое исключение во внешнюю поддерживаемую область. Встреченные функции-фильтры, `__finally`, личности GS/C++, связанные или неполные метаданные, раскрутка пролога и восстановление XMM приводят к явной ошибке. Неперехваченное исключение API останавливает исполнение с `model_error`; сбои CPU, связанные с памятью, прерыванием или недопустимой инструкцией, остаются окончательными.

Оригинальный образец `driver_wdm_seh.c` использует настоящие заголовки WDK и `/GS-`. Для обычного образа и образа с активным CFG задаются `NEVERD_WDM_SEH_FIXTURE` и `NEVERD_WDM_SEH_CFG_FIXTURE`. Пример [driver-seh-scenario.json](../examples/driver-seh-scenario.json) перемещает базу образа, перехватывает исключение API в DriverEntry и выгружает драйвер. Отдельный путь WDM METHOD_NEITHER поддерживает проверки пользовательской памяти, закреплённые MDL и перехватываемые сбои памяти.

Объект `fault`, допускающий null, сохраняет первую ошибку бэкенда. Его `kind`, `pc` и допускающие null поля `address`, `size`, `access` и `interrupt` различают неотображённую или защищённую память, недопустимые диапазоны, недопустимые инструкции и исключения CPU. Адреса представлены шестнадцатеричными строками, размеры и векторы прерываний — целыми числами. Чтение для наблюдения не может заменить исходную ошибку. Бэкенд с ошибкой не может продолжить выполнение, и эта запись не подразумевает обработку гостевых SEH.

`instructions` считает допущенные попытки выполнения гостевых инструкций. Инструкция, отклонённая политикой выполнения, не учитывается; допущенная инструкция, вызвавшая ошибку CPU, учитывается. Синтетическая диспетчеризация API и маркер возврата не увеличивают этот счётчик.

Каждая запись `writes` имеет `semantics: "attempted_guest_write"`: она описывает попытку записи CPU вне стека, включая попытку, которая позднее может вызвать ошибку или остановку по бюджету. Это не гарантия завершённой записи; записи моделей API сюда не входят. Снимки устройств и объекта драйвера описывают состояние, наблюдаемое при остановке выполнения.

Подключите `neverd/sdk/NeverDCAPIEmulation.h` (либо общий заголовок C API), создайте сеанс и вызовите `neverd_emulate_driver_json(session, path, options)`. Явно заданный непустой путь сразу запускает строгую предварительную проверку выполнения без начальной загрузки через общий API анализа. CLI использует этот путь. Передача `NULL` в качестве options выбирает значения по умолчанию. Явные параметры `neverd_driver_options_v1` требуют точного `struct_size` и положительных бюджетов инструкций, памяти, событий и времени. Освободите результат через `neverd_free_string`.

Передача `NULL` вместо пути требует загруженного сеанса и заново разбирает его файл независимо от анализа IR и загрузки с ограничением по функциям. Оба пути сохраняют образ сеанса. В течение вызова входной файл должен оставаться доступным и неизменным. Ошибки запроса/настройки возвращают `NULL` и устанавливают `neverd_last_error`; остановки выполнения возвращают JSON. API доступен и в сборках с отключённой функцией и сообщает, как её включить.

`neverd_emulate_driver_scenario_json(session, path, scenario_json, options)` использует те же параметры v1 и правила владения, добавляя строгий ввод сценария. Требуется не-NULL строка JSON с завершающим NUL. Исходный ABI `neverd_emulate_driver_json` остаётся неизменным и выполняет только инициализацию. C++-парсер `driverOptionsFromScenarioJSON` предоставляет ту же проверку сценария вызывающим `emulateDriver`.

Внутренняя точка входа C++ — `neverd::emulation::emulateDriver` в `include/neverd/emulation/DriverSession.h`. Разбор формата относится к существующему загрузчику; поведение объектов/API Windows — к `lib/emulation/windows`; состояние CPU и выполнение — к адаптеру Unicorn. Адаптер и модель используют один интерфейс гостевой памяти. Поведение Windows API не должно находиться в форке Unicorn.

В WDM `METHOD_NEITHER` поля `Type3InputBuffer` и `IRP.UserBuffer` указывают на разные пользовательские выделения. `ProbeForRead` проверяет диапазон и выравнивание без обращения к страницам; `ProbeForWrite` обращается к каждой странице. `ExGetPreviousMode` возвращает режим запроса. `MmProbeAndLockPages` закрепляет одно пользовательское выделение, `MmGetSystemAddressForMdlSafe` даёт общий алиас, а `MmUnlockPages` удаляет алиас и освобождает страницы. Произвольные процессы не моделируются.

Для непустого буфера WDM `METHOD_NEITHER` IOCTL поля `user_input_access` и `user_output_access` независимо принимают `read_write` (по умолчанию), `read_only` или `no_access`. Для буферизованных/прямых методов и пустых буферов поля отклоняются; `no_access` сохраняет указатель, но запрещает доступ к страницам.
В отчёте `configuration.user_page_access` указаны только явно заданные права с `source_request_index`, начинающимся с нуля; для пропущенного направления действует `read_write`.

## Ограниченное параллельное выполнение запросов WDM

Запрос WDM READ/WRITE/IOCTL может задать `defer_callback_drain: true`. Следующий запрос отправляется до выполнения обратных вызовов только если диспетчер вернул `STATUS_PENDING`, а IRP действительно остался ожидающим. После следующего запроса без этого поля выполняются обратные вызовы и завершается вся группа; для последнего помеченного запроса это происходит в конце сценария. Перекрывающиеся запросы могут использовать разные файловые объекты либо один объект, явно открытый в асинхронном режиме. Перекрытие на синхронном файле, групповые запросы KMDF, произвольное вытеснение и внешнее поступление запросов не поддерживаются.

## Асинхронный файловый объект

Только запрос CREATE может задать логическое поле `asynchronous_file: true`; отсутствие или false сохраняет синхронный режим. Асинхронное открытие снимает `FO_SYNCHRONOUS_IO` у гостевого `FILE_OBJECT` и не устанавливает `IRP_SYNCHRONOUS_API` для последующих файловых IRP. READ/WRITE/IOCTL на одном асинхронном файле перекрываются только при явной отсрочке обратных вызовов. CLEANUP/CLOSE ждут завершения и финализации всех предыдущих передач. Неявная позиция файла не поддерживается: `byte_offset` задаётся для каждого запроса и по умолчанию равен нулю. Другие типы запросов отвергают поле даже со значением false.
