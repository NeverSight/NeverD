# Эмуляция драйверов Windows

Необязательный эмулятор драйверов NeverD выполняет точку входа PE поддерживаемого драйвера x64 WDM и, при необходимости, явно заданный сценарий последовательных запросов перед выгрузкой драйвера. Для выполнения инструкций используется Unicorn, а для окружения Windows — собственная ограниченная модель NeverD. Драйвер не загружается в ядро хоста, а вызовы гостевых API не передаются службам ОС хоста.

## Сборка и запуск

Функция включается явно и не зависит от `BUILD_TESTING`:

```bash
cmake -S . -B build-release -G Ninja \
  -DCMAKE_BUILD_TYPE=Release \
  -DNEVERD_ENABLE_DRIVER_EMULATION=ON
cmake --build build-release --target neverd --parallel 4
build-release/bin/neverd emulate-driver path/to/driver.sys \
  --instruction-limit 100000 > driver-report.json
```

Отчёт всегда выводится в stdout в формате JSON; диагностика запросов и настройки направляется в stderr. Ограничения по умолчанию: 100000 гостевых инструкций, 64 MiB гостевой памяти, 10000 записанных событий и 5000 миллисекунд. Лимит инструкций должен быть положительным. При исчерпании бюджета выполнение останавливается с сохранением частичных наблюдений.

| Код завершения | Значение |
|----------------|----------|
| `0` | Инициализация и все запрошенные завершённые операции выполнены успешно |
| `1` | Неверные входные данные/параметры, ошибка настройки или функция отключена при сборке |
| `2` | Инициализация или завершённый запрос вернули `NTSTATUS` ошибки |
| `3` | Выполнение остановилось до завершения сценария, например из-за неподдерживаемого API, ошибки доступа или лимита бюджета |

Возвращённый статус ошибки также является завершённым наблюдением данной операции. Успешный возврат описывает только этот запуск в модели; он не доказывает работоспособность драйвера в Windows.

## Совместимость драйверов

Совместимость определяется выполняемым путём кода и его зависимостями, а не расширением `.sys`. Текущие подтверждения приёмки охватывают самостоятельно написанные freestanding fixture и пути buffered, in-direct и out-direct примера Microsoft SIOCTL WDM, включая сборку с отладочным журналом, а также прямые операции чтения и записи публичного примера Zero Павла Йосифовича. Это не подтверждает совместимость с произвольными сторонними драйверами.

| Класс драйвера или требование | Текущий объём поддержки | Недостающее окружение |
|-------------------------------|-------------------------|-----------------------|
| Программный x64 WDM-драйвер, использующий перечисленные API | Ограниченная инициализация x64 WDM, последовательные buffered/direct запросы, рабочие элементы, таймеры, DPC, события и ожидания, отчёты и ограничения | Для каждого дополнительного выполняемого API нужна определённая модель |
| `METHOD_BUFFERED` IOCTL | Последовательный buffered/direct I/O с завершением рабочим элементом или DPC | Только перечисленные ниже API; без параллельных IRP и отмены запросов WDM |
| `METHOD_IN_DIRECT`, `METHOD_OUT_DIRECT` | MDL, принадлежащие запросу, и системные отображения | идентичность физических страниц, DMA и пользовательские отображения |
| MDL, выделенные драйвером | Независимые дескрипторы моделируемого невыгружаемого пула с исходными адресами буферов | Привязка к IRP, цепочки MDL, проверка/фиксация, физические страницы и пользовательские отображения |
| READ/WRITE | Последовательный buffered/direct I/O с завершением рабочим элементом или DPC | Только перечисленные ниже API; без параллельных IRP и отмены запросов WDM; `METHOD_NEITHER` и неявная позиция файла |
| `METHOD_NEITHER` | Отклоняется | Контекст пользовательского адресного пространства, проверка доступа и обработка гостевых исключений |
| Драйвер KMDF 1.33 без PnP | Привязка, объекты/контексты, именованные управляющие устройства, последовательные очереди по умолчанию и буферизованные/прямые запросы с исполняемыми обратными вызовами | Нет устройств PnP, общего планирования очередей, расширений классов и UMDF |
| Драйвер шины/функции/фильтра PnP | Явные PDO без ресурсов, гостевой AddDevice и четыре minor-функции жизненного цикла PnP | Другие операции PnP, IRP питания, оборудование/ресурсы и KMDF PnP |
| Драйверы хранения, сети, дисплея, файловой системы и минифильтры | Контракты подсистем не поддерживаются | Фреймворки портов/классов/минипортов, NDIS/WFP, графические службы или службы файловой системы |
| Рабочие элементы, таймеры, DPC, события и ожидания | Текущий IRQL равен `PASSIVE_LEVEL` для диспетчеризации и рабочих элементов, `DISPATCH_LEVEL` для DPC | Только перечисленные ниже API; без параллельных IRP и отмены запросов WDM |
| Драйвер с обратными вызовами процессов/потоков, дескрипторами, операциями с реестром/файлами или поиском модулей ядра | Перечисленные операции реестра поддерживаются для явно настроенного дерева; остальные операции не поддерживаются | Общий диспетчер объектов, операции с файлами, состояние системы и источники обратных вызовов/событий |
| Драйвер оборудования, DMA, PCI, прерываний или виртуализации | Окружение не поддерживается | Модели устройств, физическая память, шины, прерывания и привилегированное состояние CPU |
| Драйвер Windows x86 или ARM64 | Отклоняется | Загрузка, ABI и модель выполнения для соответствующей архитектуры |
| x64 CFG | Проверенные таблицы целей и вызовы check/dispatch; неактивная инструментация сохраняет гостевые резервные функции | XFG, подавление экспортов, немоделируемая конфигурация загрузки и TLS отклоняются |

Неиспользуемый неподдерживаемый импорт может оставаться связанным. Достижение неподдерживаемой операции останавливает выполнение с диагностикой и накопленными наблюдениями. Один лишь успешный DriverEntry не доказывает поддержку последующей диспетчеризации, оборудования или путей фреймворка. Таблица API ниже определяет поддерживаемое подмножество.

## Контракт выполнения

Профиль моделирует жизненный цикл x64 WDM на CPU0 с детерминированным кооперативным планированием. Выполнение начинается в точке входа PE; при наличии сохраняется обёртка входа, созданная компилятором. Для успешной инициализации DriverEntry должен вернуть `STATUS_SUCCESS`. Ненулевой успешный статус или статус pending останавливает выполнение как неподдерживаемый контракт инициализации. Статус ошибки сохраняется как завершённый результат инициализации. Все объекты, строки, стеки, указатели на функции и выделенные области находятся в гостевой памяти. Модель предоставляет `DRIVER_OBJECT` и путь реестра для настроенного имени службы (по умолчанию `NeverDDriver`). Адаптер использует виртуальный режим TLB Unicorn, сохраняющий гостевые виртуальные адреса, включая канонические высокие адреса ядра, без создания таблиц страниц Windows. Начальное значение RFLAGS — `0x202`; профиль программного устройства использует фиксированную строку кэша размером 64 байта. Это явно заданные свойства данного сценария выполнения.
Встроенное чтение x64 CR8 наблюдает тот же `PASSIVE_LEVEL` / `DISPATCH_LEVEL`; запись CR8 и остальные операции с управляющими регистрами по-прежнему не поддерживаются.

Неизвестные импорты связываются с отложенными ловушками. Неиспользуемый импорт не мешает выполнению; выполнение его thunk или чтение немоделируемого экспортируемого значения данных приводит к `unsupported_api`. Неподдерживаемые эффекты окружения CPU также вызывают явную остановку. NeverD не заменяет нереализованные вызовы успешными значениями. Некорректные образы или неподдерживаемые требования загрузки вызывают ошибку до начала выполнения.

Элементы `DelayedWorkQueue` исполняются на `PASSIVE_LEVEL`, гостевые DPC — на `DISPATCH_LEVEL` с четырьмя предусмотренными аргументами. CPU0 использует детерминированное кооперативное планирование на границах возврата вызовов и блокирующего ожидания. Относительные, абсолютные и периодические таймеры используют виртуальное время; если ни один кадр не готов, оно продвигается до ближайшего срока таймера, ожидания или отмены. События/таймеры уведомления и синхронизации сохраняют разные правила потребления сигнала. У каждого вызова свой гостевой стек; несколько заблокированных кадров сохраняют локальные переменные и полные контексты CPU при общей памяти. Win64 передаёт первые четыре аргумента в регистрах, остальные в стеке. Запросы последовательны: диспетчеризация, пометившая IRP ожидающим, должна вернуть `STATUS_PENDING` и завершить его до следующего запроса. Без доступного источника ожидающий запрос или бесконечное ожидание останавливается с `model_error` из-за зависания. Бюджеты инструкций, памяти, наблюдений и реального времени общие.

Ограниченная модель не обеспечивает полную асинхронность Windows. Не поддерживаются alertable-ожидания и ожидания пользовательского режима, системные потоки, APC, отмена запросов WDM, спин-блокировки, параллельные IRP, общие изменения IRQL, `METHOD_NEITHER`, UMDF, устройства PnP KMDF и общее планирование очередей, полный PnP/питание, оборудование, DMA и прерывания. Инициализация выполняет явно поставленные в очередь вызовы без неявного создания запросов или выгрузки.

Рабочий элемент извлекается из очереди до начала обратного вызова, поэтому тот может освободить собственный элемент. Освобождение элемента в очереди, повторная постановка, устаревшие объекты и адреса вызова вне исполняемой гостевой памяти явно отклоняются. Ссылка на устройство удерживается до возврата. Выгрузка требует освободить все рабочие элементы и завершить очередь. Контексты CPU сохраняют общие регистры, SIMD, FPU и управляющее состояние; гостевая память остаётся общей, а восстановление контекста не позволяет возобновить CPU после сбоя.
Удаление откладывается, пока остаются файловые объекты или ссылки рабочих элементов в очереди/исполнении. При исчерпании арены объектов выделение рабочего элемента возвращает NULL.

Образы используют предпочтительный базовый адрес, если сценарий не задаёт допустимый адрес перемещения; это должны быть исполняемые файлы PE32+ x64 с подсистемой native. Импорты могут предоставляться `ntoskrnl.exe`, `ntkrnlmp.exe` или `WDFLDR.SYS`. Загрузчик выполнения поддерживает проверенные базовые релокации x64 `DIR64` и ограниченную конфигурацию загрузки security cookie, который инициализируется детерминированным гостевым значением до запуска обёртки входа. Другие немоделируемые поля конфигурации загрузки, TLS, отложенные/связанные импорты, импорты по ordinal и managed-образы отклоняются. Образы также должны пройти строгую проверку диапазонов и выравнивания.

Активный Control Flow Guard (CFG) проверяет флаги PE, слоты указателей и отсортированные исполняемые цели. Обработчики check/dispatch допускают только объявленные входы образа или зарегистрированные API-thunk, сохраняют состояние вызова Win64 и отклоняют остальные цели. Инструментация без активного CFG сохраняет исходные гостевые резервные указатели. Активный XFG, подавление экспортов и другие немоделируемые политики отклоняются; исполняемая память сама по себе не делает адрес допустимой целью.

Стек WDM может содержать несколько устройств одного гостевого драйвера. `IoAttachDeviceToDeviceStack` присоединяет отдельное исходное устройство над текущей вершиной целевого стека и возвращает прежнюю вершину. Он задаёт `StackSize` и `AlignmentRequirement`, не меняя список `NextDevice` и не копируя флаги буферизации. `IoDetachDevice` принимает сохранённое нижнее устройство и требует `PASSIVE_LEVEL`; присоединение допускается до `DISPATCH_LEVEL`. Открытие именованного нижнего устройства направляет запрос текущей вершине, но `FILE_OBJECT.DeviceObject` и отчёт сохраняют именованную идентичность. READ/WRITE использует флаги выбранной вершины. Сохранённый маршрут удерживает все устройства до возврата диспетчеризации, в том числе после отсоединения/удаления; внутренние ссылки не увеличивают `ReferenceCount`, считающий открытые дескрипторы.

`IofCallDriver` и вспомогательный `IoCallDriver` вызывают точно указанное устройство сохранённого маршрута. Настоящие inline-функции `IoCopyCurrentIrpStackLocationToNext`, `IoSkipCurrentIrpStackLocation` и `IoSetCompletionRoutine` работают с исходным гостевым IRP; проверяются курсор, число позиций и управляющие флаги. Нижняя диспетчеризация возвращает свой фактический статус отдельно от `IoStatus` и результата процедуры завершения. Разворачивание продвигает курсор, выбирает callbacks по успеху/ошибке/отмене и передаёт pending вверх. Вызванная процедура завершения отвечает за эту передачу, включая передачу после прежнего возврата `STATUS_PENDING`. `STATUS_MORE_PROCESSING_REQUIRED` останавливает разворачивание, сохраняя IRP, MDL и буферы; последующее завершение возобновляет его. Вложенное завершение требует внешнего результата остановки; окончательное освобождение выполняется один раз. Продолжения с владельцем-подсистемой сохраняют вложенные кадры WDM/WDF и унаследованный IRQL. Каждая использованная нижняя позиция стека обнуляется перед верхним callback завершения.

IRP питания, IRP, выделенные драйвером, остальные minor-функции PnP и модели оборудования/ресурсов не поддерживаются. Присоединение/перенаправление WDF, присоединение к стеку с активными файлами или callbacks, отсоединение среднего слоя, смена основной функции и цели вне сохранённого маршрута явно отклоняются. Необязательный оригинальный `driver_wdm_stack.c` с настоящим WDK задаётся через `NEVERD_WDM_STACK_FIXTURE` и `NEVERD_WDM_STACK_CFG_FIXTURE`. Нативные тесты и C API/CLI включают перемещение базы; отсутствие артефактов явно отмечается пропуском. Свидетельства выполнения ограничены Linux.

Сценарий может явно задать до 64 `pnp_devices`. Каждый элемент требует `id`, `bus: "resource_free"`, `initial_device_power: "D0"` и `initial_system_power: "working"`; пропущенные факты не угадываются. ID — регистрозависимая ASCII-строка длиной 1–64 байта, начинающаяся с буквы/цифры и далее содержащая только буквы, цифры, `_`, `-`, `.`. Обычный запрос может использовать настроенный `device_id` вместо `device`, но не оба поля. Для `kind: "pnp"` обязательны `device_id`, `minor`, `bus_completion`. Поддерживаются `start`, `query_remove`, `cancel_remove`, `remove`. Обязательный `bus_completion.status` — 32-битное целое или шестнадцатеричная строка; необязательный `delay_100ns` — неотрицательное целое до INT64_MAX, отсчитываемое от фактического получения провайдером. Конечный статус не может быть `STATUS_PENDING`; cancel-remove/remove требуют ровно `STATUS_SUCCESS` (0). Файловые поля, передача и отмена для PnP отклоняются даже при нулевых значениях. C++ API использует ту же предварительную проверку.

```json
{
  "pnp_devices": [
    {"id": "sensor0", "bus": "resource_free", "initial_device_power": "D0", "initial_system_power": "working"}
  ],
  "requests": [
    {"kind": "pnp", "device_id": "sensor0", "minor": "start", "bus_completion": {"status": "0x0", "delay_100ns": 10}},
    {"kind": "pnp", "device_id": "sensor0", "minor": "query_remove", "bus_completion": {"status": "0x0"}},
    {"kind": "pnp", "device_id": "sensor0", "minor": "remove", "bus_completion": {"status": "0x0"}}
  ],
  "unload": true
}
```

После успешного DriverEntry для каждого заданного PDO один раз исполняется `AddDevice`. Провайдер владеет отдельным `DRIVER_OBJECT`; гость не может удалять или подменять его объекты. PnP IRP имеют `KernelMode`, не связаны с файлом, не содержат ресурсов и начинаются с `STATUS_NOT_SUPPORTED`. Ответ шины используется только при фактической передаче в этот PDO; задержка использует общие виртуальные часы и существующие продолжения завершения. Окончательное верхнее завершение фиксирует или откатывает состояние независимо от статуса шины. CREATE и передача требуют Started/D0/Working; после query-remove доступны cleanup/close. Обычное удаление из Started требует успешного query, закрытых файлов, завершённых прежних запросов/callbacks и гостевого отсоединения/удаления. Чистая ошибка AddDevice освобождает только провайдера; утечки новых гостевых устройств, даже отсоединённых, вызывают `model_error`. Перед unload все провайдеры должны отсутствовать. Другие операции PnP, IRP питания, оборудование/ресурсы и KMDF PnP не входят в этот набор. Успех PnP требует фактического завершения провайдера; ранняя верхняя ошибка START/QUERY_REMOVE может оставить наблюдения шины null. Идентичность жизненного цикла устройства/файла сохраняется после отсоединения.

Исходные настройки сохраняются в `configuration.pnp_devices`. Наблюдаемые `pnp_devices` содержат `id`, `pdo`, nullable `add_device_status`, текущее `attached`, `pnp_state`, `provider_present`; после удаления `attached` равно false. Фаза AddDevice — `add_device:<ID>`; ошибки влияют на `scenario_success`, не заменяя `nt_status` DriverEntry. Каждый запрос получает nullable `device_id` и `pnp`; у PnP `file` равен null. Объект `pnp` содержит `minor`, `state_before`, `state_after`, nullable `bus_status`, `bus_received_at_100ns`, `bus_completed_at_100ns`. Настроенный статус становится наблюдением только при фактическом завершении на шине; время получения независимо. Типы прежних полей не меняются.

PnP без ресурсов использует оригинальный `driver_wdm_pnp.c` с настоящим WDK, необязательные `NEVERD_WDM_PNP_FIXTURE`/`NEVERD_WDM_PNP_CFG_FIXTURE` и нативные тесты/C API/CLI. Отсутствие артефактов явно пропускается; выполнение проверено только на Linux.

KMDF 1.33 использует точную ABI 1.33.0: 458 слотов функций имеют стабильные гостевые идентификаторы, а 38 перечисленных ниже API реализуют семантику исполнения. `WdfVersionBind` и `WdfVersionUnbind` управляют гостевой привязкой вокруг настоящей оболочки WDK `FxDriverEntry`. `WdfGetDriver` читает публичные глобальные данные драйвера. Драйверы без PnP, общие объекты, управляющие устройства, очереди и входящие запросы используют типизированные контексты, счётчики ссылок и исполняемые обратные вызовы очистки/уничтожения/выгрузки. Все моделируемые вызовы и обратные вызовы фреймворка пока требуют `PASSIVE_LEVEL`; добавление ссылок после завершения очистки остаётся вне этого профиля. Немоделируемые слоты, `WdfLdrQueryInterface`, расширения классов и UMDF явно останавливают исполнение.

Управляющие устройства требуют скопированного имени из печатных ASCII-символов и строго заданной SDDL `D:P(A;;GA;;;WD)`. Она разрешает доступ всем, не требуя выдуманного токена вызывающей стороны; другие дескрипторы безопасности, безымянные устройства и автоматические имена не поддерживаются. Инициализация владеет одним устройством WDM. Запросы могут выбирать его в существующем пространстве имён сеанса через псевдонимы символических ссылок `\DosDevices\Name` или `\??\Name`; в отчёте сохраняется каноническое имя устройства. Успешное создание потребляет объект инициализации и обнуляет его указатель; ошибка отменяет частично установленное владение устройством. `WdfControlFinishInitializing` разрешает доставку ввода-вывода. Удаление убирает устройство и его ссылки только тогда, когда это допускают моделируемые файлы, рабочие элементы и запросы; отмена или опустошение очереди запросов при удалении не поддерживаются.

Структура `WDF_IO_QUEUE_CONFIG` размером 96 байт поддерживает последовательную очередь по умолчанию с явно заданным пассивным исполнением и без синхронизации фреймворка. Очереди управляющих устройств не участвуют в управлении питанием. Специализированные обратные вызовы READ/WRITE/IOCTL имеют приоритет над вызовом по умолчанию. Принятые в очередь запросы возвращают `STATUS_PENDING` даже при синхронном завершении; регистр возврата void-функции не завершает её запрос. Отложенное завершение использует существующий планировщик. Без обработчика запрос завершается с `STATUS_INVALID_DEVICE_REQUEST`; READ/WRITE нулевой длины завершается без доставки, если она не включена. Стандартный файловый пакет успешно завершает CREATE/CLEANUP/CLOSE с Information=0. Параллельные/ручные очереди, файловые обратные вызовы, устройства PnP и полный PnP/питание не поддерживаются.

Параметры запроса используют 40-байтную структуру `WDF_REQUEST_PARAMETERS`. Функции доступа к вводу/выводу возвращают логические длины, сохраняя алиасы буферов и существующие MDL-отображения прямого ввода-вывода; вход прямого IOCTL остаётся буферизованным. Неверное направление и недостаточный буфер возвращают документированные статусы. Завершение выполняет очистку запроса и уничтожение дочерних объектов до аннулирования IRP и буферов, затем уничтожает запрос, когда это допускают ссылки. Новые вызовы функций доступа к буферам и параметрам отклоняются с начала завершения; ранее полученные указатели буферов остаются доступны во время очистки. Внешняя ссылка сохраняет контекст, но не доступ к завершённому IRP. Пользовательский `METHOD_NEITHER` по-прежнему требует нереализованной поддержки контекста вызывающей стороны, проверки доступа и блокировки.

Отмена моделируется для запросов описанных выше очередей управляющих устройств. Если отмена уже произошла, `WdfRequestMarkCancelableEx` возвращает `STATUS_CANCELLED` без обратного вызова. Успешный `WdfRequestUnmarkCancelable` снимает обработчик; последующая отмена лишь записывает состояние отмены. `WdfRequestIsCanceled` читает это состояние у живого запроса без отметки об отменяемости. После успешной отметки об отменяемости завершение требует успешного снятия отметки либо начала доставки обратного вызова отмены: постановки в очередь недостаточно. После начала доставки обработчик может согласовать завершение с рабочим элементом, в том числе во время собственного ожидания. Отдельная внутренняя ссылка удерживает запрос до возврата обработчика отмены. При завершении IRP всё равно становится недействительным первым, а заключительное продолжение уничтожения запроса тоже может ожидать. Приоритет имеют DPC, затем обработчики отмены в порядке FIFO, затем обычные рабочие элементы; обработчики отмены также предшествуют возобновлению готовых пассивных ожиданий.

Для уже отменённого запроса прежний void-метод `WdfRequestMarkCancelable` синхронно выполняет гостевой обработчик отмены до своего возврата. Дочернее продолжение может ожидать, завершить запрос через вложенную очистку и выполнить окончательное уничтожение до возобновления исходного API. Отмена после регистрации использует описанный выше планируемый путь. Это воспроизводит публичный код при `PASSIVE_LEVEL` и `WdfSynchronizationScopeNone`; [Microsoft](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdfrequest/nf-wdfrequest-wdfrequestmarkcancelable) требует от драйверов без автоматической синхронизации использовать Ex. Здесь реализована совместимость, а не рекомендация применять прежний API в такой конфигурации.

`WdfRequestGetInformation` и `WdfRequestSetInformation` используют исходное 64-битное поле `IRP.IoStatus.Information`, включая прямую запись гостя. Set лишь присваивает значение; длина передачи проверяется при завершении. `WdfRequestCompleteWithInformation` записывает то же поле до очистки; изменения через заранее сохранённый IRP во время очистки определяют итоговый Information, хотя GetInformation в этой фазе уже возвращает ноль. `WdfRequestGetIoQueue` возвращает исходную очередь. При стандартной файловой конфигурации `WdfRequestGetFileObject` возвращает NULL, не выдавая WDM FILE_OBJECT за файловый объект WDF. `WdfRequestWdmGetIrp` возвращает тот же IRP; гостевые `IoCompleteRequest`/`IofCompleteRequest` не могут обойти завершение WDF. Пока дескриптор запроса действителен во время или после завершения, GetInformation/GetIoQueue возвращают ноль; получение MDL сначала записывает NULL в допустимый выход, затем возвращает `STATUS_INTERNAL_ERROR`. SetInformation/GetFileObject/WdmGetIrp в этой фазе отклоняются. Ограничения существующих функций буферов и параметров не меняются.

`WdfRequestRetrieveInputWdmMdl` и `WdfRequestRetrieveOutputWdmMdl` по требованию описывают имеющийся SystemBuffer для буферизованных входа WRITE, выхода READ и входа/выхода IOCTL. Направление должно быть допустимым и ненулевой длины до использования единственного кэшированного MDL запроса; первое успешное получение фиксирует ByteCount даже при иной логической длине другого направления. `MmGetSystemAddressForMdlSafe` возвращает исходный VA; дополнительные отображения, их снятие и освобождение драйвером запрещены. Прямые выходы READ/IOCTL и вход WRITE возвращают исходный `IRP.MdlAddress`, не создавая отображения самим получением; вход прямого IOCTL использует кэш SystemBuffer. MDL, IRP и буферы прекращают существование при завершении. Внутренние ссылки отмены и внешние ссылки сохраняют только контекст WDF. `METHOD_NEITHER` и доступ к физическим PFN остаются неподдерживаемыми.

Моделируемые API KMDF: `WdfDriverCreate`, `WdfDriverGetRegistryPath`, `WdfDriverWdmGetDriverObject`, `WdfWdmDriverGetWdfDriverHandle`, `WdfObjectGetTypedContextWorker`, `WdfObjectAllocateContext`, `WdfObjectContextGetObject`, `WdfObjectReferenceActual`, `WdfObjectDereferenceActual`, `WdfObjectCreate`, `WdfObjectDelete`, `WdfControlDeviceInitAllocate`, `WdfDeviceInitFree`, `WdfDeviceInitAssignName`, `WdfDeviceInitSetIoType`, `WdfDeviceCreate`, `WdfDeviceCreateSymbolicLink`, `WdfControlFinishInitializing`, `WdfDeviceWdmGetDeviceObject`, `WdfIoQueueCreate`, `WdfDeviceGetDefaultQueue`, `WdfIoQueueGetDevice`, `WdfRequestComplete`, `WdfRequestCompleteWithInformation`, `WdfRequestGetParameters`, `WdfRequestRetrieveInputBuffer`, `WdfRequestRetrieveOutputBuffer`, `WdfRequestRetrieveInputWdmMdl`, `WdfRequestRetrieveOutputWdmMdl`, `WdfRequestSetInformation`, `WdfRequestGetInformation`, `WdfRequestGetFileObject`, `WdfRequestGetIoQueue`, `WdfRequestWdmGetIrp`, `WdfRequestMarkCancelable`, `WdfRequestMarkCancelableEx`, `WdfRequestUnmarkCancelable`, `WdfRequestIsCanceled`.

Необязательная проверка с настоящим WDK отдельно компилирует `driver_kmdf_lifecycle.c` и `driver_kmdf_control.c` с подлинной библиотекой входа KMDF. `NEVERD_KMDF_FIXTURE` / `NEVERD_KMDF_CFG_FIXTURE` выбирают образы жизненного цикла; `NEVERD_KMDF_CONTROL_FIXTURE` / `NEVERD_KMDF_CONTROL_CFG_FIXTURE` выбирают обычный образ управляющего устройства и вариант с активным CFG. Отсутствующие внешние артефакты явно пропускаются. Нативная и C API/CLI-проверка описана в [тестировании](testing.md). Текущие доказательства исполнения ограничены Linux.

Пределы IRQL заданы в `KernelAPIIRQL.def`; зависимые от аргументов правила проверяет соответствующая модель. DPC не может вызывать API реестра, выделять, освобождать или читать/писать страничный пул. Unicode-преобразования `DbgPrint` требуют `PASSIVE_LEVEL`, поддерживаемые ANSI-вывод и операции с нестраничной памятью доступны на `DISPATCH_LEVEL`. Стеки ограничены: вышедший за границы указатель не может попасть в стек другого заблокированного рабочего потока. Активные таймеры в расширении устройства запрещают преждевременное освобождение устройства. Общие изменения IRQL не предоставляются.

Истечение таймера удовлетворяет зарегистрированные ожидания до того, как DPC сбросит или переустановит таймер. DPC из очереди выполняются раньше возобновления пробуждённых кадров `PASSIVE_LEVEL`. Если память запроса ещё содержит DPC в очереди, завершение IRP отвергает её освобождение до завершения и аннулирования буфера.

Форматирование `DbgPrint` поддерживает целые `d/i/u/o/x/X`, указатель `p`, текст `s/c`, `%%`, Unicode с заданной длиной `wZ/lZ`, широкие строки `ls/ws`, флаги, ширину/точность, включая `*`, и модификаторы длины целых Windows. Считывается не более 32 переменных аргументов и 1024 байтов формата. Ширина и точность ограничены 512. Числа с плавающей точкой, `%n`, неизвестные сочетания и преобразования текста вне ASCII явно останавливают выполнение; модель не угадывает кодовую страницу Windows и не вызывает хостовый printf для гостевых данных.

Время жизни исходных записи и буфера RegistryPath заканчивается при возврате DriverEntry. Если строка нужна позже, драйвер должен скопировать её во время инициализации.

Арена объектов/пула занимает 1 MiB. Неинициализированные байты пула имеют детерминированное содержимое `0xCD`, освобождённые — `0xDD`. Это один конкретный сценарий выполнения. Доступы CPU и моделируемые буферные API отклоняют обращения к освобождённым выделениям пула, удалённым устройствам, невыделенным байтам арены, непрозрачным полям объектов и запись в поля объектов только для чтения. Эти проверки охватывают время жизни объектов данной модели; это не общий анализ безопасности памяти драйвера. Незаписанные слоты таблицы диспетчеризации показываются нулём со значением «не зарегистрирован». Запрос сценария к незарегистрированной основной функции завершается моделируемым обработчиком по умолчанию с `STATUS_INVALID_DEVICE_REQUEST`; ошибка остаётся видимой и в статусе диспетчеризации, и в статусе ввода-вывода. Модель не выдумывает гостевой адрес функции для этого обработчика, а чтение гостем незаписанного слота по-прежнему не поддерживается. Явная регистрация null-указателя обратного вызова является ошибкой.

## Сценарии запросов

Передайте JSON-файл через `--scenario`, чтобы выбрать запросы и необязательную выгрузку:

```bash
build-release/bin/neverd emulate-driver path/to/driver.sys \
  --scenario scenario.json > driver-report.json
```

Пример `scenario.json` для драйвера, создающего `\Device\NeverDIO` и принимающего буферизованный IOCTL `0x222000`:

```json
{
  "requests": [
    {"kind": "create", "device": "\\Device\\NeverDIO"},
    {"kind": "ioctl", "code": "0x222000", "input": "00112233", "output_size": 4},
    {"kind": "cleanup"},
    {"kind": "close"}
  ],
  "unload": true
}
```

Имя устройства и код IOCTL должны соответствовать драйверу. При create отсутствие `device` выбирает единственное живое устройство; неоднозначный выбор завершается ошибкой. Последующие запросы используют устройство своего файла, если явно не указано совпадающее имя. Необязательный `file` — беззнаковый 32-битный идентификатор сценария, по умолчанию ноль. У каждого идентификатора собственные FILE_OBJECT и FsContext, а порядок операций — create, передачи, cleanup, close. Запросы независимых файлов могут чередоваться. Эксклюзивные устройства отклоняют второе открытие. Эти идентификаторы представляют файловые объекты, а не дублированные дескрипторы. Поддерживаются buffered и оба метода direct IOCTL. Диспетчеризация должна завершить IRP синхронно либо соблюдать описанный выше контракт обратных вызовов для ожидающего запроса. Недопустимая длина вывода и доступ к завершённому IRP явно завершаются ошибкой. Запрошенная выгрузка не должна оставлять живые устройства, символические ссылки, выделения пула или файловые объекты.

Необязательное корневое поле `"load_address": "0x190000000"` запрашивает изменение базового адреса; отсутствие поля или `"0x0"` означает предпочтительный адрес. Образ должен удовлетворять требованиям релокации. Исходная команда инициализации и C API не подразумевают никакого сценария.

В корне допустимы только `load_address`, `requests`, `unload`, `kernel_exports`, `registry` и `pnp_devices`. Запросы, кроме PnP, принимают `kind`, необязательные `device` или `device_id` (взаимоисключающие) и `file`. Для IOCTL обязателен `code`, допустимы `input`, `output_size` и `direct_input`. Запрос `read` принимает `output_size` и `byte_offset`; `write` — `input` и `byte_offset`. Смещения по умолчанию равны нулю, принимают целые числа или шестнадцатеричные строки и должны помещаться в неотрицательное знаковое 64-битное значение. Запросы жизненного цикла отклоняют поля передачи данных. Неизвестные или повторяющиеся поля отклоняются. `code` принимает беззнаковое 32-битное целое JSON или шестнадцатеричную строку с `0x`. `input` — шестнадцатеричная строка байтов чётной длины без префикса и пробелов; отсутствие означает пустой ввод. `output_size` — беззнаковое целое JSON, по умолчанию ноль. Дроби и записи с плавающей точкой отклоняются.

Только READ/WRITE/IOCTL принимают необязательное поле `cancel_after_100ns`, целое число JSON от 0 до `INT64_MAX` (9223372036854775807). Задержка отсчитывается от подачи запроса в виртуальных единицах по 100 нс, а не в реальном времени. Ноль применяет отмену после маршрутизации фреймворком и до гостевого обработчика ввода-вывода; если маршрутизация уже завершила запрос, завершение имеет приоритет. При положительной задержке время продвигается к сроку таймера, ожидания или отмены только при отсутствии готовых обработчиков и кадров. Настройка отмены WDM останавливает исполнение с `model_error`; общая отмена очередей и PnP остаётся неподдерживаемой. Каждый отчёт о запросе содержит `cancel_requested_at_100ns`: фактическое абсолютное виртуальное время отмены либо null, если её не было, в том числе когда завершение произошло раньше. Запрос отмены сам по себе не завершает IRP и не определяет его итоговый статус.

Для direct IOCTL поле `input` инициализирует первый системный буфер, а `direct_input` — отдельный второй буфер, описанный MDL, с дополнением нулями до `output_size`. `METHOD_IN_DIRECT` требует доступа на чтение, но не означает системное отображение только для чтения. Оба метода используют доступные для чтения и записи буферы сценария. `MdlMappingNoWrite` снимает право записи отображения, а `MdlMappingNoExecute` — право исполнения. Снятие отображения отзывает системный VA; повторное отображение сохраняет те же зафиксированные данные. Завершение прекращает время жизни MDL и отображения. Публичные поля MDL, используемые макросами WDM, моделируются; поля process/PFN, вручную созданные MDL, пользовательские отображения и прямой доступ через исходный UserBuffer отклоняются. У direct-буфера нулевой длины MDL равен null.

`IoAllocateMdl` выделяет независимые метаданные для непустого буфера без переполнения адреса размером не более 1 MiB; буфер при этом не проверяется и не фиксируется. `Irp` должен быть NULL, а `SecondaryBuffer` и `ChargeQuota` — FALSE. При исчерпании арены возвращается NULL. `MmBuildMdlForNonPagedPool` требует, чтобы весь диапазон находился внутри одного живого блока невыгружаемого пула. Безопасная вспомогательная функция и обычные макросы WDM используют исходный адрес, сохраняя общую память и существующие права даже при новых флагах запрета записи/исполнения. Дополнительные системные отображения и снятие отображения отклоняются. `IoFreeMdl` завершает только время жизни дескриптора; буфер пула имеет независимое время жизни. Допустимы оба порядка освобождения, если освобождённая память больше не используется. Все моделируемые поля MDL доступны только для чтения; доступ к process/PFN, цепочки и ручное изменение полей не поддерживаются. При выгрузке должны быть освобождены все MDL драйвера.

Для любого метода IOCTL при ненулевом `output_size` значение `Information` не должно превышать `output_size`, даже если входной буфер больше. Если выходного буфера нет, `Information` может содержать определённый драйвером 64-битный результат; это значение не используется как число копируемых байтов. Отчёт сохраняет числовое значение и добавляет точную шестнадцатеричную строку `information_hex` для клиентов JSON, которые не могут представить все 64-битные целые.

Для READ/WRITE метод передачи выбирают `DO_BUFFERED_IO` или `DO_DIRECT_IO`. Neither и конфликтующие флаги останавливают выполнение. Information проверяется относительно длины передачи; запись возвращает количество, чтение — байты.

`kernel_exports` сопоставляет именам процедур явные логические значения доступности, например `"kernel_exports": {"OptionalRoutine": false}`. Моделируемые экспорты и статические импорты получают стабильные адреса, общие с `MmGetSystemRoutineAddress`. Явно отсутствующий экспорт разрешается в NULL и не может удовлетворить статический импорт. Экспорт, объявленный присутствующим, но не имеющий модели API, разрешается в отложенную ловушку. Неизвестное динамическое имя останавливает выполнение с диагностикой неопределённой доступности; отсутствие никогда не выводится из отсутствия реализации. Имена ограничены по длине и состоят из печатных ASCII-символов; разрешение учитывает регистр. Реестр — свойство конкретного сценария, а не утверждение о соответствии каждому выпуску Windows.
`IoMarkIrpPending`, `IoGetCurrentIrpStackLocation` и `MmGetSystemAddressForMdlSafe` — моделируемые вспомогательные функции заголовков WDM; это не объявляет их экспортируемыми по умолчанию, поэтому их доступность как экспортов требует статического импорта или явного объявления в `kernel_exports`.

Текст сценария ограничен 2 MiB; допускается не более 64 запросов, не более 65536 байтов на каждый входной или выходной буфер и не более 512 KiB запрошенных байтов суммарно, включая содержимое `direct_input`. Бюджеты инструкций, наблюдений, гостевой памяти и времени действуют на весь сценарий. Арена 1 MiB также содержит объекты и метаданные, поэтому образ может исчерпать память модели до использования максимального объёма буферов сценария.

## Сценарии реестра

Необязательный массив `registry` задаёт конкретное дерево реестра внутри сеанса.
У каждой записи ключа есть обязательный `path` и необязательный массив `values`;
каждое значение содержит `name`, беззнаковое целое `type` и шестнадцатеричные
`data`. Пустое имя выбирает значение по умолчанию. Например, значение DWORD
задаётся как `{"name":"Mode","type":4,"data":"01000000"}`. Байты сохраняются
точно: модель не исправляет завершающие нули строк и не раскрывает переменные
окружения.

Пути должны быть абсолютными ASCII-путями внутри `\\Registry\\Machine` или
`\\Registry\\User`. Родительские ключи создаются неявно. Имена ключей и значений
сравниваются без учёта регистра по правилам ASCII; имена вне ASCII и дубликаты
отклоняются. Если `registry` отсутствует, доступность реестра не определена и
вызовы реестра останавливают выполнение. `"registry": []` явно задаёт пустое
пространство имён. Ключи, значения, данные реестра хоста и настройки службы не
выводятся из самого драйвера.

`ZwOpenKey` и `ZwCreateKey` возвращают независимые непрозрачные дескрипторы;
права каждого дескриптора проверяются при запросе, записи, создании дочерних
ключей и удалении. Настроенное дерево предоставляет поддерживаемые биты
`KEY_ALL_ACCESS`, включая обычные маски `KEY_READ` и `KEY_WRITE`. Это явно
доступное тестовое дерево без ACL Windows и проверки привилегий. Общие права,
`MAXIMUM_ALLOWED`, альтернативные представления реестра, пользовательские
дескрипторы безопасности, классы и символические ссылки не поддерживаются.
Относительное создание требует дескриптора непосредственного родителя с
`KEY_CREATE_SUB_KEY`. Входные ключи энергонезависимы; новые ключи могут быть
временными (volatile), но создание энергонезависимого дочернего ключа внутри
временного отклоняется. Перезагрузка и сохранение на диск не моделируются.

`ZwQueryValueKey` реализует классы Basic, Full, Partial и их определённые
варианты Align64: точные размеры, выровненные данные, частичные результаты и
различающиеся статусы `STATUS_BUFFER_TOO_SMALL` и `STATUS_BUFFER_OVERFLOW`.
`ZwSetValueKey` и `ZwDeleteValueKey` изменяют только дерево этого сеанса.
`ZwDeleteKey` отклоняет удаление ключа с существующими дочерними ключами;
дескрипторы удалённого ключа возвращают `STATUS_KEY_DELETED` до закрытия.
`ZwClose` освобождает дескриптор независимо от ключа; запрошенная выгрузка
завершается ошибкой, пока остаются открытые дескрипторы реестра.

Ограничения: 256 ключей с учётом родителей, 1024 значения, 65536 байтов на
значение, 512 KiB данных значений суммарно, 1024 байта ASCII на путь ключа,
256 байтов на имя значения и 256 одновременно открытых дескрипторов. Создание
и изменения соблюдают те же ограничения, что и предварительная проверка
сценария. Поле отчёта `configuration.registry` сохраняет исходные входные
данные, а `registry` перечисляет итоговые пути и значения существующих ключей,
включая изменения до остановки. Неопределённое состояние реестра представлено
как null. Признак volatile и идентификаторы дескрипторов не входят в этот снимок.

## Проверка примера Microsoft

Запускаемый по желанию [скрипт проверки](../../scripts/validate_windows_driver_sample.py) загружает исходники Microsoft SIOCTL ревизии, закреплённой в [манифесте проверки](../../unittests/emulation/fixtures/sioctl-validation.json), проверяет хеши SHA-256 и компилирует неизменённый исходный код с заголовками MinGW-w64 DDK. В выбранном выходном каталоге сохраняются исходная лицензия/происхождение, команды сборки, сценарий и отчёты. Нужны доступ к сети, Clang, `lld-link`, `nm` и заголовки DDK из MinGW-w64:

```bash
python3 scripts/validate_windows_driver_sample.py \
  --neverd build-release/bin/neverd \
  --output build-release/driver-validation/sioctl
```

Для нестандартного каталога заголовков MinGW-w64 используйте `--headers`. Скрипт создаёт библиотеку импорта MS COFF из зависимостей скомпилированного объектного файла. Проверка запускает отдельные сценарии buffered, in-direct и out-direct через DriverEntry, create, IOCTL, cleanup, close и unload. Добавьте `--debug` и выберите отдельный выходной каталог, чтобы скомпилировать с `DBG=1` и проверить гостевые сообщения журнала. Исходный пример не регистрирует обработчик cleanup, поэтому моделируемый обработчик по умолчанию завершает cleanup с `STATUS_INVALID_DEVICE_REQUEST` (`0xC0000010`). Драйвер всё же закрывается и выгружается, а успешный IOCTL возвращает ожидаемые байты. Для этого полного сценария ожидаемый код выхода CLI — **2**, а `scenario_success` равен false. Сам скрипт завершается успешно только при совпадении всех этих результатов, включая видимый сбой cleanup; он не переписывает пример, чтобы скрыть этот результат.

## Отчёты и SDK

JSON-отчёт различает `stop_reason`, допускающие null поля `nt_status` и `nt_success`, PC остановки и число инструкций. Он сохраняет вызовы API и наблюдаемое состояние до остановки, включая объекты устройств и адреса обратных вызовов драйвера. Гостевые адреса представлены шестнадцатеричными строками, чтобы потребители JSON не теряли 64-битную точность. Объект `configuration` записывает ограничения запуска, имя службы, переопределения `kernel_exports` и входное дерево `registry`. Профиль — `wdm-x64-scheduled-v8`. Поле `nt_status` остаётся результатом DriverEntry, а `scenario_success` описывает инициализацию и завершённые запросы вместе. `phase`, `requests` и `unload_completed` показывают, какие части запрошенного жизненного цикла были выполнены. Каждый вызов API и каждая запись CPU также содержат фазу (`driver_entry`, `add_device:<ID>`, `request:N`, `callback:N` или `unload`). Для каждого запроса приводятся статусы диспетчеризации и ввода-вывода, завершение, длина информации и возвращённые байты `output_hex`. `preferred_image_base` описывает исходный базовый адрес PE. `security_cookie` — гостевой адрес инициализированного cookie либо `"0x0"`, если он не требовался. Поля запроса: `kind`, `device`, `device_id`, `pnp`, `file`, `byte_offset`, `code`, `irp`, `completed`, `cancel_requested_at_100ns`, `dispatch_status`, `io_status`, `information`, `information_hex` и `output_hex`. Числовое поле `information` остаётся точным десятичным целым JSON; `information_hex` сохраняет те же биты и для клиентов, читающих числа JSON с точностью только до 53 бит.

Наблюдения рабочих элементов имеют фазу `callback:N`. Для ожидающего запроса `dispatch_status` сохраняет `STATUS_PENDING`; окончательный статус отдельно записывается в `io_status` и определяет вклад в `scenario_success`.

Объект `fault`, допускающий null, сохраняет первую ошибку бэкенда. Его `kind`, `pc` и допускающие null поля `address`, `size`, `access` и `interrupt` различают неотображённую или защищённую память, недопустимые диапазоны, недопустимые инструкции и исключения CPU. Адреса представлены шестнадцатеричными строками, размеры и векторы прерываний — целыми числами. Чтение для наблюдения не может заменить исходную ошибку. Бэкенд с ошибкой не может продолжить выполнение, и эта запись не подразумевает обработку гостевых SEH.

`instructions` считает допущенные попытки выполнения гостевых инструкций. Инструкция, отклонённая политикой выполнения, не учитывается; допущенная инструкция, вызвавшая ошибку CPU, учитывается. Синтетическая диспетчеризация API и маркер возврата не увеличивают этот счётчик.

Каждая запись `writes` имеет `semantics: "attempted_guest_write"`: она описывает попытку записи CPU вне стека, включая попытку, которая позднее может вызвать ошибку или остановку по бюджету. Это не гарантия завершённой записи; записи моделей API сюда не входят. Снимки устройств и объекта драйвера описывают состояние, наблюдаемое при остановке выполнения.

Подключите `neverd/sdk/NeverDCAPIEmulation.h` (либо общий заголовок C API), создайте сеанс и вызовите `neverd_emulate_driver_json(session, path, options)`. Явно заданный непустой путь сразу запускает строгую предварительную проверку выполнения без начальной загрузки через общий API анализа. CLI использует этот путь. Передача `NULL` в качестве options выбирает значения по умолчанию. Явные параметры `neverd_driver_options_v1` требуют точного `struct_size` и положительных бюджетов инструкций, памяти, событий и времени. Освободите результат через `neverd_free_string`.

Передача `NULL` вместо пути требует загруженного сеанса и заново разбирает его файл независимо от анализа IR и загрузки с ограничением по функциям. Оба пути сохраняют образ сеанса. В течение вызова входной файл должен оставаться доступным и неизменным. Ошибки запроса/настройки возвращают `NULL` и устанавливают `neverd_last_error`; остановки выполнения возвращают JSON. API доступен и в сборках с отключённой функцией и сообщает, как её включить.

`neverd_emulate_driver_scenario_json(session, path, scenario_json, options)` использует те же параметры v1 и правила владения, добавляя строгий ввод сценария. Требуется не-NULL строка JSON с завершающим NUL. Исходный ABI `neverd_emulate_driver_json` остаётся неизменным и выполняет только инициализацию. C++-парсер `driverOptionsFromScenarioJSON` предоставляет ту же проверку сценария вызывающим `emulateDriver`.

Внутренняя точка входа C++ — `neverd::emulation::emulateDriver` в `include/neverd/emulation/DriverSession.h`. Разбор формата относится к существующему загрузчику; поведение объектов/API Windows — к `lib/emulation/windows`; состояние CPU и выполнение — к адаптеру Unicorn. Адаптер и модель используют один интерфейс гостевой памяти. Поведение Windows API не должно находиться в форке Unicorn.
