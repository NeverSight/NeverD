# Восстановление мобильных приложений

[← Указатель документации](README.md) · [Полное руководство по Android](android.md) · [Полное руководство по iOS](ios.md)

`neverd mobile` восстанавливает читаемый Java из входов Android APK, DEX и smali. Для входов iOS IPA, `.app` и Mach-O он экспортирует нативный C и реконструирует поддерживаемые тела методов Objective-C в исходники `.m`, вместе с экспериментальными исходниками Swift и метаданными среды выполнения. Это экспериментальный процесс CLI; мобильные контейнеры не принимаются нативным C SDK или загрузчиком GUI.

## Подготовка

Соберите цель `neverd` с поддержкой C++20. Мобильный процесс встроен в нативную CLI и не использует интерпретатор Python. Распространяйте исполняемый файл вместе с нативными библиотеками, необходимыми вашей сборке.

Нативная обработка ZIP использует zlib для CRC-32 и DEFLATE. CMake предпочитает установленную библиотеку через `find_package`; иначе он загружает zlib 1.3.2 с закреплённым SHA256 и собирает её статически. Этой мобильной реализации ZIP не нужны вспомогательные инструменты Python в Windows. Сохраняйте уведомления о зависимостях из [THIRD_PARTY_NOTICES.md](../../THIRD_PARTY_NOTICES.md).

Движок по умолчанию реализован на C++20 и не требует среды выполнения Python, Java или JADX. Только явный `--jadx PATH` выбирает отдельно установленный адаптер совместимости; `NEVERD_JADX` и PATH не выбирают его автоматически, и автоматического перехода к нему нет. Необязательный адаптер требует JADX 1.5.6+ со стандартными плагинами входов DEX/smali и Java 11+. Его отчёт указывает фактический движок `jadx` и версию. Установка и лицензии зависимостей описаны в [руководстве по Android](android.md#необязательный-адаптер-совместимости-jadx).

## Android

Для быстрого списка классов без восстановления Java используйте
`neverd mobile app.apk --list-classes`, при необходимости с
`--class-prefix com.example` или `--json`.
[Контракт инвентаризации](android.md#быстрая-инвентаризация-классов) описывает
порядок, ограничения и проверку выбранного содержимого. Режим запроса не требует
каталога вывода; его необязательный `-o` задаёт новый файл.

Для прямых ссылок в байткоде используйте
`neverd mobile app.apk --find-refs string --query 'example' --json`.
[Контракт запросов ссылок](android.md#запросы-ссылок-в-коде) также охватывает
операнды типов, методов и полей, буквальное/точное сопоставление, позиции каждого
вхождения, сохранение UTF-16 и границы проверки кода. Без `--json` эта операция
выводит JSON Lines. Для неё действует то же поведение `-o`, требующее нового файла.

Следующие примеры и описание вывода относятся к восстановлению.

```sh
neverd mobile app.apk -o recovered-app
neverd mobile classes.dex -o recovered-dex
neverd mobile MainActivity.smali -o recovered-class
neverd mobile decoded/smali -o recovered-java
```

Все корневые `classes.dex`, `classes2.dex` и последующие пронумерованные DEX-файлы в APK анализируются вместе. Каталог smali просматривается рекурсивно, и все его классы анализируются за один вызов, включая вложенные и соседние классы. Используйте каталог при восстановлении классов, ссылающихся друг на друга. Отдельный файл smali предоставляет только свой класс.

Вывод встроенного восстановления содержит `sources/`, `metadata/android-methods.json` и `report.json` с `backend: {"name": "neverd", "version": "1", "execution": "builtin"}`. Отчёт включает `android_method_recovery`: `method_count = recovered_method_count + declaration_only_method_count`, причём `unrecovered_method_count` должен равняться нулю перед публикацией. Исходные объявления `native`/`abstract` учитываются отдельно от восстановленных тел. Явно выбранный внешний адаптер сохраняет собственные журналы бэкенда. Ресурсы APK, манифесты, нативные библиотеки и динамически загружаемый код находятся вне этого пути Java; нативные библиотеки можно отдельно анализировать с помощью `neverd decompile`.

Встроенные средства чтения для восстановления совместно используют независимо реализованную типизированную модель Dalvik и генератор Java с ограниченным объёмом работы для представимого обычного кода DEX 035/037–040 и smali. DEX 041, динамические вызовы вроде `invoke-custom`, некоторые пути инициализации, неизвестные операции и идентификаторы, непредставимые в Java, явно вызывают ошибку. Сгенерированный Java может использовать цикл диспетчеризации; он не выполняет исходный DEX и не вызывает его через мост среды выполнения. Исходные комментарии, форматирование и удалённые имена восстановить нельзя. Экспериментальный движок не обещает функционального равенства с JADX, семантической эквивалентности или полного восстановления произвольных APK.

## iOS

[Полное руководство по iOS](ios.md) описывает выбор IPA, `.app` и Mach-O, подготовку, все параметры CLI, схемы исходников, покрытие и проверку.

```sh
neverd mobile App.ipa -o recovered-ios
neverd mobile App.app -o recovered-arm64 --arch=arm64
neverd mobile App.app -o framework-analysis --artifact Frameworks/Example.framework/Example
neverd mobile executable -o metadata --metadata-only
```

Каждый запуск выбирает один исполняемый файл. `--artifact` задаётся относительно пакета приложения и для IPA, и для `.app`. При выборе среза fat-бинарника приоритет имеют arm64, arm, x86_64, затем i386; проекция в исходный язык нацелена на arm64/x86_64. Зашифрованные выбранные срезы отклоняются. Экспериментальный нативный путь выводит C и поддерживаемые тела методов Objective-C, включая привязки ABI скаляров/указателей, чисел с плавающей точкой, смешанных аргументов и стека. Раскладки классов/ivar среды выполнения и отдельные категории сохраняются после проверки; неразрешённые раскладки, сигнатуры, вызовы и прочие зависимости остаются явно отмеченными пропусками.

Восстановление Swift классифицирует сигнатуры внутри процесса C++ с помощью `LLVMSwiftDemangle` из форка LLVM NeverD. Оно не запускает внешний деманглер или команду поиска инструментальной цепочки и не требует установленного компилятора Swift для сборки или запуска NeverD. Сборки из исходников форка и соответствующие пакеты LLVM включают этот компонент; NeverD не загружает отдельную зависимость с исходниками Swift. Инвентарь сигнатур записывает `demangler: {"name": "llvm-swift-demangle", "execution": "builtin", "version": "6.3.3"}`. Поддерживаемые сигнатуры привязываются к нативным точкам входа и расположениям ABI до вывода настоящих функций `.swift`, методов/инициализаторов классов и методов структур с фиксированной раскладкой. Обобщённые/устойчивые к изменению раскладки, асинхронные/выбрасывающие исключения формы, неподдерживаемые вызываемые формы, генерируемые средой выполнения, и неполные группы зависимостей исходников остаются невосстановленными.

Обычный вывод включает `sources/native.c`, необязательные `sources/objc.m` и `sources/swift.swift`, объявления и метаданные среды выполнения, JSON покрытия методов/сигнатур, журналы, `artifacts/selected.macho` и `report.json`. Журналов поиска внешней инструментальной цепочки Swift или внешнего деманглинга нет. Сгенерированный исходный код не вызывает исходный бинарник как мост восстановления. Swift `source_units` группирует объявления типов и методы; строки отдельных методов нельзя просто объединять для реконструкции классов. Внешний `status: "success"` означает публикацию вывода, а не полное покрытие методов или семантическую эквивалентность.

`--metadata-only` не запускает ни экспортёр нативных исходников, ни деманглинг сигнатур и не выводит исходники или покрытие методов. Все режимы используют разрешённые метаданные Objective-C нативного загрузчика. Метаданные Swift используют ограниченные чтения нативного образа; неподдерживаемые fixup, перемещаемые раскладки или ссылки сохраняют частичную диагностику. `--max-func` ограничивает восстановление нативных функций и игнорируется в режиме только метаданных. Отсутствующие тела нативных функций приводят к ошибке обычного запуска. Временные распакованные входы удаляются.

Исходные комментарии, форматирование, удалённые идентификаторы и структуры исходного кода, утраченные при компиляции, нельзя реконструировать точно. Перед использованием вывода изучите статус и причину восстановления каждого метода, отдельные счётчики вызываемых/невызываемых/неклассифицированных сущностей Swift и документированные ограничения.

## Ограничения и ошибки

Для восстановления `-o` должен задавать новый каталог вне любого входного каталога. Режимы запросов вместо этого принимают необязательный новый файл вывода. Существующий вывод никогда не перезаписывается. Результаты восстановления сначала готовятся во временной области и публикуются только после успешного восстановления и проверки вывода. Результаты запросов буферизуются до успешной проверки всех выбранных DEX. Успешные запуски нативной CLI возвращают ноль. Ошибки восстановления возвращают ненулевой код; `--json` сообщает об обработанных ошибках через `schema_version`, `status: "error"` и `error`. Ошибки разбора аргументов, запуска нативного исполняемого файла или библиотек и прерывания могут вместо этого сообщаться через stderr. Получатель результата должен сначала проверять код завершения.

Значения по умолчанию: 20 000 записей, 2 GiB входных/извлечённых данных или итогового вывода и 300 секунд для встроенного анализа Android/iOS либо каждого явно выбранного процесса JADX. Дочерние процессы iOS получают остаток общего бюджета анализа. Встроенные средство чтения и генератор также соблюдают ограниченный бюджет работы. Настройте `--max-files`, `--max-bytes` и `--timeout`, чтобы изменить эти положительные ограничения. Временная рабочая область контролируется во время выполнения бэкендов; разрешается до трёхкратного лимита записей/байтов, чтобы подготовленный вход и промежуточный вывод могли сосуществовать. Диагностика ограничена 16 MiB на процесс.

При восстановлении подготовка APK записывает только корневые `classes.dex`, `classes2.dex` и последующие пронумерованные DEX-файлы. Каждая запись ZIP всё равно проходит проверки заголовка/диапазона, распаковку, проверку длины и CRC и учитывается в лимитах числа записей архива и несжатых байтов. Незаписанные ресурсы могут иметь различные имена с учётом регистра, например `res/-A.xml` и `res/-a.xml`. Точные дубликаты имён ZIP и конфликты идентичности файла/каталога остаются ошибками; переносимые проверки коллизий регистра файловой системы применяются к действительно записываемым записям. Полное извлечение, включая вход IPA, по-прежнему отклоняет такие коллизии вывода. Пути обхода каталогов, ссылки, специальные файлы и зашифрованные записи ZIP по-прежнему отклоняются во всём архиве. Входные каталоги также не допускают символические ссылки и специальные файлы.

Эти ограничения — меры устойчивости, а не песочница для кода стороннего бэкенда. Явные команды JADX и экспорта нативных исходников выполняются как локальные дочерние процессы. Временный вывод неуспешного запуска удаляется. При ненулевом коде завершения бэкенда включается ограниченный конец диагностического журнала. При тайм-ауте сохраняется сообщение о тайм-ауте, к которому добавляется ограниченный конец журнала, если захваченный текст доступен. Ошибки запуска и нарушения бюджетов сохраняют собственные сообщения об ошибке.

## Проверка

Python используется только приведёнными ниже средствами тестирования при разработке; встроенное восстановление мобильных приложений выполняется в нативной CLI C++20.

```sh
cmake --build build --target check-neverd-mobile
ctest --test-dir build -L NeverDMobileTests --output-on-failure
python3 scripts/test_mobile_android_internal.py --d8 PATH --neverd build/bin/neverd
python3 scripts/test_mobile_android_backend.py --jadx /opt/jadx/bin/jadx --neverd build/bin/neverd
```

Тесты компонентов покрывают разбор, небезопасные контейнеры, ошибки бэкендов, очистку вывода, выбор архитектуры и сохранность вывода. Тесты, вызывающие собранную CLI, используют `NEVERD_BUILD_DIR`. Внутренний runner Android использует JDK (`java` и `javac`) и D8, чтобы собрать независимые DEX/APK fixture, затем скомпилировать и выполнить восстановленный Java. Это зависимости проверки, а не требования встроенного восстановления. Запускайте с текущей сборкой и изучайте результат, прежде чем считать случай проверенным. Отдельный runner совместимости дополнительно требует JADX; успешные fixture не доказывают восстановление произвольных приложений.

На macOS с Apple Clang, его SDK и собранным NeverD выполните фактическое сравнение исполнения Objective-C:

```sh
python3 scripts/test_mobile_ios_backend.py --neverd build/bin/neverd
cmake --build build --target check-neverd-mobile-ios
```

Runner собирает собственную Objective-C fixture, восстанавливает реализации её методов и связывает только восстановленный `.m` с тем же независимым вызывающим тестовым кодом. Fixture из 22 методов сравнивает 141 наблюдаемый результат, покрывая границы целых, ветвления, циклы, чтение/запись через указатели, скрытые и неиспользуемые аргументы, биты идентичности float/double, смешанные параметры и позиции в стеке. Прежде чем считать случай проверенным, необходим текущий успешный запуск. Все запрошенные архитектуры и варианты fixup должны завершиться; по умолчанию покрываются arm64/x86_64 × classic/default. Отсутствующий вариант или архитектура, которую хост не может выполнить, считаются ошибкой; пропуски не допускаются. Эти свидетельства fixture не доказывают полноту для произвольных программ iOS. `NeverDMobileIOSBackend` зарегистрирован в CTest на macOS, включая основной тестовый профиль CI.

Независимый runner восстановления Swift — `python3 scripts/test_mobile_swift_backend.py --neverd build/bin/neverd`. Он повторно компилирует сгенерированный Swift и свой тестовый код без связывания исходного бинарника; неподдерживаемые вызываемые сущности и различия поведения считаются ошибками. Семантика покрытия и сохраняемые свидетельства ошибок описаны в [руководстве по iOS](ios.md).

[Процесс Mobile Real Applications](../../.github/workflows/mobile-real-apps.yml) использует общедоступные приложения, закреплённые в [манифесте корпуса](../../scripts/mobile_real_apps.json). Его критерий приёмки требует независимых инвентарей каждого DEX в каждом APK и каждого Mach-O в каждом полном пакете iOS, независимой пересборки оригиналов и сгенерированного исходного кода, а также сравнения поведения. Отсутствующие этапы, неизвестное покрытие инвентаря или отсутствующие обязательные случаи не проходят этот критерий. Этапы перекомпиляции реальных приложений и проверки поведения остаются неполными, поэтому поддержка сохраняет метку Experimental; прохождение тестов защитных проверок тестового инструмента не доказывает успех на реальных приложениях.

Случаи Android пытаются скомпилировать весь инвентаризированный набор сгенерированного Java с помощью javac и D8, используя только объявления Android SDK. Исходный байткод приложения, реализации зависимостей и заменяющие заглушки не могут восполнить отсутствующее восстановление. Частичное восстановление и ошибки компилятора сохраняются в свидетельствах; успешная компиляция всё равно требует независимой проверки, полной реконструкции APK и сравнения поведения ART. Эталон iOS сверяет записи методов Objective-C на диске с выводом инструментов Apple, сохраняя идентичности класса, метакласса, категории, списка и порядковой позиции. Неразрешённые указатели или пропущенные слоты оставляют инвентарь неизвестным. Отдельные инвентари объявлений SDK устройства и симулятора поддерживают работу с импортами фреймворков, не считая заголовки доказательством раскладки экземпляров или поведения.
