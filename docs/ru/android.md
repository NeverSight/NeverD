# Восстановление Java для Android

[← Указатель документации](README.md)

`neverd mobile` восстанавливает читаемый Java-код из APK, DEX и smali с помощью отдельно установленного бэкенда JADX. Процесс проверяет и подготавливает байткод, совместно анализирует связанные классы, проверяет результат и публикует каталог исходного кода с машиночитаемым отчётом. Это экспериментальная возможность CLI. Работа с APK и вывод Java недоступны через нативный C SDK, SDK плагинов Python, загрузчик GUI или `neverd decompile --language`.

Восстановленный Java-код — реконструкция байткода. Исходные комментарии, форматирование, особенности выбора исходного языка и удалённые идентификаторы недоступны; байткод Kotlin также преобразуется в Java. Успешное выполнение не доказывает семантическую эквивалентность и не гарантирует, что каждый метод удастся скомпилировать. Этот процесс не запускает анализируемые приложения.

## Быстрый старт

Подготовив среды выполнения, описанные ниже, выберите новый каталог вывода:

```sh
neverd mobile app.apk -o recovered-app
neverd mobile classes.dex -o recovered-dex
neverd mobile MainActivity.smali -o recovered-class
neverd mobile decoded/smali -o recovered-java
```

Откройте `recovered-app/sources/` для чтения файлов Java и `recovered-app/report.json` для просмотра перечня входных файлов и ограничений. Если классы smali ссылаются друг на друга, предпочтительнее передать каталог.

## Настройка сред выполнения

| Компонент | Требование | Выбор |
|-----------|------------|-------|
| NeverD | Соберите цель `neverd`; вместе с исполняемым файлом распространяйте соседний каталог `mobile/` | `build/bin/neverd` или исполняемый файл в PATH |
| Python | Python 3.10 или новее, независимо от встроенного хоста плагинов | `--python`, затем `NEVERD_PYTHON`, затем `python3`/`python` в PATH |
| Бэкенд Java | JADX 1.5.6 или новее со стандартными плагинами ввода DEX и smali | `--jadx`, затем `NEVERD_JADX`, затем `jadx` в PATH |
| Среда Java | Java 11 или новее; для проверки компиляцией и запуском нужен JDK | `JAVA_HOME` или Java в PATH |

NeverD не загружает зависимости автоматически. Получите полный [дистрибутив JADX](https://github.com/skylot/jadx/releases/tag/v1.5.6), сохраните структуру `bin/` и `lib/` и при распространении не удаляйте включённые в него лицензии. Проверенная версия бэкенда — 1.5.6; более поздние версии должны соответствовать тому же контракту CLI. Настройка зависимостей выполняется отдельно от сборки конвейера LLVM в NeverD.

### Linux и macOS

```sh
cmake --build build --target neverd
python3 --version
java -version
/opt/jadx/bin/jadx --version

./build/bin/neverd mobile app.apk -o recovered-app \
  --python python3 --jadx /opt/jadx/bin/jadx
```

Для регулярного использования задайте `NEVERD_JADX=/opt/jadx/bin/jadx` и при необходимости укажите путь к интерпретатору в `NEVERD_PYTHON`. Если Java ещё недоступна, задайте в `JAVA_HOME` каталог установки JDK. Пути с пробелами необходимо заключать в кавычки.

### Windows PowerShell

```powershell
$env:JAVA_HOME = 'C:\Tools\jdk'
& .\build\bin\neverd.exe mobile .\app.apk -o .\recovered-app `
  --python 'C:\Tools\Python\python.exe' `
  --jadx 'C:\Tools\jadx\bin\jadx.bat'
```

По пути `.bat`/`.cmd` бэкенда определяется единственный файл `lib/jadx-*-all.jar` в дистрибутиве; NeverD вызывает Java напрямую. Этот JAR также можно передать в `--jadx`. Пути приложений никогда не подставляются в командную оболочку. При сборке с несколькими конфигурациями исполняемый файл может находиться в `build/bin/Release/`. Если перенести только исполняемый файл без каталога `mobile/`, возникнет ошибка отсутствующего вспомогательного модуля.

## Поддерживаемые входы и ограничения

| Вход | Поведение | Существенное ограничение |
|------|-----------|-------------------------|
| `.apk` | Проверяется весь ZIP, затем совместно анализируются корневые `classes.dex`, `classes2.dex` и последующие пронумерованные DEX-файлы | Только код; ресурсы и манифест не декодируются |
| `.dex` | Проверяется сигнатура DEX, затем содержимое декодирует бэкенд | Переименованный или усечённый файл не становится корректным байткодом |
| `.smali` | Анализируется переданный класс | Соседние классы, на которые он ссылается, не загружаются неявно |
| Каталог smali | Файлы `.smali` собираются рекурсивно и анализируются совместно | Включите вложенные классы и зависимые корневые каталоги smali в каталог входа |

Для анализа распакованного дерева APK с каталогами `smali/` и `smali_classes2/` передайте их общий каталог. Бэкенд получает только файлы `.smali`, но сначала проверяется и копируется всё переданное дерево; крупные посторонние ресурсы тоже учитываются в лимитах входа. Небольшой каталог только с нужными корневыми каталогами smali сокращает объём работы.

Разделённые APK обрабатываются как отдельные входы. Каждый APK с DEX можно обработать независимо, но команда не объединяет комплект APK; части только с ресурсами завершаются ошибкой из-за отсутствия корневого DEX. `.aab`, `.apks`, `.xapk`, `.odex`, `.oat` и `.vdex` не принимаются как мобильные входы. Поддержка некоторых из этих форматов самим бэкендом не означает их поддержку этой командой NeverD.

Ресурсы APK, `AndroidManifest.xml`, файлы assets, JNI/нативные библиотеки и код, загружаемый во время выполнения, не восстанавливаются как Java. Извлеките нативную библиотеку `.so` отдельно и используйте `neverd decompile library.so -o library.c`. Для этого статического процесса зашифрованный или упакованный код должен уже быть доступен в виде обычного DEX/smali; распаковка защищённого кода, подключение к устройствам и обход защиты не выполняются.

## Параметры и приоритет

```sh
neverd mobile app.apk -o recovered-app --platform=android \
  --jadx /opt/jadx/bin/jadx --timeout=600 \
  --max-files=30000 --max-bytes=4294967296 --json
```

| Параметр | По умолчанию | Значение |
|----------|--------------|----------|
| `-o DIRECTORY` | Обязателен | Новый каталог вывода вне любого входного каталога; существующий результат никогда не перезаписывается |
| `--platform=auto\|android` | `auto` | Явно выбрать Android или определить платформу по входу |
| `--jadx PATH` | Окружение/PATH | Запускной файл бэкенда или JAR дистрибутива; явный параметр имеет приоритет |
| `--python PATH` | Окружение/PATH | Интерпретатор для поставляемого вспомогательного модуля; явный параметр имеет приоритет |
| `--timeout N` | `300` | Положительное число секунд на каждый процесс бэкенда, включая запрос версии |
| `--max-files N` | `20000` | Положительный лимит записей, включая создаваемые каталоги |
| `--max-bytes N` | `2147483648` | Положительный лимит байтов для входа, извлечённых данных и итогового вывода |
| `--json` | Выключен | Вывести отчёт в JSON вместо краткого описания для пользователя |

`--arch` со значением, отличным от `auto`, `--artifact`, `--metadata-only` и ненулевой `--max-func` относятся к iOS и отклоняются для Android. Явно переданный `--arch=auto` допустим для Android. Передача произвольных параметров бэкенду не предусмотрена. Каталоги конфигурации, кэша и временных файлов бэкенда изолированы для каждого запуска; внешние настройки бэкенда и конфигурация плагинов не импортируются.

Лимиты управляют ресурсами, но не создают песочницу для процесса бэкенда. Рабочая область подготовки также контролируется: для входа, извлечённых данных и вывода допускается суммарно до трёх настроенных лимитов записей и байтов. Журналы ограничены 16 MiB на процесс. Для крупных входов может потребоваться больше памяти в куче Java или больший тайм-аут; повышение одного лимита не отключает остальные.

## Структура вывода и отчёт JSON

```text
recovered-app/
  sources/                 восстановленные пакеты и классы Java
  logs/jadx-version.log    запрос версии бэкенда
  logs/jadx.log            диагностика бэкенда
  report.json              версионируемый перечень и ограничения восстановления
```

Временные копии и кэши бэкенда удаляются. Точные имена и количество файлов Java зависят от реконструкции бэкенда; вложенные классы могут находиться в исходном файле внешнего класса. Поэтому количество исходных файлов Java не равно количеству классов DEX.

Сокращённый пример отчёта:

```json
{
  "schema_version": 1,
  "status": "success",
  "platform": "android",
  "source": "app.apk",
  "input_kind": "apk",
  "backend": {"name": "jadx", "version": "1.5.6"},
  "input_code_files": ["classes.dex", "classes2.dex"],
  "dex_count": 2,
  "smali_count": 0,
  "java_source_count": 2,
  "java_sources": ["sources/example/Main.java", "sources/example/Peer.java"],
  "logs": ["logs/jadx-version.log", "logs/jadx.log"],
  "limitations": ["Java is reconstructed from bytecode; original comments, formatting, and stripped names cannot be restored."]
}
```

`input_kind` принимает значение `apk`, `dex`, `smali` или `smali-directory`. `input_code_files` перечисляет имена входного байткода или пути smali, а `java_sources` и `logs` задаются относительно корня вывода. `source` — базовое имя входного файла или каталога. Реальные отчёты содержат дополнительные ограничения реконструкции; сохраняйте их при передаче результатов другим инструментам.

При автоматизации проверяйте код завершения процесса, прежде чем использовать `status`, и при перенаправлении stdout сохраняйте отчёт вне нового каталога вывода:

```sh
neverd mobile app.apk -o recovered-app --json > recovery-result.json
```

Успешное выполнение вспомогательного модуля возвращает ноль. Ошибки восстановления возвращают ненулевой код; после запуска модуля `--json` формирует объект ошибки с полями `schema_version`, `status: "error"` и `error`. Нативный разбор аргументов, отсутствие Python, использование Python версии ниже 3.10 или отсутствие вспомогательного модуля могут вызвать более ранний сбой с сообщением в stderr вместо JSON. При прерывании сообщение также может выводиться в stderr. Обработчики результатов должны учитывать эти случаи.

## Обработка ошибок и устранение неполадок

Публикация транзакционна: существующий вывод сохраняется, а неудачный промежуточный результат удаляется. Команда завершается ошибкой при ненулевом коде бэкенда, записанных в журнал ошибках сборки smali или декомпиляции, пропуске дублирующихся классов, явных маркерах неполного кода, пустых файлах Java или отсутствии Java-результата. Сообщение бэкенда об успехе само по себе не доказывает корректность каждого метода.

| Симптом | Действие |
|---------|----------|
| Отсутствует Python или вспомогательный модуль | Установите или выберите Python 3.10+ и сохраните каталог `mobile/` рядом с NeverD |
| Бэкенд не запускается или версия не поддерживается | Проверьте `--jadx`, полную структуру дистрибутива, Java и минимальную версию бэкенда |
| Некорректный заголовок DEX или нет корневого DEX | Проверьте фактический формат входа; используйте APK с кодом, обычный DEX или smali |
| Нет файлов smali | Укажите каталог с файлами `.smali`, а не исходным кодом Java или только ресурсами |
| Дублирующийся класс или частичное восстановление | Удалите повторяющиеся определения либо отдельно анализируйте нужный набор байткода; исправьте некорректный smali вместо принятия неполного результата |
| Превышен тайм-аут или лимит байтов либо записей | Используйте меньший вход с нужным кодом или осознанно повысьте соответствующий лимит |
| Небезопасный путь в архиве или ссылка | Создайте обычный переносимый вход без путей выхода из каталога, ссылок, специальных файлов и конфликтующих путей |
| Вывод уже существует | Выберите другой каталог вывода; не используйте повторно каталог предыдущего успешного запуска |

При успешном выполнении журналы бэкенда сохраняются. Рабочие каталоги неудачных запусков вместе с журналами удаляются; при ненулевом коде завершения бэкенда сообщение об ошибке включает ограниченный фрагмент конца диагностического вывода. Для тайм-аутов и превышения ресурсных лимитов выводятся отдельные сообщения. Для изучения проблемы конкретного бэкенда воспроизведите её на изолированном входе с собственной CLI бэкенда и отдельным каталогом диагностики. Никогда не считайте восстановление успешным только потому, что до ошибки появились какие-то файлы Java.

## Проверка и глубина поддержки

```sh
cmake --build build --target check-neverd-mobile
NEVERD_BUILD_DIR=build python3 -m unittest discover -s scripts/tests -p 'test_mobile_*.py' -v
python3 scripts/test_mobile_android_backend.py --jadx /opt/jadx/bin/jadx --neverd build/bin/neverd
```

Первые две команды проверяют контракты мобильных компонентов и собранной CLI; требования тестовых примеров для отдельных платформ могут приводить к явно отмеченным пропускам. Средство проверки реального бэкенда дополнительно требует JDK (`java` и `javac`). Оно создаёт примеры одиночного smali, связанных и вложенных классов smali, DEX и настоящего multidex APK, затем компилирует и запускает восстановленный Java-код. Примеры покрывают ветвления, циклы, массивы, обработку исключений, ссылки между классами, некорректный вход и пропуск дублирующихся классов. Это подтверждает работу на конкретных примерах, но не обещает полного восстановления произвольных приложений.

[Workflow Mobile Decompilation](../../.github/workflows/mobile.yml) запускает компонентные тесты в Linux, macOS и Windows с Python 3.10 и 3.13, а также отдельную проверку реального Android-бэкенда в Linux с дистрибутивом, закреплённым контрольной суммой. Отдельный процесс для iOS и его текущие ограничения описаны в [обзоре мобильной декомпиляции](../mobile.md).
