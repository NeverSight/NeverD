# Восстановление нативного кода и исходников iOS

[← Указатель документации](README.md) · [Обзор мобильного анализа](../mobile.md)

`neverd mobile` принимает IPA, `.app` и Mach-O, экспортируя нативный C, метаданные среды выполнения и экспериментальные исходники Objective-C `.m` и Swift `.swift` для поддерживаемых нативных тел. Опубликованный результат может содержать невосстановленные методы: перед использованием проверьте покрытие. Мобильные контейнеры обрабатывает CLI; нативный C SDK отдельно загружает выбранный Mach-O.

Компиляция удаляет комментарии, форматирование, идентификаторы и конструкции языка. Этот процесс реконструирует представление исходного кода, но не исходный текст и не доказательство эквивалентного поведения произвольного приложения. Анализируемое приложение не запускается.

## Начало работы и зависимости

```sh
cmake --build build --target neverd
neverd mobile App.ipa -o recovered-ios
neverd mobile App.app -o recovered-arm64 --arch=arm64
neverd mobile executable -o metadata --metadata-only
neverd mobile App.app -o recovered-framework --artifact Frameworks/Example.framework/Example
```

Соберите цель `neverd` инструментами с поддержкой C++20. Мобильный процесс работает внутри нативного CLI без интерпретатора Python. Деманглинг сигнатур Swift предоставляет `LLVMSwiftDemangle` из форка LLVM проекта NeverD. Компонент включён и в сборки форка из исходников, и в соответствующие опубликованные пакеты LLVM; NeverD не загружает исходники Swift как отдельную зависимость. Для сборки и запуска NeverD не требуется устанавливать компилятор или инструменты Swift. Зависимости от LLVM, Capstone и других нативных библиотек сохраняются: распространяйте необходимые библиотеки и лицензионные уведомления. Для независимой компиляции созданных исходников Apple и проверки поведения Swift на macOS по необходимости используются Apple Clang, SDK и `swiftc`.

Восстановление сигнатур Swift использует структурированные узлы `LLVMSwiftDemangle` непосредственно в процессе C++. Оно не ищет и не запускает внешний деманглер или команды поиска инструментов. Прежний параметр пути к исполняемому файлу удалён, прежняя переменная окружения деманглера больше не читается. `--metadata-only` не выполняет ни нативный экспорт исходников, ни деманглинг сигнатур.

Список сигнатур в `metadata/swift-signatures.json` указывает встроенный компонент следующим образом:

```json
{
  "demangler": {
    "name": "llvm-swift-demangle",
    "execution": "builtin",
    "version": "6.3.3"
  }
}
```

```sh
neverd mobile App.ipa -o recovered-swift --timeout=600 --json
```

## Входные данные и выбор

IPA должна содержать ровно один каталог верхнего уровня `Payload/*.app`. Главный исполняемый файл IPA и `.app` задаётся `CFBundleExecutable` в `Info.plist`. В обоих форматах `--artifact` задаётся относительно этого приложения и выбирает один вложенный исполняемый файл, а не рекурсивный анализ всех frameworks и расширений. Для непосредственного Mach-O параметр `--artifact` недопустим.

Для fat-бинарников `--arch=auto` предпочитает arm64, arm, x86_64, затем i386. Отсутствующий или неподдерживаемый срез явно отклоняется. Проекция в исходный язык сейчас рассчитана на arm64/x86_64; выбор другой архитектуры не означает поддержку Objective-C/Swift. Срез с `cryptid != 0` отклоняется: предоставьте уже расшифрованные читаемые данные. Архивы и каталоги не допускают опасных путей, символических ссылок, специальных файлов и конфликтующих записей.

## Параметры и ограничения ресурсов

| Параметр | По умолчанию | Значение |
|----------|--------------|----------|
| `-o DIRECTORY` | Обязателен | Новый каталог вне входного каталога; существующий результат сохраняется |
| `--platform=auto\|ios` | `auto` | Определить платформу или выбрать iOS |
| `--arch=auto\|arm64\|arm\|x86_64\|i386` | `auto` | Выбрать один срез Mach-O |
| `--artifact PATH` | Главная программа | Путь исполняемого файла относительно приложения |
| `--metadata-only` | Выключен | Только метаданные, без исходников и вызова инструментов |
| `--max-func N` | `0` | Предел нативных функций; ноль — все найденные; игнорируется в режиме метаданных |
| `--timeout N` | `300` | Положительный общий бюджет анализа в секундах; дочерние процессы используют оставшееся время |
| `--max-files N` | `20000` | Положительный лимит записей; список символов Swift также ограничен |
| `--max-bytes N` | `2147483648` | Положительный бюджет байтов входа, распаковки и итогового результата |
| `--json` | Выключен | Версионированный отчёт в JSON |

Рабочая область контролируется; копии входа и промежуточные результаты могут занимать до трёх бюджетов записей/байтов. Журналы ограничены 16 MiB на процесс, JSON сигнатур Swift дополнительно ограничен 32 MiB. Это контроль ресурсов, не изоляция процессов. Увеличение timeout не отменяет другие лимиты. Методы, исключённые по `--max-func`, остаются невосстановленными в доступном списке метаданных.

## Исходники Objective-C и структура runtime

Нативный загрузчик связывает запись метода, исполняемый адрес IMP и поддерживаемую кодировку типа с явными позициями исходного ABI. Фиксированные скалярные/указательные параметры сохраняют скрытые `self`/`_cmd`, неиспользуемые аргументы, отдельные целочисленные/вещественные регистры и поддерживаемые позиции стека. Переинтерпретация битов float/double отделена от числового преобразования. Подсказки типов служат проекции исходников, но не являются аутентифицированным свидетельством ABI или разрешением патчить код.

`sources/objc.m` помещает реально восстановленные операторы в тела `@implementation`, сохраняя необходимые C-помощники и типизированные вызовы. Цели вызовов требуют поддерживаемой связи с исходным представлением; неизвестные цели и неполные группы зависимостей остаются невосстановленными. Отсутствующие определения, неисполняемые адреса, конфликтующие типы, неподдерживаемый ABI, неполное декодирование и отклонённый IR не становятся восстановленными методами только из-за наличия декларации.

Метаданные сохраняют суперкласс, начало/размер экземпляра и скалярные/указательные ivar с проверенными смещениями, ширинами и выравниванием. Декларации при необходимости добавляют заполнение. Метод, которому нужна неизвестная раскладка экземпляра, остаётся невосстановленным. Категории сохраняют отдельные идентичности класс/категория/адрес и реализации; строго одинаковые записи в обоих списках считаются один раз. Поддерживаемые внешние категории используют существующие декларации Foundation. Неизвестные внешние заголовки сообщаются как отсутствующие зависимости, без выдуманной замены класса.

Восстановление также требует полных объявлений классов, определений локальных классов-предков и исходного кода, где значения определены до использования на каждом пути, а достижимые выходы содержат необходимый возврат; пустая `@implementation` для локального суперкласса создаётся только при проверенной раскладке и полном перечне методов, доказывающем отсутствие собственных обычных методов. При нехватке этих доказательств или конфликте имени с известным импортом Foundation затронутые методы остаются в знаменателе покрытия с указанием причин, а независимо восстанавливаемые классы продолжают выводиться; эти проверки имён не охватывают все имена SDK, все SDK iOS и их версии.

Поддерживаемые вызовы Objective-C Block требуют полной ABI с фиксированными скалярными параметрами, включая скрытый объект Block и все позиции передачи аргументов и результата. Кодировка времени выполнения `@?` расширяется до `id` только в объявлениях и не задаёт прототип вызова. Ссылки на глобальные Block сохраняют идентичность общего объекта. Для поддерживаемых синхронных скалярных захватов необходимо доказать нативное размещение захваченных значений и поток вызова. Ускользающие или асинхронные захваты, немоделируемые правила владения объектами/byref, функции copy/dispose и неизвестные структуры памяти остаются невосстановленными.

Реконструкция runtime ограничена: не обещаются полные свойства и протоколы, исходные аннотации владения, произвольные агрегаты, вариадические хвосты, тела с зависимостью от исключений и немоделируемые раскладки Block/захватов. Кодировка описывает фиксированные аргументы и не доказывает отсутствие многоточия в оригинале. Цепочечные указатели используются только для слотов, разрешённых загрузчиком; остальные форматы сохраняют диагностику.

## Исходники Swift и раскладка памяти

Структурированный вывод demangler разделяет вызываемые сигнатуры и невызываемые метаданные. До проекции тела поддерживаемые сигнатуры связываются с символами, входами и явным машинным ABI выбранного бинарника. Получатели Swift следуют Swift ABI; скрытые аргументы Objective-C их не заменяют. Пользовательский файл сигнатур также остаётся подсказкой, требующей проверки.

Экспериментальный emitter создаёт поддерживаемые свободные функции, методы классов, назначенные инициализаторы и методы struct с фиксированной раскладкой, включая поддерживаемые mutating-получатели. Декларациям классов/структур и хранимым полям нужны восстановленные метаданные раскладки. Нативный вызов выводится только при полной поддерживаемой группе необходимых деклараций и тел. Единицы исходников содержат их совместно, без моста, вызывающего оригинальный бинарник.

Тела поддерживаемых Swift getter/setter восстанавливаются из нативной реализации и объединяются в свойства. Закрытое хранилище сохраняет установленное расположение полей; инициализаторы и остальные методы используют те же имена хранилища. Одно объявление свойства или запись поля не доказывает восстановление тела аксессора.

Поддерживаемые выделяющие память конструкторы, тривиальные деструкторы/освобождение памяти, аксессоры метаданных типа и точки входа `_modify`/resume могут проецироваться в выданную единицу типа. Для каждой необходимы ограниченное доказательство полного нативного потока и эффектов, реально восстановленные зависимости контекста/инициализатора/свойства, а также проверки обработки исключений и IR связанных тел. Записи выделяющего конструктора должны совпадать с реальным инициализатором; `_modify` должен связывать точное изменяемое поле и продолжение. Вызовы метаданных времени выполнения сохраняют моделируемую семантику внутри восстановленного типа. Эти входы явно обозначаются как исходные проекции компилятора, а не как отдельно восстановленные тела обычных методов или исходный текст программы.

Обобщённые или resilient-раскладки, async/throwing-функции, неизвестные соглашения вызова, неподдерживаемые accessor/allocator/thunk, неполная инициализация и несвязанные нативные/runtime-зависимости остаются индивидуально `unrecovered`. Mangled-символ или имя номинального типа не являются восстановленным методом. Удалённые символы и неклассифицированные узлы demangler делают покрытие неполным или неизвестным.

## Выходные данные и покрытие

```text
recovered-ios/
  artifacts/selected.macho
  sources/native.c
  sources/objc.m
  sources/swift.swift
  metadata/objc.h
  metadata/objc.json
  metadata/objc-methods.json
  metadata/swift.json
  metadata/swift-signatures.json
  metadata/swift-methods.json
  logs/
  report.json
```

Файлы исходного языка существуют только при возможности вывести код. `objc.json` содержит классы, категории, ivar и исходные кодировки; `objc.h` — поддерживаемые декларации. `swift.json` хранит номинальные типы и mangled-символы. JSON сигнатур/методов сохраняют классификацию, пропуски, причины и счётчики. Журналы содержат нативную диагностику и диагностику нативного Swift-экспорта, если он выполняется. Журналы поиска внешних инструментов Swift и внешнего деманглинга не создаются. Пути в `report.json` относительны его каталогу. Выбранный бинарник — артефакт анализа; генерируемый код не линкует его как мост восстановления.

Временные копии пакета и промежуточные JSON удаляются. Обычный запуск без нативных тел завершается ошибкой даже при наличии метаданных. Режим метаданных создаёт лишь выбранный файл, `objc.h`, `objc.json`, `swift.json`, `report.json`; исходников и файлов сигнатур/покрытия нет, а `native_function_count`, `objc_method_recovery`, `swift_method_recovery` равны `null`. Все режимы используют метаданные Objective-C, разрешённые нативным загрузчиком. Метаданные Swift читаются из нативного образа с проверкой границ; неподдерживаемые fixup, перемещаемые структуры или ссылки сохраняют диагностику частичного результата.

Этот сокращённый пример намеренно показывает частичное восстановление:

```json
{
  "schema_version": 1,
  "status": "success",
  "platform": "ios",
  "architecture": "arm64",
  "objc_method_recovery": {
    "status": "partial",
    "method_count": 3,
    "recovered_method_count": 2,
    "unrecovered_method_count": 1
  },
  "swift_method_recovery": {
    "status": "partial",
    "coverage_status": "partial",
    "method_count": 4,
    "recovered_method_count": 2,
    "source_body_method_count": 1,
    "compiler_projection_method_count": 1,
    "unrecovered_method_count": 2,
    "metadata_symbol_count": 5,
    "unclassified_symbol_count": 1
  }
}
```

Внешний `status: "success"` означает публикацию проверенного результата. `recovered`, `partial`, `unrecovered`, `no-methods` описывают найденный список, не семантическую эквивалентность или полноту оригинальной программы. У каждого невосстановленного метода есть причина. Objective-C `recovered` дополнительно требует полных runtime-метаданных. Пустой список не доказывает отсутствия методов.

Swift `coverage_status` считает только классифицированные вызываемые элементы. Общий Swift `status` учитывает неизвестные символы и может быть `unclassified`, `unsupported-architecture`, `no-symbols`. Невызываемые метаданные находятся в `non_method_symbols` с `not-callable`, неизвестные — с `unclassified`. `types`, `type_metadata_count`, `source_type_count` отдельно считают метаданные/выведенные типы и не должны увеличивать число методов.

В каждой восстановленной строке Swift поле `source_representation` равно `native-method-body` или `compiler-generated-from-type`. Для проекций компилятора также сохраняются `compiler_projection_kind` и `compiler_projection_evidence`. `source_body_method_count` считает восстановленные нативные тела методов, а `compiler_projection_method_count` — доказанные проекции компилятора. Их сумма равна `recovered_method_count`. Входы компилятора остаются в знаменателе `method_count`, а их точная идентичность входит ровно в одну соответствующую единицу исходного кода `type`. Метаданные типа или одно имя зависимости не увеличивают число восстановленных методов. Нативный пакетный JSON содержит `source` в строках компилятора и единицах типа; мобильные `source_units` сохраняют только описания без `source`, а полный исходный код находится в `sources/swift.swift`.

Swift-блок `source_units` содержит `{kind, module, name, source, method_entries, method_identities}`; kind — `function` или `type`, идентичность — `{entry, mangled_symbol}`. Разные символы могут иметь один вход с различными ABI-проекциями. Каждая восстановленная идентичность появляется ровно один раз, невосстановленные не включаются. `method_entries` точно соответствует упорядоченной проекции входов `method_identities`, включая повторные адреса. Полностью одинаковые идентичности нельзя молча объединять. `source` последовательно объединяет исходники единиц с переводом строки после каждой. Mobile хранит общий текст в `sources/swift.swift`, описания единиц — в JSON покрытия. Поле `source` отдельного метода предназначено для просмотра; простое объединение таких строк не восстанавливает декларации классов.

## Прямой нативный экспорт и SDK

```sh
neverd export recovered-ios/artifacts/selected.macho \
  --format=objc-methods --max-func=20 -o objc-batch.json
neverd export recovered-ios/artifacts/selected.macho \
  --format=swift-methods \
  --source-signatures=recovered-ios/metadata/swift-signatures.json -o swift-batch.json
```

Swift-экспорт принимает структурированный список сигнатур, созданный встроенным анализатором при обычном запуске mobile. Objective-C JSON содержит `native_source`, `native_function_count`, `objc_metadata` и C-код, имя, возвращаемый тип, параметры каждого метода. Перед `.m` Mobile дополнительно проверяет декларации, тела и раскладки, поэтому итоговое покрытие может быть уже покрытия C. Успешный нативный экспорт может не содержать восстановленных методов.

Для сессии с уже загруженным Mach-O функции `neverd_objc_methods_json(session, max_functions)` и `neverd_swift_methods_json(session, signatures_json, max_functions)` возвращают эти отчёты. Ноль выбирает все найденные функции. Строки освобождаются через `neverd_free_string`; `NULL` обозначает сбой с объяснением в ошибке сессии. Эти API не загружают контейнеры IPA/`.app`.

## Проверка и диагностика

На macOS сборки с включённым `BUILD_TESTING` предоставляют цель `check-neverd-mobile-ios`, которая запускает все три набора нативной проверки восстановления через CTest.

Python используется только в приведённых ниже тестовых сценариях разработки; встроенное мобильное восстановление выполняется нативным CLI на C++20.

```sh
cmake --build build --target check-neverd-mobile-ios
ctest --test-dir build -L NeverDMobileTests --output-on-failure
python3 scripts/test_mobile_ios_backend.py --neverd build/bin/neverd
python3 scripts/test_mobile_ios_calls_backend.py --neverd build/bin/neverd
python3 scripts/test_mobile_swift_backend.py --neverd build/bin/neverd
```

На macOS скрипты Objective-C компилируют оригиналы, восстанавливают `.m` и связывают только сгенерированный код с независимой вызывающей программой. Скалярный скрипт проверяет границы целых чисел, ветвления, циклы, чтение/запись по указателям, скрытые аргументы, побитовую идентичность float/double, смешанные и стековые аргументы. Скрипт вызовов дополнительно проверяет диспетчеризацию сообщений, наследование, Category, память переменных экземпляра, нативные вспомогательные функции, вызовы/захваты/общую идентичность Block. Набор вызовов требует восстановления 21/21 метода и совпадения 134/134 независимых результатов в каждом варианте arm64/x86_64 × classic/default. Запускайте проверки с текущей сборкой нативного CLI.

Строгий скрипт Swift проверяет 22 пользовательских объявления, три входа getter/setter и семь вызываемых входов, созданных компилятором; ни один нельзя удалить из перечня. Каждый вариант содержит 855 независимых проверок ожидаемых результатов исходной программы. Сгенерированный `.swift` и вызывающая программа компилируются независимо, без исходной dylib, модуля, моста или написанных вручную подменяющих объявлений. Проверяются скалярные/нативные вызовы, инициализация и память классов, методы структур с передачей по значению/mutating, вещественные и стековые аргументы, указатели и циклы. Нативный CLI на C++20 должен пройти все четыре варианта arm64/x86_64 × classic/default без пропусков: восстановить по 25 нативных тел и семь проекций компилятора, сохранить все 32 вызываемые идентичности и пройти 855/855 проверок как для оригиналов, так и для независимо скомпилированного сгенерированного Swift. Эти результаты относятся только к данному набору и не гарантируют восстановление произвольных приложений или исходного текста программы. Скрипт отклоняет неполное покрытие, ошибки компиляции исходного кода и расхождения поведения.

Все три скрипта поддерживают `--arch all|arm64|x86_64`, `--fixups both|classic|default`, `--timeout N` и `--work-dir NEW_DIRECTORY`. `--setup-only` проверяет оригиналы, а не восстановление. Для приёмки должны завершиться все запрошенные варианты архитектуры и fixup, в том числе в скалярном тесте. Отсутствующий вариант или невозможность выполнить запрошенную архитектуру на хосте означает провал; пропуски не допускаются. Сохранённые артефакты сбоя позволяют различать отсутствующее покрытие, ошибки компиляции и расхождения поведения. Перед заявлением о проверенной поддержке ознакомьтесь с текущими результатами тестов.

[Workflow Mobile Real Applications](../../.github/workflows/mobile-real-apps.yml) использует публичные приложения с версиями, зафиксированными в [манифесте корпуса](../../scripts/mobile_real_apps.json). Приёмка требует независимых перечней всех Mach-O в полных пакетах iOS и всех DEX в APK, независимой повторной сборки оригиналов и созданного исходного кода, а также сравнения поведения. Отсутствующие этапы, неизвестная полнота перечня или пропущенные обязательные случаи приводят к провалу. Этапы recompile и behavior для реальных приложений ещё не завершены, поэтому сохраняется пометка Experimental. Успешные проверки самого тестового стенда не означают успешную проверку реальных приложений.

Публикация транзакционна: выберите новый каталог, сначала проверьте код завершения, а перенаправленный JSON храните снаружи. Ошибка удаляет временный вывод и сохраняет существующий. При ненулевом коде выхода движка добавляется ограниченный хвост журнала. При тайм-ауте движка исходное сообщение сохраняется, а ограниченный хвост добавляется, если доступен уже захваченный текст журнала. Превышения бюджетов сохраняют свои отдельные сообщения. Нативный CLI возвращает ноль при успехе и ненулевой код при ошибке восстановления. С `--json` обработанные ошибки содержат `schema_version`, `status: "error"` и `error`. Ошибки разбора аргументов, запуска нативного файла или библиотек и прерывания могут сообщаться только через stderr. Сначала проверяйте код завершения.

Для зашифрованного среза предоставьте читаемый вход, а при отсутствии архитектуры проверьте доступные срезы. Читайте точные причины и диагностику пропущенных методов. Увеличение `--max-func` помогает только исключённым по лимиту функциям. Недостающие раскладки, сигнатуры, внешние заголовки, поддержка исключений или ABI требуют реализации либо дополнительных действительных метаданных, а не заявления о полном восстановлении. При распространении инструментов или пакетов сохраняйте применимые лицензионные уведомления.
