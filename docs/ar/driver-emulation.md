# محاكاة برامج تشغيل Windows

ينفّذ محاكي برامج التشغيل الاختياري في NeverD نقطة دخول PE لبرنامج تشغيل x64 WDM مدعوم، ويمكنه تنفيذ سيناريو صريح من الطلبات المتزامنة قبل إلغاء تحميله. يستخدم Unicorn لتنفيذ تعليمات المعالج، ونموذج NeverD المحدود الخاص لبيئة Windows. لا يحمّل برنامج التشغيل في نواة المضيف، ولا يمرّر استدعاءات واجهات الضيف إلى خدمات نظام تشغيل المضيف.

## البناء والتشغيل

يجب تفعيل هذه الميزة صراحةً، وهي مستقلة عن `BUILD_TESTING`:

```bash
cmake -S . -B build-release -G Ninja \
  -DCMAKE_BUILD_TYPE=Release \
  -DNEVERD_ENABLE_DRIVER_EMULATION=ON
cmake --build build-release --target neverd --parallel 4
build-release/bin/neverd emulate-driver path/to/driver.sys \
  --instruction-limit 100000 > driver-report.json
```

يُكتب التقرير دائمًا بصيغة JSON إلى stdout، بينما تُكتب رسائل تشخيص الطلبات والإعداد إلى stderr. الحدود الافتراضية هي 100000 تعليمة ضيف، و64 MiB من ذاكرة الضيف، و10000 حدث مسجّل، و5000 ملّي ثانية. يجب أن يكون حد التعليمات موجبًا. يؤدي نفاد الميزانية إلى إيقاف التنفيذ مع الاحتفاظ بالمشاهدات الجزئية.

| رمز الخروج | المعنى |
|------------|--------|
| `0` | نجحت التهيئة وكل العمليات المطلوبة التي اكتملت |
| `1` | مدخلات/خيارات غير صالحة، أو فشل الإعداد، أو تعطيل الميزة وقت البناء |
| `2` | أعادت التهيئة أو أحد الطلبات المكتملة قيمة `NTSTATUS` تدل على الفشل |
| `3` | توقف التنفيذ قبل اكتمال السيناريو، مثل الوصول إلى API غير مدعوم أو وقوع عطل أو بلوغ حد الميزانية |

تُعد حالة الفشل المعادة مشاهدة مكتملة لتلك العملية. أما العودة الناجحة فتصف هذا التشغيل داخل النموذج فقط؛ ولا تثبت أن برنامج التشغيل يعمل تحت Windows.

## توافق برامج التشغيل

يتحدد التوافق بحسب مسار الشيفرة الذي نُفّذ واعتماداته، وليس بحسب الامتداد `.sys`. تشمل أدلة التحقق الحالية حالات اختبار freestanding مكتوبة أصلًا للمشروع، والمسار المخزّن مؤقتًا من مثال Microsoft SIOCTL WDM. ولا تثبت التوافق مع أي برنامج تشغيل خارجي عشوائي.

| فئة برنامج التشغيل أو متطلبه | النطاق الحالي | البيئة الناقصة |
|------------------------------|---------------|----------------|
| برنامج تشغيل برمجي x64 WDM يستخدم الواجهات المدرجة | تهيئة محدودة ودورة حياة متزامنة واحدة لملف | كل API إضافي يُنفّذ يحتاج إلى نموذج محدد |
| IOCTL من نوع `METHOD_BUFFERED` | مدعوم ضمن سيناريو الطلبات الصريح | لا تتوفر ملفات مفتوحة متعددة أو إكمال غير متزامن |
| `METHOD_IN_DIRECT` و`METHOD_OUT_DIRECT` و`METHOD_NEITHER` | تُرفض | MDL والصفحات المقفلة وفحص صلاحية الوصول وعمر مخزن المستخدم |
| برنامج تشغيل KMDF / UMDF | غير مدعوم | ربط إطار العمل وكائناته وطوابيره واستدعاءاته الراجعة وبيئة التنفيذ المضيفة المناسبة |
| برنامج تشغيل ناقل/وظيفة/مرشّح PnP | قد تعمل التهيئة ضمن مجموعة API الفرعية؛ دورة حياة مكدس الأجهزة غير مدعومة | إرفاق الأجهزة والإرسال إلى برنامج تشغيل أدنى وطلبات IRP الخاصة بـPnP والطاقة |
| برامج تشغيل التخزين والشبكة والعرض ونظام الملفات والمرشحات المصغرة | عقود الأنظمة الفرعية غير مدعومة | أطر المنفذ/الفئة/المنفذ المصغّر وخدمات NDIS/WFP والرسومات أو نظام الملفات |
| برنامج تشغيل يستخدم خيوط عمل أو مؤقتات أو DPC أو APC أو انتظارًا أو إلغاءً | غير مدعوم | الجدولة وانتقالات IRQL والمزامنة والملكية غير المتزامنة |
| برنامج تشغيل يستخدم استدعاءات راجعة للعمليات/الخيوط أو مقابض أو عمليات سجل/ملفات أو اكتشاف وحدات النواة | غير مدعوم خارج الواجهات المدرجة | مدير الكائنات وحالة النظام ومصادر الاستدعاءات الراجعة/الأحداث |
| برنامج تشغيل عتاد أو DMA أو PCI أو مقاطعات أو افتراضية | البيئة غير مدعومة | نماذج الأجهزة والذاكرة الفعلية والنواقل والمقاطعات وحالة المعالج ذات الامتيازات |
| برنامج تشغيل Windows لمعمارية x86 أو ARM64 | يُرفض | التحميل وABI ونموذج التنفيذ الخاص بالمعمارية |
| صورة x64 تتطلب CFG أو إعداد تحميل غير مدعوم أو TLS أو ميزات PE أخرى مرفوضة | تُرفض وقت التحميل | دلالات صريحة للمحمّل/بيئة التنفيذ تغطي هذه المتطلبات |

يمكن أن يظل استيراد غير مدعوم لكنه غير مستخدم مرتبطًا. يؤدي الوصول إلى عملية غير مدعومة إلى التوقف مع رسالة تشخيص والمشاهدات التي جُمعت حتى تلك النقطة. لا يثبت نجاح DriverEntry وحده دعم مسارات الإرسال اللاحقة أو العتاد أو إطار العمل. جدول API أدناه هو المرجع المعتمد للمجموعة الفرعية المدعومة.

## عقد التنفيذ

يمثل ملف التنفيذ هذا دورة حياة واحدة لبرنامج x64 WDM أحادي الخيط عند `PASSIVE_LEVEL`. يبدأ التنفيذ من نقطة دخول PE، مع إبقاء غلاف الدخول الذي أنشأه المترجم إن وُجد. يجب أن يعيد DriverEntry القيمة `STATUS_SUCCESS` لنجاح التهيئة؛ أما حالة نجاح غير صفرية أو حالة pending فتوقف التنفيذ باعتبارها عقد تهيئة غير مدعوم. تُحفظ حالة الفشل بوصفها نتيجة تهيئة مكتملة. تقع كل الكائنات والسلاسل والمكدسات ومؤشرات الدوال والتخصيصات في ذاكرة الضيف. يوفّر النموذج `DRIVER_OBJECT` ومسار سجل لاسم الخدمة المضبوط، وقيمته الافتراضية `NeverDDriver`. يستخدم المهايئ نمط TLB الافتراضي في Unicorn للحفاظ على عناوين الضيف الافتراضية، بما فيها عناوين النواة العليا القياسية (canonical)، من دون تركيب جداول صفحات Windows. قيمة RFLAGS الابتدائية هي `0x202`؛ ويستخدم ملف تعريف الجهاز البرمجي سطر ذاكرة مخبئية ثابتًا بحجم 64 بايت. هذه خصائص صريحة لسيناريو التنفيذ هذا.

تُربط الاستيرادات المجهولة بمصائد مؤجلة. لا يمنع الاستيراد غير المستخدم التنفيذ؛ لكن تنفيذ thunk الخاص به أو قراءة قيمة بيانات مصدّرة غير ممثلة في النموذج يؤدي إلى `unsupported_api`. تؤدي تأثيرات بيئة المعالج غير المدعومة أيضًا إلى توقف صريح. لا يستبدل NeverD الاستدعاءات غير المنفذة بقيم نجاح. تفشل الصور المشوّهة أو متطلبات التحميل غير المدعومة قبل التنفيذ.

لا ينفّذ ملف التنفيذ هذا نواة Windows كاملة، ولا بيئة KMDF، ولا دورة حياة PnP/الطاقة، ولا IRP غير متزامن أو معلّق، ولا IOCTL بطرائق direct/neither، ولا المقاطعات أو جدولة خيوط متعددة. لا تُنفّذ الاستدعاءات الراجعة إلا عندما يطلبها السيناريو صراحةً؛ أما تشغيل التهيئة وحدها فيظل يتوقف بعد DriverEntry.

تستخدم الصور عنوانها الأساسي المفضّل ما لم يختر السيناريو عنوان نقل صالحًا، ويجب أن تكون ملفات تنفيذية PE32+ x64 ذات نظام فرعي native. يمكن أن تأتي الاستيرادات من `ntoskrnl.exe` أو `ntkrnlmp.exe`. يدعم محمّل التنفيذ عمليات نقل العنوان الأساسي x64 `DIR64` التي اجتازت التحقق، وإعداد تحميل محدودًا لملف تعريف الارتباط الأمني security cookie؛ وتُهيّأ قيمته داخل الضيف بصورة حتمية قبل غلاف الدخول. تُرفض CFG وحقول إعداد التحميل الأخرى غير الممثلة وTLS والاستيرادات المؤجلة/المربوطة والاستيرادات برقم ordinal والصور المُدارة. يجب أن تجتاز الصور أيضًا فحوصًا صارمة للنطاقات والمحاذاة.

يحدد نموذج API الأولي عمدًا عقدًا محدودًا:

| الواجهات | السلوك الممثل والقيود |
|----------|----------------------|
| `RtlInitUnicodeString` | ينشئ `UNICODE_STRING` في الضيف من مصدر محدود منتهٍ بـNUL |
| `ExAllocatePoolWithTag` و`ExFreePoolWithTag` و`ExFreePool` | تخصيصات بيانات لأنواع المخزن `0` و`1` و`512`؛ حجم/وسم موجبان، وسم مطابق عند التحرير الموسوم، ومن دون إعادة استخدام العناوين |
| `IoCreateDevice` و`IoDeleteDevice` | نوع جهاز `0x22` وخصائص `0` أو `0x100` وامتدادات محدودة وأسماء ASCII من شكل `\Device\Name` |
| `IoCreateSymbolicLink` و`IoDeleteSymbolicLink` | أسماء ASCII من شكل `\DosDevices\Name` أو `\??\Name` ضمن نطاق أسماء جلسة واحدة، تستهدف `\Device\Name` |
| `DbgPrint` و`DbgPrintEx` | نص ASCII حرفي و`%%`، بحد أقصى 512 بايت من المخرجات؛ التنسيق ذو الوسائط المتغيرة يوقف التنفيذ؛ جميع مرشحات المصحح مفعّلة |
| `IoGetCurrentIrpStackLocation` | يعيد موضع المكدس لطلب IRP النشط في النموذج؛ تقرأ وحدات ماكرو WDM المترجمة المعتادة حقل الضيف نفسه |
| `KeGetCurrentIrql` | يعيد `PASSIVE_LEVEL` |
| `IofCompleteRequest` و`IoCompleteRequest` | يكمل IRP المتزامن النشط في النموذج باستخدام `IO_NO_INCREMENT`؛ لا يمكن الوصول مجددًا إلى IRP أو مخزن اكتمل |
| `memcpy` و`memmove` و`memset` و`memcmp` و`RtlCopyMemory` و`RtlMoveMemory` و`RtlFillMemory` و`RtlZeroMemory` و`RtlCompareMemory` | عمليات محدودة على مخازن الضيف، بحد أقصى 1 MiB لكل استدعاء؛ ترفض واجهات النسخ غير المتداخل النطاقات المتداخلة |

ينتهي عمر سجل RegistryPath الأصلي ومخزنه عندما يعود DriverEntry. على برامج التشغيل التي تحتاج السلسلة لاحقًا نسخها أثناء التهيئة.

حجم منطقة تخصيص الكائنات/المخزن هو 1 MiB. تستخدم بايتات المخزن غير المهيّأة المحتوى الحتمي `0xCD`، وتستخدم البايتات المحررة `0xDD`. هذا سيناريو تنفيذ محدد واحد. ترفض عمليات وصول المعالج وواجهات المخازن الممثلة الوصول إلى تخصيصات مخزن محررة أو أجهزة محذوفة أو بايتات غير مخصصة في المنطقة أو حقول كائنات معتمة، كما ترفض الكتابة إلى حقول الكائنات المخصصة للقراءة فقط. تغطي هذه الفحوص أعمار كائنات هذا النموذج؛ وليست تحليلًا عامًا لسلامة ذاكرة برنامج التشغيل. تُعرض خانات جدول الإرسال التي لم تُكتب بصفر يعني «غير مسجّلة». يكتمل طلب السيناريو لدالة رئيسية غير مسجلة عبر المعالج الافتراضي الممثل، بالحالة `STATUS_INVALID_DEVICE_REQUEST`؛ ويظل الفشل ظاهرًا في حالة الإرسال وحالة الإدخال/الإخراج معًا. لا يختلق النموذج عنوان دالة داخل الضيف لذلك المعالج، وتظل قراءة الضيف لخانة لم تُكتب غير مدعومة. التسجيل الصريح لاستدعاء راجع بمؤشر null خطأ.

## سيناريوهات الطلبات

مرّر ملف JSON باستخدام `--scenario` لاختيار الطلبات وإلغاء التحميل الاختياري:

```bash
build-release/bin/neverd emulate-driver path/to/driver.sys \
  --scenario scenario.json > driver-report.json
```

لبرنامج تشغيل ينشئ `\Device\NeverDIO` ويقبل IOCTL مخزّنًا مؤقتًا برمز `0x222000`، يكون مثال `scenario.json` كما يلي:

```json
{
  "requests": [
    {"kind": "create", "device": "\\Device\\NeverDIO"},
    {"kind": "ioctl", "code": "0x222000", "input": "00112233", "output_size": 4},
    {"kind": "cleanup"},
    {"kind": "close"}
  ],
  "unload": true
}
```

يجب أن يطابق اسم الجهاز ورمز IOCTL برنامج التشغيل. يؤدي حذف `device` إلى اختيار الجهاز الحي الوحيد؛ ويفشل الاختيار إن كان ملتبسًا. يتتبع النموذج ملفًا مفتوحًا واحدًا، ويشترط ترتيب create ثم طلبات IOCTL ثم cleanup ثم close. لا يدعم إلا IOCTL من نوع `METHOD_BUFFERED`. يجب أن يكمل الإرسال كل IRP بصورة متزامنة؛ وتفشل صراحةً إعادة `STATUS_PENDING` أو عدم الإكمال أو أطوال المخرجات غير الصالحة أو الوصول إلى IRP مكتمل. يجب ألا يترك إلغاء التحميل المطلوب أي جهاز حي أو رابط رمزي أو تخصيص مخزن أو كائن ملف.

يطلب الحقل الجذري الاختياري `"load_address": "0x190000000"` تغيير العنوان الأساسي؛ ويؤدي حذفه أو استخدام `"0x0"` إلى اختيار العنوان المفضّل. يجب أن تستوفي الصورة متطلبات النقل. لا يتضمن أمر التهيئة الأصلي أو واجهة C API سيناريو ضمنيًا.

لا تُقبل في الجذر سوى الحقول `load_address` و`requests` و`unload`. حقول الطلب هي `kind` و`device` الاختياري، ولـ`ioctl` فقط الحقل الإلزامي `code` مع `input` و`output_size` الاختياريين. تُرفض الحقول المجهولة أو المكررة. يقبل `code` عدد JSON صحيحًا غير موقّع من 32 بت أو سلسلة سداسية عشرية تبدأ بـ`0x`. أما `input` فهو سلسلة بايتات سداسية عشرية بطول زوجي، بلا بادئة أو مسافات؛ وحذفه يعني مدخلًا فارغًا. `output_size` عدد JSON صحيح غير موقّع؛ وحذفه يعني الصفر. تُرفض الكسور وصيغ كتابة الأعداد العائمة.

يقتصر نص السيناريو على 2 MiB، وبحد أقصى 64 طلبًا، و65536 بايت لكل مخزن إدخال أو إخراج، و512 KiB إجمالًا لبايتات الإدخال والإخراج. تسري ميزانيات التعليمات والمشاهدات وذاكرة الضيف والوقت على السيناريو كله. تحتوي منطقة 1 MiB أيضًا على الكائنات والبيانات الوصفية، ولذلك يمكن للصورة استنفاد ذاكرة النموذج قبل استهلاك الحد الأقصى لمخازن السيناريو.

## فحص قبول مثال Microsoft

ينزّل [سكربت التحقق](../../scripts/validate_windows_driver_sample.py)، الذي يُشغّل اختياريًا، مصدر Microsoft SIOCTL عند المراجعة المثبّتة في [بيان التحقق](../../unittests/emulation/fixtures/sioctl-validation.json)، ويتحقق من تجزئات SHA-256، ثم يترجم المصدر غير المعدّل باستخدام ترويسات MinGW-w64 DDK. يحتفظ بالترخيص/المنشأ الأصليين وأوامر البناء والسيناريو والتقارير في مجلد المخرجات المختار. يتطلب وصولًا إلى الشبكة وClang و`lld-link` و`nm` وترويسات DDK الخاصة بـMinGW-w64:

```bash
python3 scripts/validate_windows_driver_sample.py \
  --neverd build-release/bin/neverd \
  --output build-release/driver-validation/sioctl
```

استخدم `--headers` إذا كان مجلد ترويسات MinGW-w64 في موضع غير افتراضي. ينشئ السكربت مكتبة استيراد MS COFF من اعتماديات ملف الكائن المترجم. يشغّل الفحص DriverEntry وcreate وIOCTL المخزّن مؤقتًا الخاص بالمثال وcleanup وclose وunload. لا يسجّل المثال الأصلي معالج cleanup؛ لذلك يكمل المعالج الافتراضي في النموذج cleanup بالحالة `STATUS_INVALID_DEVICE_REQUEST` (`0xC0000010`). يستمر برنامج التشغيل في الإغلاق وإلغاء التحميل، ويعيد IOCTL الناجح البايتات المتوقعة. لهذا السيناريو الكامل، يكون رمز خروج CLI المتوقع **2** وتكون `scenario_success` بالقيمة false. ينجح السكربت نفسه فقط عندما تتطابق كل هذه النتائج، بما فيها فشل cleanup الظاهر؛ ولا يعيد كتابة المثال لإخفاء تلك النتيجة.

## التقارير وSDK

يميز تقرير JSON بين `stop_reason` و`nt_status` و`nt_success` القابلين للقيمة null، وبين PC عند التوقف وعدد التعليمات. ويحفظ استدعاءات API والحالة القابلة للمشاهدة التي جُمعت قبل التوقف، بما فيها كائنات الأجهزة وعناوين الاستدعاءات الراجعة لبرنامج التشغيل. تُمثّل عناوين الضيف بسلاسل سداسية عشرية حتى لا يفقد مستهلكو JSON دقة 64 بت. يسجّل الكائن `configuration` حدود التشغيل واسم الخدمة. اسم ملف التنفيذ هو `wdm-x64-synchronous-v1`. يظل `nt_status` نتيجة DriverEntry، بينما تصف `scenario_success` التهيئة والطلبات المكتملة معًا. تحدد `phase` و`requests` و`unload_completed` أي أجزاء دورة الحياة المطلوبة قد نُفّذت. يسجّل كل استدعاء API وكل عملية كتابة من المعالج مرحلتها أيضًا: `driver_entry` أو `request:N` أو `unload`. ويعرض كل طلب حالتي الإرسال والإدخال/الإخراج والإكمال وطول المعلومات وبايتات `output_hex` المعادة. يصف `preferred_image_base` العنوان الأساسي الأصلي لـPE. أما `security_cookie` فهو عنوان الضيف لملف تعريف الارتباط المهيّأ، أو `"0x0"` إن لم تكن هناك حاجة إليه. حقول الطلب هي `kind` و`device` و`code` و`irp` و`completed` و`dispatch_status` و`io_status` و`information` و`output_hex`.

يعدّ `instructions` محاولات تنفيذ تعليمات الضيف التي سُمِح بها. لا تُحتسب التعليمة المرفوضة من سياسة التنفيذ؛ أما التعليمة المسموح بها التي تتعطل داخل المعالج فتُحتسب. لا تزيد عمليات إرسال API الاصطناعية أو علامة العودة هذا العداد.

يحمل كل عنصر `writes` القيمة `semantics: "attempted_guest_write"`: فهو يسجّل محاولة كتابة من المعالج خارج المكدس، بما فيها محاولة قد تتعطل لاحقًا أو تتوقف بسبب الميزانية. ولا يضمن اكتمال الكتابة، ولا يشمل الكتابات التي تنفذها نماذج API. تصف لقطات الأجهزة وكائن برنامج التشغيل الحالة المشاهدة عند توقف التنفيذ.

ضمّن `neverd/sdk/NeverDCAPIEmulation.h`، أو الترويسة الجامعة لـC API، وأنشئ جلسة ثم استدعِ `neverd_emulate_driver_json(session, path, options)`. يدخل المسار الصريح غير الفارغ مباشرةً إلى الفحص الصارم السابق للتنفيذ، دون التحميل أولًا عبر واجهة التحليل العامة. تستخدم CLI هذا المسار. يؤدي تمرير `NULL` للخيارات إلى اختيار القيم الافتراضية. تتطلب خيارات `neverd_driver_options_v1` الصريحة قيمة `struct_size` الدقيقة وميزانيات موجبة للتعليمات والذاكرة والأحداث والوقت. حرّر النتيجة باستخدام `neverd_free_string`.

أما تمرير `NULL` للمسار فيتطلب جلسة محمّلة، ويعيد تحليل ملفها بصورة مستقلة عن تحليل IR والتحميل المقيد بدوال محددة. يحافظ المساران على صورة الجلسة. أبقِ ملف الإدخال متاحًا ومن دون تغيير طوال مدة الاستدعاء. تعيد إخفاقات الطلب/الإعداد `NULL` وتضبط `neverd_last_error`؛ أما توقف التنفيذ فيعيد JSON. تظل الواجهة متاحة في البنى التي عُطّلت فيها الميزة، وتوضح طريقة تفعيلها.

تستخدم `neverd_emulate_driver_scenario_json(session, path, scenario_json, options)` خيارات v1 وقواعد الملكية نفسها، مع إضافة إدخال سيناريو صارم. تُطلب سلسلة JSON غير NULL ومنتهية بـNUL. يبقى ABI الأصلي لـ`neverd_emulate_driver_json` دون تغيير، ومقتصرًا على التهيئة. يوفّر محلّل C++ المسمى `driverOptionsFromScenarioJSON` التحقق نفسه من السيناريو لمستدعي `emulateDriver`.

نقطة الدخول الداخلية في C++ هي `neverd::emulation::emulateDriver` في `include/neverd/emulation/DriverSession.h`. تحليل الصيغ مسؤولية المحمّل الموجود؛ وسلوك كائنات/واجهات Windows مسؤولية `lib/emulation/windows`؛ وحالة المعالج وتنفيذه مسؤولية مهايئ Unicorn. يستخدم المهايئ والنموذج واجهة ذاكرة الضيف نفسها. لا ينتمي سلوك Windows API إلى تفريع Unicorn.
